# AGENTS.md - Voltpilot-EMS project knowledge

Durable, project-intrinsic knowledge for anyone (human or agent) working in this repo.
The product architecture is in [`docs/architecture.md`](docs/architecture.md); this file is the operational "how it's built and run" reference.

## What this is

Self-hosted multi-tenant EMS (PV / battery / load management), DACH market. Monorepo.
On top of the runnable local backbone and binding contracts, several increments now add real functionality: the **portal + authentication spine** (the Spring Boot `api` runs in compose, validates Keycloak JWTs, and serves tenant-scoped sites/devices/telemetry plus device-claiming, enforced end-to-end by Postgres Row-Level-Security; the React portal has real OIDC login and a telemetry view), the **live ingest pipe** (`services/ingest` + `services/timescale-writer`, wired into the `edge` compose profile - real edge telemetry now flows MQTT -> Redpanda -> TimescaleDB and surfaces in the portal), **`services/forecast`** (load/PV: baseline models active + a shadow-mode ML model registry with XGBoost challengers, daily evaluation and the portal "Prognosequalität" view - see its sections), the **`services/market-data`** ENTSO-E day-ahead price adapter, the Node-RED **edge** (SunSpec Modbus simulator), and the **`services/optimization`** battery-dispatch engine (MILP over prices + forecasts -> retained MQTT schedule + portal Fahrplan view; see its section). The remaining service (marketing-adapter) is still a thin skeleton - see the service map and "Status" per service README.

MVP data path (architecture section 4/7): `Node-RED edge -> EMQX (MQTT) -> Ingest -> Redpanda (telemetry.raw) -> TimescaleDB-Writer -> TimescaleDB`. This path is **built** (see "Live ingest pipe" below); it runs under the compose `edge` profile. A plain backbone `up` still leaves the portal reading only **dev-seeded** demo telemetry.

## Run the local stack

```bash
cp .env.example .env
docker compose up -d          # backbone (timescaledb, emqx, redpanda, keycloak) + the api service
docker compose ps             # all report healthy, including voltpilot-api
docker compose down           # stop (keep volumes) ; add -v to wipe data

# The web portal runs outside compose (Vite dev server):
(cd frontend/portal && npm install && npm run dev)   # http://localhost:5173
```

The **edge** (Node-RED + SunSpec simulator) is guarded behind the compose `edge` profile, so the default `docker compose up -d` stays backbone-only:

```bash
docker compose up -d emqx                                        # broker
docker compose --profile edge up -d --build edge-sim edge-nodered
# telemetry flows to EMQX; publish a retained schedule to drive setpoints.
# Details + copy-paste test commands: edge/node-red/README.md
docker compose --profile edge down
```

Notes:
- `compose` now starts **`api`** alongside the backbone (built from `services/api`, healthy once Keycloak + TimescaleDB are up). The Python services are still NOT started (backbone-first); each has a `Dockerfile` for later.
- The edge (`edge/*`) **and the live ingest pipe (`ingest` + `writer`)** are guarded behind the `edge` profile, so the default `docker compose up -d` stays backbone-only. `docker compose --profile edge up -d --build` brings up the whole live path (edge -> EMQX -> ingest -> Redpanda -> writer -> TimescaleDB); see "Live ingest pipe" below. Services reach EMQX at `emqx:1883`, Redpanda at `redpanda:29092`, TimescaleDB at `timescaledb:5432` and the simulator at `edge-sim:502` over the compose network.
- The **optimizer** is guarded behind its own `optimize` profile (see "Optimization engine"): `docker compose --profile feeds --profile optimize up -d --build` runs the full plan-and-publish loop against real day-ahead prices.
- `.env` holds **dev-only** secrets, clearly marked. Never reuse them outside local dev.
- Data persists in named volumes `timescale-data`, `emqx-data`, `redpanda-data`.
- Redpanda advertises two listeners: `redpanda:29092` (in-cluster) and `localhost:9092` (host). Services inside compose must use the internal one.
- Keycloak realm `voltpilot` is imported on start from `infra/local/keycloak/` with clients `voltpilot-api` (confidential; its service account holds `realm-management` roles for the admin API) and `voltpilot-frontend` (public/PKCE, `tenant_id` mapper), plus dev users (see the auth + admin sections): `admin`/`admin` (Portal-Admin, `platform-admin`), `demo`/`demo` (tenant A) and `demo2`/`demo2` (tenant B).
- TimescaleDB is bootstrapped once from `infra/local/timescale/*.sql`, applied in filename order (`01-init.sql`: extension + example `telemetry` hypertable + tenant/site/device/asset + a deterministic dev seed; `02-day-ahead-prices.sql`: the market-data hypertable; `02-forecast.sql`: the `forecast` hypertable; `03-weather.sql`: site geo + `weather_forecast`; `04-schedule.sql`: battery efficiency + the `schedule` hypertable) so the backbone works without the app services. The **core schema is owned by Flyway migrations in `services/api`** (`db/migration`), which run on api start and are idempotent, so they layer cleanly over that bootstrap and own a fresh DB outright; the `forecast` and `market-data` services ship their own migrations (see their sections for version coordination).
- **The full stack has been verified end-to-end from a clean bring-up** (`docker compose --profile edge up -d --build`): all five merged increments co-run, the api's Flyway `V1/V2/V100` apply cleanly over the init-script bootstrap, all three hypertables (`telemetry`/`forecast`/`day_ahead_prices`) exist, OIDC auth + RLS isolation + the telemetry API + the React portal login/telemetry view all work, and the edge publishes contract-conformant telemetry to EMQX. See the README "Run the full stack locally" section for the exact commands + verification. Two footguns worth knowing: (1) the `infra/local/timescale/*.sql` init scripts only run on a **fresh** data volume, so after pulling newly-merged increments you must `down -v` (or the new `forecast`/`day_ahead_prices` tables silently stay absent on an already-initialized volume); (2) host-port collisions on `8090`/`5432`/etc. are resolved by overriding the port in the git-ignored `.env` (e.g. `API_PORT`, and matching `VITE_API_BASE`), not by editing compose.

## Portal API: auth, tenancy & RLS (services/api)

The user-facing spine. See `services/api/README.md` for the endpoint list.

**Auth (Keycloak OIDC).** The api is an OAuth2 resource server validating realm `voltpilot` JWTs. The frontend logs in via the public `voltpilot-frontend` client (Authorization Code + PKCE); every token carries a `tenant_id` claim (a Keycloak user attribute, mapped on both clients).

- **Issuer/JWKS split (the "issuer trap" fix).** `KC_HOSTNAME=http://localhost:8081` pins Keycloak's public URL, so browser- and script-minted tokens all carry `iss=http://localhost:8081/realms/voltpilot`. The api validates that issuer (`OIDC_ISSUER_URI`) but fetches signing keys from the compose-internal `OIDC_JWK_SET_URI=http://keycloak:8080/.../certs` - so it never needs to resolve `localhost:8081`. Spring's resource server accepts both `issuer-uri` + `jwk-set-uri` set together: keys from the latter, `iss` checked against the former.
- OIDC is off by default (`VOLTPILOT_SECURITY_OIDC_ENABLED=false`) for offline unit tests; compose sets it `true`. CORS origins via `VOLTPILOT_CORS_ALLOWED_ORIGINS` (default `http://localhost:5173`).

**Multi-tenancy via Postgres RLS.** `TenantFilter` reads `tenant_id` from the JWT into a request-scoped `TenantContext`; `TenantAwareDataSource` stamps it onto each borrowed connection via `set_config('app.tenant_id', ...)` and RESETs on return to the pool. RLS policies (migration `V2`) scope every table (`tenant`/`site`/`device`/`asset`/`telemetry`) with `tenant_id = current_setting('app.tenant_id')`. No tenant set => **default-deny** (zero rows).

- **Two DB roles, on purpose.** The compose `POSTGRES_USER` (`voltpilot`) is a Postgres **superuser**, and superusers BYPASS RLS. So the api connects at runtime as a dedicated **`voltpilot_app`** role (NOSUPERUSER/NOBYPASSRLS, created by Flyway `V1` with a placeholder password from `APP_DB_PASSWORD`) for which RLS is enforced. **Flyway** runs as the superuser (`spring.flyway.user`) to own the schema, create the role/policies, and seed both tenants (bypassing RLS). Tables are also `FORCE ROW LEVEL SECURITY` so even the owner is scoped.

**Migrations (Flyway).** In `services/api/src/main/resources/db/`: `migration/` = prod-safe core (`V1` idempotent schema + app role, `V2` RLS, `V4` cross-tenant admin role - see the admin section; **V3 is skipped**, reserved by `services/forecast`); `dev/` = the DEV-ONLY seed (`V100`, two tenants + demo telemetry), added to `spring.flyway.locations` only under the `local` profile (compose sets `SPRING_PROFILES_ACTIVE=local`; tests activate it too). `baseline-on-migrate` + `baseline-version=0` let the idempotent `V1` run over the compose bootstrap DB. **An applied `V*.sql` migration is immutable - never edit one that may already be applied on a live DB, not even a comment: Flyway fingerprints every applied migration and fails startup validation on a checksum mismatch (fresh CI/Testcontainers DBs never compare, so the break only surfaces on a long-lived DB like prod).**

**Seeded dev users (dev-only):**

| Keycloak user | Password | Role | tenant_id | Sees |
|---|---|---|---|---|
| `admin` | `admin` | `platform-admin` (Portal-Admin) | *none* | Admin console: all tenants + users |
| `demo`  | `demo`  | `operator` (Portal-User) | `00000000-…-0001` | Demo Site Berlin / `demo-inverter-01` |
| `demo2` | `demo2` | `operator` (Portal-User) | `10000000-…-0001` | Nordwind Hamburg / `nordwind-inverter-01` |

**Self-registration (`POST /api/v1/registration`, public).** The front door of customer onboarding: one unauthenticated request creates a `B2C` tenant (name = the customer's person/company name) **and** its Keycloak login (username = lowercased email, `tenant_id` attribute + `operator` role via `KeycloakAdminClient`), so the standard OIDC+RLS spine isolates self-registered customers exactly like admin-provisioned ones (`RegistrationController`; tenant row via the BYPASSRLS `TenantRepository` since there is no caller tenant yet). If Keycloak refuses (email taken -> 409) or is unreachable, the tenant is deleted again (compensating rollback, `TenantRepository.deleteById`; best-effort - a failed cleanup delete is logged and never masks the original error). Toggle: `VOLTPILOT_REGISTRATION_ENABLED` (default `true`; setting `false` removes the endpoint via `@ConditionalOnProperty`). Two security notes: (1) the `secured` chain permits `POST /api/v1/registration` AND the ERROR dispatch (`dispatcherTypeMatchers(ERROR)`) - without the latter, Spring Security 6 masks every anonymous 400/409 as 401 because the `/error` forward is itself access-controlled; (2) anonymous volume is bounded by `RegistrationRateLimiter` - a sliding window per client address (taken from the `X-Forwarded-For` proxy chain honoring only the configured number of own proxy hops, `rate-limit.trusted-proxies` - default 0 = socket address only, prod compose sets 2 for external proxy + frontend nginx; earlier header entries are client-supplied and ignored) plus a global cap, defaults 10/client + 100 total per hour (`voltpilot.registration.rate-limit.*` / `VOLTPILOT_REGISTRATION_RATE_LIMIT_*`), refusing with 429 BEFORE any tenant/Keycloak work (portal maps it to German "später erneut versuchen" copy); state is in-memory per api instance, and email verification/captcha remain known future work. Portal: the login screen offers "Konto erstellen" (`App.tsx` `RegisterForm`, posts via the token-free `register()` in `api.ts` - deliberately not `request()`, whose token refresh would redirect anonymous visitors to Keycloak), then **signs the customer straight in** (seamless auto-login, below); the "Jetzt anmelden" screen with `login(loginHint)` remains only as fallback when the direct grant is refused (e.g. an older realm import). The form itself is lockout-hardened (there is NO self-service password reset without SMTP, so an unseen password typo would otherwise cost a support call - support recovers via the admin reset-password lever, see the admin-endpoints section): show/hide password toggle (`.vp-pw-labelrow`), per-field inline German errors shown on blur or on an invalid submit (which also focuses the first invalid field - the submit button is never silently disabled), a live "Noch N Zeichen" -> green-check password-length hint, a real `<form>` so Enter submits, `autoFocus` + `autoComplete` (`name`/`email`/`new-password`); the design-system `Input` forwards its ref to the native input for this. Proven e2e by `RegistrationApiTest` (real Keycloak + TimescaleDB: register -> login via the PUBLIC frontend client's direct grant (the exact auto-login call) -> create site -> claim device without an operator; duplicate email 409 without orphan tenant; bean-validation 400s).

**Seamless post-registration auto-login (no second credential entry).** The customer just typed email + password into the registration form, so the portal never sends them to the Keycloak login page to retype them: `loginWithCredentials()` in `auth.ts` mints tokens at the token endpoint (`grant_type=password` on the public `voltpilot-frontend` client - `directAccessGrantsEnabled=true` in BOTH realm imports, dev + prod), stores them in `sessionStorage` (`vp.auth.tokens`), and reloads the SPA; `initAuth()` then re-validates stored tokens via a refresh grant (guaranteed-valid before injecting, so keycloak-js `init` is never called twice) and boots with `init({token, refreshToken, idToken, checkLoginIframe: false})` straight into the onboarding wizard. `onAuthRefreshSuccess` keeps the store current so a mid-onboarding page reload stays signed in; without stored tokens, `initAuth()` is byte-identical to the old `check-sso` path. Two caveats: (1) this path sets NO Keycloak SSO cookie - the session lives in the tab (sessionStorage) and ends with it; `login()`/`logout()` clear the store; (2) ROPC on a public client is deliberate here (the credentials come from our own registration form seconds earlier) but it widens the token endpoint's brute-force surface - registration itself is rate-limited (see above), and BOTH realm imports enable Keycloak brute-force detection (`bruteForceProtected`, temporary lockout: 10 failures -> 60s wait escalating to 15 min, never permanent; support lifts a lock - and recovers a forgotten password - via "Passwort zurücksetzen" on the Benutzer page (see the admin-endpoints section; the reset clears the attack-detection lock too), so password guessing at the token endpoint locks the account temporarily while the right owner is never stranded. Proven by `RegistrationApiTest.passwordGuessingAtTheTokenEndpointLocksTheAccountTemporarily`; like every realm change, it reaches an EXISTING Keycloak volume only after a fresh import (or a one-time admin-console edit).

**Site creation ("Variante C": both admin- and customer-created).** A site (Standort) is created two ways, and neither lets the client pick the tenant:
- **Customer, tenant-scoped:** `POST /api/v1/sites` (`SiteController.createSite`) inserts a site for the CALLER's tenant. `tenant_id` is taken from `TenantContext` (the JWT `tenant_id` claim), **never from the body**, and the existing `site` RLS `WITH CHECK` (migration `V2`, which already covers INSERT - a single policy applies to ALL commands) both permits the write and guarantees the row lands in the caller's tenant. So a crafted foreign `tenant_id` field in the body is simply ignored - **no new migration was needed** (the app role already has `INSERT` on `site` from `V2`). This closes the onboarding dead-end: a fresh customer makes a site here, then the "claim device" dropdown is populated. Reads/creates go through the RLS-scoped `SiteRepository` (`.create(...)`).
- **Admin, cross-tenant:** `GET/POST /api/v1/admin/tenants/{tenantId}/sites` (`AdminController`, platform-admin-gated) via `AdminSiteRepository` bound to the `voltpilot_admin` BYPASSRLS `adminJdbcTemplate` (same pattern as `TenantRepository`). The tenant comes from the **path** (validated to exist), never from body data - the only cross-tenant site write path.
- `CreateSiteRequest` DTO validates: name `@NotBlank`, `biddingZone` `@Pattern(DE-LU|AT|CH)` (defaults `DE-LU`), lat/lon range-checked (`-90..90` / `-180..180`, optional; needed for the weather forecast). Kept in `docs/contracts/openapi.yaml`. Portal: the customer empty-state offers a "Standort anlegen" form (`App.tsx` `CreateSiteForm`) so onboarding never dead-ends, plus an "add further site" form; the admin console has a per-tenant `SitesPanel` (`admin/AdminApp.tsx`).

**Device claiming** (`POST /api/v1/devices/claim`) is one insert into the caller's tenant, made typo-proof and repeat-proof for the onboarding path: the controller **canonicalizes** `externalRef` (trim; sticker IDs with case-insensitive `VP-` prefix are uppercased - `DeviceController.canonicalExternalRef`; non-sticker refs like the dev-seeded `demo-inverter-01` pass through untouched), and the claim is **idempotent within the tenant** - re-claiming a ref the caller already owns (wizard restart, double submit) returns **200 with the existing device** at its original site (RLS-scoped `DeviceRepository.findByExternalRef`), never a conflict. `external_ref` stays **globally unique**, so a device owned by ANOTHER tenant (which RLS hides) still fails the unique constraint -> HTTP 409 (the portal's "anderes Konto … Support" copy is therefore truthful); a site outside the tenant -> 404. The portal mirrors the canonicalization as-you-type (`normalizeDeviceIdInput` in `Onboarding.tsx`, reused by the dashboard claim form) and tells an already-owned re-claim apart by the returned device id. Proven by `PortalApiTest.claimIsIdempotentPerTenantAndCanonicalizesStickerIds`.

**Provisioned-device registry (sticker claims are gated).** Sticker IDs (canonical `VP-` prefix) must exist in the global `provisioned_device` table (api migration `V20260702020000`; manufacturing data, so deliberately NO tenant_id/RLS - like `day_ahead_prices`; the app role is SELECT-only, writes are revoked) or the claim fails fast with **HTTP 422** instead of creating a ghost device that would "wait for first data" forever; a provisioned claim inherits the registry's `kind`. Non-sticker refs (dev seeds, integrations, `tools/pki/provision-device.sh` with non-VP refs) stay ungated. Operators register manufactured IDs via `GET/POST /api/v1/admin/provisioned-devices` (platform-admin-only; POST canonicalizes, requires the `VP-` prefix, and is idempotent - re-registering returns 200 with the existing entry; the listing joins `device`/`tenant` cross-tenant via the BYPASSRLS `AdminProvisionedDeviceRepository` to show who connected each device) and through the unified shell's "Geräte-Registry" page (`pages/admin/GeraeteRegistryPage.tsx`, Plattform nav group). Dev sticker IDs (`VP-DEMO-0001..3`, `VP-E2E-0001`) come from the DEV-ONLY migration `db/dev/V20260702020100` - date-versioned, NOT an edit of `V100`, because editing an applied migration breaks Flyway checksum validation, and a plain `V101` would sort BEFORE the date-versioned registry table and fail. Both portal claim forms map 422 to "Diese Geräte-ID ist uns nicht bekannt … Aufkleber". Proven by `PortalApiTest.unknownStickerIdIsRejectedInsteadOfCreatingAGhostDevice` and `AdminApiTest.adminProvisionsStickerIdsWhichGateAndInformCustomerClaims`; `RegistrationApiTest` provisions its device through the admin API first, journey-true. The gate composes with zero-touch provisioning: the claim endpoint still pushes the retained `provision/{ref}/config` for a registered sticker ref (canonical uppercase topic), proven by `ProvisioningClaimTest.registeredStickerRefClaimPublishesRetainedProvisioningConfig`.

**Self-generated edge refs are check-digit-gated too (the SECOND claim gate).** The shipping customer Edge-App, with no configured reference, generates its own `edge-` ref and shows it on its `:8484` web app for the customer to type - a `VP-` sticker gate does not apply. To stop a one-character typo silently creating a permanent ghost device, the generated ref now carries a trailing **check character**: `edge-` + 6 body chars + 1 check char (a position-weighted mod-31 checksum over the body, alphabet `abcdefghjkmnpqrstuvwxyz23456789`, no 0/O/1/l/i lookalikes). The generator (`edge-app/core/internal/agent/agent.go` `newGeneratedRef`/`refCheckChar`) and the api validator (`services/api/.../web/EdgeRef.java`) **MUST stay byte-identical** - the Go `ref_test.go` and `EdgeRefTest` pin the shared vectors (e.g. body `abcdef` -> check `j`, so `edge-abcdefj` is valid) from both sides. `DeviceController.claim` rejects a mistyped generated ref with **422** exactly like the sticker gate. Crucially the gate is NOT "any `edge-` prefix": `EdgeRef.isGeneratedFormat` matches only `edge-` + **6..8 pure-alphabet** chars (a generated ref plus a single-char edit), so free-form/dev refs with hyphens or out-of-alphabet chars (`edge-fresh-01`, `edge-inverter-42`) stay **ungated** for backward compatibility; already-claimed refs short-circuit before the gate via the idempotent `findByExternalRef`. `canonicalExternalRef` now case-folds BOTH prefixes (`VP-` uppercase, `edge-` lowercase) so a mobile keyboard's `autoCapitalize` can't split one device into two rows; the portal mirror `normalizeDeviceIdInput` matches. Both portal claim UIs (`Onboarding.tsx` `DeviceStep`, `DeviceDrawers.tsx` `AddDeviceDrawer`) share ONE label/placeholder/help (`DEVICE_ID_FIELD`) + one 422 message (`DEVICE_ID_UNKNOWN_MSG`) - the former "Aufkleber vs Typenschild vs Web-App" mismatch that fed the typo risk is gone. Proven by `PortalApiTest.mistypedGeneratedEdgeRefIsRejectedWhileTheValidRefClaims`. **Ops visibility:** enrolled-but-unclaimed devices (a device uploaded an enrollment CSR but no matching `device` row exists - the typo's other half, otherwise invisible) surface at `GET /api/v1/admin/enrollments/pending` (`AdminEnrollmentRepository`, BYPASSRLS admin datasource, `LEFT JOIN device WHERE d.id IS NULL`; the device-facing enrollment poll stays opaque). The ingest provisioning resolver (`ProvisioningHandler.canonicalRef`) canonicalizes the ref for the device lookup like the claim path (a lowercase `VP-` hello now resolves the uppercase-stored row) but still replies on the ORIGINAL topic (MQTT topics are case-sensitive).

**Tests** (`./mvnw test`, auto-skip without Docker via `disabledWithoutDocker`): `TenantFilterTest` + `KeycloakRealmRoleConverterTest` + `EdgeRefTest` (unit, always run); `RlsIsolationTest` (Testcontainers TimescaleDB, JDBC-level RLS proof); `PortalApiTest` (Testcontainers TimescaleDB + Keycloak, full OIDC + tenant-isolation + claim e2e); `AdminApiTest` (same stack - admin creates tenant + customer user, the new customer logs in tenant-scoped, a Portal-User gets 403 on admin routes); `RegistrationApiTest` (same stack - self-serve onboarding chain, see the self-registration section). ## Admin API & the Portal-Admin / Portal-User split (services/api + frontend)

Two distinct kinds of principal, separated in the **backend** (the UI only picks a surface):

- **Portal-Admin = platform operator.** Keycloak realm role **`platform-admin`**. **Not** tenant-scoped (carries **no** `tenant_id`). Manages tenants and customer users across the whole platform. Seeded login `admin`/`admin`.
- **Portal-User = customer.** Realm role **`operator`**, scoped to exactly one tenant via the `tenant_id` claim + RLS (the `demo`/`demo2` users). Unchanged from before.

**Role -> authority mapping.** `KeycloakRealmRoleConverter` maps the token's `realm_access.roles` onto `ROLE_*` authorities, wired into the `secured` chain via `jwtAuthenticationConverter`. `@EnableMethodSecurity` + `@PreAuthorize("hasRole('platform-admin')")` on `AdminController` is what makes a customer token get **403** on every `/api/v1/admin/**` route. This converter is the ONLY thing that turns a token into an authority; it is orthogonal to tenant scoping (still `TenantFilter` + RLS).

**Admin endpoints** (`AdminController`, all Portal-Admin-only): `GET/POST /api/v1/admin/tenants`; `GET/POST /api/v1/admin/tenants/{tenantId}/sites`; `GET/POST /api/v1/admin/tenants/{tenantId}/users`; `POST /api/v1/admin/tenants/{tenantId}/users/{userId}/disable`; `POST /api/v1/admin/tenants/{tenantId}/users/{userId}/reset-password` (the support lever: no SMTP means no self-service reset, so support sets a new password here - `temporary` default true = must-change-on-next-login, min 8 chars like registration - and `KeycloakAdminClient.resetPassword` also lifts any brute-force lockout via the attack-detection API so the new password works immediately; surfaced as "Passwort zurücksetzen" in the shell's Benutzer page); `GET/POST /api/v1/admin/provisioned-devices` (the manufacturing registry gating sticker claims - see the device-claiming section). Kept in `docs/contracts/openapi.yaml` (tag `admin`). The per-user routes (`disable`, `reset-password`) verify the addressed user actually carries the path's tenant (`requireUserInTenant`) - a user reached through the wrong tenant's path is 404, never acted on. Proven by `AdminApiTest.supportResetsAForgottenPasswordAndLiftsTheLockout` (lock the account by guessing -> reset -> new password works immediately, old one refused, wrong-tenant path 404, short password 400).

**Cross-tenant without weakening RLS.** Admin reads/writes span all tenants, but the customer-facing RLS must NOT be loosened. So there are **two DB roles / two datasources**: customer endpoints keep the `@Primary` tenant-aware `voltpilot_app` datasource (NOBYPASSRLS, RLS enforced); the admin repository (`TenantRepository`) uses a **separate** `adminJdbcTemplate` bound to the dedicated **`voltpilot_admin`** role (**BYPASSRLS**, created by Flyway **`V4`**, granted table privileges since BYPASSRLS skips policies not grants). The two never mix. Note: defining `adminJdbcTemplate` backs off Boot's auto `JdbcTemplate`, so `DataSourceConfig` declares an explicit **`@Primary` `jdbcTemplate`** on the tenant-aware datasource - customer repos must get that one.

**User provisioning via Keycloak Admin REST API.** `KeycloakAdminClient` authenticates as the **`voltpilot-api` service account** (`client_credentials`) which is granted `realm-management` roles (`manage-users`/`view-users`/`query-users`/`view-realm`) in the realm import; it creates the user with the `tenant_id` attribute + `operator` role (so the existing OIDC+RLS spine isolates them exactly like the seeded tenants), then sets the password. `base-url` is the compose-internal Keycloak (`KEYCLOAK_ADMIN_BASE_URL`, default `http://keycloak:8080`), decoupled from the browser-facing issuer like the JWKS split; secret via `KEYCLOAK_API_CLIENT_SECRET` (env only). **Keycloak-26 footgun:** the realm import declares a **declarative user profile** (in `voltpilot-realm.json` `components`) with `tenant_id` declared + `unmanagedAttributePolicy: ADMIN_EDIT` and firstName/lastName **optional** - without it, the Admin API silently drops the unmanaged `tenant_id` and password-grant login fails with "Account is not fully set up".

**Admin tenant switcher (`X-Tenant-Id`).** For *reading customer data* the portal is one app for both roles (see the web-portal section): an admin selects a tenant and the CUSTOMER endpoints render that tenant's data via the `X-Tenant-Id` header, which `TenantFilter` honors **only** for `platform-admin` tokens. A customer's tenant always comes from the validated JWT claim (the header is ignored outright), so the override can never widen customer access; an admin without the header stays default-deny (zero rows). This deliberately reuses the RLS-scoped `voltpilot_app` datasource for those reads - no BYPASSRLS, no duplicated endpoints; the BYPASSRLS admin datasource remains only behind `/api/v1/admin/**`. CORS allows the header. Proven by `AdminApiTest.adminReadsCustomerEndpointsForSelectedTenantViaHeader` + `customerCannotSwitchTenantsViaHeader`.

**Frontend.** `frontend/portal/src/auth.ts` exposes `isPlatformAdmin()` (reads `realm_access.roles`); the unified shell (`src/shell/AppShell.tsx`) adds the "Plattform" nav group (Mandanten/Benutzer pages under `src/pages/admin/`) and turns the top-bar tenant chip into a real switcher for admins (`api.ts` `setTenantOverride` stamps the header on every request; customers get a read-only badge). The former separate `src/admin/AdminApp.tsx` console is retired; admin calls still go through `src/admin/adminApi.ts` reusing `api.ts`'s exported `request`.

## Entity lifecycle: edit + delete (Standorte/Geräte/Mandanten/Benutzer/Registry)

Every entity the portal can create can now also be edited and deleted - by customers for their own tenant and by Portal-Admins for any tenant.
Migration **`V20260702030000`** carries the groundwork; a checked fact worth knowing: the V2 (and later) RLS policies have no FOR clause, so they already cover UPDATE/DELETE - what was missing were table GRANTs (app role: DELETE on the series tables + SELECT/DELETE on `forecast`; admin role: explicit grants on the collector tables, because V4's default privileges never applied to tables the dev init scripts created before Flyway ran).
The migration also adds **`device.name`** (optional customer-facing label "Bezeichnung").

- **Standort:** `PUT /api/v1/sites/{id}` (name/zone/coords, validation mirrors create) and `DELETE /api/v1/sites/{id}` - GUARDED: 409 while devices exist; on success assets cascade by FK and the site's series rows (telemetry/rollups/forecast/schedule/weather/quality - no FKs on hypertables, deleted by `SeriesRepository` in the same transaction) go with it, all through the RLS-scoped app datasource.
  `GET /api/v1/sites/{id}/deletion-preview` feeds the portal confirm dialog (device count, telemetry range/count, series counts).
- **Gerät:** `PUT /api/v1/devices/{id}` edits ONLY kind + label - `external_ref` is identity (MQTT topics, registry gate) and immutable, the UI says so.
  `DELETE /api/v1/devices/{id}` = unclaim: deletes the device row + its telemetry AND cleans MQTT best-effort (`ProvisioningPublisher.clearRetained` publishes empty retained payloads to `provision/{ref}/config` and the schedule topic, so the physical device falls back to its watchdog default and a rebooting device gets no stale identity).
  A sticker ref stays in the manufacturing registry and is claimable again - claim -> unclaim -> re-claim re-publishes the retained config (proven by `ProvisioningClaimTest.unclaimClearsRetainedConfigAndReclaimRepublishesIt`).
- **Admin any-tenant for sites/devices = the tenant switcher.** Admin edit/delete of a tenant's sites/devices deliberately reuses the CUSTOMER endpoints with `X-Tenant-Id` (the RLS-scoped path; BYPASSRLS stays behind `/api/v1/admin/**` only). Proven by `AdminApiTest.adminUpdatesTenantAndEditsCustomerSitesViaTenantSwitcher`.
- **Mandant (admin only):** `PUT /api/v1/admin/tenants/{id}` (name/segment); offboarding via `POST /api/v1/admin/tenants/{id}/delete` with a **type-to-confirm** body (`confirmName` must equal the exact tenant name, else 400 before anything happens).
  The DB cascade (series rows by tenant, then the tenant row whose FKs cascade site/device/asset) runs in ONE transaction (`TenantRepository.offboard`); if Keycloak cannot even be enumerated the whole thing is refused (502).
  Afterwards the devices' retained MQTT topics are cleared and the tenant's Keycloak users deleted best-effort - the `TenantOffboardingReport` lists `deletedUsers` and `failedUsers`, so a partial directory failure is visible, never silent (portal shows a report screen; failed users flagged for manual cleanup).
- **Benutzer (admin only):** `PUT .../users/{userId}` (email/name; username immutable), `POST .../enable` (counterpart to disable), `DELETE .../users/{userId}`.
  **Self-guard:** an admin can never disable or delete their OWN account - checked against the token `sub` BEFORE any tenant check, so it also fires through an arbitrary tenant path (409; `AdminController.requireNotSelf`).
- **Geräte-Registry (admin only):** `DELETE /api/v1/admin/provisioned-devices/{ref}` removes a wrongly registered sticker ID - 409 while a claim references it (unclaim first), path canonicalized like the claim.
- **Portal:** the detail drawers grew "Bearbeiten" (inline forms mirroring the create forms) and a `DangerZone` component (`src/components/DangerZone.tsx`): collapsed red button -> explicit consequence list -> confirm; the tenant delete additionally requires typing the tenant name.
  Design-system `Icon` gained `pencil`/`trash`.
- **Tests:** `PortalApiTest` (site edit incl. cross-tenant 404 + validation, guarded delete + series cascade, device edit/unclaim/re-claim), `AdminApiTest` (tenant edit, switcher-based admin site edit/delete, type-to-confirm offboarding cascade incl. Keycloak login gone, user edit/enable/delete + self-guard, registry delete guard), `ProvisioningClaimTest` (retained-config clear + re-claim republish against real EMQX).

## Device data purge ("Datenaufzeichnungen löschen")

Delete ALL recorded timeseries data of one device - portal-side AND device-side - WITHOUT unclaiming it: claim/enrollment/certs/ACL/config stay intact and new data flows normally afterwards.
Contract: `docs/contracts/mqtt-data-purge.schema.json` (additive; reuses the existing `status` up- and `command` down-topics, so NO broker-ACL change).
ONE purge authority: `services/api` `purge/DevicePurgeService` - both entry points run through it.

- **What a cloud purge does, in order** (the ordering is load-bearing):
  1. **Watermark first**: `device.data_purged_before = now()` (migration `V20260706000000`), committed as its own statement.
     The timescale-writer's insert refuses any sample whose OBSERVATION `time` is `<=` the watermark (extra `NOT EXISTS` on `device`), so a store-and-forward edge replaying old buffer entries can NEVER resurrect purged history - correctness does not depend on the device cooperating.
  2. **Delete + rollup rebuild in one transaction** (`SeriesRepository.purgeDeviceRecordings`): the device's raw `telemetry` rows go, then the SITE's `telemetry_rollup_15m/1h/1d` are deleted and re-inserted from the remaining raw rows (rollups aggregate per SITE, and an upsert can never empty a bucket - hence rebuild, not refresh).
     All RLS-scoped through the app role (the migration grants it INSERT/UPDATE on the rollups).
     Unclaim reuses the same method, which also fixed the old gap where unclaim left the removed device's contribution in the rollups.
  3. **Retained `purge_data` command** to `ems/{t}/{s}/{d}/command` (best-effort via `ProvisioningPublisher.publishPurgeCommand`; `clearRetained` clears it on unclaim): an offline device receives it on reconnect and wipes its local buffers BEFORE replaying. `deviceNotified` in the response tells the portal whether it went out.
- **Entry points:** portal `POST /api/v1/devices/{id}/purge-data` (tenant-scoped like every device route, foreign tenant = 404; admins via the tenant switcher) and the device's own `purge_request` on ITS status topic, consumed by `purge/PurgeRequestListener` (paho subscriber on `ems/+/+/+/status`; flag `VOLTPILOT_PURGE_MQTT_LISTENER_ENABLED`, on in both composes). Authorization of the MQTT path = the broker ACL + mTLS cert CN (a device can only publish on its own topic = it may purge its own data); the listener re-validates topic==payload identity and resolves the device via the RLS repository with the topic tenant (`TenantContext.set/clear` around it).
- **Edge side (`edge-app/core`):** `agent/purge.go`. Local trigger = the guarded "Datenaufzeichnungen löschen" card on the `:8484` dashboard (`POST /api/purge-data`, type-LÖSCHEN confirm): wipes the store-and-forward buffer (`buffer.PurgeThrough(t)` - drops entries observed `<= t`, KEEPS newer ones with their original seq) + the live-chart ring (`history.PurgeThrough`), persists the request (`purge-request.json`) and (re-)publishes it on every cloud connect until confirmed - so an offline purge is queued explicitly, never lost, and the UI shows honest states (`ausstehend` -> `angefordert` -> `bestaetigt`, `Snapshot.DataPurge`). The cloud's retained `purge_data` command (new `command`-topic subscription in `cloud.go`) is BOTH the portal-purge push and the confirmation signal; it wipes `<= purged_before` only, so samples recorded after the purge survive and upload normally. Remember: `static/*` is `//go:embed`-ed - rebuild the core binary after UI edits.
- **Tests:** api `PortalApiTest.purgeDeviceDataDeletesRecordingsRebuildsRollupsAndKeepsDeviceClaimed` (two devices/one site: rollups reflect only the kept device, purged-only buckets vanish, device stays claimed, idempotent re-purge, RLS 404) + `ProvisioningClaimTest` (retained command observed by a reconnecting device; device-published `purge_request` purges via the listener, spoofed identity ignored); writer `WriterPipeTest.purgeWatermarkRefusesReplayedOldSamplesButAcceptsNewOnes`; edge `buffer`/`history` PurgeThrough units, `web` endpoint tests, and `purge_integration_test.go` (offline round trip: purge while disconnected -> queued request on reconnect -> confirmation -> only post-purge samples reach the cloud; portal-initiated retained command wipes local buffers, foreign-device command ignored).

## Live ingest pipe (`services/ingest` + `services/timescale-writer`)

The MVP core data loop: real edge telemetry flows `Node-RED edge -> EMQX (MQTT) -> ingest -> Redpanda (telemetry.raw) -> timescale-writer -> TimescaleDB telemetry hypertable`, and the portal's telemetry view shows it live for the `demo` user. Both services are stateless Spring Boot apps in the compose **`edge` profile** (so `docker compose --profile edge up -d --build` runs the whole live path; a plain backbone `up` does not, leaving the portal on dev-seed only).

**Ingest (`services/ingest`, container port 8091).** A Spring Integration Paho adapter subscribes to `ems/+/+/+/telemetry` at **QoS1**. Each message is validated/normalized (`TelemetryValidator`) against `docs/contracts/mqtt-telemetry.schema.json`: `schema_version == "1.0"`, tenant/site/device are UUIDs, `ts` is RFC-3339, `measurements` is an object, **and the topic identity must equal the payload identity** (a device may not publish under another's topic). Valid messages become a `telemetry.raw` event (`docs/contracts/telemetry-raw.event.schema.json`: adds `event_id` + `ingested_at` + `source_topic`, carries `measurements` through unchanged) produced to Redpanda **keyed by `{tenant_id}:{site_id}`** so a site's samples share a partition and stay ordered. Malformed messages are **logged and skipped** (never crash the stream); the QoS1 delivery is already acked and Redpanda is the durable log.

**Writer (`services/timescale-writer`, container port 8092).** A `@KafkaListener` consumes `telemetry.raw` and inserts one row into `telemetry`, mapping `measurements.{power_kw,soc_pct,pv_power_kw,load_kw,grid_limit_kw}` to columns plus the full event JSON into `payload`, with `time=observed_at`, **`received_at=ingested_at`** and the event's `tenant_id`/`site_id`/`device_id`.
- **`time` vs `received_at` (device liveness).** `time` is the OBSERVATION timestamp the edge stamps; `received_at` (api migration `V20260703000000`, `DEFAULT now()`) is the ARRIVAL time, taken from the event's `ingested_at`. Device online/offline liveness (`DeviceRepository` -> `DeviceDto.lastSeenAt` -> portal `deviceLiveStatus`, 5-min window) derives from **`max(received_at)`, NOT `max(time)`**. This is load-bearing: a store-and-forward edge that reconnects replays its buffered samples oldest-first with their ORIGINAL (hours-old) observation timestamps (`edge-app/core` buffer), so an actively-publishing device would wrongly read offline if liveness used `time` - while its values still render on the dashboard (which reads the site's latest sample, not a freshness window). That exact split was a real prod symptom. Any new device-liveness query MUST use `received_at`.
- **Tenant handling (RLS).** The writer connects as the **non-privileged `voltpilot_app`** role - the same role the portal reads with - and, per event, opens a transaction that runs `set_config('app.tenant_id', <event tenant>, true)` before the INSERT. The RLS `WITH CHECK` (api migration V2) then both permits the write and **guarantees the row's `tenant_id` equals the session tenant** - a mismatched tenant can never be written, and the row lands exactly where that tenant's portal read (also RLS-scoped) finds it. (This is why `writer` `depends_on` `api`: api's Flyway owns the schema, the RLS policies and the `voltpilot_app` role.)
- **Idempotency / at-least-once.** Insert is a guarded `INSERT ... WHERE NOT EXISTS` on `(device_id, time)`, so a Kafka redelivery is a no-op. Offsets commit only after the listener returns (`ack-mode: record`, auto-commit off); a transient DB failure re-throws so Kafka redelivers - safe because the insert is idempotent. Per-site partition ordering means redeliveries are sequential, not concurrent.

**Closing the loop for `demo`.** No seed/ID change was needed: the edge's default identity (`VP_TENANT_ID/SITE_ID/DEVICE_ID` = `…0001/…0002/…0003`) already matches Tenant A / Demo Site Berlin / `demo-inverter-01`, which is exactly what the `demo` login surfaces. Live rows therefore appear in the demo telemetry view alongside (newer than) the dev seed.

**Tests (Testcontainers, `disabledWithoutDocker`, `docker.api.version` pinned like api).** `services/ingest`: `TelemetryValidatorTest` (unit, always runs - mapping + every rejection case) and `IngestPipeTest` (real EMQX + Redpanda: publish an edge-shaped MQTT message, assert the contract-shaped `telemetry.raw` event with the right key/fields). `services/timescale-writer`: `WriterPipeTest` (real Redpanda + TimescaleDB: produce a `telemetry.raw` event, assert exactly one hypertable row with the right identity/measurements, **idempotency** on duplicate delivery, and **RLS scoping** - visible to the owning tenant, hidden from another). The two pipe tests meet at the frozen `telemetry.raw` contract and together cover MQTT -> Redpanda -> Timescale. They use throwaway containers on random ports and never touch the shared dev stack.

## Zero-touch device onboarding (provisioning handshake)

The customer enters ONLY the Edge-Referenz (+ picks the site) in the portal - no IDs, no copy-paste commands. The physical device knows only its ref + the broker host. Contract: **`docs/contracts/mqtt-provisioning.schema.json`** (additive; telemetry/schedule stay frozen): the device publishes `provision/{ref}/hello` (QoS1, retried) and subscribes to `provision/{ref}/config`; the cloud answers a CLAIMED ref with the identity `{tenant_id, site_id, device_id}` published **retained** on the config topic; the device adopts it and switches to the normal frozen telemetry topics. Refs are MQTT-topic-safe by contract (`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`).

Two cloud publishers, deliberately redundant:
- **Resolver in `services/ingest`** (`provisioning/` package, enabled by default, `VOLTPILOT_PROVISIONING_ENABLED` to toggle): a second Paho adapter on `provision/+/hello`; `ProvisioningHandler` validates (topic ref == payload ref, schema_version, ref charset - malformed = log+skip like telemetry), looks the ref up in the `device` table via `JdbcDeviceDirectory` (LAZY plain JDBC with the trusted backend credentials - a hello carries no tenant, so the RLS app role can't serve it; no pooled datasource, so ingest starts/streams fine with the DB down) and publishes the retained config. Unclaimed ref = no answer (the device just retries - normal pre-onboarding state).
- **On-claim publish in `services/api`** (`ProvisioningPublisher`, off by default, compose sets `VOLTPILOT_PROVISIONING_ENABLED=true` + `MQTT_BROKER_URL`): the claim endpoint pushes the retained config the moment the claim succeeds, so an already-waiting device converges instantly ("claim-later"). **Best-effort by design** - claiming must never fail on a broker outage; the resolver answers the next hello retry.

Retention gives free **re-provision after restart** (the device gets its identity on subscribe). The **portal status** derives from `Device.lastSeenAt` (newest telemetry time, added to `DeviceDto`): null = "wartet auf erste Daten", within 5 min = online. `tools/edge-simulator` has a `--host` + `--ref` zero-touch mode performing this handshake (explicit-UUID flags still work). Tests: `ProvisioningHandlerTest` (unit), `ProvisioningPipeTest` (ingest; real EMQX+TimescaleDB: claimed/retained/unclaimed/claim-later), `ProvisioningClaimTest` (api; claim via REST -> retained config observed by a subscribed "device", incl. a registry-gated `VP-` sticker ref claimed lowercase converging on its canonical uppercase topic), simulator handshake tests against an in-process MQTT broker stub. The MQTT handshake runs on the dev/plain listener; for production, the same know-only-your-ref experience is delivered over HTTPS by **first-boot device enrollment** (see its section below), which hands the device its mTLS certificate automatically.

## Secure MQTT broker (real remote-device onboarding, mTLS)

The path for a physical Node-RED edge to reach a **self-hosted** broker over the internet and publish contract telemetry. Full model in [`docs/security-mqtt.md`](docs/security-mqtt.md); device-facing guide in [`docs/connect-a-device.md`](docs/connect-a-device.md). The dev experience is **unchanged** - the hardened broker lives in the production compose (`docker-compose.prod.yml`), not the dev `docker-compose.yml`, so the base EMQX block is untouched.

- **Two listeners.** Plaintext `1883` stays for local dev + the internal ingest consumer. A hardened **mTLS `8883`** listener (`verify_peer` + `fail_if_no_peer_cert`) is defined by the production compose `docker-compose.prod.yml` (server cert + device CA mounted from `infra/mqtt/certs/`, git-ignored). Devices make an **outbound-only** connection (architecture §6 - no inbound edge ports).
- **Identity binding.** Device cert subject `O={tenant_id}, OU={site_id}, CN={device_id}` (+ SPIFFE SAN). CN carries `device_id` (UUID fits the 64-char CN limit; the full `tenant/site/device` path does **not**, which is why it is NOT crammed into one CN). The broker sets `peer_cert_as_username=cn` / `peer_cert_as_clientid=cn` (in EMQX 5.x a GLOBAL `mqtt.*` setting, env `EMQX_MQTT__PEER_CERT_AS_*` - the listener-scoped env form is rejected as `unknown_env_vars`; verified on 5.8.3, harmless for cert-less 1883 clients), so a device can't spoof its identity.
- **Per-tenant/-device ACL** in `infra/mqtt/acl/acl.conf` (EMQX file authorizer, first-match): internal `vp-internal` user gets full `ems/#` (ingest); each device gets a **generated grant** allowing only its own `ems/{t}/{s}/{d}/telemetry|status` (up) and `…/schedule|command|config` (down); any UUID username without a grant is **default-denied everything** (that is how revocation works). Cross-tenant publish is denied. The `acl/` DIRECTORY (never the file) is bind-mounted into EMQX (ro) and the api (rw): the api's grant writer replaces `acl.conf` atomically via rename, which fails with EBUSY when the target is a single-file mountpoint - and a single-file mount would pin the broker to the replaced inode anyway (both verified live; this was a real prod outage). **`acl.conf` must stay world-readable (0644)**: EMQX reads it as a different non-root uid, and both grant writers' temp files (`mktemp` / `Files.createTempFile`) are born 0600 - the rename carries that mode onto the file, a running broker keeps its compiled rules, and the breakage only surfaces at the next authz reload/restart as a boot-time validation failure (`failed_to_read_acl_file: Permission denied`; also a real prod outage). Both writers now force 0644 on every write path, and the deploy workflows `chmod 755` the dir + `chmod 644` the file after the ACL merge as belt-and-braces. Grant changes apply via `tools/pki/reload-broker-authz.sh` - **`emqx ctl conf reload` does NOT re-read the file** (the file authorizer compiles rules at source init and only re-initializes on a config change; verified on 5.8.3 - the script forces the re-init through `emqx eval 'emqx_authz:update({replace, file}, ...)'`); the CI deploy workflows run it after `up -d`, and they MERGE the deployed ACL's generated grant region via `tools/pki/merge-acl-grants.sh` instead of overwriting it (runtime grants would otherwise be revoked on every deploy).
- **CA + issuance tool** `tools/pki/voltpilot-ca.sh` (openssl, `openssl.cnf`): `init-ca` (CA once + broker server cert), `issue --tenant --site --device` (client cert + ACL grant), `revoke --device` (CRL + grant removal), `gen-crl`, `list`. Keys land in `tools/pki/out/` (git-ignored) - **never committed**.
- **Provisioning** `tools/pki/provision-device.sh` ties it together: calls the portal `POST /api/v1/devices/claim` (reusing device-claiming, tenant from the JWT `tenant_id` claim), then issues the cert bound to the returned `device_id`, and prints connection params.
- **Run it:** `docker compose -f docker-compose.prod.yml up -d` (the standalone production stack, which includes the hardened broker) after `init-ca` + staging `infra/mqtt/certs/`. Only `8883` is public (1883/dashboard → loopback); firewall is the real guarantee (hardening checklist in `docs/security-mqtt.md`). Full deploy flow: `docs/deploy.md`.
- **Verify (Docker-free):** `python3 tools/pki/verify_mqtt_security.py` - runs a real mutual-TLS handshake (valid cert connects, no/untrusted cert rejected, revoked cert fails CRL) and evaluates the real `acl.conf` with EMQX first-match semantics (own-path allow, cross-tenant deny, down-only enforcement, internal allow). This sandbox blocks Docker, so the live EMQX-on-18883 + mosquitto recipe is documented (not executed) in `docs/security-mqtt.md`.

## First-boot device enrollment over HTTPS (kinderleicht mTLS onboarding)

The automatic path to a device certificate - closes the former "mTLS zero-touch is future work" gap: a fresh edge device knows ONLY its reference and the portal URL, generates its keypair locally (the key never travels), uploads a CSR, and polls for its certificate; the moment the customer claims the ref in the portal, the api signs the CSR with the device CA and the device switches to normal 8883 mTLS operation.
No manual cert copying; contract = the `enrollment` tag in `docs/contracts/openapi.yaml` (a Go edge agent is the intended consumer).
Device-facing flow in `docs/connect-a-device.md`, trust-boundary discussion in `docs/security-mqtt.md`.

- **Endpoints** (`EnrollmentController`, both UNAUTHENTICATED + rate-limited; permitted in the `secured` chain; whole feature absent unless `VOLTPILOT_ENROLLMENT_ENABLED=true`): `POST /api/v1/enrollment/{ref}/csr` (stores the pending CSR keyed by the canonical ref - same canonicalization as the claim; idempotent replace until issued, then 409 - re-keying goes through revoke + unclaim/re-claim; `VP-` refs pass the provisioned-device registry gate exactly like claims, 422 otherwise) and `GET /api/v1/enrollment/{ref}/certificate` (404 `status=pending` while unclaimed - IDENTICAL for unknown refs, so polling cannot enumerate; once claimed returns `{deviceCertPem, caPem, mqttHost, mqttPort, tenantId, siteId, deviceId}`; the cert stays retrievable for retries - the private key is the secret and never left the device).
- **The api is a second CA issuer, interop-by-design** (`enrollment/DeviceCertificateAuthority`, BouncyCastle): subject is ALWAYS the claim-derived `O=tenant/OU=site/CN=device_id` + SPIFFE SAN (whatever subject the CSR requested is ignored - a CSR proves key possession, never picks identity), extensions mirror `openssl.cnf [v3_device]`, and issuance uses the SAME CA working dir as `voltpilot-ca.sh`: openssl serial-file protocol, `index.txt` line, `newcerts/<serial>.pem` - so `revoke`/`gen-crl`/`list` cover api-issued certs. `AclGrantWriter` writes the byte-identical grant block the shell tool writes (and unclaim removes it best-effort via `EnrollmentService.onDeviceUnclaimed`, so a stale cert loses broker access; EMQX mounts the ACL directory read-only, api mounts it read-write). The writer's atomic tmp+rename is kept primary; if the rename is refused (`FileSystemException`, the single-file-mount EBUSY case) it degrades to a documented NON-atomic in-place rewrite with a warning - on a single-file mount that is the only write that propagates. **Right after each grant write (issuance) AND removal (unclaim) the api auto-reloads the broker authorizer** so the change is enforced within seconds instead of at the next deploy/cron reload - see "Broker authz auto-reload" below; `tools/pki/reload-broker-authz.sh` stays the backstop.
- **Storage**: `device_enrollment` table (api migration `V20260702040000`) - pre-claim manufacturing-style data like `provisioned_device`, deliberately no tenant/no RLS; the app role gets INSERT/UPDATE (the endpoints run unauthenticated through the app datasource), DELETE revoked (rows double as issuance audit trail). The claim-state lookup uses the BYPASSRLS admin datasource (`EnrollmentDeviceLookup` - an enrollment poll carries no tenant, same reasoning as ingest's `JdbcDeviceDirectory`).
- **CSR policy** (`Csrs`): PEM PKCS#10, self-signature verified (proof of possession), keys RSA >= 2048 or EC P-256/P-384, 20 KB size cap; German refusal copy. Rate limiting: `EnrollmentRateLimiter` with its own `voltpilot.enrollment.rate-limit.*` namespace - the sliding-window mechanics were extracted to `SlidingWindowRateLimiter` (base of `RegistrationRateLimiter` too, budgets independent); defaults sized for the documented 30-60 s poll etiquette (240/client/h + 5000 global).

## Broker authz auto-reload (`BrokerAuthzReloader`)

Closes the "claimed-but-refused" timing gap: EMQX's file authorizer compiles `acl.conf` ONCE at source init and never re-reads it on its own (`emqx ctl conf reload` and `authz cache-clean` provably leave the old rules active, verified on 5.8.3 - the whole reason `tools/pki/reload-broker-authz.sh` exists).
Before this, a freshly claimed device was refused by the broker until the deploy-time reload or the 5-min ops cron ran - a gap that bit twice.

- **What it does.** After `AclGrantWriter.writeGrant` (enrollment issuance) or `removeGrant` (unclaim), `EnrollmentService` calls `BrokerAuthzReloader.requestReload()`, which re-initialises the EMQX file authorization source so the grant is enforced **within seconds**.
- **Mechanism (verified live on EMQX 5.8.3).** The api container cannot run `emqx eval` (no docker socket), so it reaches the broker over the **REST management API v5** - the HTTP twin of the script's `emqx_authz:update({replace, file}, ...)`: `PUT {api-url}/authorization/sources/file` with `{type:file, enable:true, rules:<the current acl.conf content>}`. The REST file source is modelled by **content (`rules`), not a path** - it rejects a `path` field (HTTP 400 `unknown_fields`) - so the reloader reads the same mounted `acl.conf` that `AclGrantWriter` just wrote and hands over its bytes; EMQX recompiles and the new grant is live. Proven end to end: a grant appended after boot is DENIED until the PUT and ALLOWED immediately after (real MQTT publish check).
  - **Path-hijack, and why it's harmless.** A side effect of PUTing `rules` is that EMQX repoints the running source at its own `data/authz/acl.conf` copy. This does not matter here because (a) the mounted `acl.conf` stays the single source of truth - the api and the shell tools only ever write it, and the reloader re-reads it on every reload; and (b) the `EMQX_AUTHORIZATION__SOURCES` env pin **resets the path back to the mounted file on the next broker restart** (also verified live). The shell backstop (`emqx_authz:update` with `path=/opt/emqx/etc/acl/acl.conf`) likewise resets the path and recompiles from the mounted file - the two mechanisms produce identical rules and never fight over content.
- **Non-fatal, coalesced, feature-flagged.** A reload failure only logs a warning - it NEVER fails an issuance or unclaim (the cron/deploy reload remains the backstop). Reloads run on a single background daemon thread and are coalesced over a short debounce window (default 300 ms), so a burst of grant changes collapses into one REST call that reads the latest file. The bean exists only when `voltpilot.enrollment.broker-authz-reload.enabled=true` AND an `api-url` is set, so dev, tests and non-enrollment deployments never need EMQX.
- **Auth.** Either an EMQX API key (HTTP Basic, stateless - preferred) via `broker-authz-reload.api-key`/`api-secret`, OR the dashboard user/password (`username`/`password`, a cached login token, re-login on 401). The prod compose uses the latter, reusing `EMQX_DASHBOARD_USER`/`EMQX_DASHBOARD_PASSWORD` already shipped by the emqx service - no new secret. (Note: creating an API key via the EMQX REST `POST /api_key` is broken on 5.8.3 - `INTERNAL_ERROR` badmatch; use the dashboard UI or a bootstrap file to mint one, or just use the dashboard credentials.)
- **Config** (`voltpilot.enrollment.broker-authz-reload.*` / `VOLTPILOT_BROKER_AUTHZ_RELOAD_*`): `enabled` (default false; **prod compose sets true**), `api-url` (the REST base incl. `/api/v5`, prod `http://emqx:18083/api/v5` on the internal network - the dashboard port stays loopback-only to the host), `api-key`+`api-secret` OR `username`+`password`, `timeout` (PT5S), `debounce` (PT0.3S). **Prod `.env` additions:** none required beyond the existing `EMQX_DASHBOARD_PASSWORD` - the feature reuses it; `VOLTPILOT_BROKER_AUTHZ_RELOAD_ENABLED=false` opts out. **Needs a redeploy** to take effect (new api env). The deploy-workflow + cron `reload-broker-authz.sh` is deliberately KEPT as defense in depth.
- **Two-constructor footgun (@Autowired is load-bearing).** `BrokerAuthzReloader` has TWO constructors - the production `@Value`-injected one and a package-private test seam (`Path, FileSourceUpdater, long, ScheduledExecutorService`). The production constructor **must** stay annotated `@Autowired` so Spring selects it: with multiple constructors and none marked, Spring cannot pick the injection constructor, falls back to a (non-existent) no-arg constructor, and the whole api context crash-loops on startup with `No default constructor found` the moment `broker-authz-reload.enabled=true` matches the `@ConditionalOnProperty` (i.e. in prod). This shipped once (#42) because the unit/live tests construct the class directly and never exercised the Spring wiring with the flag on.
- **Tests.** `BrokerAuthzReloaderTest` (pure unit, always runs): reload pushes the current file content, is non-fatal when the broker call throws / the file is missing, and coalesces a burst into one call picking up the latest content (mocked `FileSourceUpdater`). `BrokerAuthzReloaderContextTest` (pure Spring slice via `ApplicationContextRunner`, always runs - the regression guard for the footgun above): boots the reloader with the flag ENABLED + minimal EMQX config and asserts the bean is created via its `@Value` constructor (and is absent when the flag is off); it fails with the exact `No default constructor found` crash if the `@Autowired` is dropped. `BrokerAuthzReloaderLiveIT` is an **opt-in** live proof of the real HTTP path against a running EMQX (skipped unless `EMQX_REST_URL` is set; not collected by surefire's default `*Test` pattern) - used to verify the flip live. The existing `EnrollmentApiTest` exercises issuance/unclaim with the reloader UNCONFIGURED (default disabled -> `ObjectProvider` empty -> no-op), proving the enrollment path is unaffected when the feature is off.

## Standalone edge simulator (`tools/edge-simulator`)

An **installable-anywhere** simulated edge device: a single dependency-light Python program (only `paho-mqtt`) that publishes a believable PV/battery/load day to any VoltPilot broker, so a "device" on another LAN host writes into the captain's stack and shows up in the portal. It is **separate from** the Node-RED `edge/` (which models SunSpec/Modbus hardware) - do not conflate them. Full docs in `tools/edge-simulator/README.md`.

- **Contract-exact.** Publishes to `ems/{tenant_id}/{site_id}/{device_id}/telemetry` at QoS1 (+ `.../status` heartbeat), payload verbatim per `docs/contracts/mqtt-telemetry.schema.json` (`schema_version "1.0"`; note the field is **`ts`**, not `timestamp`). Feeds the existing ingest pipe unchanged. Identity defaults mirror the `demo` dev seed (`…0001/…0002/…0003`), so a no-arg local run lands in the demo telemetry view.
- **Zero-touch mode.** `--host <broker> --ref <edge-ref>` performs the provisioning handshake (see "Zero-touch device onboarding") instead of taking UUIDs: hello-retry until the ref is claimed in the portal, adopt the retained config, then publish normal telemetry. Explicit `--tenant-id/--site-id/--device-id` still work and skip the handshake.
- **Config** via CLI > env (`EDGE_SIM_*`, also honors `VP_TENANT_ID/SITE_ID/DEVICE_ID`) > optional `.env`. Plain `1883` and **mTLS `8883`** (device certs from `tools/pki/provision-device.sh`; TLS auto-enables on 8883 or when a client cert is set). No SNI-override flag - `init-ca --domain --ip` puts both in the server cert SAN so dialing either verifies; `--insecure` is the dev escape hatch.
- **Simulation.** Diurnal PV (zero at night, noon peak), household load profile, battery charge-midday/discharge-evening (SoC clamped 10-100%), `power_kw = load - pv + battery` (signed +import/-export), mild noise (seedable). `--time-scale N` replays a full day fast (e.g. 288 → a day in 5 min); `--time-scale 1` tracks the real clock. `--count N` exits after N messages.
- **Packaging.** `requirements.txt`, `Dockerfile` (multi-arch, non-root), example `voltpilot-edge-sim.service` systemd unit for a Pi, and an **opt-in compose service `edge-simulator`** under its **own `sim` profile** (NOT `edge`, so it never double-publishes with `edge-nodered`): `docker compose --profile sim up -d --build edge-simulator`.
- **Tests/proof.** `python3 -m pytest tools/edge-simulator/test_edge_sim.py -q` (or `python3 test_edge_sim.py`) runs fully offline - validates generated payloads against the **real** schema, the power-balance identity, PV day/night, battery cycle, SoC bounds, topic format, config precedence. Live proof: `tools/edge-simulator/proof/publish_and_verify.sh` publishes N and shows rows land in TimescaleDB (needs the `edge`-profile ingest path up). The real paho wire path (CONNECT + QoS1 PUBLISH/PUBACK) was verified against an in-process broker stub since this sandbox blocks Docker.
## VoltPilot Edge-App (`edge-app/`): the installable customer-side edge

The productized two-layer edge the captain decided on (2026-07-02); one docker-compose package the customer installs on their device.
Full docs in [`edge-app/README.md`](edge-app/README.md).
It is SEPARATE from `edge/` (the thin dev Node-RED edge in the cloud-stack compose) and from `tools/edge-simulator` (the MQTT-publisher sim) - do not conflate the three.

- **Layer 2 = `edge-app/core` (Go, module `.../edge-app/core`, binary `vp-edge-core`)** - identical at every customer, the ONLY thing talking to the cloud:
  first-boot HTTPS **enrollment** (EC P-256 key on-device -> CSR -> poll; consumes the api's enrollment endpoints exactly; conflict/unknown-ref states surfaced in German), the single outbound **mTLS MQTT** link (paho; broker derives identity from the cert CN),
  **honest failure states in the enroll state machine** (`enroll.State` - so `:8484` distinguishes "broken" from "waiting for you to claim", not one cheerful "warte" for everything): `portal_nicht_erreichbar` on a dial error / timeout / 5xx during CSR upload or cert poll (a 404 stays `pending`; clears itself when the portal answers again), `geraet_fehler` on a LOCAL first-boot failure (unwritable `/data`, key/CSR build - `enrollAndConnect` retries with capped backoff instead of silently exiting the goroutine), `cloud_fehler` when the cert is on disk but `startCloud` fails (retried with backoff, distinct from a blip), and `cloud_getrennt` when a live link drops (the pairing checklist moves OFF the green `verbunden` so it agrees with the Cloud stat). `getCertificate` also rejects a claim response with no `mqttHost`/`mqttPort`.   **while-connected identity re-reconciliation** (`enroll.Enroller.Reconcile` + `agent.reconcileLoop`, `VP_RECONCILE_INTERVAL_SECONDS`, default 300 s, also nudged on every cloud disconnect): the device re-polls `GET /enrollment/{ref}/certificate` and, if the portal now reports a DIFFERENT `device_id` (an unclaim+re-claim, or a `down -v`+re-claim, mints a new device row and the api re-issues the cert against the stored CSR - same key), **adopts** the new cert/identity on disk and tears down + rebuilds the cloud link on the new topics (reconnect is mandatory - the broker enforces the cert-CN identity via its ACL; the store-and-forward buffer is stamped at publish time so pending entries flow to the new id). Because the VoltPilot crew cannot reach a customer's logger, the operator runs the standalone dependency-free **[`edge-app/nodered/deye/solarman-probe.js`](edge-app/nodered/deye/solarman-probe.js)** ON THE EDGE VM (`node solarman-probe.js --ip <logger> --serial <n> --family <f>`; also `--start/--count` for a raw register dump) to prove the transport + confirm register maps against real hardware. Confirmed real logger for the on-hardware test: IP `192.168.0.28`, datalogger serial `2985159064`, port 8899, LSW3 stick on a **`SUN-*-SG01HP3-EU` 3-phase HV HYBRID** (~50 kW class; inverter serial `2407224048`, read from identity regs `0x0003..0x0007` as ASCII) - **NOT a string inverter** (an early guess the register dump disproved: regs `0x0050..0x00CC` are the hybrid's battery/charge CONFIG area - charge/discharge current `0x006C/0x006D`, capacity `0x0066`, charge voltages `0x0083/0x0086` - so the live measurements sit at `0x024C+`, decoded by the **`hybrid_3p`** family; the old `--family string` map read those config regs as measurements and produced 30 MW garbage). **`hybrid_3p` covers BOTH 3-phase hybrid lines** (SG04LP3 LV 2-MPPT **and** SG01HP3 HV 3-4-MPPT - same ha-solarman high-map): `soc 0x024C`, `batt 0x024E`, `grid 0x0271`, `load 0x028D`, **PV = sum of all 4 MPPTs `0x02A0..0x02A3` (dec 672-675)**, single read block `024C0058` (88 regs). Addresses are authoritative from ha-solarman `deye_sg04lp3.yaml` (+ Deye Modbus manual for PV3/PV4); two things stay VERIFY-on-device: the **grid sign** (`invert_grid_sign`) and the **HV power scaling** (config `power_scale`, default 1/W per ha-solarman - as read on the captain's SG01HP3 in #49; if a live read on ANOTHER HV unit shows PV ~10× low vs the logger status page or `power_kw` saturating at ±32.7 kW/int16, that firmware reports decawatts → set `power_scale: 10` in the inverter config, NO code edit - it multiplies all power fields pv/grid/load/batt, never SoC). **The `at_cli` fallback** uses the **bundled `deye` CLI** (`github.com/s10l/deye-logger-at-cmd`, a Go binary; the nodered Dockerfile builds it in a `golang` stage - default branch is **`main`** (pinned via `DEYE_REF`), main package is in `src/`, binary lands at `/usr/local/bin/deye`; offline fallback = drop a release binary there). The operator sets `flow.deye_wechselrichter = [{ip, communication, port, serial, mb_slave_id, family, invert_grid_sign, invert_batt_sign, power_scale, limit_stages}]` in the *Deye-Konfiguration* node; `family` (`string`/`hybrid_1p`/`hybrid_3p`/`micro`) selects the register map. **The four families reconcile ha-solarman's FIVE Deye definitions** (`deye_string`→`string`; `deye_2mppt`+`deye_4mppt`→`micro`; `deye_hybrid`→`hybrid_1p` low map; `deye_sg04lp3`→`hybrid_3p` high map) - see the model→family table in `DEYE.md`. **`string` and `micro` report ONLY generation** = the inverter's own AC-output register (`0x0050`/`0x0051` for string, `0x0056`/`0x0057` for micro; 32-bit low-word-first ×0.1→W), which is post-inverter and already sums ALL MPPT strings (MPPT-count-agnostic, 1-4). A string/micro inverter has NO grid-meter or house-load register (that is a hybrid feature), so the pre-#49 `string` map's grid/load fields (`0x00C6`/`0x00CB`) were fictional and were removed; `micro` (formerly write-only) now reads AC output too. The `at_cli` exec nodes shell out to `deye -t ip:48899 -xmb <REGHEX4><COUNTHEX4>` (read, fn 0x03, answer `+ok=0103<byteCount><data><crc>`); **32-bit values are LOW-WORD-FIRST** `(reg[+1]<<16)+reg[0]`. Reads are done as **one contiguous block per family** (`hybrid_1p` 22 regs, `hybrid_3p` 88 regs, string/micro a 2-reg AC-output pair - all well under the 125-reg fn-0x03 max) via a **sequential** read loop (never two `deye` processes at once on the one logger). Only the canonical cloud fields are published to `vp-telemetrie` (soc only for hybrids); **battery power is NOT a telemetry field** (read for sign calibration/status only - the cloud derives it from the power balance), and `grid_limit_kw`/§14a is not exposed by these Deye registers. **Sign convention is firmware-dependent** (sunsynk inverts vs ha-solarman raw): the `invert_grid_sign`/`invert_batt_sign` flags + the on-device calibration procedure (midday PV surplus → grid negative; forced charge → batt positive) are the answer - never trust a library's sign blindly; **all scaling/signs are VERIFY-on-device**. **Family auto-detect:** the "Familie erkennen" inject probes `-xmb 00B80001` (low-map SoC) vs `-xmb 024C0001` (high-map SoC) - exactly one reads a sane 0..100 → hybrid_1p vs hybrid_3p (string/micro have no SoC, chosen manually). **String/micro power-limit write** (active-power curtailment 0..100%) goes to reg `0x0028` via `-xmbw 00280001 02 <pct>`, with optional `limit_stages` snapping - this is the clearly-labeled EMS control stop where VoltPilot maps its §14a/curve onto device stages. **Hybrid battery charge/discharge control is deliberately OUT OF SCOPE** (no direct watt setpoint; indirect via System Work Mode + Time-of-Use + amp current limits, model-dependent, can damage a battery) - left as a documented TODO with researched control registers in `DEYE.md`. The canonical, unit-tested decode (parser + register maps + scaling + power-limit/auto-detect helpers) lives in **[`edge-app/nodered/deye/deye-decode.js`](edge-app/nodered/deye/deye-decode.js)** (`node --test edge-app/nodered/deye/`, no hardware/network); the flow's function nodes carry a **synced copy** of that logic (a Node-RED flow is self-contained JSON and cannot `require` a repo file). **SoC drop-don't-fabricate gate (real prod symptom - 12k LV SoC time series spiking 0/100):** a Solarman logger that can't reach the inverter (typical at night) still returns a well-framed, CRC-valid response - usually an all-zero register block or, on a misaligned frame, an out-of-range value. Decoding those verbatim published `soc_pct=0` (axis floor) or `soc_pct>100` (chart 0-100 axis CLIPS it to the ceiling → the "100" spikes), while the true stepped curve stayed faintly underneath; the register map itself (`0x024C`) is CORRECT per ha-solarman - it is NOT a wrong-register bug, and NOT the family auto-detect (the self-wiring path routes on the configured `family`, never re-probes). Fix: `decode()` DROPS a battery-family reading whose SoC is unreadable or outside `(0,100]` (returns null → NO sample published, never a fabricated 0; `socPlausible()`), so the chart gaps instead. `flows-sync.test.js` now guards the inline `auto-deye-decode` copy against the module (incl. the drop cases). **The gate is enforced on EVERY live display path, not only the Deye decode** (real prod symptom #2 - the `:8484` SoC tile rendered a raw read as "1.270 %"): the edge core drops an implausible-SoC sample at its ONE local-bus ingest choke point (`agent.onLocalTelemetry` via `guards.SocPlausible`, the Go twin of `socPlausible()`; `TestSocPlausible` pins the same vectors as `deye-decode.test.js` so the two cannot drift - the refCheckChar/EdgeRef precedent), so garbage from ANY Layer-1 flow (generic Modbus, custom wiring, a pre-gate Deye build) can never reach the dashboard tiles/energy flow (state snapshot), the live charts (history ring), the cloud (telemetry buffer + status-heartbeat `lastRawSoc`) or the setpoint guards; every display keeps its last good value and the existing >90 s freshness UI (`.stale` + "keine aktuellen Daten") turns honest on its own because `LastTelemetry` only advances on kept samples (`telemetry_gate_test.go`). **Transient IN-BAND spike gate (`guards.Despiker`, real prod symptom #3 - the captain's SoC momentarily reading e.g. 2 % between two steady 94 % samples, "genauso bei anderen Werten"):** the `SocPlausible` gate above only rejects OUT-OF-band values, so a physically-impossible but in-band single-sample jump passes it. `guards.Despiker` runs right after `SocPlausible` at the SAME `agent.onLocalTelemetry` choke point and gates **per channel** (a dropped channel is removed from THAT sample only; the good channels in the same sample still flow - `lastRawSoc`/the SoC tile keep last-good, `lastReading` treats a despiked SoC as "unknown" exactly like a SoC-less sample). Two regimes: **SoC is integrative** (cannot step fast) → a physically-motivated RATE bound (allowed |Δ| = `socMargin` 5 % + `socMaxRatePctPerSec` 1 %/s × elapsed, so it scales with the real inter-sample gap; a gap beyond `despikeGapReset` 5 min accepts a fresh baseline, so a reboot never false-rejects). **Power channels (`power_kw`/`pv_power_kw`/`load_kw`) can legitimately step fast** (cloud edge, load switching) → NOT rate-limited, only a GROSS excursion (both `|Δ| > powerAbsFloorKw` 100 kW AND `> powerRelFactor` 8× the previous magnitude - the "30 MW" decode-garbage signature) is suspect; when in doubt a power sample passes (a missed spike is cosmetic, a suppressed real transient is a bug). `grid_limit_kw` is UNgated (a §14a envelope change is a legitimate step). **Accept-after-confirmation (no deadlock, no lookahead):** a suspect jump is dropped but remembered as a candidate; after `despikeConfirmCount` (3) consecutive agreeing readings the new level is adopted, so a genuinely resynced BMS or a corrected reading converges instead of sticking on the stale level forever (the earlier readings stay dropped - drop-never-alter). Dropped samples are counted in the state snapshot (`DespikedDropped`) and logged at debug rate-limited (`despikeLogInterval` 30 s). Proven by `guards/despike_test.go` (the 94→2→94 symptom, steady discharge passes, persistent level converges, long-gap reboot, power spike-and-return dropped, genuine fast power step passes) + `agent/despike_gate_test.go` (the symptom end to end: the 2 never reaches the state/history-ring/buffer; a glitchy multi-channel sample keeps its good channels). **Follow-up option for OLD edge builds (NOT built - the captain's device until he updates still uploads spikes):** the server-side `timescale-writer` could add a STATELESS belt-and-braces heuristic (e.g. drop an out-of-`(0,100]` SoC on insert, matching the portal-side `sanitizeSoc`), but a stateful per-device rate/jump gate does NOT belong in the writer (it must stay a stateless idempotent inserter); the portal-side render gap for a bad DB row is the existing mitigation. Belt-and-braces in the portal: the shared `sanitizeSoc` (`src/plausible.ts`, the single portal-side source) maps an out-of-range `socPct` to null in `TelemetryChart.tsx` (`connectNulls:false` → gap, never a clip-spike) AND backs the Übersicht "Batterie-Ladestand" tile, which falls back to the newest plausible reading with a calm "Stand vor X" note when that lags the live data by >5 min (the deviceLiveStatus window) - so a pre-existing bad DB row can't render anywhere either. Operator guide: **[`edge-app/nodered/DEYE.md`](edge-app/nodered/DEYE.md)** (per-family register tables, the auto-detect probe, the CLI install, config shape, sign calibration, and the honest scope note).
- **Inverter selection (`core/internal/inverter` + the local web app).** The customer/operator picks their inverter ONCE in the Edge-App web UI (`:8484` → "Wechselrichter einrichten", `static/inverter.html`+`inverter.js`): **brand → family/type → connection params**. ## Production deployment (single VM/VPS, "deploy like saalo")

MVP-on-one-server: an external reverse proxy on another host terminates TLS (the company's **Nginx Proxy Manager** for the internal-VM deployment; Caddy stays documented as the alternative), the whole server-side stack runs from **`docker-compose.prod.yml`** (a self-contained, standalone file - NOT merged with the dev `docker-compose.yml`), and Forgejo does push-to-deploy once CI secrets are set. Full guide in [`docs/deploy.md`](docs/deploy.md); the recipe mirrors the saalo repo's proven pattern.

- **Two deploy paths, one compose.** (a) **Manual first deploy, no CI** (the leading `docs/deploy.md` section "Erstes Deployment (interne Ubuntu-VM)"): git clone to `/srv/docker/voltpilot` on the VM (the clone IS the deploy dir - the compose bind-mounts `infra/prod/`, `infra/mqtt/`, `deploy/keycloak/themes/` by relative path), fill `.env`, stage the MQTT certs (required - EMQX file-mounts them), then `docker compose -f docker-compose.prod.yml build && ... up -d`. Every app service carries a `build:` context next to its `image:` name, so `build` tags local images under the registry names and `up` uses them without pulling. (b) **CI push-to-deploy** (`.forgejo/workflows/deploy.yaml`): pull-based roll-out over SSH, `IMAGE_TAG` pinned to the SHA (ignores `build:`).
- **Two public ports only.** `frontend` on `APP_PORT` (plain HTTP, firewalled so only the reverse-proxy host reaches it) and EMQX `8883` (mTLS, for devices - **TCP, not proxied by NPM's HTTP proxy hosts**; devices dial `<VM-IP>:8883` directly, or an NPM Stream). Everything else (api/keycloak/keycloak-db/timescaledb/redpanda/ingest/writer/collectors) is internal on the `voltpilot-prod` network; `1883`/`18083` are loopback-only. **The frontend's nginx is the single web entry point** (`frontend/portal/nginx.conf`): serves the SPA and reverse-proxies `/api/ -> api:8090` and `/auth/ -> keycloak:8080`, so the API and Keycloak stay internal. The proxy must forward `https://${DOMAIN} -> http://VM:${APP_PORT}` preserving `Host` and setting `X-Forwarded-Proto: https` - NPM's default proxy-host template does both (enable Block Common Exploits + Websockets Support); the `/auth` login flow breaks without that header.
- **Keycloak in prod mode.** `start --import-realm` against a **dedicated** `keycloak-db` (isolated from TimescaleDB, mirrors saalo). Served under the `/auth` relative path (`KC_HTTP_RELATIVE_PATH`, `KC_HOSTNAME=https://${DOMAIN}/auth`, `KC_PROXY_HEADERS=xforwarded`). Prod realm `infra/prod/keycloak/voltpilot-realm.json` parametrizes the browser origin, confidential secret and Portal-Admin password via `${VP_PUBLIC_ORIGIN}` / `${VP_API_CLIENT_SECRET:change-me}` / `${VP_PORTAL_ADMIN_PASSWORD:admin}` (Keycloak-26 realm-import placeholder replacement reads env vars as `${VAR}`/`${VAR:default}`; the Wildfly-era `${env.VAR}` prefix is NOT substituted and aborts the import - verified on 26.0.5; all vars set on the keycloak service). So the api's issuer is `https://${DOMAIN}/auth/realms/voltpilot` while JWKS is fetched internally at `http://keycloak:8080/auth/realms/voltpilot/...certs` (the same issuer-trap split as dev). The prod realm mirrors the dev realm's **admin increment** (platform-admin role, seeded `admin` Portal-Admin user, `realm-management` service-account grants, declarative user profile for `tenant_id`), and the prod api sets the matching env: `ADMIN_DB_PASSWORD` (the BYPASSRLS `voltpilot_admin` role would otherwise run on its hardcoded dev password) and `KEYCLOAK_ADMIN_BASE_URL=http://keycloak:8080/auth` (note the `/auth` path - the dev default without it 404s in prod). **Keycloak-26 prod-mode footgun:** `start --import-realm` strict-parses the realm JSON and ABORTS boot on unknown fields (e.g. a `_comment` key) - `start-dev` never caught this; docs for the prod realm live in `infra/prod/keycloak/README.md` instead.
- **VoltPilot Keycloak login theme** in `deploy/keycloak/themes/voltpilot/` (login only; saalo's structure: `parent=keycloak.v2` + one override stylesheet, so ALL flows incl. error/forgot-password pages inherit the styling). Colors/typography come from the portal design-system tokens (`frontend/portal/designsystem/tokens/*.css`), the wordmark is the real logo PNG copied from `designsystem/assets/`, DE/EN message overrides brand the titles, and both realm imports set `loginTheme: voltpilot` + enable `de` as the default locale. The theme dir is bind-mounted read-only into keycloak in BOTH composes; the deploy workflows scp it and `docker compose up -d --force-recreate keycloak` after `up -d`: in `start` mode themes are cached at boot AND pre-gzipped into `/opt/keycloak/data/tmp/kc-gzip-cache` on the container FS, which SURVIVES a plain `restart` - browsers (gzip) then still get the OLD css while curl (no gzip) sees the new one (haunted-cache footgun, verified on 26.0.5). Dev `start-dev` keeps the caches off, but an already-running dev keycloak needs ONE `up -d` recreate to pick up the new theme mount + realm setting.
- **Images for the CI path.** All six deployed images (`api`, `ingest`, `timescale-writer`, `frontend`, `market-data`, `forecast`) come from `git.tecmaxx.de/mamotec/voltpilot-ems/<svc>:${IMAGE_TAG}`; the deploy pins `IMAGE_TAG` to the commit SHA. Each has a prod Dockerfile; the **frontend** Dockerfile grew an nginx.conf + `VITE_*` build args (`VITE_API_BASE` empty => same-origin `/api`; `VITE_KEYCLOAK_URL=https://${DOMAIN}/auth`) - the compose `build:` block passes the same args from `.env` for the manual path (changing `DOMAIN` means rebuilding the frontend).

The two non-RLS hypertables (`day_ahead_prices`/`forecast`) are created by the prod init script `infra/prod/timescale/00-collector-tables.sql` (mirrors the service migrations; runs on a fresh volume before the api's Flyway owns the core schema). ## Contracts (binding)

## Market data (ENTSO-E day-ahead prices)

`services/market-data` is the anti-corruption adapter that feeds day-ahead spot prices into the optimizer (architecture section 11/13: "Marktdaten: ENTSO-E Transparency, hinter Adapter").

- **Port / providers.** `DayAheadPriceSource` (in `source.py`) is the provider-agnostic port; every caller depends on it, never on ENTSO-E. `EntsoeDayAheadPriceSource` is the first implementation; a commercial provider is a drop-in replacement. `ResilientPriceSource` decorates any source with retry (exponential backoff), a circuit breaker, and a **last-good cache**, so the optimizer always gets a usable series even when ENTSO-E is down.
- **Internal representation.** `PriceSeries` / `PricePoint` (EUR/MWh, UTC slot bounds, `PT15M`/`PT60M`). No vendor vocabulary crosses this boundary.
- **Zone -> EIC mapping** lives only in `zones.py`: `DE-LU -> 10Y1001A1001A82H`, `AT -> 10YAT-APG------L`, `CH -> 10YCH-SWISSGRIDZ`. DE-LU is implemented end to end; adding AT/CH is a one-line edit there.
- **Storage.** Prices are timeseries -> the `day_ahead_prices` **hypertable**, keyed by `(bidding_zone, resolution, ts)`. Prices are market-wide **per bidding zone, not per tenant**, so there is deliberately **no `tenant_id`** (and no RLS) on this table, unlike `telemetry`. Schema is owned by the forward-only migration `services/market-data/db/migration/V20260701001200__day_ahead_prices_hypertable.sql` (Flyway/Liquibase-compatible; **date-based version chosen so it does not collide with the api service's future `V1, V2, ...` baseline** - coordinate future market-data migrations to stay in this `V2026...` scope). The local dev stack mirrors it via `infra/local/timescale/02-day-ahead-prices.sql` (additive; the existing `01-init.sql` is untouched).
- **Token.** `ENTSOE_SECURITY_TOKEN` is a **captain-provided secret** (blank in `.env.example`); obtain via ENTSO-E Transparency registration + a "Restful API access" email (see `services/market-data/README.md`). It is **not** needed for tests/CI - parsing, mapping and resilience run entirely off recorded fixtures in `tests/fixtures/`. A live token is needed only for a real end-to-end fetch; that end-to-end verification is still open.
- **Fetch cadence.** ENTSO-E publishes the next day's prices ~12:45 market time; run `python -m voltpilot_market_data fetch --zone DE-LU --persist` daily after that (cron `0 13 * * *`, or a future K8s CronJob from the service `Dockerfile`). The CLI `--zone` defaults to the `MARKET_DATA_ZONE` env var (fallback `DE-LU`) when omitted, so the container `CMD` is just `fetch --persist` and picks its zone from the environment. Following the backbone-first convention, the service is **not** wired into `docker-compose.yml`.

## Optimization engine (`services/optimization`)

The product's heart: a deterministic battery-dispatch MILP (Pyomo + HiGHS) in MPC style - rolling **24h horizon, 15-min slots**, re-planned **every 15 min** per site with a battery asset. **Predict-then-optimize** (captain's long-term direction is ML forecasting): forecasting stays a separate, swappable layer; the optimizer only consumes slot-aligned price/forecast series, so learned models later replace the baselines without touching it. Full detail in `services/optimization/README.md`.

- **Inputs per site** (`inputs.py`): battery params from `asset` (capacity/max charge/max discharge existed since V1; **`roundtrip_efficiency_pct`** added by api migration **`V20260701020000`**, dev batteries seeded at 92%), day-ahead prices from `day_ahead_prices` (PT60M rows are expanded to quarter hours; horizon truncates to priced coverage, < 4h skips the site), load/PV forecasts from the `forecast` hypertable - **reading ONLY the ACTIVE model's rows** (`VOLTPILOT_ACTIVE_LOAD_MODEL`/`VOLTPILOT_ACTIVE_PV_MODEL`, defaults = the baselines; see "Shadow-mode forecasting") and **falling back to the persistence baseline over the last 3 days of telemetry when no stored run covers the horizon**, REUSING `voltpilot_forecast` (`fallback.py`; sibling path dep `pip install -e ../forecast`, the Docker build context is therefore the REPO ROOT), latest `soc_pct` + observed `grid_limit_kw` from telemetry.
- **MILP** (`solver.py`): minimize `sum(price * grid_kw * dt)` with grid = load - pv + charge - discharge; constraints: SoC dynamics with sqrt-split round-trip efficiency, SoC bounds (5-95% platform default), charge/discharge power caps, **§14a `grid_limit_kw` as a hard cap on net import AND export**, terminal `soc_end >= soc_start` (no savings by dumping the battery). **Binaries exclude simultaneous charge+discharge** - deliberately not an efficiency argument, because at NEGATIVE prices (normal in DE-LU) an LP profitably burns energy through the round trip. Import and export are priced symmetrically at spot (Direktvermarktung MVP assumption). An infeasible §14a cap degrades to a plan without the grid constraint (edge guards + the grid operator enforce it physically anyway).
- **Savings headline**: projected EUR vs. the no-battery baseline (same load/PV, battery idle), per slot in the DB, summed for the portal ("Heute geplant: X,XX € gespart ggü. ohne Speicher"). Zero on a flat curve by construction.
- **Persistence (ML groundwork)**: every run upserts its full plan into the **`schedule` hypertable** (PK `(site_id, generated_at, time)`; battery/grid power, SoC trajectory, the forecast inputs used, price, cost vs. baseline cost). Tenant-scoped via RLS exactly like telemetry/weather; the optimizer writes as the trusted backend role and stamps `tenant_id` (weather-collector pattern). Plan-vs-actual is a later join against `telemetry`.
- **Publish**: retained QoS1 to `ems/{t}/{s}/{d}/schedule` per the **frozen** `docs/contracts/mqtt-schedule.schema.json` (see Contracts) for the site's battery `asset.device_id`; sites with an unclaimed battery are persisted but not published. Republish cadence (15 min) sits well inside the edge's 20-min staleness window, so the Default-Watchdog only engages on real outages.
- **API + portal**: `GET /api/v1/sites/{siteId}/schedule` (SiteController -> RLS-scoped `ScheduleRepository`, latest run + `savingsEur`; foreign site 404, no plan yet = empty well-formed plan) feeds the portal's **"Fahrplan"** section (`ScheduleChart.tsx`: battery bars over the stepped price line on a shared time axis, planned-SoC trajectory, today/tomorrow divider, savings stats).
- **Compose**: own **`optimize` profile** (not `feeds` - it consumes the feeds and publishes MQTT; not `edge` - it is cloud-side): `docker compose --profile feeds --profile optimize up -d --build` (without the feeds every site is skipped until prices land). Prod: the `optimization` image joins the pulled set in `docker-compose.prod.yml`. Env: `POSTGRES_*` (trusted backend role), `MQTT_HOST/PORT` (+ optional `MQTT_USERNAME/PASSWORD`), `OPTIMIZER_INTERVAL_SECONDS` (900), `OPTIMIZER_HORIZON_HOURS` (24).
- **Tests** (offline, no Docker needed): `tests/test_solver.py` (economic behavior on synthetic curves: charge-cheap/discharge-expensive, zero savings on flat, spread-below-losses stays idle, power/SoC/grid-limit compliance, efficiency in the SoC dynamics, no simultaneous charge+discharge at negative prices, infeasible-cap fallback), `tests/test_contract.py` (payload validates against the frozen schema incl. formats), `tests/test_engine.py` (cycle orchestration with fakes), `tests/test_fallback.py` (persistence reuse), `tests/test_active_model.py` (shadow-mode regression: only the active model's forecast rows are consumed; the promotion env flip switches them). The api's `PortalApiTest.scheduleEndpointReturnsLatestPlanTenantScoped` proves the read path + RLS against real TimescaleDB/Keycloak.

## Historie (history/reporting: `services/api` history package + portal "Historie" page)

The customer-facing history view (captain's decisions: **money lens leads**, private customers first, core value **Nachvollziehbarkeit** - the customer can see and verify what the system did and why).
Read-only feature: one migration, one endpoint, one portal page.

- **Telemetry rollups instead of continuous aggregates.** TimescaleDB **hard-refuses caggs on hypertables with row-level security** ("cannot create continuous aggregate on hypertable with row security", verified on 2.17.2), and `telemetry` has FORCE RLS.
  So api migration **`V20260701030000`** builds the same outcome from primitives that respect the RLS spine: plain rollup **hypertables** `telemetry_rollup_15m/1h/1d` (per-bucket energies pv/load/grid-import/grid-export/battery-charge/battery-discharge kWh + SoC min/max/last + `n_samples`), RLS-scoped exactly like telemetry, refreshed by a TimescaleDB **background job** (`add_job`, 15-min interval) running an idempotent upsert cascade (raw -> 15m -> 1h -> 1d) over a 7-day trailing window as the job owner = the Flyway superuser (bypasses RLS to aggregate all tenants).
  The migration backfills all raw history once; data arriving >7 days late needs a manual `CALL refresh_telemetry_rollups(<since>)`.
  Raw `telemetry` stays untouched (no retention - the raw corpus is future ML training data).
  Semantics live in the migration header: energy = avg(power over the bucket's samples) x bucket hours with per-sample import/export split; actual battery power derived from the power balance (`battery_kw = power_kw - load_kw + pv_power_kw`); daily buckets are **Europe/Berlin** days (the v1 platform timezone, `HistoryRange.ZONE`).
- **Endpoint** `GET /api/v1/sites/{siteId}/history?range=day|week|month|year&at=<date>` (SiteController -> `history/HistoryService` -> RLS-scoped `HistoryRepository`; foreign site 404, bad range 400; in `openapi.yaml`).
  Day = live 15-min buckets straight from raw telemetry (never behind the rollup refresh); week/month/year = the rollups, with per-bucket grid cost merged from the 15m-rollup x `day_ahead_prices` join.
  Totals formulas documented on `HistoryTotalsDto`: grid cost = 15-min import energy x matching day-ahead price; battery savings = sum(baseline - cost) over persisted `schedule` slots taking the **latest run per slot** (`DISTINCT ON (time) ... ORDER BY generated_at DESC`, so overlapping MPC runs never double-count; **null** where no plan exists); Autarkiegrad = 1 - import/consumption; Eigenverbrauchsquote = (pv - export)/pv.
  Day range additionally returns the **Tagesprotokoll** (`history/Tagesprotokoll`, pure functions: battery charge/discharge windows above a 0.1 kW noise threshold with energy-weighted avg price and avoided-cost EUR, PV peak, price extremes; plain-German server-formatted texts) and the **plan-vs-actual** trajectory (latest persisted plan value per 15-min slot).
- **Portal page "Historie"** (`pages/HistoriePage.tsx`, nav id `historie`): Tag/Woche/Monat/Jahr segmented tabs (`.vp-seg`) + prev/next/Heute stepper, **money headline first** (Netzbezug EUR + Speicher-Ersparnis EUR as KpiCards, with honest notes when prices/plans are missing), energy Stats below, `HistoryChart.tsx` (day: actual battery bars over the stepped price curve with the plan overlaid dashed - the traceability centerpiece; week/month/year: kWh bars), Tagesprotokoll timeline (`.vp-timeline`), designed empty state for fresh sites.
- **Tests**: `TagesprotokollTest` + `HistoryRangeTest` (pure unit, always run: heuristics on synthetic days, Berlin/DST window arithmetic, totals formulas + null semantics); `PortalApiTest.historyDayComputesTotalsProtocolAndPlanOverlay` + `historyWeekAggregatesFromTheRollupTables` (real TimescaleDB + Keycloak: fixed past-day seed with hand-computed expectations, protocol events, plan overlay, the rollup path incl. `CALL refresh_telemetry_rollups`, RLS 404, bad range 400).

## Shadow-mode forecasting (model registry + Prognosequalität)

The captain-approved ML path with **Nachvollziehbarkeit as the core requirement** (full lifecycle doc: [`docs/forecasting.md`](docs/forecasting.md)).
The decision layer stays the exact MILP; the forecast layer is a measurable, comparable, swappable **model registry**: an ML challenger must PROVABLY beat the baseline on recorded history before it may ever influence a plan - and the evidence is visible in the portal in plain German.

- **Registry + tagging** (`voltpilot_forecast/registry.py`): every forecaster carries a stable model id; every persisted `forecast` row carries it in the `model` column (PK widened to include it). Baselines `load-persistence` (`SeasonalPersistenceLoadForecaster`) and `pv-physical` (`PhysicalPvForecaster`) stay the ACTIVE defaults. Challengers `load-xgb` and `pv-residual-xgb` run in **shadow**: they predict + persist every cycle, nothing downstream consumes them.
- **Active model = env, promotion = a human flip.** `VOLTPILOT_ACTIVE_LOAD_MODEL` / `VOLTPILOT_ACTIVE_PV_MODEL` (defaults = baselines) feed three consumers that must stay in sync: the **optimizer** (`inputs.py` filters its forecast reads on the active model - proven by `tests/test_active_model.py`), the **forecast collector** (logs them) and the **api** (renders the "live" badge). There is NO automatic promotion; the captain flips the env after the evaluation proves a sustained win, and can flip back the same way.
- **The challengers** (`voltpilot_forecast/ml.py`, optional `[ml]` extra = xgboost+numpy via the native Booster API - no sklearn; LightGBM's wheels were no friendlier, both need OpenMP: macOS `brew install libomp`, the Dockerfile installs libgomp1): `load-xgb` = XGBoost on tabular features (`features.py`: Berlin-local slot-of-day/weekday/weekend + German-holiday flag (`holidays.py`, Gauss Easter), leakage-safe lags -1d/-7d, windowed means, outdoor temperature from stored weather); `pv-residual-xgb` = the physical PV model + a learned residual on weather features (prediction = physical + residual, clipped to [0, capacity]). Deterministic seeds.
- **Self-gating (honesty)**: a challenger refuses to train below **21 full telemetry days** (`VOLTPILOT_ML_MIN_DAYS`; a day counts at >= 48 of 96 slots) - below the gate it emits NO predictions and records `status='collecting'` + days_collected/required in `forecast_model_state`, which the portal renders as "Sammelt Daten: Tag X von 21". Nightly retrain (first collector cycle per Berlin day) persists the explainability trail: trained_at, train_rows, top-5 feature importances with plain-German labels.
- **Collector** (`forecast_collect.py`, console script `voltpilot-forecast-collect`, compose `feeds` profile as **`forecast-collector`**, prod service `forecast`): every 15 min per site it loads telemetry + stored weather (latest run per hour - past hours = "the weather that was forecast then"), runs baselines + gated challengers, persists all model-tagged, upserts `forecast_model_state`, and once per Berlin day triggers the evaluation - one container for collect + retrain + evaluate. PV nameplate is estimated from the observed generation peak (+5 %) until plants are modelled.
- **Evaluation** (`evaluation.py` pure math + `evaluate.py` DB glue, `voltpilot-forecast-eval`): per site x model x **Berlin day**, compares each model's per-slot FRESHEST prediction issued at/before the slot (`run_at <= time` - what the optimizer would have consumed) against 15-min telemetry actuals -> `forecast_accuracy` (MAE kW, nMAE % - NULL on all-zero days, bias, **skill = 1 - mae/mae_baseline**, NULL for the baseline itself). Plan economics -> `plan_accuracy` (freshest ex-ante plan cost + no-battery baseline vs realized signed grid cost from telemetry x price, over exactly the comparable slots). All upserts idempotent - re-running a day after late telemetry overwrites.
- **Schema** (api migration **`V20260701040000`**, canonical runtime owner): retrofits/creates `forecast.model` (backfills old rows as the baseline ids, widens the PK) and owns `forecast_model_state`, `forecast_accuracy`, `plan_accuracy` - all three tenant-stamped + RLS-scoped exactly like telemetry (writers = trusted backend role, api reads via the app role). `forecast` itself stays without RLS (backend-only consumers). Service-side mirror migration `services/forecast/migrations/V20260702000000__forecast_model_column.sql`; bootstrap mirrors in `infra/local/timescale/02-forecast.sql` + `infra/prod/timescale/00-collector-tables.sql`.
- **API + portal**: `GET /api/v1/sites/{siteId}/forecast-quality` (SiteController; active models from config, model states, daily error/skill series, plan economics; foreign site 404, fresh site = empty well-formed lists; in `openapi.yaml`) feeds the portal page **"Prognosequalität"** (`pages/PrognosePage.tsx`, nav id `prognose`): live model per Verbrauch/PV with Ø-Abweichung (7 Tage), challenger cards (honest "Sammelt Daten: Tag X von 21" progress vs "In X der letzten Y Bewertungen genauer"), per-kind MAE comparison chart (`ForecastQualityChart.tsx`: active solid blue, challenger dashed orange), top-feature list in plain German, and the shadow-mode explainer ("keinerlei Einfluss ... automatisch passiert das nie").
- **Tests (the assurance)**: forecast - `test_registry.py` (tagging + env resolution + per-model repository isolation), `test_holidays.py`/`test_features.py` (computus; leakage-free lags; every feature has a German label), `test_ml.py` (gating below/at threshold, deterministic seed, **skill sanity: the learner beats persistence on a weekly pattern with skill > 0.5** and the PV residual corrects a systematic bias), `test_evaluation.py` (exact hand-computed MAE/nMAE/skill/plan-economics, DST day bounds, idempotent upserts), `test_collect.py` (full collector cycle over a fake DB + evaluate_day end to end); optimization - `test_active_model.py` (only active-model rows consumed; env flip switches). Api: `PortalApiTest.forecastQualityIsTenantScopedAndMarksTheActiveModel` (real TimescaleDB+Keycloak, RLS 404). CI runs the forecast matrix with `.[dev,ml]` so the challenger tests run in the gate.

## MaStR integration ("Anlage verknüpfen": registry-fed asset master data)

The OPTIONAL site-level onboarding step: the customer enters their **SEE unit number(s)** (PV + optionally storage; storage units are ALSO SEE-numbered) from the BNetzA registration confirmation, the api fetches the public Marktstammdatenregister record, the portal shows it in plain German for CONFIRMATION, and only "Übernehmen" persists the values onto the site's assets - feeding the PV forecast (PlantSpec) and the optimizer's battery params with authoritative values instead of assumptions.
Registry data is a customer-confirmed prefill, NOT ground truth.
Groundwork: the feasibility scout report (access paths, verified field availability, masking rules) and the captain's proven energy-sharing-voltpilot SOAP implementation, which `MastrSoapClient` ports.

- **Dual-source port** (`services/api` `mastr/` package, the DayAheadPriceSource pattern): `PlantRegistryClient` is the anti-corruption interface; `MastrJsonClient` (keyless public web-search JSON backend, exact unit-number Kendo filter) is the DEFAULT so dev + a fresh deployment need no secret; `MastrSoapClient` (official BNetzA webservice) activates when BOTH `MASTR_API_KEY` + `MASTR_MARKTAKTEUR_NUMMER` are set - promotion is pure config. The captain's one-time free registration (MaStR account -> Marktakteur -> Webdienstnutzer) yields the credentials; blank placeholders live in `.env.example`/`.env.prod.example`, never a real key.
- **The SOAP envelope is built by string, deliberately** (ported from the proven reference; live-verified 2026-07-02): generic SOAP libs mishandle the WCF namespace split - the wrapper element needs the `Request` suffix in the `Modelle/Anlage` namespace while `apiKey`/`marktakteurMastrNummer`/`einheitMastrNummer` sit in the `Modelle` namespace, and `SOAPAction` is the BARE method name in quotes. A SEE lookup tries `GetEinheitSolar` then `GetEinheitStromSpeicher` (method map extensible for SEW/SEB/... later). The JSON backend needs two hard guards (it silently ignores misspelled filter columns): `Total == 1` AND the returned `MaStRNummer` must echo the request.
- **Catalog decoding** (`MastrCatalog`): the registry stores orientation/tilt/battery technology as catalog IDS. Azimuth 695..702 -> 0..315° (PlantSpec convention, 180 = Süd); tilt bins 806..810 -> midpoints (12.5/30/50/75/90°); **Ost-West (704) and nachgeführt (703/811) map to NO single value** - degrees stay null (forecaster defaults apply), the label is shown honestly, a German warning explains. Balkonkraftwerke carry no orientation at all -> nulls, no warning ("nicht im Register hinterlegt" in the UI). Location for private operators is masked to PLZ+Ort - shown for the customer's own plausibility check, NEVER written to site coordinates.
- **Endpoints** (`MastrController`, tenant-scoped like all site routes, RLS 404 for foreign sites; in `openapi.yaml`, tag `registry`): `POST /api/v1/sites/{id}/mastr-lookup {einheitNummer}` -> mapped preview, nothing persisted (error bodies carry a customer-facing German `message`: wrong-prefix hints incl. SES/SSE/EEG, not-found, registry-down 502); `POST /api/v1/sites/{id}/mastr-apply {pv?, storage?}` -> upserts the site's `pv`/`battery` asset rows (update-in-place keeps row ids + device links; battery values land in the EXISTING optimizer columns, `roundtrip_efficiency_pct` untouched) + provenance; `GET /api/v1/sites/{id}/assets` -> rows incl. provenance for the drawer.
- **Schema** (api migration **`V20260702010000`** - `...02000000` is taken by services/forecast): asset gains nullable `pv_capacity_kwp`, `module_count`, `azimuth_deg`, `tilt_deg`, `commissioned_on` + registry-NEUTRAL provenance (`registry`, `registry_unit_id`, `registry_fetched_at` - an AT/CH registry is a drop-in later). Existing asset RLS policy + grants (V2) cover the new columns; no infra bootstrap mirror needed (pure ALTER ... ADD COLUMN IF NOT EXISTS layers over any volume). Migration **`V20260703010000`** then adds a **unique index on `asset (site_id, type)`** so the apply is an atomic `INSERT ... ON CONFLICT (site_id, type) DO UPDATE` (`AssetRepository`, wrapped in `@Transactional` on `MastrController.apply`) that can never double-insert on a concurrent re-submit - this formalizes the long-standing "one asset row per (site, type)" invariant, so the deferred **multi-battery-sites** future work must drop/rework this constraint.
- **Forecast wiring**: `forecast_collect.load_sites` LEFT JOINs the site's `pv` asset; a linked site forecasts with `PlantSpec(pv_capacity_kwp, azimuth_deg|180, tilt_deg|30)` instead of the observed-peak estimate (which stays the fallback for unlinked sites). The optimizer needed NO change - applied storage values land in the asset columns `inputs.py` already reads.
- **Portal** (`components/MastrDrawer.tsx` + the "Anlage" section in the `StandortePage` detail drawer): input step (client-side `^SEE\d{12}$` validation with the same friendly SES/SSE/EEG hints) -> confirmation cards (plain German, nullable fields as "nicht im Register hinterlegt", warnings, masked-location note, DL-DE-BY-2.0 attribution) -> Übernehmen -> linked state shows kWp/orientation/storage + MaStR numbers + "zuletzt abgerufen" + a "MaStR verknüpft" badge. The device-claim flow is untouched.
- **Tests**: `MastrSoapClientTest` (exact envelope/SOAPAction shape, fixture parsing, solar->storage fallthrough, fault mapping), `MastrJsonClientTest` (VERBATIM-recorded public-backend fixtures of the two real sample units SEE966831669444/SEE972142227037 in `src/test/resources/mastr/` - no live registry call in CI, provenance in the fixtures README), `MastrCatalogTest` (every catalog id from the report's tables), `MastrNumbersTest`/`MastrServiceTest`, and `MastrApiTest` (Testcontainers TimescaleDB+Keycloak; the REAL `MastrJsonClient` runs against a fixture-serving `MastrHttp` bean via `ObjectProvider` - lookup preview, apply persists + provenance, RLS foreign-site 404 on all three routes). ## Conventions & decisions worth knowing

- **Maven over Gradle** for JVM services: `mvn` is available and the wrapper is self-contained; keeps one build tool across the JVM tier. Each service is an independent Maven project (no shared reactor) to preserve clean service boundaries.
- The committed Maven wrapper `distributionUrl` targets **Maven Central**, not any private mirror, so `./mvnw` works on a clean machine.
- `api` OIDC is toggled off by default (`VOLTPILOT_SECURITY_OIDC_ENABLED`) so unit tests run offline; `timescale-writer` still excludes `DataSourceAutoConfiguration` until the writer is wired.
- One Postgres instance intentionally serves **both** timeseries (hypertables) and master data (architecture section 10).
- **RLS needs a non-superuser connection.** Never point the api's runtime datasource at the `voltpilot` superuser - it would silently bypass RLS. Use `voltpilot_app` (see the auth section). New tenant-owned tables must add an RLS policy in a migration and be granted to `voltpilot_app`.
- Tenant scoping is enforced in the DB, not the queries: repositories carry **no** `tenant_id` predicate. Out-of-tenant rows are invisible, so "not found" is 404, not 403.
