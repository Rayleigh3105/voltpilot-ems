# Portal v3 · M6 — das Anlagen-Modell (#/anlage/{id}/modell, spec docs/portal-v3/M6-komponenten.md; D3 gesperrt; historisc

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 017).

- **Portal v3 · M6 — das Anlagen-Modell (`#/anlage/{id}/modell`, spec `docs/portal-v3/M6-komponenten.md`; D3 gesperrt; historische Basis, der aktuelle Einstieg steht unten bei „Geräte-Erlebnis Slice 1").** Die überladene `pages/EntitaetenSection.tsx` als Kundenfläche ist weg; `plantModel` und `zentraleListe` bleiben die eine Datenbasis für Anlagenbild UND Listen-Zweitsicht. Ein neu gemeldetes Gerät erscheint weiterhin als „Neues Gerät gefunden … jetzt zuordnen" und wird in EINEM Zug zugeordnet (`components/ZuordnenDialog.tsx`). CSS bleibt komponenten-lokal; `index.css` ist unangetastet.
  - **Captain-Korrektur (verbindlich): eine Anlage hat GENAU EIN Edge-Gerät.** Deye-Hybrid und die Fronius sind Geräte DAHINTER, die der Box Messwerte liefern — die Seite darf nie so aussehen, als gäbe es mehrere Boxen. Deshalb rendert `komponenten.edgeBoxLine(devices, reportedDeviceCount)` die Box als Vermittler-Karte, und die Geräte-Leiste hängt sichtbar an ihr (`.vp-am-behind`, eingerückte Schiene). Die Box kommt aus der **schon geladenen** `devices`-Liste (`AnlagenPage` reicht sie durch — KEIN zusätzlicher Request); ohne beanspruchtes Gerät wird nichts erfunden (`null`), mehrere Boxen werden ehrlich gezählt statt zu einem falschen Singular kollabiert.
  - **Live-Werte sind der Kern** (ohne Zahlen bleibt jede Struktur-Seite Doku): jede Komponente trägt ihren Wert von jetzt, jede Rollen-Gruppe ihre Kopfzahl — und die Σ ist **per Konstruktion die Summe der GEZEIGTEN Zeilen** (21,2 + 23,5 + 0,2 = 44,9), damit der Kunde gegen das Cockpit prüfen kann. Eine Komponente ohne Wert wird in `group.note` GEZÄHLT („1 Komponente ohne aktuellen Wert"), nie als 0 gerechnet. Die PV-Aufteilung je Gerät kommt aus dem SELBEN `pvReconcile.reconcileProducerPv`, das der Energiefluss benutzt — keine zweite Wertableitung, und seit `vp-pin-werte-f8` strikt Pin-basiert (siehe den A1-Punkt weiter unten); eine verwaiste Komponente trägt an JEDER Rolle `reading: null`. **Vorzeichen erreichen den Kunden als WORT** (30,0 kW · „Einspeisung"), nie als Minus: die `live.ts`-Konvention schlägt hier bewusst das Mockup, das „− 30,0 kW" zeichnete.
  - **Die PV-ASPEKT-Zeile ist load-bearing:** der v1→v2-Backfill komponiert für die Module AM Wechselrichter keinen eigenen `producer`, der Hybrid trägt sein `pv_power_kw` an der Speicher-Entität. Ohne die Aspekt-Zeile (`id = "{entityId}#pv"`, `aspect: 'pv'`, Label „Solarmodule am …") zeigte eine normale Ein-Wechselrichter-Anlage **gar keine PV**, und eine Mehr-Wechselrichter-Anlage eine zu kleine Σ. Konsequenz für Konsumenten: `PlantComponent.id` ist NICHT mehr überall eine Entitäts-UUID — für Entitäts-Zugriffe immer `c.entityId` nehmen, und Flächen mit Entitäts-Deep-Links (`verlauf.measurementTree`) überspringen `aspect !== 'main'`.
  - **Zustände statt Zähl-Sprache:** `deviceState`/`deviceSummary` sagen „Liefert Daten" + „Misst Netz, Speicher, Haus und eigene PV · steuert den Speicher" statt „verbunden · liefert 5 Messwerte"; die Messwert-Chips wandern in ein „Details"-Aufklappen je Komponente. Ein PROVEN verwaister Pin (`orphanedPin`, PR #271) bekommt KEIN synthetisches Gerät mehr (das widerspräche der eigenen Zeile), sondern den ehrlichen Zustand „nicht mehr mit einem gemeldeten Gerät verbunden" + die beiden Bereinigungs-Hebel direkt daneben (nächster Punkt; das frühere `reconnectOffer` ist ersatzlos entfallen — es fand auf einer voll zugeordneten Anlage nie ein Angebot). Gerät↔Komponente wird über den PIN gematcht (`edgeSourceId` ODER `adoptedEntityId`, PR #272), nie über Reihenfolge oder Namen. Der Umbenennen-Stift steht seit dem Alias-Konzept JEDEM Kunden zur Verfügung (siehe „Eigene Namen für Komponenten“ weiter unten); die frühere `showTechnicalLayer()`-Schranke ist gefallen, weil der Kunden-Zwilling der Label-Route existiert.
  - **Die BEREINIGUNG hängt an der Komponente (vp-bereinigung-ui-k3, Vorfall Pilsting 29.07.).** Der gemeldete Zustand: WR1 verwaist („–"), WR2 am Pin der Quelle „Fronius Anlage", ein Geist-Eintrag am Pin von „Fronius Anlage WR2" — also **jedes gemeldete Gerät verpinnt, nur an die falschen Komponenten**. Damit gab es kein „Neues Gerät gefunden", und weil der ganze Reparaturweg aus PR #271 an genau diesem Dialog hing, war die Bereinigung **überhaupt nicht erreichbar** („Wie kann ich das Gerät was nichts misst löschen, ich bekomme es nicht weg."). Die zwei Hebel sitzen deshalb jetzt an der Komponentenzeile selbst: **„Zuordnung ändern"** (Gerätewähler mit Edge-Namen, aktuellem Wert und — falls belegt — der Komponente, die es hält) und **„Komponente löschen"** (Folgenliste in Kundendeutsch, inkl. der kWp, die das Anlagen-Total verlassen). **Sichtbarkeit:** an einer VERWAISTEN Zeile prominent neben der Warnung („wieder verbinden / löschen"), an einer gesunden ruhig im „Details"-Aufklappen. Ableitung + Copy sind rein in `komponenten.ts` (`componentActions` · `assignChoices` · `currentChoice` · `swapNote` · `deleteConsequences`, unit-getestet gegen genau diese Konstellation); `components/ZuordnungAendern.tsx` rendert nur.
    - **Der TAUSCH läuft serverseitig in EINEM Zug** (`repin` mit `swap: true`, eine Transaktion). Ein clientseitiges „erst lösen, dann setzen" wurde bewusst verworfen: ein Fehler zwischen den zwei Aufrufen ließe BEIDE Komponenten ohne Gerät zurück — genau der halbe Zustand, den die Bereinigung beenden soll. **Die andere Komponente bekommt den bisherigen Pin nur, wenn dieses Gerät noch gemeldet wird**; sonst wird sie gelöst (einen verwaisten Pin weiterzureichen würde den Defekt nur verschieben) — und `swapNote` sagt genau das vorher an.
    - **Gates, spiegelbildlich zum Server (`SiteEntityAdoptController`):** plattform-komponierte Komponenten (`battery-hybrid` / `house-load`) bieten GAR KEINE Aktion, gelöscht werden darf nur, was einen Gerätepin trägt (ein aus den Stammdaten komponierter Netz-Zähler/Haus ist Grundausstattung, kein Fehlgriff), und die PV-Aspekt-Zeile (`aspect !== 'main'`) ist keine eigene Komponente. Ein Knopf, den der Server nur mit 422 beantworten könnte, wird nie gezeigt.
    - **`SiteEntity.capacityKwp`** (additiv auf `GET /sites/{id}/entities`) macht den Löschdialog ehrlich: er NENNT die kWp, die vom Anlagen-Total abgezogen werden, statt vage zu warnen.
  - **Das WÖRTERBUCH ist gesperrt (D3): Gerät / Komponente / Messwert.** Die Wörter **Entität · Messpunkt · Quelle · Mess-Einheit · Kanal** kommen in der Kundensicht NICHT vor (ein Vokabular-Wächter in `komponenten.test.ts` + `AnlagenModellSection.test.tsx` greppt jedes erzeugte Label). Sie leben nur noch in der **Installateur-Ansicht** — die technische `EntitaetenSection` wird als admin-only `<details>`-Panel im selben Route gerendert (M7 gated es hinter der Rolle; nichts wurde gelöscht). Die Kanal→Deutsch-Zuordnung bleibt `src/channels.ts` mit Rohnamen-Fallback.
  - **ALLE Ableitung ist das reine, unit-getestete `src/komponenten.ts` (`komponenten.test.ts`):** `plantModel(entities, topology, localSetup, sources)` → `{headline, devices, components, groups, newlyReported}` (`effects` ist mit der dritten Spalte entfallen). Faktenbasis des heutigen Backends: eine **Komponente = eine v2-Entität** (Rollen-Bucket aus Typ + Topologie-Kategorie; ein Hybrid komponiert MEHRERE Entitäten = Speicher/Netz/Haus); ein **Gerät = eine vom Edge GEMELDETE Kiste** (`localSetup`, NICHT die eine `device`-UUID) — der Gateway-Wechselrichter speist die komponierten Entitäten, eine übernommene Quelle ihre eine. Reuse: `rollen.ts` (`adoptableSources`/`suggestEntityType`) + `topology.ts` (`defaultRole`) — keine zweite Rollen-Ableitung. „—"-Disziplin: fehlender Wert bleibt fehlend, nie eine erfundene 0; eine Komponente ohne Gerät-Link rendert trotzdem.
  - **Navigation:** neuer `AnlagenSub` `modell` (Route additiv, `nav.ts`); der alte `entitaeten`-Sub redirectet über `LEGACY_SUBS` → `modell` (Lesezeichen bleiben; `AnlagenSub` trägt `entitaeten` nicht mehr, `activeAreaKey('modell')` → `anlagen-modell`).
