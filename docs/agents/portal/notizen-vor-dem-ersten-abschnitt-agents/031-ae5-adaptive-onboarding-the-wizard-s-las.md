# AE5 adaptive onboarding: the wizard's last step is now entity- + profile-driven (vp-ae5-onboarding, spec data/vp-ems-rep

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 031).

- **AE5 adaptive onboarding: the wizard's last step is now entity- + profile-driven (`vp-ae5-onboarding`, spec `data/vp-ems-replatform/adaptive-ems-ui-v1-spec.md` §2/§3/§10).** `FLOW_STEPS = ['Anlage', 'Register', 'Gerät', 'Anwendungen']` (the last step's LABEL was „Nutzung" until Stufe 0 of the Anwendungs-Programm renamed it; the component id `NutzungStep` stays) — **Gerät moved AHEAD of that adaptive last step** (the entity bootstrap + usage-profile + auto-start seeding need the Anlage's master data AND its gateway device). The reworked `NutzungStep` (`components/AnlageFlow.tsx`) has three optional/skippable parts: **Ihre Geräte** (entities), **Nutzungsprofil** (AE7), **Umgang mit dem Speicher** (Speicherschonung, unchanged). It CONSUMES AE7/AE1/E1b — it does not rebuild them.
  - **Admin path = full adaptive** (the pilot/V1-Beweis is admin-onboarded via the tenant switcher): on entering the step it best-effort runs the v2 **bootstrap** (`entitiesApi.bootstrap` → composes battery-hybrid/producer/grid-meter from master data + pushes the registry), lets the admin add consumer entities (Wallbox/Heizstab/generisch via `entitiesApi.create`, `creatableConsumerTypes` filters the catalog), and on finish seeds the profile's **auto-start** flow (`entitiesApi.autoStart` → `POST .../flows/auto-start`, idempotent). Then the existing AE2/AE3/AE4 pages render the adaptive view since a topology + profile now exist. **Customer path stays v1-safe**: the admin-only ops (bootstrap/create/autoStart) are gated on `isPlatformAdmin()`; a customer only READS the entities + derived profile and can set the override — a self-reg site with no v2 entities falls back to the v1 telemetry view (`useAdaptiveLive` gate), byte-identical.
  - **Backend endpoints (do NOT rebuild):** profile is `GET/PUT /api/v1/sites/{id}/profile` (customer+admin, body `{override}`, null clears → auto-derive; `api.setUsageProfileOverride`). Bootstrap + auto-start are **admin-only** (`/api/v1/admin/sites/{id}/v2-entities/bootstrap`, `/api/v1/admin/sites/{id}/flows/auto-start`) reached through the shell's `X-Tenant-Id` switcher (plain `request`, like `optimizerApi`/`entitiesApi`).
  - **Pure logic in `src/adaptiveOnboarding.ts` (unit-tested `adaptiveOnboarding.test.ts`):** `PROFILE_OPTIONS` (auto/arbitrage/peak/private cards, German outcome copy, no internals), `initialProfileChoice`/`profileChoiceChanged`/`overrideForChoice` (write only on a real change; the profile override radios reuse `.vp-schonung` card CSS), `autoStartSummary` (finish-screen line), `creatableConsumerTypes`, `entityGroupLabel`/`entitiesRecognisedSummary`. Load-bearing: a `choiceTouched` ref stops the async profile load from clobbering a user's picked profile. New CSS block "AE5 adaptive onboarding" (`.vp-onb-block`/`.vp-onb-entities`/`.vp-onb-entity-role`/`.vp-onb-add`/`.vp-visually-hidden`), verified in-browser at a 343px card width, zero horizontal overflow. The former Lastspitzen-intent block in the wizard was DROPPED — picking the "peak" profile is now the wizard's expression of peak-shaving (Leistungspreis is still configured later on the Optimizer page).
