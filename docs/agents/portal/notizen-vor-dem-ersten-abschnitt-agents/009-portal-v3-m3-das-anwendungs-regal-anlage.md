# Portal v3 · M3 — das Anwendungs-Regal (#/anlage/{id}/profile, spec docs/portal-v3/M3-profile.md).

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 009).

- **Portal v3 · M3 — das Anwendungs-Regal (`#/anlage/{id}/profile`, spec `docs/portal-v3/M3-profile.md`).** ⚠ **Das Kundenwort ist seit dem 24.08.2026 „Anwendung"** (Captain-Vokabular, Stufe 0 des Anwendungs-Programms — Konzept `data/vp-portal-zielbild-anwendungen`): „Modus"/„Modus-Profil"/„Modi" stehen in KEINEM Kundentext mehr, und `copy.test.ts` wacht darüber. **Die Code-Ids bleiben unangetastet** — `ModeKind`, `ModusContainer`, `profiles.ts`, die Route `/profiles`, die Spalte `profile`, die `vp-modus-*`-Klassen; sie umzubenennen wäre ein API-/Schema-Wechsel, den Stufe 0 ausdrücklich nicht macht. Die EINE dokumentierte Ausnahme des Wächters ist die BETRIEBSART EINES GERÄTS („auf Modus „eco““) — fachlich etwas anderes als eine Anwendung der Anlage. Der Funktionsumfang der Anlage steht als Regal mit Schaltern da — auf JEDER Anlage, auch einer v1-Anlage. **Jedes Profil ist ein direkter Kundenschalter** (Owner-Entscheidung): nur `an`/`aus`, **kein „Angefragt", keine Anfragewand** (`profiles.test.ts` verbietet diese Copy). Fehlt eine Voraussetzung, kippt der Schalter trotzdem, die Karte nennt konkret was fehlt, und der Teil, der nicht laufen kann, läuft nicht — nie ein Schein-Erfolg.
  - **ALLE Ableitung ist das reine, unit-getestete `src/profiles.ts` (`profiles.test.ts`)** — die COPY (Nutzen-Satz, Freischaltungs-Chips) kommt seit Stufe 1 aus dem EINEN Anwendungs-Katalog (siehe den eigenen Punkt darunter): `benefitLine`/`unlockChips`/`requirementChips`/`blockedReason` (Server-Satz gewinnt, sonst ein ebenso ehrlicher lokaler Satz)/`originLine`, `profileStatesFrom` und **`applyProfileStates`** — das **Overlay**: `aus` entfernt eine abgeleitete Anwendung, `an` erfindet nie eine, Regeln bleiben unberührt, und **ohne Zustände ist das Ergebnis byte-gleich zu vor M3** (in `surface.test.ts` + `migration.test.ts` festgenagelt). ⚠ Das **RENDERNDE** Regal ist `steuerungArea.profileRows`; die frühere Kartensicht `profileShelf()` hatte ausser ihrem eigenen Test nie einen Aufrufer und ist in Stufe 0 des Anwendungs-Programms ERSATZLOS entfallen (ihre M3-Zusage „ohne Server-Antwort leer, nie erfunden" prüft `migration.test.ts` seither an `profileRows`).
  - **`surface.ts` konsumiert es:** `AnlageSurfaceInput.profileStates` (optional) wird nach `activeModes` angewandt — die Ableitung selbst ändert sich NICHT. `useAnlageSurface` holt `api.siteProfiles(siteId)` **fail-soft** dazu und gibt die Antwort zusätzlich als `profiles` heraus.
  - **Der Schalter schreibt NUR den Willen** (`api.setSiteProfile`); der Server schaltet daraufhin genau die Bausteine dieses Profils frei und sät den Start-Flow. **Nie ein clientseitiges „tu so, als wäre es frei"** — das Gate prüft weiterhin selbst (Backend-Details in der Root-AGENTS.md „Anwendungen (im Code: Modus-Profile)"). Zusätzlich in `api.ts`: `siteProfiles`/`setSiteProfile`/`autoStart` (Kunden-Route).
  - **Navigation:** neuer `AnlagenSub` `profile` (Route additiv, `nav.ts`) und ein FOOT-Eintrag für das Regal in `ebenenNav.ts` — die M1-Basisgruppe bleibt die fünf FESTEN Anlagen-Bereiche, das Regal ist eine anlagenweite Verwaltungsfläche und auf jeder Anlage erreichbar (der Mehr-Sheet trägt es mit). Neues Design-System-Icon `sliders` (in `Icon.jsx` + `.d.ts`).
  - **Render-only:** `pages/ProfileSection.tsx` (Karten mit `role="switch"`, „Schaltet frei"-/Voraussetzungs-Chips, Sperrgrund, Herkunftszeile, „Weitere Profile"-Fold) + der REUSE des Ko-Optimierungs-Streifens (`CoOptimizationStrip` + `steuerungArea.socReservationStack`). CSS ist das komponenten-lokale `components/Profile.css` (index.css unangetastet); der Schalter ist 52×30 sichtbar mit einer **≥44 px Trefferfläche über `::before`**. In Chrome bei **375 / 768 / 1440** gemessen: 0 px horizontaler Überlauf, Raster 1/2/3-spaltig.
