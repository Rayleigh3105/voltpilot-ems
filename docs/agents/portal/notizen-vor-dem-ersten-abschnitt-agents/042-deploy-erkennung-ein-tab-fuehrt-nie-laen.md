# Deploy-Erkennung: ein Tab führt nie länger als einen Augenblick eine andere Fassung aus als die ausgelieferte (src/deplo

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 042).

- **Deploy-Erkennung: ein Tab führt nie länger als einen Augenblick eine andere Fassung aus als die ausgelieferte (`src/deployWatch.ts` `useDeployWatch`, eingehängt in `UnifiedPortal`; Scout vp-stale-view-w2, verschärft nach der DRITTEN „alte Ansicht"-Eskalation am 06.08.2026).** Vorher gab es KEINEN Mechanismus, der einer offenen SPA-Sitzung einen Deploy mitteilt — ein tagelang offener (angehefteter/wiederhergestellter) Tab lief mit der UI seines Boot-Stands weiter, denn die APIs sind additiv und die alte App funktioniert klaglos. Der Anker ist das **Entry-Bundle**: `/` wird mit `cache: 'no-store'` geholt (**am Browser-Cache VORBEI — das ist die tragende Hälfte**, sonst beantwortet der Cache die Frage „was liefert der Server JETZT" mit sich selbst) und der `/assets/index-<hash>.js`-Pfad gegen den des laufenden Dokuments verglichen — kein Versions-Endpunkt, nichts zu pflegen, und weil geprüft wird, was der Server WIRKLICH liefert, fängt es JEDE stale Schicht ab, ohne sie kennen zu müssen.
  - **⚠ Die Auslöser sind der Fix, nicht die Prüfung.** Die 04.08.-Fassung hatte zwei strukturelle Löcher, beide im echten Chrome nachgestellt (Wegwerf-Harness: Node-Server mit der PROD-Cache-Politik + die ECHTEN Module über esbuild gebündelt, zwei Bündel „ALTE/NEUE ANSICHT"): (1) **der Rückkehr-Pfad konnte gar nicht neu laden** — der stille Reload hing an `document.visibilityState === 'hidden'`, der einzige Auslöser beim Zurückkommen ist aber `visibilitychange → sichtbar`, dort ist der Zustand per Definition `visible`; der Zweig war vom Rückkehr-Auslöser aus UNERREICHBAR, und Hintergrund-Takte drosseln/frieren Browser ein, also lief er im Feld praktisch nie. Gemessen (echte Vorgaben, bfcache-Rückkehr über einen Deploy): alte Ansicht, **nicht einmal ein Hinweis**. (2) **Der Boot galt als Prüfung** (`lastCheck = Date.now()`), was nur stimmt, wenn das laufende Dokument WIRKLICH das ausgelieferte ist — ein Client mit heuristisch gecachter `index.html` (Auslieferung VOR dem 30.07.-Fix), hinter einer Zwischenschicht oder mit wiederhergestelltem Tab lief damit eine halbe Stunde ungeprüft, und eine Portal-Sitzung ist kürzer. Gemessen: FRISCHER Boot (`pageshow persisted=false`), alte Ansicht, während der Server längst das neue Bündel liefert.
  - **Automatisch neu geladen wird nach AUSLÖSER, nicht nach Sichtbarkeit:** **Boot** · **Rückkehr nach echter Abwesenheit** (>= `RESUME_CHECK_AFTER_MS`, 60 s — ein kurzer Blick woandershin löst nichts aus) · **bfcache-Rückkehr** (`pageshow` mit `persisted`) · **verdeckter Tab**. Der laufende Takt eines SICHTBAREN Tabs (`DEPLOY_POLL_MS` 5 min, frühestens alle `DEPLOY_CHECK_MIN_INTERVAL_MS` = 30 min) zeigt weiter NUR den `.vp-update-toast` — wer gerade liest, bekommt die Seite nicht unter den Augen weggezogen. Die Regel in einem Satz: **beim ANKOMMEN übernehmen, beim LESEN fragen.**
  - **Die ehrliche Ausnahme: `hasUnsavedInput()`** — über einer offenen Aufgabenfläche (`.vp-modal` / `[aria-modal="true"]` / `dialog[open]`), mit dem Fokus in einem Eingabefeld oder innerhalb `INPUT_GRACE_MS` (5 min) nach einer echten Eingabe wird NIE automatisch neu geladen; dort bleibt der Hinweis der Weg. **⚠ Bewusst NICHT über einen `value`/`defaultValue`-Vergleich der Felder:** React hält bei einem KONTROLLIERTEN Feld `defaultValue` mit `value` in Deckung, ein getipptes Feld sähe dort unverändert aus und ein vorbelegtes umgekehrt verändert — die Erkennung wäre in BEIDE Richtungen falsch. `role="dialog"` allein blockiert absichtlich nicht (Mehr-Blatt, Hilfe-Panel, Fahrplan-Erklärung sind reine Anzeigeflächen).
  - **Schleifen-Schutz unverändert und im Browser nachgemessen:** je Ziel-Bundle höchstens EIN automatischer Reload (sessionStorage `vp.deployWatch.autoReloadedFor`). Gegen einen Server, der bei JEDEM Abruf einen anderen Stand liefert, blieb es bei genau einer `reload`-Navigation über 42 s; danach übernimmt der Hinweis. Fehlschläge sind STUMM (Netz, non-2xx, HTML ohne Bundle-Referenz), und im Dev-Server (Dokument lädt `/src/main.tsx`, kein Entry-Bundle) deaktiviert sich die Prüfung selbst, ohne einen einzigen Abruf. Unit-getestet in `deployWatch.test.ts` (25).
  - **Nachgemessen gegen prod (06.08.2026): die AUSLIEFERUNG ist sauber** — `/` `cache-control: no-cache` + `cf-cache-status: DYNAMIC`, gehashte Bündel `immutable`, ein verschwundenes Bündel ein hartes 404 mit `no-cache` + allen Sicherheits-Headern. Cloudflares `speculation-rules` ist **Prefetch** (`cf-speed-brain`, `eagerness: conservative`), KEIN Prerender — es führt kein JS aus und kann daher keinen alten Stand rendern. Wer das Symptom erneut untersucht: die Serverkette zuerst messen, dann den Lebenszyklus — sie war schon zweimal unschuldig.
