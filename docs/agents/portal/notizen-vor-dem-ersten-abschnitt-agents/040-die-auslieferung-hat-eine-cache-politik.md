# Die Auslieferung hat eine Cache-Politik, und sie steht in EINEM add_header-Block (Captain-Meldung 30.07.2026

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 040).

- **Die Auslieferung hat eine Cache-Politik, und sie steht in EINEM `add_header`-Block (Captain-Meldung 30.07.2026: „nach dem Deploy zeigt ein Reload das Layout einer früheren Version").** `location /` setzte GAR KEIN `Cache-Control`, also nur `Last-Modified`/`ETag` — und der Browser wendet dann HEURISTISCHES Caching an: er benutzt eine alte `index.html` OHNE Rückfrage weiter, und die verweist auf die alten gehashten Bündel, die ebenfalls noch im Cache liegen. Ergebnis war die komplette alte Anwendung über einem längst neuen Server. Die Politik: **`/assets/*` (Vites content-gehashte Dateien) `public, max-age=31536000, immutable`**, **alles andere `no-cache`** — also `index.html` samt SPA-Fallback UND die bewusst UNgehashten Extras `favicon.svg`/`silent-check-sso.html`/`.js` (die behalten ihren Namen über Releases hinweg, `immutable` würde sie für immer festnageln). Nie `no-store` — das verbietet auch die billige 304-Antwort.
  - **Die Falle, die man beim nächsten Umbau wieder trifft: `add_header` wird NICHT vererbt, sobald ein inneres `location` eigene `add_header`-Direktiven hat.** Ein naives `location /assets/ { add_header Cache-Control ... }` liefert die Bündel deshalb OHNE CSP/X-Frame-Options/X-Content-Type-Options/Referrer-Policy aus (im Container nachgemessen: genau EIN Header bleibt übrig). Deshalb ist die Politik eine `map $uri $vp_cache_control`-VARIABLE, die ein einzelnes `add_header` in DERSELBEN `location /` konsumiert — ein Ort, ein Header-Satz, kein Duplikat, das auseinanderdriften kann. `$uri` ist der Pfad NACH `try_files`, der Fallback wird also als `/index.html` bewertet. Wer hier ein zweites `location` einführt, muss ALLE Sicherheits-Header dort wiederholen.
  - **Wächter: `npm run test:cache`** (`test/cache-smoke.sh`, im deploy.yaml-Frontend-Gate neben `test:csp`) fährt das ECHTE gebaute nginx-Image: `/`, `/index.html` und eine unbekannte SPA-Route → `no-cache`; die aus der ausgelieferten `index.html` GEPARSTEN (nie geratenen) `/assets/*` → `immutable`; die ungehashten Extras → `no-cache`; auf JEDER dieser Antworten müssen die vier Sicherheits-Header stehen (das ist der Wächter für die Falle oben); und `/` mit passendem `If-None-Match` muss wirklich 304 antworten.
  - **Vorgelagerte Kette geprüft:** im Repo gibt es keinen HTML-cachenden Reverse-Proxy (`docker-compose.prod.yml`, `deploy/`, `.forgejo/workflows/`, `docs/deploy.md`; der dokumentierte Caddyfile ist ein reines `reverse_proxy`, NPM ist ein Proxy-Host-Template) und **keinen Service Worker** (kein `serviceWorker`/`workbox`/`registerSW` in `src`/`public`/`index.html`) — beides wäre eine zweite, hartnäckigere Ursache desselben Symptoms. Operator-Notiz dazu in `docs/deploy.md` „Do not let the external proxy cache HTML".
