Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 011).

- **Der EINE Anwendungs-Katalog: `src/anwendungen.ts` + die byte-gleiche Kopie `src/anwendungen/catalog.json` (Anwendungs-Programm Stufe 1; Server-Seite + die vier Klassen in der Root-`AGENTS.md`).** Derselbe Katalog lag an ACHT Stellen in zwei Sprachen (Konzept `data/vp-portal-zielbild-anwendungen` §2.2) — im Portal waren das `surface.ts MODE_LABELS`, `profiles.ts COPY`, `manifestFor(...).settings` und `modeSettings.ts SETTING_DEFS.claimedBy`. Alle vier lesen jetzt aus der Katalog-Datei; die Hand-Tabellen sind ERSATZLOS weg (grep-Beweis im PR).
  - **⚠ Die Kopie ist BYTE-gleich mit der Server-Ressource gepinnt** (`anwendungen.sync.test.ts` + der Java-Zwilling) — **beide zusammen ändern**, das `flows/catalog.sync.test.ts`-Muster.
  - **⚠ Die Aktivierungs-LOGIK bleibt Code** und ist gegen den Java-Zwilling `profile/AnwendungDerivation` über `docs/contracts/v2/anwendung-vectors.json` gepinnt. `anwendungen.test.ts` fährt dabei BEIDE Portal-Zwillinge über dieselben Vektoren — `derivedAnwendungen` UND, für die vier Modus-Arten, `surface.ts activeModes` — und vergleicht sie Fall für Fall; genau die zwei Zwillinge, die §2.2 als ungepinnt gefunden hat. Mutationsgeprüft: eine gedrehte Regel lässt 8-9 Fälle fallen.
  - **⚠ EINE bewusste Copy-Vereinheitlichung: der Markt-Modus heißt überall „Marktoptimierung".** Der Server (und damit die Regal-Karte) sagte das schon immer, nur `MODE_LABELS` sagte „Marktvermarktung" — zwei Namen für dieselbe Sache direkt nebeneinander (Nav-Gruppe gegen Karte) waren die Doppeldeutigkeit, gegen die der Katalog gebaut ist.
  - **⚠ `MODE_RANK` wird NICHT katalog-gespeist.** Der Katalog-`rang` ordnet das REGAL, `MODE_RANK` die aktiven Modi der Projektion — sie zu verschmelzen änderte die Cockpit-/Nav-Reihenfolge einer Bestandsanlage sichtbar. `migration.test.ts` nagelt beide Mengen fest.
  - **Stufe 1 ändert die FLÄCHE nicht.** Die vier neuen Regal-Einträge (`monitoring`/`speicher-fahrplan` als Basis, `ueberschuss`/`verbraucher` als Regel-Anwendungen) sind KEINE `ModeKind`s: sie erscheinen im Regal (die Server-Antwort trägt sie), erzeugen aber keinen Cockpit-Block, keine Nav-Gruppe und kein Manifest. Ihre `bausteine` im Katalog DOKUMENTIEREN, was die Fläche schon heute aus `baseSurface` bzw. den Regeln rendert — Stufe 3 löst daraus das Layout auf.
  - **Ein Konsistenz-Test verhindert einen Eintrag ohne Fläche** (`anwendungen.test.ts`): je Modus-Art müssen `bausteine.cockpit`/`ansichten`/`geldstrom` und `einstellungen` exakt dem entsprechen, was `manifestFor` beisteuert, jede Baustein-Id ein bekanntes Vokabular treffen, und `claimedBy` die Umkehrung von `einstellungen` sein.
  - **⚠ Der Copy-Wächter liest den Katalog MIT** (`copy.test.ts`): er ist ein KUNDEN-Textwohnort, liegt aber als JSON und würde vom Datei-Walker sonst nicht erfasst — die `_comment`-Blöcke sind ausdrücklich ausgenommen (Entwickler-Doku). Mutationsgeprüft.
  - **Ehrlichkeit der Lese-Schicht:** eine unbekannte Id (neuerer Server, ältere Kopie) liefert `null`/die Id selbst/`[]`, gilt als SCHALTBAR (der Server ist die Wahrheit und lehnt sonst ehrlich ab) und ist weder Basis noch Regel — nie geraten.
