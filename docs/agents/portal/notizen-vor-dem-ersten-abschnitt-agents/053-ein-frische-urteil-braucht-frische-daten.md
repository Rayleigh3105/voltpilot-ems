# Ein FRISCHE-Urteil braucht frische Daten — nie eine Uhr über einem stehenden Schnappschuss (src/liveness.ts, Captain-Mel

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 053).

- **Ein FRISCHE-Urteil braucht frische Daten — nie eine Uhr über einem stehenden Schnappschuss (`src/liveness.ts`, Captain-Meldung 30.07.: „ziemlich oft Warnung Gerät meldet sich nicht, obwohl ich gerade Daten bekomme … F5 und alles ist wieder in Ordnung").** Die Geräteliste (`api.listDevices`) wurde genau EINMAL je Seitenaufruf geholt, `lastSeenAt` blieb damit stehen — und ein 30-s-Ticker verglich sie gegen eine weiterlaufende Wanduhr. Nach fünf Minuten offenem Portal überschritt jedes Gerät zwangsläufig `ONLINE_WINDOW_MS`, das Kopfzeilen-Abzeichen kippte auf „Warnung · Gerät: meldet sich nicht" und konnte sich NIE erholen (nichts erneuerte den Bezug), während das Cockpit darunter — das `/overview` in seinem eigenen Takt neu holt — ruhig grün blieb. **Die Regel, die das strukturell ausschließt: Lebendigkeit wird gegen die ANTWORTZEIT des Servers gemessen** (`livenessReference(fetchedAt, now)` → `deviceHealthForSite`), also aktualisiert jede frische Antwort Zustand UND Bezugszeit gemeinsam, und ein FEHLGESCHLAGENER Poll ändert schlicht nichts — das ist stärker als eine N-Fehlversuche-Schwelle, weil es keinen Zähler gibt, der falsch stehen könnte. Ein gedrosselter Hintergrund-Tab lässt den Zustand EINFRIEREN statt zu verfallen (auch eine echte Warnung friert ein, sie verschwindet nicht heimlich); die Warnung erscheint nur noch, wenn der SERVER das Gerät wirklich als still meldet. Bewusst NICHT gebaut: eine Obergrenze, ab der ein alter Schnappschuss doch als „still" gilt — ein Portal, das den Server nicht erreicht, weiß über das GERÄT nichts Neues.
  - **Das Gegenstück ist `src/useFreshnessPoll.ts`** (Intervall + **`visibilitychange` → sofort nachholen**, statt aufs nächste Intervall zu warten; `poll` liegt in einer Ref, damit ein neu erzeugter Callback den Takt nicht bei jedem Render zurücksetzt). `App.tsx` frischt damit `devices` + `devicesAt` alle `LIVENESS_POLL_MS` still auf — Fehlschläge sind stumm (das rote Banner gehört einem vom Kunden ausgelösten Laden), und der Tenant wird beim Absenden festgehalten, damit eine späte Antwort nach einem Mandantenwechsel nicht die falschen Geräte einsetzt. **Jede neue Fläche, die `deviceLiveStatus`/`edgeBoxLine` o. ä. über nicht selbst gepollten Daten auswertet, muss die Bezugszeit mitbekommen** (`AnlagenPage`/`AnlagenModellSection` tragen sie als `devicesFetchedAt` durch), sonst kehrt genau dieser Fehler zurück.
  - **„Alles in Ordnung" ist grün, aus den bestehenden Tokens:** `--vp-flow-batt` (satt, Punkt + Rahmen), `--vp-flow-batt-soft` (Fläche) und das neu als Token geführte `--vp-flow-batt-ink` (#166534, 7,1:1 auf Weiß — der Ton stand vorher schon als Literal in `.vp-role-pill`). Warn-/Hinweis-Zustände behalten ihre Farben. Der Wächter `src/shell/healthGreen.test.ts` liest die Stylesheets und failt auf jedem NEUEN Grünton im Shell-CSS.
