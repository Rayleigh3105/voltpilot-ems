# The "Anlage anlegen" flow is REGISTER-FIRST (captain 2026-07-09, vp-anlage-anlegen-flow).

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 032).

- **The "Anlage anlegen" flow is REGISTER-FIRST (captain 2026-07-09, `vp-anlage-anlegen-flow`).** `FLOW_STEPS = ['Anlage', 'Register', 'Gerät']` (was `['Anlage','Gerät','Speicher']`): step 2 no longer asks battery specs by hand - the customer enters their **MaStR number(s)** and VoltPilot pulls PV + Speicher from the Marktstammdatenregister via the existing `mastr-lookup`/`mastr-apply` (site-scoped, so the site shell is created in step 1 BEFORE the lookup runs). The battery has its OWN SEE number; when the register cross-links them (`MastrPreview.linkedUnitNumber`) the second field is **auto-adopted after the PV lookup** (badge "verknüpft", captain decision 2) so the customer usually types only one number. Manual hand-entry is the always-reachable FALLBACK ("Keine Nummer? Daten manuell eingeben" → the old battery form; Balkonkraftwerke / unregistered / unknown number) - NOT removed, just no longer default. Preview shows the mapped specs + a `plz/ort` plausibility line ("89551 Königsbronn - stimmt das?"). Fertig summary lists PV/Speicher/Gerät/"Quelle: Marktstammdaten". Same component serves mobile (one step per screen) AND desktop (centered dialog, wider preview) - it is responsive by its host container (`.vp-onboarding` 560px card / `Modal`), verified in-browser 375/768/1440, zero horizontal overflow.
  - **Pure logic in `src/anlageFlow.ts` (unit-tested `anlageFlow.test.ts`):** `initialFlowStep(hasSite)` now resumes at the **Register** step (2, skippable) not Gerät; `validateSeeNummer`/`normalizeSeeNummer` (MOVED here from `MastrDrawer.tsx`, which now re-exports them); `pickStorageNumber(pvPreview, explicit)` (explicit wins, else adopt `linkedUnitNumber`); `buildMastrApply(previews)` (maps PV/storage onto the apply payload); `mastrPvSummary`/`mastrStorageSummary`/`mastrLocationLabel` (Fertig one-liners, `fmtNum` → NBSP before units, so tests compare against `` `9,80${NBSP}kWp · Süd 30°` ``). Component in `components/AnlageFlow.tsx` (`AnlageFlow.test.tsx` mocks `leaflet` + `api.mastrLookup`/`mastrApply`). `MastrDrawer.tsx` stays as the "Anlage verknüpfen" UPDATE UI on an EXISTING Anlage (Technik section); only new Anlagen use the register-first flow.
  - **"Gleicher Standort wie …" reuse chips (captain decision 5):** the Anlage step takes `existingSites` (via `AnlageAnlegenDrawer`'s new `existingSites` prop, threaded from App.tsx/Uebersicht/Anlagen call sites) and renders `.vp-chip` buttons for each already-placed Anlage; clicking one prefills lat/lon + bidding zone. Multiple Anlagen may share a location (no separate "Standort" entity - data model unchanged: one Site = one PV + one battery via `uq_asset_site_type`).
  - **Two design-system icons added for this flow:** `link` (chain, the verknüpft hint) + `search` (the "Im Register suchen" button) in `designsystem/components/core/Icon.jsx` + `.d.ts`. New CSS block "Register-first Anlage anlegen flow" in `index.css` (`.vp-mastr-card`/`.vp-kv-list`/`.vp-summary-list`/`.vp-chip`/`.vp-field-row`/`.vp-hint-row`) - all `min-width: 0`, right-aligned `dd` with `overflow-wrap: anywhere` so long register values never overflow at 375.
  - **Tradeoff noted:** register location prefill is offered as the plausibility LINE only (no auto-geocode-into-updateSite) - the customer already set the pin on the step-1 map, so the register PLZ/Ort is shown to confirm, never silently written (decision 3, "never a silent overwrite"). The desktop preview is the same two-phase enter→preview as mobile (not a literal side-by-side), which keeps ONE robust responsive implementation.
