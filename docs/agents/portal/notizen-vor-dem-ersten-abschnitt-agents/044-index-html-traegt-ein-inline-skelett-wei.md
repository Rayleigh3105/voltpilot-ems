# index.html traegt ein INLINE-Skelett, weil Chrome sonst das ALTE Bild haelt (Captain-Meldung 31.07.2026

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 044).

- **`index.html` traegt ein INLINE-Skelett, weil Chrome sonst das ALTE Bild haelt (Captain-Meldung 31.07.2026: „nach jedem Deploy 2-3 s die eingefrorene alte Ansicht"; das ist NICHT die Cache-Politik eine Zeile hoeher).** Chromes **Paint-Holding** zeigt beim Reload das letzte Bild der alten Seite weiter, bis das NEUE Dokument erstmals etwas Inhaltliches zeichnet — und die SPA zeichnete erst nach JS-Download (662 kB gzip) + React-Mount + Keycloak-Pruefung. `#vp-boot-skeleton` in `index.html` nimmt `<BootSplash>`/`<AuthScreen>` optisch vorweg (3-px-Markenstreifen oben, Wortmarke als TEXTfassung links, Spinner rechts; ab 900 px zweispaltig wie `.vp-auth` — **die Umschaltbreite ist dieselbe, wer eine aendert, aendert beide**, sonst blitzt beim Start die falsche Aufteilung) und beendet das Halten, sobald das Stylesheet da ist.
  - **Vier Randbedingungen, alle load-bearing:** (1) **nur inline** — kein Bild, keine Schriftdatei, kein zweiter Request, sonst braeuchte `index.html` einen Hash und verloere seine `no-cache`-Auslieferung; die Wortmarke ist inline-SVG + Systemschrift-Stack. (2) **kein inline `<script>`** — die Produktions-CSP ist `script-src 'self'` OHNE `'unsafe-inline'` (der Login-Ausfall vom 17.07.); inline `<style>` ist erlaubt (`style-src … 'unsafe-inline'`), deshalb ist die Entfernung React-seitig geloest. (3) **Farben sind aus `designsystem/tokens/colors.css` HART einkopiert** (`--vp-grad-hero`/`--vp-surface`/`--vp-border`/`--vp-action`) — die Tokens kommen erst mit dem Stylesheet; wer die Marke neu toent, muss hier mitziehen. (4) **`position: fixed`-Overlay ueber `#root`**, kann also nie einen Layout-Sprung ausloesen.
  - **Entfernt wird es GENAU EINMAL, in `BootErrorBoundary.componentDidMount`** (`components/Boot.tsx` `removeBootSkeleton`): die Boundary umschliesst jedes `render()` in `main.tsx` und bleibt ueber alle Boot-Zustaende montiert, `componentDidMount` feuert also am ERSTEN committeten Frame — nach Reacts DOM-Schreiben, aber VOR dem Paint, deshalb ist der Uebergang flackerfrei und gilt auch fuer den Fehlerpfad. Kein `setTimeout`, kein `requestAnimationFrame` — beides waere ein sichtbarer Doppel-Frame.
  - **Die verbleibende Grenze kennen: das Stylesheet in `<head>` ist RENDER-BLOCKING**, das Skelett zeichnet also fruehestens bei CSS-fertig. Gemessen (Wegwerf-Harness auf eigenem Port, gzip wie nginx, echtes `emulate`; VORHER = dieselben Assets ohne Skelett): **ungedrosselt FCP 152 → 80 ms · Fast 4G 1176 → 468 ms · Fast 3G 5170 → 1630 ms**. Beim VORHER klaffen `first-paint` und `first-contentful-paint` weit auseinander (Fast 3G 1620 vs 5170 ms) — genau das Fenster, in dem der Captain das alte Bild sah; NACHHER fallen beide zusammen. **Nachgemessener Hebel, bewusst NICHT gezogen:** das Stylesheet ans Ende von `<body>` zu verschieben druecken Fast 3G weiter auf **624 ms** (= der HTML-Roundtrip selbst), braeuchte aber ein Vite-`transformIndexHtml`-Plugin und riskiert ein FOUC, falls die App je vor ihrem CSS montiert — der Gewinn auf einer normalen Leitung sind ~100 ms, das Risiko dauerhaft.
  - **Waechter:** `src/bootSkeleton.test.ts` (liest `index.html`: Skelett vorhanden, kein externer Verweis, kein inline `<script>` — docker-frei, waehrend `test:csp`/`test:cache` einen Daemon brauchen) + die Uebergabe-Faelle in `components/Boot.test.tsx`. **Vite emittiert hier KEIN `modulepreload`** — es gibt genau einen Entry-Chunk, es gaebe also nichts vorzuladen; das CSS-`<link>` steht bereits im `<head>` und wird beim Parsen entdeckt, ein zusaetzliches `rel="preload"` waere wirkungslos.
