- **M5 Leer-Zustand + Anlege-Kette — an empty Anlage's cockpit IS the setup path (Epic "Projektion" #527, ticket #533; design `data/vp-anlagen-face-k9/report.md` §3 „Neu / leer" + §4, F6 decided).** `AnlageSeite` gained a THIRD render path ahead of M3's stack: **1 Gerät verbinden ✓ → 2 Geräte übernehmen → 3 Steuerung wählen** (`components/AnlageSetup.tsx` + component-local `AnlageSetup.css`, the CockpitBlocks precedent — `index.css` untouched). No placeholder cards, no empty charts: there is nothing to show, so the WAY is shown. Step 1 reuses the unchanged `AddDeviceDrawer`, step 3 only POINTS at M2's toolbox (it is not rebuilt), and the wizard hands over with the shared `SETUP_NEXT_HINT` line on the AE5 finish screens.
  - **The gate is deliberately NARROW — never `!hasEntities` alone.** EVERY current v1 Anlage has no v2 entities; switching on that would replace every existing customer's cockpit with a setup path. The pure, unit-tested `src/setupPath.ts` `setupPathActive({hasEntities, modeCount, statusLoaded, lastSeenAt, hasLiveSample})` therefore also requires that the Anlage has **never delivered measurements** — a running v1 Anlage keeps its cockpit (report §6.2, pinned from both sides in `pages/AnlagenPage.test.tsx`), and its reported sources stay admin-first under „Geräte", which is exactly F6's boundary ("outside the guided path adoption stays admin-first"). `statusLoaded` prevents a flash before the overview row resolves; a null/undefined surface (older backend) always falls back to v1.
  - **Customer adoption is CATALOG-GUARDED, not a free editor (F6).** `adoptionPlan(source)` derives the entity type from the SAME `rollen.ts suggestEntityType` (role + brand) the admin bridge uses, shows it read-only, and asks ONLY what only the customer knows — producer: kWp + MaStR, controllable consumer: Anschlussleistung, grid meter: nothing. **No type picker, no guard input, and a source without a confident suggestion is not adopted at all** (honest hint instead). The backend type catalog is admin-only (`/api/v1/admin/entity-type-catalog`), so the guided path must never depend on it — `TYPE_LABELS` carries the German words, a fetched catalog label merely overrides them.
  - **KNOWN BACKEND GAP (deliberate, frontend-only ticket):** `entitiesApi.adopt` still targets the platform-admin `POST /api/v1/admin/sites/{id}/v2-entities/adopt`. A plain customer token gets 403 and the drawer says so honestly (`ADOPT_FORBIDDEN_MSG`, "VoltPilot kann das für Sie übernehmen"); admins-in-customer-page work today via the `X-Tenant-Id` switcher. Completing F6 needs the customer twin on `SiteEntityController` (the `SiteFlowController`/`SiteTopologyController` RLS-fenced pattern) — the portal then needs one route change in `entitiesApi.adopt` and nothing else.
  - **The post-adopt bridge** (`adoptedBridge`) offers "«Wallbox» übernommen — Regel dafür anlegen?" ONLY for controllable types (never a rule for a meter) and links into Steuerung; while it is showing, the page PINS the setup path (`onStay`) so the ground does not move under the customer mid-chain. Tests: `setupPath.test.ts` (gate + steps + guided adoption exhaustively), `components/AnlageSetup.test.tsx` (the chain incl. the 403 honesty), `pages/AnlagenPage.test.tsx` (the M5 branch + the v1 invariant from both sides).
