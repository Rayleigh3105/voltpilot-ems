# Steuerung Stufe 0 „Entwirrung": das Regal ist die Kapsel „BETRIEBSMODELLE" (Konzept data/vp-steuerung-konzept-b3 §5 Stuf

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 1, Punkt 010).

- **Steuerung Stufe 0 „Entwirrung": das Regal ist die Kapsel „BETRIEBSMODELLE" (Konzept `data/vp-steuerung-konzept-b3` §5 Stufe 0; Server-Seite in der Root-`AGENTS.md`).** Der behobene Befund war ZUSCHNITT, nicht Datenlage: neun Zeilen in EINER Optik — Basis-Anwendungen mit einem Schalter, den der Server mit **400** ablehnt, Regel-Anwendungen mit einem Schalter **ohne jede Wirkung**, und die vier Geschäfts-Anwendungen —, jede mit `contribution` als Untertitel, also auf einer Privat-Anlage **neun Mal „—"**. Keine der vier Kundenfragen (*Was bringt mir das? Was brauche ich? Was passiert beim Einschalten? Läuft es jetzt?*) war beantwortet.
  - **⚠ Das Kundenwort ist seit dem Captain-Entscheid 25.08.2026 „Betriebsmodell"**; „Anwendung" ist KEIN Kundenwort mehr (es bleibt das interne Modell und jede Code-Id). `PROFILE_CAPSULE_TITLE` heißt „Betriebsmodelle", das Intro nennt den Grundmodus („Ohne Betriebsmodell fährt Ihr Speicher den Eigenverbrauchs-Fahrplan …"), und der Leer-Satz behauptet keinen Mangel mehr, sondern benennt genau diesen Grundmodus.
  - **Die Zeile trägt Nutzen-Satz + Voraussetzungs-Chips statt „—"** (`ProfileRow.benefit`/`.requirements` aus `benefitLine`/`requirementChips`, also aus dem EINEN Katalog bzw. der Server-Antwort). **`contribution` ist seither `string | null`** und steht NUR da, wo es eine echte Zahl gibt — ein Gedankenstrich beantwortet keine Frage. CSS: `.vp-profrow-benefit`/`.vp-profrow-reqs`/`.vp-profrow-req[.met]` in `components/Steuerung.css`.
  - **⚠ Das Portal filtert ein ZWEITES Mal** (`profileRows` → `anwendungen.imRegal`): der Server liefert im Feld `profiles` schon nur das Regal, aber ein ÄLTERER Server schickt weiterhin alle neun Zeilen — die Kapsel bleibt trotzdem aufgeräumt. Eine dem Katalog UNBEKANNTE Id (neuerer Server) wird ausgelassen statt ohne Nutzen-Satz gerendert; eine Automation erreicht das Regal strukturell nie.
  - **⚠ `SiteProfiles` hat ZWEI Listen, und das war eine NOTWENDIGKEIT, kein Stil.** `profiles` ist das Regal, `weitere` (optional — ein älteres Backend hat es nicht) trägt die Karten der Basis- und Regel-Anwendungen. Zwei bestehende Flächen LESEN sie, und ein blosses Weglassen wäre dort eine stille Regression gewesen: das Cockpit-Tor **„ist Eigene Auswertung an?"** (`AnlagenPage` `eigenAn`) und das **Willens-Overlay** `profileStatesFrom` — ein gespeichertes `aus` einer Regel-Anwendung ginge sonst verloren und ein abgeschalteter Modus würde stillschweigend wiederbelebt. **Jede Fläche ausserhalb der Steuerung fragt über `profiles.alleProfile(...)`**, nie über `profiles.profiles`. Mutationsgeprüft in `migration.test.ts`.
  - **Der Phantom-Satz ist weg:** die zwei `leer_zustand`-Sätze verwiesen auf eine Seite „Komponenten & Regeln", die es NICHT gibt (die Navigation kennt „Anlagen-Modell" und „Steuerung"; die Regel-Liste wohnt auf derselben Seite eine Kapsel tiefer). Sie nennen jetzt „Regeln" auf dieser Seite. Ein Test in `anwendungen.test.ts` UND `AnwendungKatalogTest` verbietet den Namen katalogweit.
  - **Der Wizard-Schritt heißt „Betrieb"** (`FLOW_STEPS`, war „Anwendungen", davor „Nutzung") und schlägt **GENAU EIN Betriebsmodell** vor — oder ehrlich keins. Das neunzeilige Regal ist dort ERSATZLOS entfallen; zwei Konstanten tragen die Copy (`AnlageFlow.tsx` `KEIN_BETRIEBSMODELL`, `REGELN_SPAETER`).
    - Die Regel ist die reine `anwendungen.betriebsmodellVorschlag(profil, karten)`: **`an` ist das Startmodell eines Profils (höchstens EINES je Profil), `angeboten` sind seine Rückfälle** — vorgeschlagen wird der erste Kandidat, dessen Voraussetzungen ALLE erfüllt sind. Damit ist Konzept §3.9 wörtlich abgebildet: „Gewerbe: Lastspitzenkappung, wenn Leistungspreis hinterlegt, sonst Marktoptimierung, wenn Marktzugang; Privat: keins."
    - **⚠ Ohne `an`-Kandidaten wird NICHTS vorgeschlagen** — auch dann nicht, wenn ein `angeboten`-Modell technisch könnte. Genau das ist „Privat: keins": ein Rückfall ohne Startwahl wäre eine Empfehlung, die niemand getroffen hat. Was NICHT kann, wird GENANNT (`zurueckgestellt`), nie still angehakt; ein Modell mit `blocked_reason_immer` (die atypische Netznutzung) ist nie Kandidat.
    - **⚠ Die Katalog-Daten tragen die Regel:** `marktvermarktung.preset.gewerbe` ist seither `angeboten` statt `an`, damit je Profil höchstens ein `an` steht. `vorauswahl` läuft beidseitig (TS + Java) über das REGAL und liefert deshalb höchstens einen Eintrag.
  - **ERSATZLOS entfallen** (kein Aufrufer mehr, das `roleLabel`-Muster): `anwendungen.regalFuerProfil` und `anwendungen.presetVorschlag` samt ihren Tests.
  - **⚠ Die Zeile ist seit dieser Stufe MEHRZEILIG, deshalb richtet sich `.vp-profrow` an `flex-start` aus:** Statuspunkt, Chevron und Schalter gehören zum TITEL. Mit dem geerbten `align-items: center` standen sie bei vier Zeilen mitten im Fliesstext, als gehörten sie zu ihm (im Browser aufgefallen, nicht im Test). Die Versätze sind aus der Zeilenhöhe der Überschrift gerechnet, nicht geraten; die einzeilige `.vp-autorow` daneben bleibt unverändert mittig.
  - **Beweise:** `anwendungen.test.ts` (Regal = die vier Betriebsmodelle, `regal` folgt der Klasse, Regal ∪ Rest = alles Sichtbare, `imRegal` urteilt über Unbekanntes nie „ja", kein Phantom-Satz, die sechs Fälle der Vorschlags-Regel) · `steuerungArea.test.ts` (Nutzen + Chips, `contribution: null` statt „—", der zweite Filter, Automation erreicht das Regal nie) · `SteuerungSection.test.tsx` (die Kapsel heißt „Betriebsmodelle", nur Betriebsmodelle mit Nutzen + Chip, „Anwendungen" als Überschrift verboten) · `AnlageFlow.test.tsx` (Privat schlägt keins vor, Gewerbe genau eines, der Rückfall, das Genannte, keine „immer an"-Zeile mehr) · `migration.test.ts` (der Stufe-0-Wächter: ausgeblendet ≠ gelöscht, Overlay liest beide Listen, Projektion unberührt). **Im echten Chrome bei 1440 und 375 gemessen:** 0 px horizontaler Überlauf, 0 überstehende Elemente, Schalter 52×30 (Trefferfläche ≥ 44 px über `::before`), die Chips brechen am Telefon um statt zu überlaufen. ⚠ Diese Messung lief gegen eine STATISCHE Fläche mit dem echten CSS, nicht gegen den Live-Stack — der Docker-Daemon lag zum Bauzeitpunkt (Platte voll), also waren api und Keycloak nicht erreichbar. Sie deckt damit genau das neu hinzugekommene Layout-Risiko ab (die umbrechende Chip-Reihe und die mehrzeilige Zeile), nicht den Datenweg; den decken die DOM-Tests.
