# The Fahrplan mini preview derivation is pure src/schedule.ts

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 2, Punkt 045).

- **The Fahrplan mini preview derivation is pure `src/schedule.ts`** (unit-tested): `planSentence(slots, plantKind, now)` composes the ONE German sentence from the dominant charge/discharge windows by energy ("Mittags laden, abends verkaufen (17–20 Uhr)."; DV "verkaufen" vs EV "nutzen"; a mostly grid-fed charge window says "günstig laden"; all-idle = "Der Speicher hält heute seine Ladung."), `savingsTodayEur` (null when no priced slot - never a fake zero), `planHourBars` (24 hourly bars, dominant direction, netzladen-cyan when most charge energy is grid-fed). `chargeKind` is PV-AWARE (FK3 display follow-up, 2026-07-16): a charging slot is `netzladen` only when the charge exceeds the slot's available PV (`batteryKw > pvKw - curtailKw + PV_SOURCE_DEADBAND_KW` while importing; per-slot PV = the new `ScheduleSlot.pvKw`), because an EEG cloudy-day slot legitimately charges solar while the house imports its load - pv-less slots fall back to the old charging-while-importing rule; the server twin `SlotEconomics.decisionLabel` (admin diagnostics) mirrors it and must stay in sync. The bars' CSS (`.vp-plan-mini`) uses the `--vp-chart-charge/gridcharge/discharge` tokens so preview and full chart agree. FK2 banked-value honesty lives there too: `bankedValueLine(plan.bankedValueEur)` (one calm line under the Fahrplan Euro-Zeile - positive "davon in den Folgetag gespeichert: +X €", negative sign-honest "aus dem Vortag entnommen"; null/noise hides it) and `horizonHint(slots, now)` (the pre-13-Uhr "Fahrplan reicht bis zum Tagesende" note when the plan's own horizon ends within today - display-side derivation, no backend field), both rendered in `pages/DataPages.tsx` `FahrplanSection`.
  - **Fahrplan honesty + chart pass (audit `vp-audit-view` F1–F7, 2026-07-24), all pure in `schedule.ts`:** `planStaleNote(generatedAt, slots, now)` — the optimizer re-plans every 15 min, so a run older than `PLAN_STALE_AFTER_MS` (2 h) gets an amber `.vp-alert-warn` banner ABOVE the chart naming heute/gestern/das Datum, plus „Die Balken zeigen einen bereits vergangenen Zeitraum…" when `planCoversNow` is false; the ChartSubtitle then says „So war der Tag geplant" instead of „So plant Ihr Speicher den Tag". It states only what the plan proves and **never guesses the cause** (device offline / no prices / optimizer down are indistinguishable from the plan alone). Die Ersparnis nutzt `savingsTodayEur` → „—" + „Für heute liegt noch kein Fahrplan vor." (never a fabricated 0,00 €); seit dem Seiten-Neubau steht sie als EURO-ZEILE statt als KPI-Kachel (siehe „Die Fahrplan-Seite sind VIER BLÖCKE"). `planInsightParts` builds the takeaway as bold/plain parts with **mutually exclusive clauses** — the „flacher Preisverlauf … in Ruhe" ending may only fire on a genuinely idle plan (it used to be the else-branch of the savings clause, so a visibly cycling plant was told its curve was flat). `socRangeLine` names the planned SoC band in words — the readable fallback wherever the SoC axis has no room.
  - **EINE Farbsprache an JEDEM Fahrplan-Bauteil (Konzept `data/vp-fahrplan-kunde-konzept` §6.6, PR 1; K5-Revision 28.08.2026).** Solar laden = grün `charge` · Netzladen = türkis `gridCharge` · **Entladen (decken/verkaufen/kappen) = beere `battDischarge`** (`--vp-chart-battdischarge`, gefüllt) · Abregeln = orange `pv` · Ruhe = neutralgrau; **Rot (`discharge`) NUR für Kosten/Warnung/echte Abweichung** (Netzbezug im `HistoryChart`, die Lastspitzen-Ziel-Linie) — eine entladende Batterie verdient Geld und darf nie wie ein Fehler aussehen. `roleColor`/`slotBarColor` und die Legenden lesen dieselben zentralen Marken; der Cockpit-Ministreifen folgt ebenfalls dem Beerenton. **Grün↔türkis bleibt unter dem Normal-Vision-Floor — die strukturelle Antwort ist Wort+Icon an jeder bedeutungstragenden Stelle (K10), NIE eine weitere Ad-hoc-Palette.** In `ScheduleChart` the SoC axis is now VISIBLE on the right at `offset: 44` (hidden below 480 px, where `socRangeLine` carries it), the x-axis labels carry `DD.MM.` on the first slot of each day, and the „Jetzt" markLine only draws while the plan actually covers now (`rotate: 0` — the documented edge-label gotcha).
  - **`hasCurtailment` ist DAS EINE Gate für alles Orange — Legende UND Canvas (Fix 2 der Pilsting-Analyse, Scout `vp-pilsting-abregeln` Frage 4, 02.08.2026).** Der behobene Fehler war genau das Anti-Muster, das die Legenden-Gating-Regel verhindern sollte: das Gate prüfte die DATEN und schaltete allein die Legende frei, während das Canvas Orange **nie** zeigte — Träger der Farbe war der Batterie-Balken, und der ist im Abregeln-Slot (Rolle `abregeln` = Batterie idle) 0 kW hoch; die gedrosselte Menge war nirgends gezeichnet und die Prognosen-Ebene ist seit Stufe 2 standardmäßig aus. Jetzt hängen VIER Dinge an demselben `hasCurtailment`/`CURTAIL_DEADBAND_KW`: das orange **Band** (`curtailSpans` → `markArea`, niedrige Opacity — das Muster der Vergangenheits-Schattierung), der schmale orange **Sockel-Tick** je Slot (`curtailTickData`, das `:8484`-Ticks-Muster), die zuschaltbare **Fläche** und die **Legenden-Zeile**. `curtailing` wird EINMAL im Komponenten-Körper berechnet und in die Canvas-Closure hineingereicht — Legende und Canvas können damit nicht wieder auseinanderlaufen.
    - **Drei Konstruktionsentscheidungen, die man kennen muss:** (1) das Band reitet auf der **Preis-Reihe**, weil die Batterie-Reihe ihre `markArea` schon für die Vergangenheits-Schattierung trägt (eine Reihe, eine markArea); (2) `curtailSpans` **verbreitert einen Ein-Slot-Block auf einen Nachbarn** — eine Spanne von einem Index auf sich selbst ist auf der Kategorie-Achse null Pixel breit (dieselbe Falle wie bei der Historie-Ereignis-Spur), die exakte Slot-Wahrheit trägt deshalb der Tick; (3) der Tick ist ein **Scatter mit Rechteck-Symbol und Wert 0** (`symbolSize`/`symbolOffset` in PIXELN), er hängt damit nicht an der kW-Skala und kann keine Leistung behaupten, die er nicht misst.
    - **Die gedrosselte Menge lebt in der Prognosen-Ebene** (`curtailArea` → zwei gestapelte Linien: unsichtbarer Cap `pvKw − curtailKw` + Differenz mit `areaStyle`, sodass `cap + delta === pvKw` exakt gilt) — sie erklärt, WARUM die PV-Prognose über dem Einspeise-Cap liegt. Keine Backend-Änderung: `pvKw`/`curtailKw` stehen längst im Slot-DTO. Ehrlichkeit wie bei jeder Plan-Linie: ohne PV-Wert bleibt der Slot `null` (Lücke), nie eine erfundene 0.
    - **Wortlaut + Form:** `CURTAIL_LEGEND_LABEL` ist **„Abregeln — geplant"** (der PLAN-Wortlaut aus Fix 1, `fahrplanWhy.PLANNED_TAG` — die Cloud kennt keinen Ausführungs-Beleg), `shape: 'area'` statt `'bar'`. Der Tooltip nennt die Menge (`curtailTooltip` → „Abregeln geplant: X kW (Einspeise-Cap Y kW)"); er besteht **nur aus Konstanten + `toLocaleString`-Zahlen** (XSS-Regel der Chart-Formatter) und lässt den Cap-Teil weg, statt ohne PV-Wert eine 0 zu behaupten.
    - **Beweise:** `schedule.test.ts` (Spannen/Verbreiterung, Ticks, Fläche inkl. Cap+Delta=PV und „ohne PV leer", Tooltip inkl. der XSS-Zusicherung) und `ScheduleChart.test.tsx` — dessen `useEChart`-Mock **rechnet die Render-Closure aus und fängt die `setOption`-Option ab** (`lastOption`/`series(name)`), sonst wäre genau die Divergenz „Legende bewirbt, Canvas zeigt nicht" unbeobachtbar. Die Option-Form ist zusätzlich einmalig gegen ein echtes ECharts (SSR-`renderToSVGString`) gegengeprüft.
