# Plattform → Geräte-Registry ist der ONBOARDING-FUNNEL (Admin-Umbau Stufe 1, Baustein B3).

Ausgelagert aus `frontend/portal/AGENTS.md` am 05.09.2026 (Abschnitt Nr. 2, Punkt 042).

- **Plattform → Geräte-Registry ist der ONBOARDING-FUNNEL (Admin-Umbau Stufe 1, Baustein B3).** Drei Stufen statt zwei: **registriert** → **wartet auf Zuordnung** → **verbunden**, als Kopf-Streifen (das `MandantenPulse`-Muster) über zwei benannten Tabellen. Die mittlere Stufe ist das TIPPFEHLER-FENSTER — ein Gerät hat seinen CSR hochgeladen, aber der Kunde hat eine andere Referenz getippt, also trifft es auf keinen Claim; sichtbar war das auf KEINER der beiden Seiten, obwohl `GET /api/v1/admin/enrollments/pending` seit dem Enrollment-Bau existiert (der grep nach einem Portal-Aufrufer war leer). Reine UI-Arbeit auf einem fertigen Endpunkt. Ableitung + Copy sind das reine `src/onboardingFunnel.ts` (`funnelStages`/`pendingRows`, `onboardingFunnel.test.ts`); `adminApi.listPendingEnrollments()` ist der Client (mandantenlos per Konstruktion). **Drei Regeln:** ein Wartender älter als `TYPO_SUSPECT_AFTER_MS` (24 h) heißt „vermutlich Tippfehler", ein frischer „normal während der Einrichtung", und ein `everIssued`-Gerät (war verbunden, wurde getrennt) wird NIE als Tippfehler gelesen — das ist ein anderer Zustand. Die Sektion ist read-only (die Reparatur liegt beim Kunden bzw. Support), und ihr Abruf ist von der Registry ENTKOPPELT: fällt er aus, steht dort ein Fehlerzustand mit Wiederholen statt einer leeren Liste, die „niemand wartet" behaupten würde.
