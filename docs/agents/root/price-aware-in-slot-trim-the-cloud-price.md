# Price-aware in-slot trim: the cloud prices, the edge enforces (2026-07-30)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 80).


The 15-min setpoint stands for the whole quarter hour, but PV and house load move every second - so a forecast shortfall was silently covered from the GRID. Captain observation at Anlage Pilsting (30.07., 14:44): PV 15,3 · Haus 7,6 · Batterie lädt 11,1 · **Netzbezug 3,4 kW** at a 3,3 ct spot against a 22 ct evening, i.e. the purchase was economically RIGHT - which is exactly why "just charge the surplus" is the WRONG fix (that is the price-blind Eigenverbrauchslogik, the same category error as the fixed night-emptying bug with the sign flipped). The answer is CONDITIONAL, and the split is architectural law: **THE CLOUD DECIDES WHETHER A SLOT IS EXPENSIVE, THE EDGE ONLY LIMITS.** The edge evaluates no price, ever (one price truth - the `pricing.py`/`SlotEconomics` discipline).

- **The rule (`services/optimization/voltpilot_optimization/slot_trim.py`)**: the marginal willingness to pay for one more AC kWh charged in slot t is `WTP_t = eta*λ_t − wear`, where **λ_t is the model's OWN marginal value of stored energy** (the LP dual the explain layer already extracts and persists as `stored_value_ct_kwh`). A grid purchase for the battery is uneconomic iff `import_price_t > WTP_t + margin` (`SLOT_TRIM_MARGIN_CT_PER_KWH` 0.5 ct - it swallows the 0.1 ct degeneracy rounding of the persisted λ AND keeps a hairline case untrimmed). A plain threshold ("above X ct") was deliberately rejected: it is wrong at the next price regime, whereas this test IS the model's optimality condition and self-adjusts. Sanity check on the observed case: WTP ≈ 28 ct ≫ 14,6 ct import → NOT uneconomic → Pilsting keeps doing exactly what it did.
- **Emission** (`solver._charge_from_surplus_only`, stamped in `_with_explanation` next to the why-fields; `PlanSlot.charge_from_surplus_only`): only on slots whose plan actually COMMANDS a charge (the `pv_limit_kw` discipline - every other payload stays byte-identical), plus a consistency guard that never flags a slot the plan itself grid-charges in. λ comes from explain, so `OPTIMIZER_EXPLAIN_ENABLED=false` (or the new `OPTIMIZER_SLOT_TRIM_ENABLED=false` kill switch) degrades to today's behavior.
- **Contract**: the OPTIONAL per-slot boolean **`charge_from_surplus_only`** in `docs/contracts/mqtt-schedule.schema.json` = the edge's DUTY to clamp commanded CHARGE to the MEASURED surplus `max(pv − load, 0)`. Distinct from the top-level `grid_charge_allowed`: that one is REGULATORY (EEG, charge ≤ measured PV PRODUCTION, house may import in parallel) and the Go edge fails SAFE on it; this one is ECONOMIC (charge ≤ measured SURPLUS, so the battery causes no import at all) and is deliberately **FAIL-OPEN** - a missing economic hint must never reshape dispatch, and an inferred restriction would destroy real arbitrage. Most restrictive wins; neither ever widens anything.
- **Edge (`edge-app/core/internal/guards/slottrim.go` `PriceTrimmer`, applied in `applySetpoint` after Clamp/arbitration and before the peak guard)**: restrict-only on charge, asymmetric hysteresis (engage immediately - a passing cloud is what must not be bought; release only after the plan setpoint has comfortably fit the surplus for `TrimReleaseDwell` 90 s), the applied cap follows a SHRINKING surplus at once and a growing one only in `TrimStepKw` steps (stable register writes). **Safety by algebra:** after a trim the predicted grid power is `max(load − pv, 0) ≥ 0`, so the site is never pushed into export → the §14a export bound and any feed-in cap are untouchable, and the import bound was applied to a value the trim only reduces further; the result lives strictly in `[0, kw]`, so the rated band + SoC window hold trivially and FK3 (looser) can never be widened. Unknown pv/load → INACTIVE (never regulate blind - the economic-guard convention, cf. PeakShave). The self-consumption fallback follows pv − load, i.e. the surplus itself, so the trim is a no-op there.
- **A trim is a DELIBERATE limitation, never a failed write:** the TRIMMED value is what gets published, so the register readback matches it and the PR #280 confirmation logic cannot read it as "Sollwert nicht übernommen". It is surfaced as its own state (`state.TrimInfo` → the `:8484` control card's reason line), because an unnamed limitation reads as a defect.
