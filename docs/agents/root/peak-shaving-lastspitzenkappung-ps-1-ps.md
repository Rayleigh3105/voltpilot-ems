# Peak Shaving / Lastspitzenkappung (PS-1 + PS-2, cloud side)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 88).


Captain go 2026-07-16 (spec: scout `vp-battery-models-b9` report Teil 3): RLM sites pay a **Leistungspreis** (€/kW per billing period) on the period's highest 15-min mean grid IMPORT; the battery shaves it. Cloud planning, the edge peak guard (PS-3) and the customer-facing reporting (PS-4) are all BUILT - see the last two bullets.

- **Master data (api migration `V20260716020000`):** nullable `site.leistungspreis_eur_kw` (**non-NULL IS the module flag** - the max_feed_in philosophy, no separate boolean), `site.abrechnung_leistung` (`jahr`|`monat`, NOT NULL default `jahr`, Europe/Berlin calendar periods), nullable `site.peak_reserve_soc_pct` (PS-2), plus `schedule.peak_target_kw` (run-level fact repeated per slot, the terminal_value pattern; mirrored in `infra/local/timescale/04-schedule.sql`). **Configuration is ADMIN-ONLY** (captain: VoltPilot richtet vertragsnahe Module ein): the three fields are written EXCLUSIVELY via the platform-admin `PUT .../optimizer-config` (`peakShaving` block, full-representation - null LP = module off, null abrechnung resets to `jahr`) and echoed read-only on `SiteDto`; they deliberately do NOT exist on Create/UpdateSiteRequest.
- **`peak_so_far` is computed FRESH per optimizer cycle, never stored** (`inputs._peak_so_far_kw`, module-active sites only): `max(grid_import_kwh)*4.0` from `telemetry_rollup_15m` since the Berlin period start (`billing_period_start`), blended (max) with the RUNNING quarter-hour's raw `avg(greatest(power_kw,0))` because the rollup refresh lags ≤15 min. **Plausibility gate** (`plausible_peak`, `config.PEAK_SPIKE_FACTOR` 3.0): the period's top bucket is discarded for the second-highest when it exceeds 3× it - one unfiltered legacy-edge telemetry spike must not anchor the whole year; a real recurring peak (similar top buckets) always survives.
- **MILP (`solver.py`, in BOTH builds - economic, no new infeasibility path, §14a fallback untouched):** epigraph `peak >= grid_import_t`, `peak >= peak_so_far`, objective `+ LP*(peak − peak_so_far)` (exact for the period; no dt - it is a per-POWER price) `+ peak_ratchet_eur_per_kw(LP) * peak_below` where `peak_below` is the plain horizon peak. **The ratchet weight is `min(3%·LP, 0.30 €/kW)`** - the cap is load-bearing and was proven necessary: uncapped 3% of a Jahres-LP (100-200 €/kW → 3-6 €/kW per plan) PROVABLY dominates real arbitrage (a 400 €/MWh spread earns only ~0.6 €/kW of charge power - the solver covered cheap load instead of exporting at 500). The report's binding requirements (wear-scale, "nie echte Arbitrage dominieren") win over its "z. B. 2-5%" example; derivation in `config.py`. Export is NEVER in the epigraph (import-only instrument).
- **PS-2 reserve:** `BatteryParams.peak_reserve_pct` joins the reservation STACK via the same `soc_floor_kwh` machinery as the P11 backup reserve (incl. below-floor-start relaxation): each reservation is an ABSOLUTE SoC floor, `max` binds (technical < backup < peak-reserve) - NOT additive; hard at any price.
- **Publish/persist:** module-active plans carry the ADDITIVE optional top-level contract fields **`grid_import_limit_kw`** (= the solved `peak`, the future edge peak-guard target) and **`peak_reserve_soc_pct`** (`mqtt-schedule.schema.json`, schema_version stays 1.0; absent = no module, old edges ignore both safely - documented x-failsafe); `schedule.peak_target_kw` persists the target per run (NULL = module off, never fabricated).
- **Tests:** optimization `tests/test_peak_shaving.py` (hand-computed: hold-vs-economically-break the peak, ratchet shaves below the anchor after a torn peak / never blocks a profitable cycle, period-start flattening, export unpenalized, reserve stack + hard floor, §14a compose + fallback-build shaving, EEG discharge-only, contract fields, billing-period/gate/wiring units) + `test_freshness.py` column resolution; api `AdminApiTest.peakShavingModuleIsAdminConfiguredAndEchoedReadOnlyOnTheSite` (writes land on the exact columns `inputs.py` reads, SiteDto read-only echo, customer path cannot touch them, validation, authz/tenancy).
- **PS-3 edge peak guard (`edge-app/core`, the local closed loop - the billing peak is a 15-min MEAN, so a stochastic load jump at :07 must be counter-regulated INSIDE the running quarter hour; the 15-min cloud MPC can only plan peaks).** `plan.Parse` reads the two optional contract fields (validated; reserve only alongside a valid target; nil = module off = byte-for-byte pre-PS, persisted with the plan across reboots); the accessors `PeakImportLimit()`/`PeakReserveSoc()` are DELIBERATELY staleness-independent - on a dead cloud link the guard keeps defending the LAST known target (contract x-failsafe amended for PS-3; safe because restrict-only). `guards.PeakTracker` integrates the gated composite `power_kw` (import-only - RLM meters register per direction, export never offsets; hold-last between samples, wall-clock :00/:15/:30/:45 quarters via `Truncate` - Berlin offset is whole hours so no tzdata; >2-min measurement gap = tracker inactive, never regulate blind) and projects the remaining-quarter import allowance; `guards.PeakShave` runs AFTER `Clamp` in `applySetpoint` (BOTH modes) and only ever LOWERS the setpoint toward a non-negative import target, respecting rated discharge + the SoC floor - so §14a (both directions), EEG solar-only and the band are provably never violated. **Fallback composition:** ordinary self-consumption discharge stops at the plan-carried `peak_reserve_soc_pct`; peak DEFENSE may discharge below it down to `SocMinPct` (that is what the reserve is for); a fresh plan's own setpoints are never reserve-floored (the cloud plans its own stack). `/api/state` additively exposes `peak_target_kw`/`peak_reserve_soc_pct`/`peak_guard_active`/`peak_quarter_mean_kw` → the `:8484` "Betrieb" card (`static/betrieb.js`, //go:embed - rebuild core after edits). Tests: `guards/peakguard_test.go` (tracker boundaries/gap/backfill/allowance math, PeakShave incl. compliance-composition proof), `plan` parse/round-trip, `agent/peak_guard_test.go` (reserve floor, defense-below-reserve, legacy byte-for-byte, schedule-mode shave, blind-inactive, telemetry plumbing), `web` (card structure + envelope), e2e-compose publishes the fields.
- **PS-4 reporting ("Vermiedene Spitze: X kW × Y €/kW = Z €", read-only, no schema change):** `GET /api/v1/earnings` carries a per-site **`peakShaving`** block - present exactly when the module is active (non-NULL Leistungspreis), RANGE-INDEPENDENT like `expectedMarketValue*` (always the RUNNING Berlin billing period). `repo/PeakShavingRepository` computes per period from `telemetry_rollup_15m`: measured peak = `max(grid_import_kwh)*4`, counterfactual no-battery peak = `max(greatest(import − export + discharge − charge, 0))*4` (== `max(0, load − pv)` per the power-balance identity - the same plant, battery idle; approximations documented in its Javadoc), `avoidedKw = max(0, baseline − measured)` (floor: a battery-CAUSED peak reads 0, never negative), `avoidedEur = avoidedKw × LP` NOT pro-rated (the standing saving; final once the period closes; current contract price applied to the 12-period `history` too). Buckets without `grid_import_kwh` are skipped; a module site without measurements gets config echo + null peaks (never fabricated). Portal: the Optimierung card's proof rows (`lastspitzenProof` in `moduleSurface.ts`, InfoTip "ohne Speichereinsatz" on the Vermiedene-Spitze row; the card fetches `api.earnings('month')` fail-soft) + ONE calm `vermiedeneSpitzeLine` in the `AnlageHero` money hero (hidden below the 0.05 kW deadband). A Peak-Verlauf chart (measured vs. `schedule.peak_target_kw` per period) is deliberately NOT built yet - the `history` data for it is already in the response.
