# Customer flow release (E3b): the Kunden-Freigabe of the flow editor

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 60).


The customer-facing half of the flow platform (spec `data/vp-ems-replatform/adaptive-ems-ui-v1-spec.md` §3/§5, epic #476): a Portal-User builds/validates/simulates/activates the flows of THEIR OWN sites, on top of the E3a admin engine, WITHOUT weakening any server-side gate. The captain's framing: three tiers - Kunde selbst (frei) < VoltPilot richtet ein (vertragsnah, gated + Beratung) < System automatisch (§14a).

- **ONE lifecycle engine, two surfaces:** the whole E3a orchestration (CRUD + versioning + validate + dry-run + the AE7/peak-shaving-gated activation) was extracted verbatim into the shared **`flows/FlowService`** (a `@Service`; the DTOs `FlowVersionDto`/`FlowSummaryDto`/`SaveFlowRequest`/`ValidationResponse`/`GatedNodeDto`/`GovernanceResponse`/`GovernanceRequest` now live on it). `AdminFlowController` (`/api/v1/admin/…`, `@PreAuthorize("hasRole('platform-admin')")`) and the NEW **`SiteFlowController`** (`/api/v1/sites/{siteId}/flows…`, NO `@PreAuthorize` - the `SiteController`/`UsageProfileController` pattern: authenticated + RLS is the fence, foreign site → 404 not 403, admins reach it via the X-Tenant-Id switcher) both delegate to it - so there is ONE lifecycle truth and no forked gate. The customer routes mirror the admin ones minus the platform-admin gate; both carry the German `{message}` `@ExceptionHandler`.
- **Gates are NEVER relaxed for customers:** activation still refuses a flow carrying a GATED strategy node (`vp.strategy.market`/`.peakshaving`/`.atypical-grid`) with `gated_node_not_enabled` until a Portal-Admin enables that node type for the site - a customer CANNOT self-enable (the governance WRITE `PUT .../flow-node-governance` + the AE7 auto-start seed stay admin-only on `AdminFlowController`; the customer surface exposes governance READ-ONLY at `GET /api/v1/sites/{id}/flow-node-governance` so the editor can render a locked node). Free nodes (Eigenverbrauch strategy, device-control/data/logic/action) activate normally. Customer catalog: `GET /api/v1/flow-catalog` (authenticated, not admin-gated).
- **Lifecycle steps customers get:** full draft → validate → simulate → activate for FREE-node flows; **deactivate** their own flows (NEW `POST .../flows/{id}/deactivate` on BOTH surfaces + `FlowService.deactivate` + `FlowActivationService.deactivate` = retire the active version + re-publish the smaller deployment set, never gated by the activation flag - stopping a flow is always allowed; a flow with no active version → 409); delete; version-history read. NO governance WRITE, NO auto-start.
- **Portal reuses the E3a editor, does NOT fork it.** The editor is now driven by a site-bound **`BoundFlowApi`** (`src/flows/flowsApi.ts` `adminFlowApi(tenantId,siteId)` / `customerFlowApi(siteId)` factories - same response shapes, differing only in routes + tenant handling); `FlowEditorPage` takes `api: BoundFlowApi` (+ `canEnableGated`/`lockedHint`) instead of `tenantId`, so `pages/admin/FlowsPage` and the customer `pages/SteuerungSection` share the same palette/canvas/inspector. The palette is now governance-aware: a gated node is placeable for admins (they enable it) and for customers only once VoltPilot enabled it for the site, else it renders **locked** with the Beratung copy `EINRICHTUNG_DURCH_VOLTPILOT` (the old hardcoded Peak/atyp-NN locked pair is gone). Customer surface = the Anlage subpage `#/anlage/{id}/steuerung` (`nav.ts` sub `steuerung`, DetailCard on the Anlagen-Seite): own-flow cards + a template gallery. **Customer control templates** (pure `src/flows/customerTemplates.ts`, unit-tested `customerTemplates.test.ts` - each resolves against the site's entities + is applyDerivedClaims-stamped so it validates clean against the client validator): "Wallbox nur bei PV-Überschuss" (grid read → threshold → consumer on_off) and "Heizstab-Zeitplan" (schedule window → consumer on_off), FREE nodes only; plus the gated Marktoptimierung (pilot) shown with the Freischaltung state.
- **Honesty boundary on control (unchanged):** consumer desires flow through the built desired/arbitration path to the entity `…/command` topic; the physical go-e WRITE executor still does not exist (read-only driver). Templates that command a wallbox are buildable/activatable, and the UI shows lifecycle + whether the rollout published (poll-based; NO SSE - that is E14), never a fabricated live-ack. No per-flow ack read endpoint exists - do not invent one.
- **Tests:** api `CustomerFlowApiTest` (Testcontainers: the `demo` operator (tenant from JWT, no X-Tenant-Id) builds → validates → simulates → activates a FREE device-automation flow reaching `activation_disabled` = the gate LET IT THROUGH; a gated market flow gets `gated_node_not_enabled` for the customer, the customer cannot self-enable (admin governance PUT is 403), and once an admin enables it the SAME customer activation clears the gate; deactivate-not-active 409; foreign site 404 via RLS with `demo2`); the existing `FlowApiTest`/`FlowPeakShavingApiTest`/`UsageProfileApiTest` stay green (admin lifecycle unchanged). Portal `customerTemplates.test.ts` + the whole `src/flows/*` suite; `npm run build` green.
