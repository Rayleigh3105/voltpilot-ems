# Forecast service (`services/forecast`)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 73).


Load/PV forecasts for the optimizer (architecture section 12). Pure Python, dependency-free core, offline-first (demo + tests need no DB/network); the ML challengers live behind the optional `ml` extra. Full detail in `services/forecast/README.md`; the shadow-mode model registry, the challengers and the evaluation have their own section below ("Shadow-mode forecasting").

- **Methods.** Load = baseline (`SeasonalPersistenceLoadForecaster`, `ProfileLoadForecaster`; persistence/profile per architecture 12). PV = physical model (`PhysicalPvForecaster`): solar geometry -> clear-sky irradiance -> plane-of-array transposition -> PVWatts-style capacity/derate. Day-ahead price is not forecast (ENTSO-E-given).
- **A forecast slot is a quarter-hour MEAN, and the aggregation lives in PYTHON, not in SQL (prod defect, fixed 2026-07-30, scout `vp-netzbezug-nacht-s3` §3 link 3).** Telemetry arrives at ~5-10 s, so ~90-180 raw samples fall into one 15-min slot. `SeasonalPersistenceLoadForecaster` used to keep the LAST of them per slot (`by_slot[key] = obs.value_kw`), which made a quarter-hour forecast a random draw from within the slot - measured on the captain's Pilsting plant: **1,14 kW mean absolute sampling error, 2,26 kW peak**, before any day-to-day deviation. Since the fix every baseline sees history ONLY through `domain.slot_means(history, slot_minutes)` (`features.bucket_15min` is now a thin alias of it, so challengers and baselines provably share ONE aggregation). Two rules follow: **the two telemetry queries (`forecast_collect._telemetry_history`, optimizer `inputs._load_history`) MUST keep returning RAW samples** - a `time_bucket('15 minutes')` there would hard-code the slot width the `Horizon` owns, would have to be kept in sync twice, and would silently change the ML challengers' training rows; and **a new forecaster must aggregate through `slot_means`, never index raw samples by slot**. This matters because the optimizer plans `Entladung = Lastprognose − PV-Prognose` in an Eigenverbrauch slot and the edge executes that setpoint without load-following, so every kW of forecast error is settled at the grid (≈11 ct/kWh spread between import price and feed-in value). The optimizer's fallback path (`voltpilot_optimization.fallback.persistence_forecast`) REUSES the same forecaster and therefore inherits it - both paths plan the same quantity.
- **Interfaces (swap points).** `LoadForecaster`, `PvForecaster`, `WeatherProvider` (weather anti-corruption layer, default `ClearSkyWeatherProvider`), `ForecastRepository`. `ForecastService` is the façade the optimizer calls. The later XGBoost/LightGBM load model and a real EU-hosted weather API implement these same interfaces - consumers are unaffected (architecture 12.2/12.3).
- **Exposure.** Forecasts are timeseries (architecture section 10) -> TimescaleDB `forecast` hypertable, read via `TimescaleForecastRepository` (`.[db]` extra pulls psycopg); `InMemoryForecastRepository` is the offline default. Horizon is 48h in 15-min slots (`FORECAST_HORIZON_HOURS`, 48 since 28.08.2026 so the optimizer's 48h window rests on REAL forecasts); the PV models stop where real weather stops - see the planning-horizon section.
- **Migration version coordination.** The `forecast` hypertable ships as Flyway `services/forecast/migrations/V3__forecast_hypertable.sql`. **V1/V2 are reserved** for the core schema (master data, telemetry) that `services/api` will own when it adopts Flyway; forecast deliberately takes **V3** to avoid collision. The shadow-mode `model` column is the date-versioned `V20260702000000__forecast_model_column.sql`; the api's `V20260701040000` applies the same DDL idempotently as the canonical runtime owner (the weather_forecast precedent). `infra/local/timescale/02-forecast.sql` and `infra/prod/timescale/00-collector-tables.sql` mirror the same table shape for the bootstraps - keep all four in sync (the migrations are the source of truth).
- **Run/test.** `(cd services/forecast && python -m venv .venv && . .venv/bin/activate && pip install -e '.[dev,ml]' && pytest)` - the `ml` extra pulls xgboost/numpy for the challenger tests (they skip without it; macOS needs `brew install libomp` for the xgboost wheel, Linux libgomp1); `python -m voltpilot_forecast` prints a 24h demo forecast for the seeded demo site. The **weather collector** and the **forecast collector** are wired into the compose `feeds` profile (see below and "Shadow-mode forecasting").
