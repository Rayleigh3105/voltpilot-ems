# What-if re-optimize (`POST /api/v1/admin/sites/{siteId}/optimizer-what-if`, design §4.3)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 87).


The last piece of the admin optimizer surface: an operator moves a knob and gets a freshly solved plan to compare, **without touching the plant**. Three properties carry it, and they are the whole design.

- **Ephemeral by construction, not by convention.** `services/optimization/voltpilot_optimization/whatif.py` imports NEITHER `persistence` NOR either publisher - it only calls the pure `gather_inputs` → `optimize` pair, so no route on any side can make it write a `schedule` row or push a retained MQTT plan. `test_whatif.py` pins that at the IMPORT GRAPH (an `ast` walk over the module), which is the check that survives a future edit; the 15-min tick loop runs in a different process and shares no state with it.
- **Two solves over ONE gathered input.** A knob delta is only meaningful on the same prices/forecasts/SoC, so every run gathers once and solves twice: `baseline` (the site as configured) and `variant` (with the overrides). Comparing the variant against the site's PERSISTED run was deliberately rejected - that run was generated at another time over another horizon with another price vintage, so the delta would attribute the passage of time to the knob. The persisted run stays what is in force and the portal labels it so.
- **Overrides are the panel's knobs only** (§2.8/§4.3): wear cost, backup-reserve floor, the usable SoC band, and the `netzladen_erlaubt` posture. Prices, forecasts, tariff, §14a and the feed-in cap come from the real site, so a preview can never be a fantasy plant. Every field is OPTIONAL and ABSENT means "leave it as the site has it" - never zero, which is what makes an empty body the meaningful baseline. `backupReserveSocPct: 0` IS "no reserve" (a 0 % floor and no floor are the same constraint), so there is no separate clear flag.

Facts worth knowing before touching it:

- **It rides the EXISTING solve service, not a new container.** `POST /what-if` sits next to `/simulations` on the optimization image's `simulate-serve` surface (`simulation/server.py`, whose docstring now calls it the on-demand solve surface), so the api reuses `voltpilot.simulation.base-url` + the `SimulationHttp` seam - no compose change, no second base-url to keep in sync across dev and prod. The two POST routes are the two shapes of "solve something the tick loop did not ask for": the Ersparnis-Simulation is a long ASYNC year chain behind a job store, a what-if is a single horizon that solves in well under a second and is therefore **synchronous, in the request thread, with no job id**. Concurrency is bounded by a semaphore (`WHATIF_MAX_CONCURRENT`, default 2, → 429) so an admin leaning on the button cannot starve the simulation jobs sharing the container's CPU budget.
- **The api's RLS check IS the tenancy fence.** The solve service resolves sites with the trusted backend credentials and has no tenant concept, so `AdminOptimizerController.requireSite` must prove the site is visible in the switched tenant BEFORE the id is forwarded; a foreign site is 404 and never reaches the service (pinned by `AdminWhatIfApiTest.aForeignSiteIs404AndTheSolveServiceIsNeverContacted`, which also asserts the same site IS reachable through its own tenant so the 404 is the fence and not a broken route).
- **`load_battery_sites(dsn, site_id=None)`** grew the optional filter so a what-if resolves the site through the SAME path the tick loop uses - a preview can never disagree with the plan that will actually run. `terminal_value_eur_per_kwh` is deliberately NOT carried across: `gather_inputs` leaves it at the env override (normally None), so `effective_terminal_value_eur_per_kwh` re-derives V_end from the VARIANT's own posture (flipping netzladen changes which slots may refill the battery).
- **Portal (`pages/admin/OptimizerPage` `WhatIfPanel` + `WhatIfCompareChart`).** The knob form, a Speicherschonung preset row that only PREFILLS the wear field (sharing the 1/4/8 ct ladder with the customer-facing `web/Speicherschonung`), the delta table and the two-plans-in-one chart. ALL derivation/copy is the pure `src/optimizer.ts` (`buildWhatIfRequest`/`whatIfDeltaRows`/`whatIfVerdict`/`overrideChips`/`whatIfFallbackNote`, tested in `optimizerWhatIf.test.ts`). Four honesty rules are load-bearing: an untouched field is ABSENT from the request (else the baseline stops being "as configured"); the "Simulation - es wird nichts an die Anlage gesendet" banner is always visible, not a toast; a delta row is toned only where direction IS a value judgement (more savings good, more wear bad, throughput/cycles neutral); and a failed run DROPS the previous result rather than letting stale numbers answer the new question. `whatIfFallbackNote` says so when only one of the two runs had to drop the §14a cap - the numbers are then not comparable.
- **The comparison chart is its own component but not its own stack:** it reuses `useEChart`/`chartTheme`/`chargeKind`/`ChartLegend` exactly like `OptimizerPlanChart` (variant solid, baseline a pale outline behind it), because "what did the run in force do and why" and "what does this knob change" are different questions over different data.
- **Tests:** `test_whatif.py` (38 cases: the import-graph guard, each knob moves only its own field, the runner gathers once, request validation, and HiGHS-backed proofs that empty overrides yield two identical plans, that a high wear rate stops the cycling, that forbidding grid charging removes the arbitrage and that a reserve floor holds at any price); `AdminWhatIfApiTest` (6 Testcontainers cases with a fake in-process solve service: only-touched-knobs forwarded, empty body = as configured, the RLS fence, customer 403 / anonymous 401, battery-less 409 + invalid knobs refused before any solve, and every upstream refusal keeping its German reason while an outage never looks like a result); portal `optimizerWhatIf.test.ts` + the `OptimizerPage.test.tsx` what-if block.
