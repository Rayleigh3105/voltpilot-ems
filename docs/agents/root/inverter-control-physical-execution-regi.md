# Inverter control: physical execution + register-level readback (`vp-inverter-control`)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 94).


Captain-approved tranche (2026-07-08, decisions in firstmate `vp-inverter-control`): turn the Fahrplan from "displayed/simulated" into "physically executed, with register-level readback proof".
The write side MIRRORS the read self-wiring; adding a control family = one adapter, no core change.
**SAFETY IS NON-NEGOTIABLE (captain decision 3): control is OFF by default and no model writes live until bench-certified.**
The automated proof is against the SIMULATOR only (`edge-app/test/e2e-compose.sh`, which now asserts write→readback→match on reg 40/41/42); real Deye writes ship UNCERTIFIED (read-only) until the captain's bench session.

- **The control-adapter abstraction (`edge-app/nodered/inverter-control-routing.js`, the write twin of `inverter-routing.js`).** Pure `controlRoute(selection, setpoint, opts) -> {adapter, family, certified, controlEnabled, writes[], readbacks[], planned?, reason?}`; a separate executor does the I/O. `WriteOp = {role, fc, addr, value, encode, dwell_s, min_change}`, `ReadOp = {role, fc:3, addr, expect, tolerance}`. **Two independent gates:** (1) `controlEnabled` = the CORE kill-switch AND per-model cert verdict, published on `edge/setpoint`; when false `writes` is EMPTY but `readbacks` still run (UI shows actual state). (2) `CERTIFIED_CONTROL_FAMILIES = {sunspec}` HERE - an uncertified family (every Deye family) emits `writes:[]`/`readbacks:[]` REGARDLESS of the kill-switch, its intended ToU mapping surfaced as `planned` (display/tests only, never executed). Signs are config (`invert_control_sign`), never code. The flow's "Steuerung / Schreibplan" + "schreiben + zuruecklesen" function nodes carry a SYNCED COPY (like the read side), pinned by `flows-sync.test.js`; `build-flows.js` authors both the self-wiring auto tab's control path AND the Simulator tab's (fixed `edge-sim` sunspec selection).
- **generic_modbus/SunSpec control adapter (CERTIFIED, proven vs sim):** `battery_power`→FC6 reg40 (int16 kW×100), `control_enable`→reg41=1, `pv_limit`→reg42 (uint16 kW×100, `0xFFFF` sentinel). After each write, FC3-reads 40/41/42 back, computes per-register `{commanded, actual, match}`, publishes `edge/control/readback` (NEW local-bus topic, NOT retained). Modbus FC6 write PDUs added to `modbus-tcp.js` (`buildWriteSingleRequest`/`parseWriteSingleResponse`), exercised end-to-end against an in-process server in `modbus-tcp.e2e.test.js` (write→readback→match + mismatch case + Deye read-only no-op).
- **Deye control adapter (UNCERTIFIED, read-only until bench).** `DEYE_CONTROL_REG` in `inverter-control-routing.js` is now a **per-battery-family map SOURCED from ha-solarman** (`davidrapan/ha-solarman`, MIT: `deye_p3.yaml`→`hybrid_3p` = SG04LP3 LV **and** SG01HP3 HV; `deye_hybrid.yaml`→`hybrid_1p` = SG0\*LP1), NOT triangulated - ha-solarman drives the SAME Solarman-V5 logger, so the addresses are belastbar; only the register facts are re-expressed, no GPL/MIT code copied (attribution in-code + DEYE.md). **The earlier 0x0F00-region guess was WRONG** (a read-only bench dump of the captain's SG04LP3 showed 0x0F00.. holds LIVE TELEMETRY, not config - data/learnings.md 2026-07-08); the real levers live OUTSIDE the telemetry window in `0x008D..0x00B1` (3p) / `0x00F3..0x0117` (1p). Mapping (strategy A, ONE live ToU Program-1 slot): `work_mode`→Work Mode reg (0x008E/0x00F4 = Export First), `tou_enable`→ToU reg (0x0092/0x00F8 = 0x00FF all-week), `battery_power`→Program 1 Power (0x009A/0x0100, W/`power_scale`), `battery_target_soc`→Program 1 SOC (0x00A6/0x010C, direction via target-SoC), `grid_charge_enable`→Program 1 Charging enum (0x00AC/0x0112, Disabled/Grid, EEG-gated by `netzladen_erlaubt`), `pv_limit`→the family feed-in cap (3p "Grid Max Export power" 0x00E7 scale 10 / 1p "Max Sell Power" 0x00F5 scale 1; OMITTED when uncurtailed = contract "absent = no limit"). String/micro (no battery) plan only `pv_limit`→active-power-limit 0x0028 (the correct reg THERE; it was wrong on hybrids and removed). All `bench_pending`, never executed. Write path = standard Modbus FC6/FC16 in the V5 frame (`deye/solarman-v5.js` `writeSingleRegisterRequest`/`writeMultipleRegistersRequest`) - byte-identical to ha-solarman's `WRITE_SINGLE_REGISTER`/`WRITE_MULTIPLE_REGISTERS`, so no frame change was needed. **Bench checklist (what the captain must verify per model before certifying): [`edge-app/nodered/CONTROL-BENCH.md`](edge-app/nodered/CONTROL-BENCH.md)** (ha-solarman base addresses, direction-via-target-SoC, sign, current-vs-power, readback fidelity, EEPROM cadence, fail-safe). `inverter-control-routing.test.js` pins the per-family registers + the "no control reg inside the telemetry block" invariant; `flows-sync.test.js` guards the inline flow copy for both hybrid + string branches.

  - **The in-slot EXECUTION truth reaches the cloud (PR 3 of the Fahrplan concept `vp-fahrplan-kunde-konzept` §5, 2026-08-02) - additive end to end.** Since the in-slot duties the box DELIBERATELY deviates from the plan's watt value, so `commandedKw` carried the CORRECTED number while nothing said why: the portal stated a bare value next to a Fahrplan bar showing a different one and could only claim "the device adjusted something" (concept K2). The edge now folds `snap.Follow`/`snap.Trim` into the heartbeat's `control.execution` block (`agent.executionSummary` → `cloud.ExecutionSummary`, see `edge-app/AGENTS.md`); the listener reads it PLUS the top-level `control_source` (sent for ages, ignored until now) into five nullable columns (migration **`V20260802000000`**: `control_source`, `execution_mode`, `execution_direction`, `execution_planned_kw`, `execution_target_kw`) served on `ControlStatusDto`/`api.ts`. Three rules keep it honest: the listener DROPS an unknown mode/direction instead of storing it (a word we do not understand must not become a sentence); the target column takes `deficit_kw` for `follow` and `surplus_kw` for `trim` (which one follows unambiguously from the mode) and stays null when the device could not measure it; and `control_source` is deliberately COARSE (it collapses fallback, a v2 desired holding the battery and calibration into `default`), so `executionMode` is the only signal a claim may key on. **Compatibility is the contract: an older edge sends no block ⇒ every column stays NULL ⇒ the portal keeps its pre-PR-3 generic wording, never a guessed direction.** Portal: `control.ts executionNote()` (the ONE sentence, shared by the cockpit strip and the Fahrplan hero) + `directionLabel()` ("angehoben"/"begrenzt"), and `fahrplanJetzt.ts` gained the `sicherung` state (amber) for `executionMode === 'fallback'` - it shows the real setpoint but never borrows the plan's role or its why-sentence. `controlSource` may only NEGATE, never explain: a coarse `default` without a precise mode also resolves to `sicherung` (so a device that is not executing the plan is never told it "runs as intended") while the explanation line stays EMPTY.
