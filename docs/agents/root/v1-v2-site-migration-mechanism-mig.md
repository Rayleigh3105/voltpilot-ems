# v1 -> v2 site migration mechanism (MIG)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 55).


The rehearsed, REVERSIBLE, per-site cutover from a v1 site to the adaptive v2 EMS - full operator procedure in [`docs/migration-v1-to-v2.md`](docs/migration-v1-to-v2.md). The live sites are read-only (no battery control), so migration = data conversion + a flag flip + the edge image; NO device-control certification is on the path, and v1 stays byte-identical throughout (everything v2 is flag/instant-gated).

- **Conversion preview (dry-run).** `GET /api/v1/admin/sites/{id}/v2-entities/preview` (`EntityRegistryService.preview`, `@Transactional(readOnly=true)`) composes EXACTLY what the idempotent `/bootstrap` would create/refresh - the pilot entities, their derived AE1 topology `roles`, capabilities/guards, the resolved `gatewayDevice`/`gatewayReason` and `alreadyConverted` - WITHOUT writing. `action` is `create`/`refresh`. Roles come from `TopologyDeriver.defaultRole` (the same truth the live topology uses), so preview never disagrees with the rendered view. Bootstrap itself never mutates v1 tables (asset/site/telemetry) - it only stamps `measurement_point.entity_type/capabilities/guard_config`. Plain PV+battery → a single `battery-hybrid` entity (PV+Speicher from the hybrid); a `grid-meter`/`producer` entity appears only when the matching measurement point exists.
- **History bridge (the trickiest piece).** `site.v2_history_cutover_at` (migration `V20260719070000`, nullable; NULL = un-migrated = byte-identical v1) splices the portal Historie read-side: `HistoryService` gives v1 (`telemetry`/`telemetry_rollup_*`) the buckets whose start is BEFORE the instant and the RECONSTRUCTED v2 era (`telemetry_v2`/`telemetry_v2_rollup_15m`) those at/after it - gap-free AND overlap-free by construction (v1 owns the straddling bucket). `HistoryRepository.v2DayBuckets`/`v2RollupBuckets`/`v2CostPerBucket` rebuild the v1 `HistoryBucketDto` shape by SUMMING per-quarter energies (dimensionally matching v1 at every range - never avg×span): pv=Σ pv_power_kw, battery=battery_power_kw (measured), grid=grid-meter power_kw (import/export split per quarter), soc=soc_pct, load=residual grid+pv−battery. A bare-hybrid site (no grid-meter entity) leaves grid/load absent in the v2 era; PV/battery/SoC still bridge. NOTHING is copied. Admin `GET/PUT/DELETE .../v2-entities/history-cutover` controls it (DELETE = the migration rollback). Set the cutover on an hour/day boundary so week/month splice cleanly.
- **The switch = `VOLTPILOT_V2_PLAN_SITES`** (optimizer env, comma-separated site UUIDs; `config.v2_plan_site_ids`): a flagged site ADDITIONALLY gets a co-optimized v2 shadow plan on `ems/{t}/{s}/{d}/v2/plan`, the v1 `/schedule` plan byte-identical. Now a passthrough on the optimizer in BOTH composes (default empty). Rollback = remove the site + `up -d optimization`.
- **AUTOMATIC on-deploy backfill (design + real-data measurements: firstmate `data/vp-v2-entity-backfill/report.md`).** After a deploy every existing plant renders the complete v2 face by itself - no operator step. `V2SiteBackfillRunner` (an `ApplicationReadyEvent` listener in `services/api`) iterates every un-marked site and calls the EXISTING `EntityRegistryService.bootstrapIfEligible` under that site's `TenantContext` (RLS path; the cross-tenant ENUMERATION uses the BYPASSRLS `adminJdbcTemplate`). Deliberately NOT a Flyway data migration: the composition rules live in Java and evolve, an applied migration is immutable + checksum-validated, SQL would be a second composition truth, and the registry push needs MQTT + TenantContext. Ops kill-switch `voltpilot.entities.backfill.enabled` (default true).
- **⚠ Das Anlagen-Modell KOMPONIERT SICH SELBST - NULL Nutzer-Schritte, weder Kunde noch Admin (Captain-Order 10.08.2026; Live-Befund „Mienbach").** Der Boot-Backfill oben ist EIN Auslöser, und bis hierher war er der einzige automatische: eine Anlage, die NACH dem letzten api-Start entstand oder ihr Gerät danach beanspruchte, bekam nie eine Komposition - der Admin-Bootstrap (`POST /admin/sites/{id}/v2-entities/bootstrap`) war der einzige andere Weg, und der Portal-Assistent rief ihn hinter einem `if (admin)` auf. Eine echte Neuanlage (Telemetrie floss, Fahrplan lief) zeigte deshalb dauerhaft „Noch keine Komponenten. Sobald Ihr Gerät sich meldet …" - ein Versprechen, das die Plattform nicht halten konnte. **`entities/EntityAutoComposer` ist jetzt die AUSLÖSE-Politik** (WAS komponiert wird, bleibt allein `bootstrapIfEligible` - eine Wahrheit, kein SQL-Zwilling), mit drei Auslösern jeweils an dem Moment, in dem die Stammdaten komponierbar WERDEN: **Geräte-Claim** (`DeviceController.claim`, direkt nach `autoLinkBatteryDevice` - erst dort gibt es ein eindeutiges Gateway, also komponiert eine neue Anlage ohne jede Wartezeit), **Speicher-Speichern** (`SiteBatteryController.saveBattery` - eine Anlage, die ihr Gerät VOR dem Speicher bekam, bliebe sonst ohne `battery-hybrid`) und der **getaktete Abgleich** (`V2SiteBackfillRunner.reconcile()`, `voltpilot.entities.backfill.interval-ms`, Vorgabe 5 min - er heilt Bestandsanlagen OHNE Deploy, ohne Re-Claim und ohne Klick). Der Portal-`if (admin)`-Bootstrap-Aufruf ist ERSATZLOS entfallen (ein zweiter Weg zu derselben Wirkung ist genau der Grund, warum ein Kunde nie eine Komposition bekam).
  - **Der zweite Kompositions-Grund in `bootstrapIfEligible` ist nicht kosmetisch:** neben „gar keine Entitäten" komponiert auch eine Anlage, deren Komposition HINTER ihren Stammdaten liegt (`battery != null && batteryHybridPointId == null`). Er keyt auf den PUNKT, nicht auf dessen Entitäts-Konfiguration - eine bewusst gelöschte komponierte Entität behält ihren Punkt und wird deshalb NIE still neu komponiert (die Rollback-Zusage hält).
  - **⚠ Warum KEIN MQTT-Herzschlag-Zuhörer** (die naheliegende Variante): ein eigener Zuhörer bräuchte ein NEUES `@ConditionalOnProperty`-Flag (wie alle Geschwister per Vorgabe aus), das im gitops-Repo nachgezogen werden muss - sonst läuft er in prod nachweislich nie (die dokumentierte OTA-Listener-Falle), also genau die Fehlerklasse, die dieser Umbau beendet; und sich an einen BESTEHENDEN Zuhörer zu hängen koppelte die Komposition an das Flag eines fremden Features. Der Takt braucht weder Broker noch neues Pflicht-Flag.
  - **⚠ Der Takt hat einen EIGENEN Schalter (`voltpilot.entities.backfill.reconcile-enabled`, Vorgabe an) UND prüft ihn im Methodenrumpf**, weil Springs `@EnableScheduling` GLOBAL ist: sobald eine fremde Konfiguration (OTA, Metriken) es einschaltet, wäre `reconcile()` auch ohne `EntitiesSchedulingConfig` getaktet - im Testlauf gegen gestoppte Testcontainer (die dokumentierte `@Scheduled`-Falle). surefire setzt ihn auf `false`; dass die AUSGELIEFERTE Vorgabe AN ist, prüft `V2SiteBackfillReconcileWiringTest` an der echten `application.yml`. `enabled` bleibt der Not-Aus für BEIDES.
  - **⚠ Nie in die Transaktion des Aufrufers:** `ensureComposed` verschluckt jede Ausnahme (ein Claim ist ein Betriebsvorgang, ein fehlendes Modell nur ein Anzeige-Mangel) und komponiert bei laufender Transaktion erst NACH dem Commit - sonst markierte ein Fehler im Modell-Aufbau die Transaktion als rollback-only und risse den Speicher-Schreibvorgang mit; der Mandant wird dabei ausdrücklich in den Nach-Commit-Lauf mitgenommen (sonst RLS default-deny).
  - **⚠ Folge für das Anlegen eines Netz-Zählers:** seit die Komposition beim Claim läuft, trägt jede verbundene Anlage eine SYNTHETISIERTE `grid-meter`-Zeile - die 0-1-Regel in `MeasurementPointController.create` hätte den Kunden danach für immer mit 409 abgewiesen. Ein ECHTER Zähler ÜBERNIMMT deshalb die komponierte Zeile (`MeasurementPointRepository.adoptComposedGridMeter`, erkannt an `device_id IS NOT NULL AND edge_source_id IS NULL`); zwei Zeilen wären keine Alternative, weil die Topologie je Rolle summiert. Eine gepinnte/kundeneigene Zeile bleibt unangetastet und bekommt weiter 409.

  - **THE COMPOSITION CONTRACT (measured, do not "restore the symmetry"):** battery-hybrid from the battery ASSET unchanged; **the `pv` ASSET never composes a producer** - it is the site AGGREGATE and the hybrid already measures `pv_power_kw`, so a second PV member DOUBLE-COUNTS (measured 5,85 kW read as 11,7 kW); a producer comes ONLY from a `pv-generation` measurement POINT or `adopt()`. **`grid-meter` and `house-load` are SYNTHESIZED from the gateway device** (v1 renders Netz + Haus from the gateway's own `power_kw` / `load_kw`; without an entity owning those channels both nodes vanish). Both are measure-only (`control=false`, no `actuate` - the DB CHECK enforces it), so nothing composed can reach a device. `bootstrap` and its `preview` twin must change in LOCKSTEP or the preview lies. **`house-load` is a NEW entity-type catalog entry** (category consumer, `controllable:false`, `composed:true`) - typing it `generic-load` lit up `hasControllableConsumer` on a house nobody can switch; the portal pins follow (`flows/validate.ts` composed set, `adaptive.ts` icon).
  - **The four guards:** automatic (boot); idempotent (bootstrap refreshes in place + a site with entity rows composes nothing); **a site with no unambiguous gateway is SKIPPED and deliberately NOT marked**, so it is retried on a later boot once a device is claimed (composing for a device-less plant would replace its honest onboarding guide with an empty Energiefluss); **reversible AND sticky** via the nullable `site.v2_backfilled_at` (migration `V20260722000000`) - the runner only looks at NULL markers, so deleting a site's entities is not silently re-migrated on the next restart. Re-arm one site by clearing its marker. The run writes ONLY `measurement_point` + `entity_registry_state` + the marker - never `asset`/`telemetry`/`device`.
  - **MIG-B1, the VALUE bridge (`services/timescale-writer` `ComposedEntityFanout`).** `telemetry_v2` is fed only by an edge publishing `edge/entities/{id}/telemetry`, and no shipped self-wiring flow does that - so a correctly composed site would render four nodes and four DASHES. The writer therefore mirrors each v1 sample onto the site's COMPOSED entities: battery-hybrid `soc_pct`/`pv_power_kw`/`battery_power_kw = power_kw − load_kw + pv_power_kw`, grid-meter `power_kw` (signed), house-load `power_kw ← load_kw`. **A NULL v1 channel writes NO row** (never a fabricated 0) and the derived battery power needs all three inputs. Only entities bound to the sample's own device, only the composed types (a producer is fed by its OWN source). Registry lookup cached per site (`voltpilot.entities.fanout.cache-ttl`, 60 s = the invalidation); the insert is the same guarded per-(entity, channel, time) insert, so it self-sunsets once a device publishes its own v2 telemetry. A fan-out failure is logged and NEVER wedges the v1 pipe.
  - **MIG-B2, the READ-side entity-history splice (`services/api` `EntityHistoryRepository`, audit H1 BLOCKER).** MIG-B1 only feeds `telemetry_v2` FORWARD, so on deploy day a migrated plant with 224k v1 telemetry rows had an **EMPTY Messwerte explorer at every range** (`telemetry_v2` = 0 rows) while its own Historie one tab away showed weeks of data. The fix is READ-side and additive - **nothing is copied, no migration rewrites data**: for a COMPOSED entity the pre-v2 part of the window is reconstructed from the v1 series through the SAME channel map MIG-B1 writes forward with (day = raw `telemetry` filtered on the entity's gateway `device_id` exactly like the fan-out; week/month/year = `telemetry_rollup_15m`, whose quarter ENERGIES convert back to the quarter's average power as kWh x 4 - the rollups have no device dimension, so those ranges are site-wide, which only differs on a multi-device site). **Splice instant = `max(site.v2_history_cutover_at, the entity's first v2 sample IN THE WINDOW)`** - the same mechanism/semantics as the site-level `HistoryService.splice`: v1 owns buckets STARTING before it, v2 those at/after it, so the series is gap-free AND overlap-free; no v2 row in the window at all (the deploy-day state) = the whole window renders from v1. A NULL v1 channel yields NO bucket (never a fabricated 0), and a v2-NATIVE entity (wallbox, generic Modbus) is byte-for-byte pure v2 as before. Proven on the REAL prod dump (throwaway restore, destroyed after): 307k v1 rows / 0 v2 rows, all 3 composed entities x 4 ranges return real buckets, and the spliced house-load integrates to 34,96 kWh = the site Historie's own `consumptionKwh` to the digit. Test: `PortalApiTest.entityHistorySplicesV1TelemetryBeforeTheV2EraForComposedEntities`.
  - **hasPv/hasStorage are CAPABILITY-based** (`UsageProfileService.signals`), the same rule `TopologyDeriver.defaultRole` uses - a hybrid is category `storage` yet MEASURES `pv_power_kw`, and the old category rule reported `hasPv:false` on every real plant, so Eigenverbrauch could never fire. `hasControllableConsumer` additionally requires a non-empty `actuate`.
  - **The DV money headline (captain-approved, portal `surface.ts`).** `marktvermarktung` composes **Einspeise-Erlös** (+ **Wert des Eigenverbrauchs** when a tariff is configured), with the steering delta as the ATTRIBUTION line under the revenue (`MoneyStream.attribution: 'steering'` → `erloesKomposition.steeringAttributionNote`). `savedEur` is a delta vs. an unregulated plant and already sits INSIDE the revenue - as a sibling summand it double-counts; as the only stream it understated Pilsting 301,46 € → 13,62 €. `moneyStreams()` dedupes per id (market and Eigenverbrauch now name the same streams).
