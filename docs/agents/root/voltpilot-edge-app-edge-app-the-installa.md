# VoltPilot Edge-App (`edge-app/`): the installable customer-side edge

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 40).


The productized two-layer edge the captain decided on (2026-07-02); one docker-compose package the customer installs on their device.
Full docs in [`edge-app/README.md`](edge-app/README.md).
It is SEPARATE from `edge/` (the thin dev Node-RED edge in the cloud-stack compose) and from `tools/edge-simulator` (the MQTT-publisher sim) - do not conflate the three.

- **Layer 2 = `edge-app/core` (Go, module `.../edge-app/core`, binary `vp-edge-core`)** - identical at every customer, the ONLY thing talking to the cloud:
  first-boot HTTPS **enrollment** (EC P-256 key on-device -> CSR -> poll; consumes the api's enrollment endpoints exactly; conflict/unknown-ref states surfaced in German), the single outbound **mTLS MQTT** link (paho; broker derives identity from the cert CN),
  **honest failure states in the enroll state machine** (`enroll.State` - so `:8484` distinguishes "broken" from "waiting for you to claim", not one cheerful "warte" for everything): `portal_nicht_erreichbar` on a dial error / timeout / 5xx during CSR upload or cert poll (a 404 stays `pending`; clears itself when the portal answers again), `geraet_fehler` on a LOCAL first-boot failure (unwritable `/data`, key/CSR build - `enrollAndConnect` retries with capped backoff instead of silently exiting the goroutine), `cloud_fehler` when the cert is on disk but `startCloud` fails (retried with backoff, distinct from a blip), and `cloud_getrennt` when a live link drops (the pairing checklist moves OFF the green `verbunden` so it agrees with the Cloud stat), plus **`geraet_entfernt` for a CONFIRMED cloud-side removal (unclaim)**: the reconcile loop escalates a SUSTAINED, uninterrupted run of definitive clean-404 "not claimed" answers from a REACHABLE portal (`enroll.UnclaimDetector`, `VP_UNCLAIM_CONFIRM_MINUTES`/`_POLLS`, default 20 min + 4 consecutive polls; dial errors/timeouts/5xx RESET the run so an outage can never trip it, and a never-claimed device never reaches the loop) - on confirmation the cloud link is torn down, the store-and-forward buffer PAUSES (`Snapshot.BufferPaused`, "Aufzeichnung pausiert" in the UI - never unbounded growth toward a dead identity), identity/keys stay ON DISK, the onboarding gate re-opens the claim step with the ref, and continued polling makes a re-claim adopt the new identity and resume normally (a same-identity answer after a false alarm also self-heals). `getCertificate` also rejects a claim response with no `mqttHost`/`mqttPort`. The dashboard's `renderPairing` maps each to a visible error box + German guidance; the "alles Weitere passiert automatisch" hero copy shows only once an inverter is configured, and a `#inverterBanner` CTA shows until then (no inverter = the Node-RED read flow is idle = no telemetry). The buffer exposes a `DataLoss()` flag (set when eviction discards NEVER-published entries during an outage that overran the retention horizon, cleared once the backlog drains) -> `Snapshot.BufferDataLoss` -> the Cloud stat warns "älteste Messwerte werden verworfen" instead of the pending count silently plateauing.
  **while-connected identity re-reconciliation** (`enroll.Enroller.Reconcile` + `agent.reconcileLoop`, `VP_RECONCILE_INTERVAL_SECONDS`, default 300 s, also nudged on every cloud disconnect): the device re-polls `GET /enrollment/{ref}/certificate` and, if the portal now reports a DIFFERENT `device_id` (an unclaim+re-claim, or a `down -v`+re-claim, mints a new device row and the api re-issues the cert against the stored CSR - same key), **adopts** the new cert/identity on disk and tears down + rebuilds the cloud link on the new topics (reconnect is mandatory - the broker enforces the cert-CN identity via its ACL; the store-and-forward buffer is stamped at publish time so pending entries flow to the new id). Without this a device that enrolls only at first boot would keep publishing under its stale persisted `device_id` forever, and the portal's Geräte tab (per-device liveness keys on `telemetry.device_id = device.id`) would read **"wartet auf erste Daten"** permanently while the site-keyed Übersicht still showed values (device-identity-drift bug). Layer-2 follow-up (NOT done, deliberately): preserving the device id across re-claim (deterministic `UUIDv5(external_ref)` or soft-delete unclaim) would remove the drift trigger, but a deterministic id makes the re-claim cert-poll hit the "unchanged id" branch that skips the ACL-grant rewrite (unclaim's `onDeviceUnclaimed` removed it) -> the cert loses broker access in prod unless claim also re-writes the grant; that expands scope into the security path, so Layer 1 (which fully fixes the symptom) ships alone.
  **store-and-forward** telemetry (segmented JSONL disk ring, default 48 h, cursor + monotonic seq persisted, ack-after-QoS1-confirm, replay oldest-first with ORIGINAL timestamps - safe because ingest is idempotent per (device, time)),
  **schedule cache + execution** (frozen `mqtt-schedule` contract; plan persisted to disk for reboot-without-network; 20-min staleness window mirrored from the contract's `x-failsafe`, ALSO bounded by plan AGE - a retained-schedule redelivery on reconnect whose `generated_at` is older than the window + 5-min slack is stale immediately, so a dead optimizer's plan can't look fresh again (plan.Parse anchors ReceivedAt to generation time; 2026-07-12 audit fix); guards clamp EVERY setpoint: rated power band, SoC bounds, observed §14a envelope on import AND export, and - when the plan carries `grid_charge_allowed=false` (EEG site, P5) OR omits the field entirely (fail-safe since the 2026-07-12 audit fix; only an explicit `true` releases it) - charge ≤ MEASURED PV production (`guards.Limits.SolarOnlyCharge`; PV-bus semantics since FK3, captain decision 2026-07-16 - the house may import its load in parallel; unknown pv then blocks charge entirely - a compliance guard never charges blind; the plan-carried posture also ANDs into the `edge/setpoint` `grid_charge_allowed` adapter gate, most-restrictive-wins with `VP_GRID_CHARGE_ALLOWED`); stale/no plan -> self-consumption fallback = PV − load, which never grid-charges by construction),
  an **embedded local MQTT bus** (mochi-mqtt in-process, topics `edge/telemetry`, `edge/setpoint` (retained), `edge/status`), and the German read-only **local energy dashboard** on `:8484` (see the dashboard bullet below; `/health` for watchdogs). Config: env > `config.json` > defaults (`config.Defaults()`); an unset ref is generated once and persisted.

- **Deye transport = pick a `communication` method: `solarman_v5` (RECOMMENDED) or `at_cli` (fallback).** The Deye WiFi datalogger (LSW3 "stick") is read the ROBUST way via the **Solarman V5 protocol** = Modbus-RTU wrapped in a Solarman-V5 frame over **TCP 8899** (what Home-Assistant/pysolarmanv5 use), NOT the flaky AT-command UDP-48899 tunnel (dongle replies from a different source port / as broadcast get dropped by conntrack behind NAT). Both methods share the SAME register maps + decode - only the transport differs (`communication: 'solarman_v5'|'at_cli'` in the config; solarman_v5 default). The V5 frame codec (frame build/parse, logger-serial LE32 embedding, V5 byte-sum checksum, embedded Modbus-RTU fn-0x03 + its own CRC16, TCP-segment reassembly) is the canonical, **offline-unit-tested** **[`edge-app/nodered/deye/solarman-v5.js`](edge-app/nodered/deye/solarman-v5.js)** (`solarman-v5.test.js`, cross-checked against independent CRC/checksum impls incl. checksum/short-frame/exception cases); the flow's *"Solarman-V5 lesen"* function node carries a **synced copy** and owns the socket (needs `functionGlobalContext.net` in `settings.js` - wired). **CRITICAL: `serial` is the DATALOGGER serial (e.g. from the AP SSID `AP_<serial>` or the logger status page), NOT the inverter serial** - the #1 config mistake. Addresses authoritative from **davidrapan/ha-solarman `deye_p3.yaml`** (+ Deye Modbus manual for PV3/PV4). **HV/LV power scale is AUTO-DETECTED, mirroring ha-solarman:** `deye_p3.yaml` gives PV Power + Battery Power a dual `scale:[1,10]` (LV=1 W, HV=10 W/decawatt) and Grid/Load NO scale (always watts); ha-solarman picks LV vs HV from the "Device" register `0x0000` (`const.py` `AUTODETECTION_DEYE`: LV `0x0005`/`0x0500`→`mod 0`→×1; HV `0x0006`/`0x0007`/`0x0600`/`0x0008`/`0x0601`→`mod 1`→×10, and `0x0008`/`0x0601` = "HV 3-Phase Inverter 20-50kw" = the exact SUN-30K-SG01HP3-EU class). `deye-decode.js` reads `0x0000`, applies the class to **PV+battery only** (never grid/load/SoC). `power_scale` is now a MANUAL OVERRIDE/fallback (an explicit `1`/`10` wins; falls back to `1` when `0x0000` is unreadable - never fabricates a class); the catalog default is `0` = auto. **Correction of an earlier overclaim:** #49 confirmed the *family selection* (`hybrid_3p` over the wrong `string` map), NOT `scale=1` on the captain's SG01HP3 - so an SG01HP3 (HV) is now correctly ×10 by auto-detect. Reads are a **sequential** per-family block loop (never two `deye` processes at once on the one logger): `hybrid_1p` one 22-reg block; `hybrid_3p` TWO blocks (the 1-reg device-identity register `0x0000` for the LV/HV scale class + the 122-reg measurement block `024B007A`); string/micro a 2-reg AC-output pair - all well under the 125-reg fn-0x03 max.   - **The machine-readable device signal it reads is the core's ungated `GET http://127.0.0.1:<VP_WEB_PORT>/health`** (`edge-app/core/internal/web/web.go`): `{ref, pairing_state, cloud_connected, uptime_seconds}` - unlike `/api/state`, `/health` returns `ref` even before the claim gate, so it is the right endpoint for a headless installer. - **Standalone updater `edge-app/update.sh` (recommended update path for a RUNNING device).** One command in the deploy dir: refreshes the compose file(s) to current AND pulls + `up -d --remove-orphans` + verifies via `/health` (PASS/FAIL with pairing/cloud state + rollback hints). It **SOURCES install.sh** for `generate_compose()`/the marker/the helpers (install.sh's `main` is guarded behind a `BASH_SOURCE` check) - ONE compose template, so it needs install.sh next to it (fails with a fetch hint otherwise). Deploy-model aware: installer-marker compose -> regenerated from the template; git-tracked compose (repo clone) -> `git pull --ff-only` (never force/stash/reset); hand-edited -> kept unless `--force-compose`. A used `docker-compose.hostnet.yml` is auto-detected via the running nodered container's `network_mode` (`--hostnet` forces it when containers are stopped) and refreshed from a template embedded in update.sh that must stay byte-identical to the repo file (drift-guarded). - **Published images are MULTI-ARCH (`linux/amd64` + `linux/arm64`).** Raspberry Pi (arm64/v8) is the primary edge target, so `.forgejo/workflows/edge-images.yaml` builds a manifest list per tag (`:latest`, `:${sha}`) for BOTH `edge-app-core` and `edge-app-nodered` - `docker pull` picks the right variant per device automatically.
