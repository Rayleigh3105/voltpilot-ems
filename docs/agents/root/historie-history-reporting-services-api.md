# Historie (history/reporting: `services/api` history package + portal "Historie" page)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 89).


The customer-facing history view (captain's decisions: **money lens leads**, private customers first, core value **Nachvollziehbarkeit** - the customer can see and verify what the system did and why).
Read-only feature: one migration, one endpoint, one portal page.

- **Telemetry rollups instead of continuous aggregates.** TimescaleDB **hard-refuses caggs on hypertables with row-level security** ("cannot create continuous aggregate on hypertable with row security", verified on 2.17.2), and `telemetry` has FORCE RLS.
  So api migration **`V20260701030000`** builds the same outcome from primitives that respect the RLS spine: plain rollup **hypertables** `telemetry_rollup_15m/1h/1d` (per-bucket energies pv/load/grid-import/grid-export/battery-charge/battery-discharge kWh + SoC min/max/last + `n_samples`), RLS-scoped exactly like telemetry, refreshed by a TimescaleDB **background job** (`add_job`, 15-min interval) running an idempotent upsert cascade (raw -> 15m -> 1h -> 1d) over a 7-day trailing window as the job owner = the Flyway superuser (bypasses RLS to aggregate all tenants).
  The migration backfills all raw history once; data arriving >7 days late needs a manual `CALL refresh_telemetry_rollups(<since>)`.
  Raw `telemetry` stays untouched (no retention - the raw corpus is future ML training data).
  Semantics live in the migration header: energy = avg(power over the bucket's samples) x bucket hours with per-sample import/export split; actual battery power derived from the power balance (`battery_kw = power_kw - load_kw + pv_power_kw`); daily buckets are **Europe/Berlin** days (the v1 platform timezone, `HistoryRange.ZONE`).
- **Endpoint** `GET /api/v1/sites/{siteId}/history?range=day|week|month|year&at=<date>` (SiteController -> `history/HistoryService` -> RLS-scoped `HistoryRepository`; foreign site 404, bad range 400; in `openapi.yaml`).
  Day = live 15-min buckets straight from raw telemetry (never behind the rollup refresh); week/month/year = the rollups, with per-bucket grid cost merged from the 15m-rollup x `day_ahead_prices` join.
  Totals formulas documented on `HistoryTotalsDto`: grid cost = 15-min import energy x matching day-ahead price; battery savings = sum(baseline - cost) over persisted `schedule` slots taking the **latest run per slot** (`DISTINCT ON (time) ... ORDER BY generated_at DESC`, so overlapping MPC runs never double-count; **null** where no plan exists); Autarkiegrad = 1 - import/consumption; Eigenverbrauchsquote = (pv - export)/pv.
  **Totals honesty (audit V2/X1/H3/H8, 2026-07-24):** the four ENERGY sums follow the cost fields' discipline - **null, never 0**, when not a single bucket carried that channel (a 0-bucket day used to return a confident `pvGenerationKwh: 0.0` next to the board's honest "noch keine Daten"), and a ratio whose numerator or denominator is unknown stays null. The ex-ante plan sum is served as **`batterySavingsPlannedEur`** (`batterySavingsEur` survives ONE release as a same-valued deprecated alias) because it is NOT measured money - the measured counterpart is `savedEur` on `/api/v1/earnings` and the two legitimately differ ~8x on the same plant/period, so any surface rendering it must say "geplant". `gridCostEur` is the REAL supply cost since Stufe 3 of the structured Bezugspreis: import energy × the same `SlotEconomics.importPriceCtSql` composition the optimizer plans with (bare spot only without any price data - byte-identical to before); the additive **`tarifArt`** + **`tarifPriced`** label it honestly (`tarifPriced=false` = the number must read "zu Börsenpreisen", true = "bewertet zu Ihrem Stromtarif"; a flat tariff prices even unpriced buckets).
  Day range additionally returns the **Tagesprotokoll** (`history/Tagesprotokoll`, pure functions: battery charge/discharge windows above a 0.1 kW noise threshold with energy-weighted avg price and avoided-cost EUR, PV peak, price extremes; plain-German server-formatted texts) and the **plan-vs-actual** trajectory (latest persisted plan value per 15-min slot).
- **Bucket -> Preis geht NUR über `repo/PriceSlots`, nie wieder über ein LATERAL pro Bucket (gemessener Defekt, Scout `vp-historie-konzept-t4` §5, behoben 2026-07-30).** Die alte Zuordnung `LEFT JOIN LATERAL (... ORDER BY (p.resolution = 'PT15M') DESC, p.ts DESC LIMIT 1)` sortiert nach einem **Ausdruck**, also kann Postgres `idx_day_ahead_prices_zone_ts` nicht zum vorzeitigen Abbruch nutzen: das `LIMIT 1` greift erst nach dem Sortieren, jeder Bucket las und verwarf ~1.400 Preiszeilen (`loops=3625`, 111.985 Buffer-Hits, **1,2 s** für ein Jahresfenster - auf dem Demo-Stack reproduziert), und dieselbe Form lief **fünfmal pro `/earnings`-Anfrage**. `PriceSlots` baut die Preisreihe **einmal** je (Zone, Fenster) als `MATERIALIZED`-CTE `price_slot(bidding_zone, slot, price_eur_mwh)` - PT60M auf Viertelstunden aufgefaltet, Gewinner je Slot per `DISTINCT ON` mit **denselben** Sortierschlüsseln - danach ist es ein Equi-Join: **~9-18 ms**, und die Kosten wachsen nicht mehr mit der Zahl der Buckets. Drei Dinge, die man dabei kennen muss: (1) die einzige Annahme ist ein **viertelstunden-ausgerichtetes Join-Raster** (Rollup-Buckets, `time_bucket`, `forecast.time` erfüllen sie; die Preiszeilen selbst dürfen beliebig liegen - ihr erster abgedeckter Slot wird abgeleitet); (2) die Auffaltung nutzt bewusst ein 4-zeiliges `VALUES` statt `generate_series` - eine SRF im LATERAL kostet ~30 µs Executor-Setup **pro Preiszeile** und misst 100 ms, wo das `VALUES` 3 ms misst; (3) das Fenster-Prädikat rechnet auf einem Bind-Parameter und braucht deshalb `?::timestamptz`, sonst hält Postgres den Platzhalter für ein `interval`. Semantik-Abnahme ist `PriceSlotEqualityTest` (Testcontainers): das alte LATERAL steht dort wörtlich als Orakel und wird Slot für Slot gegen `PriceSlots` verglichen - nur PT15M, nur PT60M, gemischt, Lücken, unausgerichtete `ts`, unbekannte Auflösung, `ts DESC`-Gleichstand, und eine Preiszeile die VOR dem Fenster beginnt (der Wächter für die 75-Minuten-Untergrenze).
- **Portal surface**: **TWO worlds, two routes** (captain structure H1, 2026-07-30; concept `data/vp-historie-konzept-t4`) — `#/anlage/{id}/messwerte` (`pages/MesswerteSection.tsx`, BASE: the energy sums + the one multi-series chart carrying PV/Haus/Netz/Batterie/Ladestand + the Messwerte-Explorer as a disclosure) and `#/anlage/{id}/erloese` (`pages/ErloeseSection.tsx`, MODE-BOUND on `surface.ts` `erloes-historie`: Stromkosten, the GEPLANTE Speicher-Ersparnis, the Speicher-&-Preis proof, Tagesprotokoll). `#/anlage/{id}/historie` redirects to `messwerte` **preserving `?m=`/`z=`/`at=`**. Both share ONE skeleton (world head with an honesty badge + one-click world switch that carries the period, sticky time bar, cards, foot card) and ONE fetch+cache (`historyCache.ts`). Seit PR D trägt die Zeit-Leiste zusätzlich den **Zeitraum-Sprung** (natives Datums-/Wochen-/Monatsfeld + Jahresauswahl + der wiederverwendete `MonthStrip` ohne erfundene Werte), das **Δ zur Vorperiode** (ein zweiter Abruf desselben Endpunkts durch denselben Cache — nie gegen eine erfundene Null, gewertet nur wo die Richtung eindeutig ist) und die **Datenabdeckung**. Derivation rules, honesty badges (Gemessen · Bewertet · Geplant) and the measured CSS/ECharts footguns: `frontend/portal/AGENTS.md` "Die Historie sind ZWEI WELTEN".
- **Datenabdeckung des Zeitraums (F4/P7, additiv auf der `/history`-Antwort):** `HistoryDto.coverage` (`HistoryCoverageDto`) beantwortet, was die Seite bisher verschwieg — ab wann es überhaupt Daten gibt und wie viel des Zeitraums wirklich gemessen ist. Es ist eine **EIGENE billige Abfrage** (`HistoryRepository.coverage`: `min/max/count` + `lag()` auf `telemetry_rollup_15m`, RLS-gefenced wie alles hier), bewusst NICHT aus dem Datenblock abgeleitet — sie bleibt damit unabhängig von der Reihe UND von der Preisreihe (`PriceSlots`), berührt deren Equi-Join also nicht. Gezählt werden **Viertelstunden** (`resolutionMinutes`), nicht Anzeige-Buckets: so entsteht die Messreihe, egal ob die Seite Tage oder Stunden zeichnet.
  Die Arithmetik ist die reine, immer laufende `HistoryService.coverage(row, window, now)`: **erwartet wird erst ab der ersten je gemessenen Viertelstunde** (ein Kalenderjahr einer im Juni ans Netz gegangenen Anlage ist nicht zu 45 % lückenhaft — es gab sie vorher nicht; genau dafür reist `firstDataAt` mit), das Ende liegt eine Rollup-Kadenz (15 min) **vor jetzt** (eine gerade beendete Viertelstunde ist keine Lücke, sondern noch nicht verdichtet), `measured` wird auf `expected` gedeckelt (nie über 100 %), und `gaps` zählt innere PLUS Rand-Fehlstellen. **Kein Prozentsatz im Vertrag** — die Zähler sind die Tatsache, die Formulierung (inkl. „nie auf 100 % aufrunden") gehört der Oberfläche. `null`, wenn die Anlage nie eine Viertelstunde gemessen hat; dokumentierte Grenze: gezählt wird die v1-Messreihe, eine rein v2-native Anlage liefert deshalb keine Abdeckung statt einer behaupteten (eine migrierte ist nicht betroffen — der Fan-out des Writers speist beide Reihen).
- **Die Ereignis-Spur des Verlaufs (F6, additives `HistoryDto.events`) — was den Ausreißer ERKLÄRT, in JEDEM Zeitraum.** Das `Tagesprotokoll` bleibt unverändert die Liste der GEWÖHNLICHEN Ereignisse eines Tages; die neue Spur (`history/Ereignisse.java`, rein wie `Tagesprotokoll`) trägt ausschließlich das Auffällige: `negativpreis` (Preisreihe unter null), `abregelung` (GEPLANT aus `schedule.curtail_kw` — der Text sagt „eingeplant"), `netzgrenze` (§ 14a aus `telemetry.grid_limit_kw`), `netzladen` (gemessen), `datenluecke` und `geraet-still`. Der Vertrag ist bewusst schmal (`HistoryEventDto`: type/start/end/text): **`text` ist die Aussage OHNE Zeitangabe** — die Zeit steht in `start`/`end` und wird von der Oberfläche zeitraumgerecht davorgesetzt. Fenster entstehen durch Verschmelzen aufeinanderfolgender Viertelstunden; je Art werden höchstens `MAX_PER_TYPE` (20) ausgeliefert, die LÄNGSTEN zuerst.
  Vier schmale, additive Abfragen liefern je Viertelstunde EINE Tatsache (`HistoryRepository.negativePriceSlots`/`curtailSlots`/`gridLimitSlots`/`gridChargeSlots` + `dataGaps`, alle RLS-gefenced wie der Rest); Fenster, Texte und Obergrenzen rechnet die reine Klasse — dasselbe Muster wie `CoverageRow`. Drei Entscheidungen, die man kennen muss:
  - **§ 14a wird nur für Tag und Woche ausgewertet** (`Ereignisse.evaluatesGridLimit`): `grid_limit_kw` steht NUR in der rohen `telemetry`, die Rollup-Kaskade führt die Spalte nicht — ein Jahresfenster wäre ein Scan über Millionen Rohzeilen. **Die Oberfläche muss das aussprechen**, sonst läse sich das Fehlen eines Markers als „keine Netzgrenze"; der Zwilling ist `frontend/portal/src/historieEreignisse.ts` `spurHinweis` — beide zusammen ändern.
  - **Netzladen wird nur behauptet, wo es bewiesen ist:** die Viertelstunde muss PV UND Ladung UND Netzbezug gemessen haben (`pv_kwh IS NOT NULL`), sonst wäre jede Ladung einer PV-losen Messreihe „aus dem Netz". Der genannte Wert ist die vorsichtigere der beiden Schranken (`least(charge − pv, import)`).
  - **Die Lücken-Marker stimmen mit der Zeit-Leiste überein:** `HistoryService` holt die Abdeckungs-Rohzahlen EINMAL und liest sie zweimal — die Zeit-Leiste zählt daraus die Fehlstellen, die Spur setzt ihre Rand-Marker auf dieselben Grenzen. Ein Schluss-Rand ist `geraet-still` statt `datenluecke`, wenn die Anlage auch NACH diesem Zeitraum nichts mehr gemessen hat (`lastInWindow == siteLast`) — der Unterschied zwischen „damals fehlte etwas" und „es kommt gerade nichts".
