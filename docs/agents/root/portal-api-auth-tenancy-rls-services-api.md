# Portal API: auth, tenancy & RLS (services/api)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 6).


The user-facing spine. See `services/api/README.md` for the endpoint list.

**Auth (Keycloak OIDC).** The api is an OAuth2 resource server validating realm `voltpilot` JWTs. The frontend logs in via the public `voltpilot-frontend` client (Authorization Code + PKCE); every token carries a `tenant_id` claim (a Keycloak user attribute, mapped on both clients).

- **Issuer/JWKS split (the "issuer trap" fix).** `KC_HOSTNAME=http://localhost:8081` pins Keycloak's public URL, so browser- and script-minted tokens all carry `iss=http://localhost:8081/realms/voltpilot`. The api validates that issuer (`OIDC_ISSUER_URI`) but fetches signing keys from the compose-internal `OIDC_JWK_SET_URI=http://keycloak:8080/.../certs` - so it never needs to resolve `localhost:8081`. Spring's resource server accepts both `issuer-uri` + `jwk-set-uri` set together: keys from the latter, `iss` checked against the former.
- OIDC is ON by default (fail-secure); offline unit tests and broker-less dev setups opt out explicitly with `VOLTPILOT_SECURITY_OIDC_ENABLED=false`; compose sets it `true` explicitly. CORS origins via `VOLTPILOT_CORS_ALLOWED_ORIGINS` (default `http://localhost:5173`).
- **Dauer-Login.** Beide Realm-Importe tragen `rememberMe: true` + die vier Sitzungsdauern (12 h idle / 24 h max; mit angehaktem "Angemeldet bleiben" 90 / 180 Tage) - `accessTokenLifespan` bleibt 900 s, die SSO-SITZUNG ist das Langlebige, nicht das Token. Das Häkchen auf der Anmeldeseite ist beim ersten Aufruf VORAB gesetzt und eine Abwahl überlebt den Fehlversuch; die Regel und ihre zwei Fallen stehen am Kästchen in `deploy/keycloak/themes/voltpilot/login/login.ftl`, die Zahlen samt Begründung in `infra/prod/keycloak/README.md`. ⚠ Wie jede Realm-Änderung erreicht das eine BESTEHENDE Keycloak-Instanz nie von selbst (`--import-realm` überschreibt einen existierenden Realm nicht) - der Live-Realm wurde am 24.08.2026 von Hand nachgezogen.

**Multi-tenancy via Postgres RLS.** `TenantFilter` reads `tenant_id` from the JWT into a request-scoped `TenantContext`; `TenantAwareDataSource` stamps it onto each borrowed connection via `set_config('app.tenant_id', ...)` and RESETs on return to the pool. RLS policies (migration `V2`) scope every table (`tenant`/`site`/`device`/`asset`/`telemetry`) with `tenant_id = current_setting('app.tenant_id')`. No tenant set => **default-deny** (zero rows).

- **Two DB roles, on purpose.** The compose `POSTGRES_USER` (`voltpilot`) is a Postgres **superuser**, and superusers BYPASS RLS. So the api connects at runtime as a dedicated **`voltpilot_app`** role (NOSUPERUSER/NOBYPASSRLS, created by Flyway `V1` with a placeholder password from `APP_DB_PASSWORD`) for which RLS is enforced. **Flyway** runs as the superuser (`spring.flyway.user`) to own the schema, create the role/policies, and seed both tenants (bypassing RLS). Tables are also `FORCE ROW LEVEL SECURITY` so even the owner is scoped.

**Migrations (Flyway).** In `services/api/src/main/resources/db/`: `migration/` = prod-safe core (`V1` idempotent schema + app role, `V2` RLS, `V4` cross-tenant admin role - see the admin section; **V3 is skipped**, reserved by `services/forecast`); `dev/` = the DEV-ONLY seed (`V100`, two tenants + demo telemetry), added to `spring.flyway.locations` only under the `local` profile (compose sets `SPRING_PROFILES_ACTIVE=local`; tests activate it too). `baseline-on-migrate` + `baseline-version=0` let the idempotent `V1` run over the compose bootstrap DB. **An applied `V*.sql` migration is immutable - never edit one that may already be applied on a live DB, not even a comment: Flyway fingerprints every applied migration and fails startup validation on a checksum mismatch (fresh CI/Testcontainers DBs never compare, so the break only surfaces on a long-lived DB like prod).** **⚠ And never RENUMBER one either: the version is the AUTHORING time, the order a long-lived DB sees is the MERGE order of the PR, and parallel branches make those diverge - which is why `spring.flyway.out-of-order: true` ships (prod incident 2026-08-26, see the hardening bullet below). Consequence for every new migration: it must stand on its own against the schema as of ITS OWN version, because version order (fresh DB) and merge order (prod) are BOTH valid run orders, and no test can check that statically.** **Dev seed migrations must be EXISTENCE-GUARDED (real outage, 2026-07-07):** a deployment running `SPRING_PROFILES_ACTIVE=local` executes `db/dev/` too, and the demo tenant row may be ABSENT there (offboarded via the admin console, or a DB that never got V100's seed) - an unguarded FK insert (`tenant_id = 00000000-...-0001`) then fails with SQLSTATE 23503 and Flyway aborts api startup. Every dev seed that references the demo tenants/sites must no-op when the referenced tenant is missing (`DO $$ ... IF NOT EXISTS (SELECT 1 FROM tenant WHERE id = ...) THEN RETURN; END IF; ... END $$` - the V20260706020000/030000 pattern; V100 creates its own tenants and the provisioned-device seed is tenant-free, both fine). Regression guard: `DevSeedGuardTest`. Two facts checked live: Flyway-on-Postgres rolls a failed migration back WITHOUT recording a `success=false` history row, so a crash-looping deployment resumes cleanly once the fixed file ships; editing a FAILED (never-applied) migration is checksum-safe there, but already-seeded long-lived dev volumes need `flyway repair` or `down -v` after such an edit.

**Prod-deploy Flyway hardening (recurring footgun, permanently fixed 2026-07-08).** A long-lived VM that ran `SPRING_PROFILES_ACTIVE=local` has the `db/dev` seeds recorded in `flyway_schema_history`; editing one of them (the FK existence-guard hotfixes above) changed its checksum and Flyway's default startup validation ABORTED the api boot (checksum mismatch) - the captain's prod deploy bricked repeatedly, each time needing a manual DB repair. Four layers now make prod boot reliably, and the first needs NO human at the DB:

1. **Self-healing migration strategy (PRIMARY, `config/SelfHealingFlywayMigrationStrategy` wired by `config/FlywayConfig`).** A `FlywayMigrationStrategy` bean that keeps STRICT validation on the happy path but, on a `FlywayValidateException`, logs a loud `WARN` naming the drifted versions, runs `flyway.repair()` (realigns recorded checksums to the shipped migrations - re-executes NOTHING) and retries `migrate()` once. **Only for drift repair() can actually fix** - the out-of-order class is split off and rethrown at once, see layer 4. So deploying the new image heals an existing `local`-profile VM's dev-seed drift automatically. The catch is deliberately narrow: only a *validation* failure repairs; a genuinely broken migration (SQL error) is a different exception, uncaught, and still fails the boot. **Residual risk (accepted):** repair would also accept an accidental edit of an already-applied CORE (`db/migration`) migration with only the `WARN` - mitigation is the never-edit-applied rule + review; fresh CI/Testcontainers DBs never drift so they always run a plain strict migrate. Proven by `SelfHealingFlywayMigrationStrategyTest` (drift → repair+retry+WARN; healthy fresh DB → plain migrate, `repair()` never called).
2. **`spring.flyway.ignore-migration-patterns: "*:missing"` (base `application.yml`, hygiene).** Tolerates applied-but-now-absent migrations, scoped to `:missing` ONLY (does NOT loosen checksum validation), so a VM moved OFF the `local` profile boots cleanly even though the `db/dev` rows are now off-classpath. Proven by `FlywayIgnoreMissingBootTest` (blank-profile config validates over a DB with dev migrations recorded; a genuine checksum mismatch STILL fails at the Flyway-config level).
3. **Blank profile is the PRODUCTION default** (`docker-compose.prod.yml` `SPRING_PROFILES_ACTIVE=${SPRING_PROFILES_ACTIVE:-}`, `.env.prod.example` blank). Prod runs ONLY `db/migration`; `local` is a DEV/demo-only opt-in that additionally runs `db/dev`. No `@Profile`-gated beans exist in api main, so dropping `local` removes only the dev-seed locations - OIDC/RLS/feeds/admin are all env-driven. Full operator playbook + break-glass in [`docs/deploy.md`](docs/deploy.md) "Spring profile: production is blank, demo is `local`".
4. **`spring.flyway.out-of-order: true` (prod outage 2026-08-26).** A migration whose version sits BELOW the already-applied high-water mark is APPLIED instead of refused. Cause: the version is the AUTHORING time, the arrival is the MERGE order - `V20260846010000` (#509) merged after `V20260847000000` (#516), `V20260842000000` (#512) after `V20260844000000` (#507). Prod aborted with `Detected resolved migration not applied to database: 20260846010000`, twelve migrations stayed unapplied, the optimizer wrote into a non-existent `schedule.unplanned_load_discharge`, and the fleet went a night without a Fahrplan. **⚠ `repair()` provably CANNOT fix this** (it only touches migrations that ARE applied), so layer 1 no longer pretends to: it splits the two drift classes and, for an out-of-order arrival, logs an ERROR naming the migration + the lever and rethrows at once instead of a misleading "self-healing" line in front of the same crash. Checksum/description/type validation is untouched; break-glass `SPRING_FLYWAY_OUT_OF_ORDER=false`. Proven by `FlywayOutOfOrderBootTest` (mechanism + the incident shape over the REAL 119-migration chain, both non-vacuous), `SelfHealingFlywayMigrationStrategyTest` and the Docker-free `MigrationHygieneTest` - which also carries the two collisions out-of-order can no longer catch implicitly: a DUPLICATE version (in the source tree AND in `target/classes`, i.e. the documented stale-`git mv` trap) and the same column added twice without `IF NOT EXISTS`.

**Self-registration (`POST /api/v1/registration`, public).** The front door of customer onboarding: one unauthenticated request creates a `B2C` tenant (name = the customer's person/company name) **and** its Keycloak login (username = lowercased email, `tenant_id` attribute via `KeycloakAdminClient`; no realm role since UEMS AP-03 IP-3), so the standard OIDC+RLS spine isolates self-registered customers exactly like admin-provisioned ones (`RegistrationController`; tenant row via the BYPASSRLS `TenantRepository` since there is no caller tenant yet). If Keycloak refuses (email taken -> 409) or is unreachable, the tenant is deleted again (compensating rollback, `TenantRepository.deleteById`; best-effort - a failed cleanup delete is logged and never masks the original error). Toggle: `VOLTPILOT_REGISTRATION_ENABLED` (default `true`; setting `false` removes the endpoint via `@ConditionalOnProperty`). Two security notes: (1) the `secured` chain permits `POST /api/v1/registration` AND the ERROR dispatch (`dispatcherTypeMatchers(ERROR)`) - without the latter, Spring Security 6 masks every anonymous 400/409 as 401 because the `/error` forward is itself access-controlled; (2) anonymous volume is bounded by `RegistrationRateLimiter` - a sliding window per client address (taken from the `X-Forwarded-For` proxy chain honoring only the configured number of own proxy hops, `rate-limit.trusted-proxies` - default 0 = socket address only, prod compose sets 2 for external proxy + frontend nginx; earlier header entries are client-supplied and ignored) plus a global cap, defaults 10/client + 100 total per hour (`voltpilot.registration.rate-limit.*` / `VOLTPILOT_REGISTRATION_RATE_LIMIT_*`), refusing with 429 BEFORE any tenant/Keycloak work (portal maps it to German "später erneut versuchen" copy); state is in-memory per api instance, and email verification/captcha remain known future work. Portal: the login screen offers "Konto erstellen" (`App.tsx` `RegisterForm`, posts via the token-free `register()` in `api.ts` - deliberately not `request()`, whose token refresh would redirect anonymous visitors to Keycloak), then **signs the customer straight in** (seamless auto-login, below); the "Jetzt anmelden" screen with `login(loginHint)` remains only as fallback when the direct grant is refused (e.g. an older realm import). The form itself is lockout-hardened (there is NO self-service password reset without SMTP, so an unseen password typo would otherwise cost a support call - support recovers via the admin reset-password lever, see the admin-endpoints section): show/hide password toggle (`.vp-pw-labelrow`), per-field inline German errors shown on blur or on an invalid submit (which also focuses the first invalid field - the submit button is never silently disabled), a live "Noch N Zeichen" -> green-check password-length hint, a real `<form>` so Enter submits, `autoFocus` + `autoComplete` (`name`/`email`/`new-password`); the design-system `Input` forwards its ref to the native input for this. Proven e2e by `RegistrationApiTest` (real Keycloak + TimescaleDB: register -> login via the PUBLIC frontend client's direct grant (the exact auto-login call) -> create site -> claim device without an operator; duplicate email 409 without orphan tenant; bean-validation 400s).

**Seamless post-registration auto-login (no second credential entry).** The customer just typed email + password into the registration form, so the portal never sends them to the Keycloak login page to retype them: `loginWithCredentials()` in `auth.ts` mints tokens at the token endpoint (`grant_type=password` on the public `voltpilot-frontend` client - `directAccessGrantsEnabled=true` in BOTH realm imports, dev + prod), stores them in `sessionStorage` (`vp.auth.tokens`), and reloads the SPA; `initAuth()` then re-validates stored tokens via a refresh grant (guaranteed-valid before injecting, so keycloak-js `init` is never called twice) and boots with `init({token, refreshToken, idToken, checkLoginIframe: false})` straight into the onboarding wizard. `onAuthRefreshSuccess` keeps the store current so a mid-onboarding page reload stays signed in; without stored tokens, `initAuth()` is byte-identical to the old `check-sso` path. **Since 2026-08-07 that store has a SECOND feeder: a normal Keycloak login (Authorization Code + PKCE) is remembered the same way**, so every page load after the first takes this one-refresh path instead of three consecutive Keycloak round trips - measured 1.099 → 379 ms on the auth section alone (details + the per-tab scope + the two-token-POST floor in `frontend/portal/AGENTS.md`). Two caveats: (1) the STORE lives in the tab (sessionStorage) and ends with it, and `login()`/`logout()` clear it - on the registration path there is additionally no Keycloak SSO cookie at all, while after a normal login one exists but this path deliberately does not depend on it; (2) ROPC on a public client is deliberate here (the credentials come from our own registration form seconds earlier) but it widens the token endpoint's brute-force surface - registration itself is rate-limited (see above), and BOTH realm imports enable Keycloak brute-force detection (`bruteForceProtected`, temporary lockout: 10 failures -> 60s wait escalating to 15 min, never permanent; support lifts a lock - and recovers a forgotten password - via "Passwort zurücksetzen" on the Benutzer page (see the admin-endpoints section; the reset clears the attack-detection lock too), so password guessing at the token endpoint locks the account temporarily while the right owner is never stranded. Proven by `RegistrationApiTest.passwordGuessingAtTheTokenEndpointLocksTheAccountTemporarily`; like every realm change, it reaches an EXISTING Keycloak volume only after a fresh import (or a one-time admin-console edit).

**Site creation ("Variante C": both admin- and customer-created).** A site (Standort) is created two ways, and neither lets the client pick the tenant:
- **Customer, tenant-scoped:** `POST /api/v1/sites` (`SiteController.createSite`) inserts a site for the CALLER's tenant. `tenant_id` is taken from `TenantContext` (the JWT `tenant_id` claim), **never from the body**, and the existing `site` RLS `WITH CHECK` (migration `V2`, which already covers INSERT - a single policy applies to ALL commands) both permits the write and guarantees the row lands in the caller's tenant. So a crafted foreign `tenant_id` field in the body is simply ignored - **no new migration was needed** (the app role already has `INSERT` on `site` from `V2`). This closes the onboarding dead-end: a fresh customer makes a site here, then the "claim device" dropdown is populated. Reads/creates go through the RLS-scoped `SiteRepository` (`.create(...)`).
- **Admin, cross-tenant:** `GET/POST /api/v1/admin/tenants/{tenantId}/sites` (`AdminController`, platform-admin-gated) via `AdminSiteRepository` bound to the `voltpilot_admin` BYPASSRLS `adminJdbcTemplate` (same pattern as `TenantRepository`). The tenant comes from the **path** (validated to exist), never from body data - the only cross-tenant site write path.
- `CreateSiteRequest` DTO validates: name `@NotBlank`, `biddingZone` `@Pattern(DE-LU|AT|CH)` (defaults `DE-LU`), lat/lon range-checked (`-90..90` / `-180..180`, optional; needed for the weather forecast). Kept in `docs/contracts/openapi.yaml`. Portal: the customer empty-state offers a "Standort anlegen" form (`App.tsx` `CreateSiteForm`) so onboarding never dead-ends, plus an "add further site" form; the admin console has a per-tenant `SitesPanel` (`admin/AdminApp.tsx`).

**Device claiming** (`POST /api/v1/devices/claim`) is one insert into the caller's tenant, made typo-proof and repeat-proof for the onboarding path: the controller **canonicalizes** `externalRef` (trim; sticker IDs with case-insensitive `VP-` prefix are uppercased - `DeviceController.canonicalExternalRef`; non-sticker refs like the dev-seeded `demo-inverter-01` pass through untouched), and the claim is **idempotent within the tenant** - re-claiming a ref the caller already owns (wizard restart, double submit) returns **200 with the existing device** at its original site (RLS-scoped `DeviceRepository.findByExternalRef`), never a conflict. `external_ref` stays **globally unique**, so a device owned by ANOTHER tenant (which RLS hides) still fails the unique constraint -> HTTP 409 (the portal's "anderes Konto … Support" copy is therefore truthful); a site outside the tenant -> 404. The portal mirrors the canonicalization as-you-type (`normalizeDeviceIdInput` in `src/anlageFlow.ts`, reused by the claim drawer and the admin registry page) and tells an already-owned re-claim apart by the returned device id. Proven by `PortalApiTest.claimIsIdempotentPerTenantAndCanonicalizesStickerIds`.

**Provisioned-device registry (sticker claims are gated).** Sticker IDs (canonical `VP-` prefix) must exist in the global `provisioned_device` table (api migration `V20260702020000`; manufacturing data, so deliberately NO tenant_id/RLS - like `day_ahead_prices`; the app role is SELECT-only, writes are revoked) or the claim fails fast with **HTTP 422** instead of creating a ghost device that would "wait for first data" forever; a provisioned claim inherits the registry's `kind`. Non-sticker refs (dev seeds, integrations, `tools/pki/provision-device.sh` with non-VP refs) stay ungated. Operators register manufactured IDs via `GET/POST /api/v1/admin/provisioned-devices` (platform-admin-only; POST canonicalizes, requires the `VP-` prefix, and is idempotent - re-registering returns 200 with the existing entry; the listing joins `device`/`tenant` cross-tenant via the BYPASSRLS `AdminProvisionedDeviceRepository` to show who connected each device) and through the unified shell's "Geräte-Registry" page (`pages/admin/GeraeteRegistryPage.tsx`, Plattform nav group). Dev sticker IDs (`VP-DEMO-0001..3`, `VP-E2E-0001`) come from the DEV-ONLY migration `db/dev/V20260702020100` - date-versioned, NOT an edit of `V100`, because editing an applied migration breaks Flyway checksum validation, and a plain `V101` would sort BEFORE the date-versioned registry table and fail. Both portal claim forms map 422 to "Diese Geräte-ID ist uns nicht bekannt … Aufkleber". Proven by `PortalApiTest.unknownStickerIdIsRejectedInsteadOfCreatingAGhostDevice` and `AdminApiTest.adminProvisionsStickerIdsWhichGateAndInformCustomerClaims`; `RegistrationApiTest` provisions its device through the admin API first, journey-true. The gate composes with zero-touch provisioning: the claim endpoint still pushes the retained `provision/{ref}/config` for a registered sticker ref (canonical uppercase topic), proven by `ProvisioningClaimTest.registeredStickerRefClaimPublishesRetainedProvisioningConfig`.

**Self-generated edge refs are check-digit-gated too (the SECOND claim gate).** The shipping customer Edge-App, with no configured reference, generates its own `edge-` ref and shows it on its `:8484` web app for the customer to type - a `VP-` sticker gate does not apply. To stop a one-character typo silently creating a permanent ghost device, the generated ref now carries a trailing **check character**: `edge-` + 6 body chars + 1 check char (a position-weighted mod-31 checksum over the body, alphabet `abcdefghjkmnpqrstuvwxyz23456789`, no 0/O/1/l/i lookalikes). The generator (`edge-app/core/internal/agent/agent.go` `newGeneratedRef`/`refCheckChar`) and the api validator (`services/api/.../web/EdgeRef.java`) **MUST stay byte-identical** - the Go `ref_test.go` and `EdgeRefTest` pin the shared vectors (e.g. body `abcdef` -> check `j`, so `edge-abcdefj` is valid) from both sides. `DeviceController.claim` rejects a mistyped generated ref with **422** exactly like the sticker gate. Crucially the gate is NOT "any `edge-` prefix": `EdgeRef.isGeneratedFormat` matches only `edge-` + **6..8 pure-alphabet** chars (a generated ref plus a single-char edit), so free-form/dev refs with hyphens or out-of-alphabet chars (`edge-fresh-01`, `edge-inverter-42`) stay **ungated** for backward compatibility; already-claimed refs short-circuit before the gate via the idempotent `findByExternalRef`. `canonicalExternalRef` now case-folds BOTH prefixes (`VP-` uppercase, `edge-` lowercase) so a mobile keyboard's `autoCapitalize` can't split one device into two rows; the portal mirror `normalizeDeviceIdInput` matches. Both portal claim UIs (`components/AnlageFlow.tsx` `GeraetStep`, `DeviceDrawers.tsx` `AddDeviceDrawer`) share ONE label/placeholder/help (`DEVICE_ID_FIELD`) + one 422 message (`DEVICE_ID_UNKNOWN_MSG`, both in `src/anlageFlow.ts`) - the former "Aufkleber vs Typenschild vs Web-App" mismatch that fed the typo risk is gone. Proven by `PortalApiTest.mistypedGeneratedEdgeRefIsRejectedWhileTheValidRefClaims`. **Ops visibility:** enrolled-but-unclaimed devices (a device uploaded an enrollment CSR but no matching `device` row exists - the typo's other half, otherwise invisible) surface at `GET /api/v1/admin/enrollments/pending` (`AdminEnrollmentRepository`, BYPASSRLS admin datasource, `LEFT JOIN device WHERE d.id IS NULL`; the device-facing enrollment poll stays opaque). The ingest provisioning resolver (`ProvisioningHandler.canonicalRef`) canonicalizes the ref for the device lookup like the claim path (a lowercase `VP-` hello now resolves the uppercase-stored row) but still replies on the ORIGINAL topic (MQTT topics are case-sensitive).
