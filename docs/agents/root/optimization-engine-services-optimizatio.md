# Optimization engine (`services/optimization`)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 77).


The product's heart: a deterministic battery-dispatch MILP (Pyomo + HiGHS) in MPC style - rolling **24h horizon, 15-min slots**, re-planned **every 15 min** per site with a battery asset. **Predict-then-optimize** (captain's long-term direction is ML forecasting): forecasting stays a separate, swappable layer; the optimizer only consumes slot-aligned price/forecast series, so learned models later replace the baselines without touching it. Full detail in `services/optimization/README.md`.

- **Inputs per site** (`inputs.py`): battery params from `asset` (capacity/max charge/max discharge existed since V1; **`roundtrip_efficiency_pct`** added by api migration **`V20260701020000`**, dev batteries seeded at 92%), day-ahead prices from `day_ahead_prices` (PT60M rows are expanded to quarter hours; horizon truncates to priced coverage, < 4h skips the site), load/PV forecasts from the `forecast` hypertable - **reading ONLY the ACTIVE model's rows** (`VOLTPILOT_ACTIVE_LOAD_MODEL`/`VOLTPILOT_ACTIVE_PV_MODEL`, defaults = the baselines; see "Shadow-mode forecasting") and **falling back to the persistence baseline over the last 3 days of telemetry when no stored run covers the horizon**, REUSING `voltpilot_forecast` (`fallback.py`; sibling path dep `pip install -e ../forecast`, the Docker build context is therefore the REPO ROOT), latest `soc_pct` + observed `grid_limit_kw` from telemetry - **each behind a FRESHNESS window (F4/P4 fix, optimizer-redesign Stage 1):** a reading older than its window (`OPTIMIZER_GRID_LIMIT_MAX_AGE_MINUTES` default 60 / `OPTIMIZER_SOC_MAX_AGE_MINUTES` default 120; `config.py`, garbage env fails loudly) is IGNORED with a logged warning - a stale §14a reading means "no active limit" (a dimming event is temporary; before this, ONE old reading capped every future plan forever and could force 67% PV curtailment at positive prices), a stale SoC falls back to the 50% default, never yesterday's value. - **MILP** (`solver.py`): **market-revenue objective (P1, optimizer-redesign Stage 2 - the core)**: minimize `sum((import_price_t * import_t − export_value_t * export_t) * dt)` **plus PRICED battery wear** (P2, Stage 1): `c_wear/2` per AC-side kWh of charge AND discharge, where `c_wear` = the asset's wear cost per kWh cycled (`asset.wear_cost_ct_per_kwh`, nullable, api migration `V20260710000000`; NULL → env `OPTIMIZER_WEAR_COST_CT_PER_KWH`, default 4.0 ct ≈ 250 €/kWh replacement ÷ 6,000 LFP cycles - derivation in `config.py`). A cycle now needs `eta²·p_discharge − p_charge > ~38 EUR/MWh` at the default (kills the pre-P2 ~3-cycles/day micro-cycling); spent wear is persisted per slot as `schedule.wear_cost_eur` (NOT folded into `cost_eur` - honest net savings = baseline − cost − wear, consumers read it in a later stage). **Asymmetric pricing (`pricing.py`, replaces the symmetric bare-spot F1 bug):** `import_price_t` per `site.tarif_art` (`dynamisch` = spot + Aufschlag, `fest` = flat retail, `ohne` = spot) - **since the structured Bezugspreis (Stufe 1, report vp-nacht-bezug-e7 §3.1)** a maintained **`site_supply_price`** row (api migration `V20260729000000`, one row per site, RLS like `site`: Netzentgelt-AP/Stromsteuer/Konzession/Umlagen-as-ONE-sum/Vertriebsaufschlag ct netto + `ust_pct`) switches `dynamisch`/`ohne` to `(spot + Σ Komponenten netto) × (1 + USt)` (USt covers the SPOT share too), REPLACING the Sammelaufschlag; `fest` stays all-in and IGNORES a maintained row (WARN "fest gewinnt, nichts doppelt"); `dynamisch`+NULL-Aufschlag now WARNs loudly (the S1 night-discharge symptom fix) instead of silently pricing bare spot. **Rollout rule (golden-pinned): NO row + flag off = the exact legacy model, byte-identically** - `tests/test_golden_cooptimizer.py::test_supply_price_rollout_is_byte_identical_without_a_maintained_row` reproduces every golden fixture's committed import series through `import_prices`; a degenerate all-NULL-components row counts as no row. Grid balance: import − export = load − pv + **curtail** + charge − discharge; constraints: SoC dynamics with sqrt-split round-trip efficiency, SoC bounds (5-95% platform default), charge/discharge power caps, **curtailment bounded `0 <= curtail_t <= pv_t`** (only ever a REDUCTION of feed-in; economics now key on the EXPORT VALUE, which fixes F6: a pre-2025 feste-Vergütung plant NEVER curtails at negative spot, a DV plant still does), **§14a `grid_limit_kw` as a hard cap on import AND export**, **the FK1 static feed-in cap `site.max_feed_in_kw` as a hard cap on EXPORT ONLY** (nullable > 0 site master data, api migration `V20260716000000`, from the captain's Excel reference spec "Max Einspeisung am Netzpunkt"; on `SiteDto` + create/update requests - null on update KEEPS the stored value, the netzladenErlaubt COALESCE pattern - and edited in the portal's Vergütung & Tarif form + the create flow's Feineinstellungen; in the solver it is deliberately in BOTH builds, i.e. NOT dropped by the infeasible-§14a fallback, because curtailment can always zero the export so it can never cause infeasibility - a 100-kW-PV plant on a 75-kW connection now plans capped export + curtailment/charge; when both caps exist the tighter wins on export, import is NEVER touched by it; `tests/test_excel_spec_day.py` additionally pins the whole Excel reference day: matched config → objective 28.8797 € + the night-discharge/midday-full-charge/evening-discharge structure), and a **terminal ENERGY VALUE instead of the old hard `soc_end >= soc_start` floor (P3, Stage 3)**: the objective credits `V_end * (soc_end - soc_start)` per stored kWh; `OPTIMIZER_TERMINAL_VALUE_CT_PER_KWH` pins a fixed platform value instead. The old floor froze an EEG battery on every low-PV day (critique F3: no surplus -> nothing may charge -> nothing was allowed to discharge, all winter) and forced merchant end-of-horizon buy-backs; now a peak above V_end discharges (incl. energy stored BEFORE the horizon - deliberate, that IS the fix) and a trough/cheap tail below it holds (no dump-to-earn). **`V_end` is a REPLACEMENT cost, not a use value (fix 2026-07-27, scout `vp-fahrplan-idle-n7`; THE ONE derivation is `domain.derive_terminal_value_eur_per_kwh`, shared by the v1 input AND the co-optimizer's per-storage twin - never re-copy it).** It anchors on a low quantile (default 30th pct, `OPTIMIZER_TERMINAL_VALUE_QUANTILE`) of the per-slot REFILL price - `min(import_price, export_value)` where the grid may charge the battery; in EEG mode (only PV may charge) the slot entry splits since S2 (report vp-nacht-bezug-e7 §1.5, 2026-07-29): `export_value` where the slot HAS PV surplus (a refill is on offer, its cost the forgone feed-in), `import_price` where it has none (nothing to refill from - the stored kWh serves the house, worth the avoided Bezug; fixes the winter/bad-weather sell-out where plans dumped the battery at 0.4-6 ct into the last horizon hours while tomorrow's all-in import costs 30+ ct; on surplus-rich horizons the low quantile still lands in the export range, so sunny-day plans are unchanged - the golden suite drifted ZERO slots) - then scales down by the free-PV refill the horizon already offers (surplus the battery could absorb in slots whose export value is <= 0, against its usable band; full coverage -> 0) and is finally held strictly below the BEST in-horizon use value by `TERMINAL_VALUE_MARGIN_EUR_PER_KWH`. **KAPPEN-BEWUSST since the Pilsting scout `vp-verkauf-praemisse-s8` §1.4 (Fix c):** with a maintained `max_feed_in_kw`, surplus BEYOND the cap is not exportable, so a beyond-cap surplus slot's refill entry drops to `min(export_value, 0)` (EEG; the merchant `min` gains the free `0` channel) and the beyond-cap PORTION counts as free refill at POSITIVE prices too - both directions previously OVERSTATED V_end on capped plants (plan held/charged too much, sold too little); without a cap, or with one the surplus never reaches, the derivation is byte-identical (`tests/test_terminal_value.py` FK1 section). The api's `SlotEconomics.storedEnergyValuesCtKwh` forward best-USE approximation stays deliberately cap-blind - it is only the fallback for pre-Fahrplan-Warum rows (the persisted exact λ has precedence and is cap-honest automatically). **The bug this fixed, worth knowing because the shape recurs:** anchoring on the best USE `max(import, export)` meant a flat retail tariff (`tarif_art='fest'`, import a CONSTANT above every realistic spot peak) produced a ZERO-dispersion series, so any quantile returned retail, `V_end` came out ABOVE the horizon's own peak (28.3 ct vs 20 ct), the discharge gradient was exactly 0.000 and dispatch was structurally impossible - every `fest` plant idled its battery through every evening peak, all year, and wear cancelled symmetrically so Speicherschonung could never help. The margin is sized deliberately BETWEEN the solver gap and the throughput tie-break so it can never override "prefer idle when cycling moves no money"; the guard caps against the horizon's best use value, NOT its worst (the scout's `min(best_use)` one-liner pins `V_end` to a midday trough and re-introduces dump-to-earn into any mediocre tail). Under symmetric pricing (`ohne`) `min == max`, so `dynamisch`/`ohne` plans are unchanged - pinned by `tests/test_flat_tariff_dispatch.py`. **The P11 backup-reserve floor is HARD:** `site.backup_reserve_soc_pct` (nullable, api migration `V20260710010000`; NULL = the 5% technical floor) raises the SoC lower bound via `BatteryParams.soc_floor_kwh` - no price or terminal value ever crosses it (reserve = hard constraint, V_end = soft value; the Deye-Copilot scout documented that product silently draining below its configured min-SoC); a below-reserve start relaxes the floor to the actual start (feasibility; the MPC re-plan ratchets it back up), a reserve above the 95% ceiling pins at the ceiling. Portal/admin UI for the column is follow-up work. **Binaries exclude simultaneous charge+discharge** (at NEGATIVE prices an LP profitably burns energy through the round trip) **AND simultaneous import+export** (load-bearing: whenever export_value > import_price - a real config, e.g. spot-settled DV premium - an LP would farm the difference without physical flow). Four epsilon tie-breaks (~0.004 EUR/MWh scale, never distorting real economics) keep degenerate optima deterministic: prefer NOT curtailing when cost-neutral, prefer an IDLE battery when cycling moves no money, and **(captain decision 2026-08-09) place an otherwise cost-equal CHARGE as EARLY as possible** (`EARLY_CHARGE_TIEBREAK_EUR_PER_KW`, a per-slot charge penalty growing `∝ t/T`, in BOTH v1 `build_model` builds AND the co-optimizer for golden lockstep) - it fixes the Pilsting free/negative-price-surplus-window tie where the fill sat at the window's END; rationale is ROBUSTNESS (a cloud arriving before forecast finds a full battery) and, on plants whose curtailment is not yet released, immediately cutting the real loss-making negative-price export by the charge power. It is 10x smaller than the two siblings so it stays sub-dominant (prefer-idle decides WHETHER to cycle, early-charge only WHEN; a positive penalty on charge, so it can never reward spurious cycling). **A FOURTH one mirrors it on DISCHARGE (captain decision 2026-08-18, „erst dein Verbrauch, dann der Rest“): `EARLY_DISCHARGE_TIEBREAK_EUR_PER_KW` (same 1e-7, same `∝ t/T` shape, same v1+co-optimizer lockstep) places an otherwise cost-equal DISCHARGE as EARLY as possible - the „Jetzt-Vorzug“ IM HORIZONT-INNEREN.** On a FLAT retail tariff every deficit slot avoids the SAME import price, so „cover the 09:15 block load“ and „cover the 22:00 evening load“ are algebraically identical: the plan discharges the same total either way and only the PLACEMENT is degenerate. Measured at Anlage Pilsting/Herzogau on 2026-08-18 the battery sat idle at 17 % (NOT the 5 % floor) through a 25-30 kW block load, importing 15-23 kW at 25 ct for three hours, and spent the identical energy in the evening. **It is the TWIN of `config.TERMINAL_VALUE_COVER_NOW_DISCOUNT_EUR_MWH`** (0.2 ct/kWh off the DEFICIT entries of the EEG refill series, PR 398), which breaks the SAME tie at the horizon EDGE („cover now vs. hold past the horizon“) - the discount decides WHETHER covering wins (+0.2 ct margin), the tie-break decides WHEN; together „cover your own load as soon as you can“ holds everywhere, and the two are documented as one pair at the config constant. Both are pure tie-breaks: the fix re-placed 40 slots of the reproduction and changed neither the discharged energy, nor the export, nor the plan cost by a single digit (`tests/test_cover_now.py`, which also pins that a real price difference and a real sell peak still win, that nothing is sold below the import price, and that a tie-free horizon plans byte-identically). Consequence for the explain layer: a flat-tariff EEG plant no longer RESTS at a covering tie, so those slots read `eigenverbrauch` (portal: „Der Speicher deckt den Verbrauch…“ - no portal change was needed) instead of an unexplained `warten`, and the `decken`-with-tie-margin export now lives on a rest the SoC path genuinely forces (`test_why_facts.truebe_nacht_mit_abendspitze`). **They only work because `_solve` pins the MIP gap (`MIP_REL_GAP`/`MIP_ABS_GAP` = 1e-9, fix 2026-07-27):** HiGHS defaults to `mip_rel_gap` 1e-4, which on a ~10 EUR objective stops ~1e-3 EUR short of the optimum while a full 15 kW/44-slot cycle carries only ~6.6e-4 EUR of tie-break - so "idle" and "serve the whole evening" were tolerance-equivalent and which one came back was arbitrary, i.e. the committed setpoints could FLIP between two consecutive 15-min re-plans. Tightening the gap changes no economics (inflating the epsilons would); it costs ~10% solve time (golden suite 529 -> 582 ms) and revealed three of the eight golden scenarios were being solved suboptimally at the default. **Never raise the epsilons to "make a tie decide" - raise them only above the gap, or tighten the gap.** Pinned by `tests/test_solver_tolerance.py`. An infeasible §14a cap degrades to a plan without the grid constraint (edge guards + the grid operator enforce it physically anyway) - the fallback build carries curtailment + the EEG solar-only-charge constraint too.

Die reine Hälfte (Fenster + Bucket→Slot-Zuordnung für beide Kanäle) liegt in `repo/MeasuredSlots` und ist Docker-frei getestet (`MeasuredSlotsTest`), die SQL-Aggregation deckt `PortalApiTest.scheduleCarriesTheMeasuredLoadAndPvOfSlotsThatAlreadyHappened` ab (eigene Anlage + Aufräumen im `finally` — eine liegengebliebene Anlage mit Plan + Telemetrie verschöbe die handgerechneten Flotten-/Erlös-Zahlen der anderen Tests auf Mandant A). **Der Preis, mit dem entschieden wurde, reist seit P0 "Textwahrheit" mit** (Scout `vp-netzbezug-nacht-s3` §6): `schedule.price_eur_mwh` ist der nackte SPOT, die Entscheidung fällt am komponierten Bezugspreis - der Kundensatz behauptete deshalb im NORMALFALL Unsinn ("Börsenpreis 21,2 wäre teurer als der Speicherwert 21,5", wahrer Bezug 32,5). `ScheduleSlotDto` trägt additiv `importPriceCtKwh`/`exportValueCtKwh`/`importPriceSource`, gefüllt von `optimizer/SchedulePricingService` als **reines Weiterreichen** der schon existierenden `SlotEconomics`-Rekomposition (die Admin-Diagnose nutzt sie seit je) - KEINE zweite Preisrechnung, und ohne persistierten Spot bleibt der Wert null statt erfunden. **Banked-value honesty (FK2, audit `vp-solver-xlsx-f2` §4.3):** on "bank days" the run stores energy into the next day and `savingsEur` alone reads negative although real value was banked, so the endpoint also returns `bankedValueEur` = persisted `terminal_value_eur_per_kwh` × (SoC_end − SoC_start) × capacity plus `socStartPct`/`socEndPct` (plan-START SoC reconstructed by reversing the first slot's solver dynamics with the battery asset's efficiency - the schedule table only persists slot-END SoC; all null when honestly not computable: pre-FK2 runs, no battery asset). The Fahrplan page renders it as one calm line ("davon in den Folgetag gespeichert: +X €" / sign-honest "aus dem Vortag entnommen: X €", pure `schedule.ts bankedValueLine`), glosses the savings KPI with an InfoTip, and `horizonHint` (pure, display-side) marks the pre-13-Uhr state where the horizon legitimately ends at today's midnight ("sobald die Börsenpreise für morgen vorliegen …") so the morning hold-tail is not mistaken for a broken plan.

Dafür bekam `GET /api/v1/sites/{id}/schedule` den Parameter **`mode=latest|day`** (`web/ScheduleMode`, unbekannter Wert = **400**, nie ein stiller Rückfall — die zwei Lesarten beantworten verschiedene Fragen): `latest` ist unverändert DER Plan (jüngster Lauf; Jetzt-Held und Diagramm lesen ihn weiter), `day` ist `ScheduleRepository.dayAsPlanned` — je Viertelstunde ab Berliner Mitternacht der Wert aus dem **jüngsten Lauf, der den Slot noch VOR seinem Beginn geplant hat**. Der Gewinner je Slot wird mit EXAKT dem Splice gewählt, mit dem `HistoryRepository.savings` seit je rechnet (`DISTINCT ON (time) … ORDER BY time, generated_at DESC`) — nur das zusätzliche `generated_at <= time` macht ihn EX-ANTE, also „so war es geplant" statt „so würde man es heute planen". Vier Dinge, die man kennen muss: (1) für einen noch nicht begonnenen Slot ist jeder gespeicherte Lauf älter, das Ende der Antwort IST also der aktuelle Plan (samt seiner Slots von morgen, die der Film eingeklappt lässt) — nur der LAUFENDE Slot kann von `latest` abweichen, wenn ein Re-Plan mitten in der Viertelstunde landete; (2) das Fenster hat bewusst **keine obere Grenze** (Zeilen existieren nur bis zum Horizont des jüngsten Laufs, `time >= dayStart` begrenzt sich also selbst); (3) **lauf-bezogene Fakten** (planId, bankedValueEur, socStart/socEnd, peakTargetKw, fallback14a) beschreiben EINEN Lauf und sind in dieser Lesart **null** — `generatedAt`/`deviceId` benennen den jüngsten BEITRAGENDEN Lauf, `savingsEur` summiert die gesplicten Slots; (4) ein Slot, den kein Lauf ex ante geplant hat, hat schlicht keine Zeile — ein Tag, dessen Optimierer erst mittags lief, beginnt ehrlich mittags. **SQL-Falle:** `time` ist ein `col_name_keyword`, deshalb ist die Tabelle in dieser einen Abfrage **aliasiert** (`s.generated_at <= s.time`) — ein nacktes `time` RECHTS eines Vergleichs liebäugelt mit der Typ-Literal-Grammatik; überall sonst steht es nur links.
