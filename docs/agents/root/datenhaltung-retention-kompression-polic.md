# Datenhaltung: Retention/Kompression-Policies (Phase 1+2+3)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 105).


The time-series tables grew unbounded ("nichts wird kleiner gemacht"); Phase 1+2 caps that WITHOUT touching any product function (Historie/Earnings/Prognosequalität read the rollups + small aggregate tables, kept forever). Decision basis: scout report `data/vp-data-retention-d8` (Phase 1+2) + `data/vp-scale-readiness-p4` (Phase 3, the telemetry_v2 cap). Policies live in api migration **`V20260809000000__data_retention_policies.sql`** (Phase 1+2) and **`V20260831020000__telemetry_v2_retention.sql`** (Phase 3), both idempotent guarded (the `V20260701030000` job pattern), proven by `DataRetentionPolicyTest`.

- **⚠ THE SHARP EDGE (measured on `timescale/timescaledb:2.17.2-pg16`, BOTH directions): native compression is impossible on an RLS hypertable** - `ALTER TABLE ... SET (timescaledb.compress ...)` errors "compression cannot be used on table with row security", and enabling RLS on a compressed hypertable errors too. Same class as the documented cagg-on-RLS restriction (`V20260701030000`). So **RLS/FORCE tables (`telemetry`, `telemetry_rollup_*`, `schedule`, `weather_forecast`, `telemetry_v2*`) can only ever get RETENTION, never compression**; the ONLY compressible growing time series are the NON-RLS ones (`forecast`, `day_ahead_prices`). Retention (`drop_chunks`) works on RLS tables without restriction.
- **What the migration does:** `forecast` (no RLS, #1 disk driver, measured 32.9×) → columnar compression (`segmentby='site_id, kind, model'`, `orderby='run_at DESC, time DESC'` - covers the PK, required by TSDB) + compression policy (14 d) + retention (30 d; the daily eval results live permanently in `forecast_accuracy`). `weather_forecast` → retention 60 d, `schedule` → retention 180 d.
- **⚠ `telemetry` is DELIBERATELY left WITHOUT retention (captain 2026-08-09):** the raw corpus stays complete as future ML training material; the E1/E3 raw-retention question is deferred (a frist only after E3). The rollups (`telemetry_rollup_15m/1h/1d`) are the permanent reporting backbone and get NO policy either - `DataRetentionPolicyTest.rawTelemetryAndTheRollupsAreNeverTouched` is the regression guard for exactly this. E2 (drop `telemetry.payload` - ~57% of the telemetry size, never read) ships as Phase 2 in the WRITER (`TelemetryWriteRepository` no longer writes it; column stays, a later separate step drops it), NOT here.
- **⚠ Phase 3 (captain 2026-08-31, migration `V20260831020000`): `telemetry_v2` (the MIG-B1 fan-out mirror) gets a 90-day RETENTION - and this REVISES the stale p12-k6 "keine Policy auf telemetry_v2*" exclusion.** That exclusion was written when telemetry_v2 was an empty v2 pilot; since the entity auto-backfill, `ComposedEntityFanout` writes up to 5 telemetry_v2 rows per v1 sample on EVERY composed plant (~3,9 GB/year/plant, ~2,6× the v1 bytes for the same measurement), making it the single largest UNBOUNDED storage driver (bigger than raw v1 telemetry). Retention only (RLS blocks compression). **The v2 rollups (`telemetry_v2_rollup_15m/1h/1d`) stay FOREVER, exactly like the v1 rollups**, and raw v1 `telemetry` is untouched. **Display-neutral, verified in code (scout `vp-scale-readiness-p4` §2.1):** no display/API path reads raw telemetry_v2 older than 90 days - every raw read is a single DAY window (`EntityHistoryRepository.v2Rows` / `HistoryRepository.v2DayBuckets`, both HistoryRange.DAY only; `ConsumerRequirement*` over a current period; `TopologyRepository.latestValues` = newest sample). Entity/site Historie from WEEK up reads the v2 ROLLUPS; the `min(time)` splice-boundary reads only shift WHICH retained-forever source (v1 vs v2 rollups) provides the overlapping buckets, and the fan-out writes them as mirror images. Guarded by `DataRetentionPolicyTest.telemetryV2GetsA90DayRetentionWhileItsRollupsStayForever` (+ the v2 rollups added to the never-touched loop).
- The TimescaleDB job scheduler runs IN the database, not the api replicas → no replica-singleton double-run concern (unlike the MQTT listeners).
