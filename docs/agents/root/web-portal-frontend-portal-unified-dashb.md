# Web portal (frontend/portal) - unified dashboard shell

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 62).


React + Vite + TypeScript SPA. `npm run dev` (5173) / `npm run build` (tsc type-check + bundle).

**One shell for both roles** (the captain-approved redesign): a left sidebar, a top bar (Pfad + Anlagen-Umschalter, Mandanten-Umschalter, Konto-Menü) and one page at a time in the main area. **Seit der Navigations-Runde „zwei Ebenen" (25.08.2026) hat die Leiste ZWEI Ebenen und keine Anwendungs-Gruppen mehr:** die FLOTTEN-Ebene ist EIN Eintrag (`Portfolio` bzw. `Meine Anlagen`, Reiter Übersicht · Messwerte · Erlöse), eine geöffnete Anlage trägt FÜNF Bereiche mit Reitern (Cockpit · Fahrplan · Verlauf · Steuerung · Anlage) — Marktpreise und Prognosequalität sind Verlauf-Reiter DIESER Anlage, keine Hauptmenü-Punkte. Die Regeln, die Gesetze und die Fallen stehen in `frontend/portal/CLAUDE.md` („Navigations-Runde „zwei Ebenen""). The role never forks into a different app - Portal-Admins get *additive* nav plus the tenant **switcher** in the top bar (pick a tenant -> the customer pages render that tenant's data via `X-Tenant-Id`, see the admin section); customers see a read-only tenant badge.

- **U0 Kontotyp/Betriebsart frame (design `data/vp-ems-ui-overhaul/report.md` §2, epic UO #509 - the shell decision keys on the FRAME, not the site count).** `tenant.betriebsart` (api migration `V20260720000000`, nullable CHECK endkunde|betreiber) is the explicit override; the EFFECTIVE value resolves in ONE place - api `tenant/Betriebsart.effective(override, segment)`. **It is deliberately NOT segment-derived (pre-deploy audit HIGH-1, 2026-07-21): an unset override resolves to `null` = UNKNOWN**, because `segment` defaults to `CI` for every admin-console-provisioned tenant, so a `CI`→betreiber derivation would have silently flipped every existing single-plant customer from their cockpit into the operator Portfolio shell on the U0 deploy. Unknown falls back to the pre-U0 site-count heuristic in the portal, i.e. zero change for existing tenants; the Portfolio shell appears ONLY once an admin explicitly stores `betriebsart='betreiber'` (`BetriebsartTest`) - and is echoed on the admin tenant DTOs (`betriebsart` + `betriebsartEffective`) and on the customer login bootstrap **`GET /api/v1/tenant-context`** (`TenantContextController`, RLS-scoped app datasource: customers get exactly their tenant row, admins the switcher-selected one, admin-without-tenant = 404). Admins set/clear it via the existing `PUT /api/v1/admin/tenants/{id}` (full representation: omitted/null = Automatisch; select on the Mandanten drawer) - customers can never write it. The portal NEVER re-derives: `src/betriebsart.ts` (`isFleetShell`/`showOverviewNav`/`redirectOverviewToAnlage`, unit-tested) consumes the echoed value - *betreiber* = fleet shell from the FIRST Standort (interim landing = today's fleet Übersicht; the real Portfolio page is U5 #516), *endkunde* = cockpit, and with 2+ Anlagen the calm `FleetUebersicht` CARDS, never an operator table; `null` (no explicit override - the default for every existing tenant - older backend, or context not loaded) falls back to the v1 `sites.length >= 2` heuristic byte-identically. Admins keep always-Übersicht; the frame applies to the switcher-selected tenant. Proven by `AdminApiTest.betriebsartFrameIsAdminSetNeverSegmentDerivedAndEchoedOnTenantContext` + portal `betriebsart.test.ts`.

- **UI quality conventions** (from the final polish pass, full findings log in [`docs/ui-quality-pass.md`](docs/ui-quality-pass.md)): icons ONLY via the design-system **`Icon`** component (`components/core/Icon.jsx`, Lucide-path stroke set) - never unicode/emoji glyphs, they render inconsistently across platforms; all user-visible numbers through `src/format.ts` (de-DE locale, non-breaking space before units, `deviceKindLabel`/`fmtCoords` for enum/coordinate display); customer-facing copy never names internal components (broker/pipeline/RLS/Keycloak/collector names); dashboard stat ink + scale come from the portal-scoped tokens `--vp-stat-ink`/`--vp-text-stat-sm` (defined in `src/index.css`, consumed by `Stat`/`KpiCard` with the original marketing values as fallback); charts use `containLabel: true` grids and width-aware layout so phones never clip axes. Inline metric help ("was bedeutet diese Kennzahl?") goes through the shared **`InfoTip`** component (`src/components/InfoTip.tsx`, uses the `info` `Icon`): a small info button whose bubble is rendered into `document.body` at `position: fixed` and viewport-clamped, so it never clips inside a card or off a phone edge (hover/focus on fine pointers, tap on coarse) - reuse it for new tooltips instead of hand-rolling one. The **Prognosequalität** page (`pages/PrognosePage.tsx`) uses it to self-explain: a "Was sehe ich hier?" intro + a live-vs-Schattenbetrieb legend, and `InfoTip`s glossing the only two metrics it actually renders - **Ø Abweichung (MAE, kW)** and **Skill** (`1 − Fehler/Baseline-Fehler`); the page deliberately does NOT show nMAE/Bias/planAccuracy, so those get no tooltip. Load-bearing framing (a real owner-confusion fix): the page always states the structure is **2 Prognosearten × (1 aktives Modell + höchstens 1 Schatten-Kandidat)** - the two kinds are named identically everywhere via `KIND_LABELS` ("Verbrauchsprognose (Last)" / "PV-Prognose (Erzeugung)"), the active section is "Aktive Modelle" with one bordered `.vp-kind-card` per kind, so "zwei aktive Prognosen" never reads as a duplication.
- **Responsive:** sidebar collapses to a hamburger slide-over below 1024px; below 720px the hero stacks, tables collapse to label/value cards (`.vp-table.responsive` + `data-label`), drawers become full-screen sheets, touch targets stay ≥44px.
- Auth via `keycloak-js` (`src/auth.ts`, silent-SSO check + PKCE); the access token is attached to API calls in `src/api.ts` (`freshToken()` refreshes it). Config via `VITE_KEYCLOAK_*` / `VITE_API_BASE` (no hardcoded hosts beyond the localhost defaults; LAN recipe in the README - the dev realm allows `http://192.168.2.77:5173` as an origin).
- **Direct-to-Keycloak login (no pre-step).** An unauthenticated visit redirects STRAIGHT to the Keycloak login (`main.tsx` calls `login()` the moment `initAuth()` resolves false); the old "Jetzt anmelden" card remains only as fallback. Three carve-outs keep it loop- and dead-end-free: (1) the **`#register` route** (`nav.ts isRegisterRoute()`, matches `#register`/`#/register`) renders the portal's own registration form WITHOUT redirecting - the "Konto erstellen" form lives in the SPA (custom form + seamless auto-login), NOT in Keycloak; the Keycloak login page links back to it via the theme script `deploy/keycloak/themes/voltpilot/login/resources/js/register-link.js` (`scripts=` in theme.properties), which derives the portal origin from the auth request's `redirect_uri` query param (already validated by Keycloak against the client config, so it needs NO env/realm config and is correct in dev AND prod) and caches it in sessionStorage because the failed-login `login-actions` URL carries no `redirect_uri`. Theme file changes reach a running dev Keycloak on restart (start-dev, caches off); prod `start` mode needs the force-recreate (gzip-cache footgun above). (2) A **loop guard** (sessionStorage `vp.auth.autoLoginRedirect`, `main.tsx`): set before the auto-redirect, cleared on an authenticated boot; a boot that finds it still set while unauthenticated (browser back from Keycloak, failed code exchange) shows the manual login card instead of redirecting again - Keycloak's own error states stay visible, never a redirect loop. (3) `authError` (Keycloak unreachable) never auto-redirects (it would land on a dead host outside the SPA). Logout → origin → unauthenticated boot → straight back to the Keycloak login, as intended; RegisterForm's "Zur Anmeldung" calls `login()` (Keycloak) instead of flipping to the in-app card, and an authenticated boot with a leftover `#register` hash renders the normal portal (`pageFromHash` maps unknown → uebersicht).
- **Auth/login recovery paths (dead-end-free login).** The login surface never bounces a user out of the SPA with no way back: (1) when `initAuth()` throws (Keycloak unreachable) `LoginScreen` renders with `authError` and its primary CTA becomes **"Erneut versuchen" → `window.location.reload()`** (NOT `login()`, which would just redirect to the same dead Keycloak host outside the SPA), and the register link is hidden (it also needs Keycloak). (2) A **stored** ROPC session (fresh registration) whose refresh fails on boot is retried once (`refreshStoredTokens`); if it still fails, `auth.ts` sets a module flag surfaced via `wasSessionExpired()` → `main.tsx` passes `sessionExpired` → the login screen shows "Ihre Sitzung ist abgelaufen, bitte erneut anmelden" instead of a blank card (gated on `!authError`, since a full outage shows the outage copy). (3) `freshToken()` throws `AuthRedirectError` (exported from `auth.ts`) after triggering the login redirect; `request()` catches it and **aborts the pending call** (returns a never-resolving promise) so no unauthenticated fetch fires and no raw "API-Fehler: 401" flashes before the redirect lands. (4) `request()` and `register()` never leak raw HTTP status/`statusText` into user copy - the fallback message is plain German, a server-provided German `message` overrides it, and the numeric status stays on `ApiError.status` for branch logic. (5) A **forgot-password** note ("Passwort vergessen? Bitte kontaktieren Sie unseren Support.") is shown - there is no self-service reset without SMTP (support recovers via the admin reset-password lever). (6) Registration on a **502/503** (Keycloak down: `RegistrationController` returns 503 for transport failures, passes real Keycloak 4xx/5xx through) maps to the outage copy ("in wenigen Minuten erneut"), distinct from the transient "gleich noch einmal" hint.
- Telemetry chart uses **ECharts** (`src/TelemetryChart.tsx`). Live channel is REST polling on load (WebSocket/SSE deferred - acceptable per the increment scope).
- **ONE "Anlage anlegen" flow (captain decision 5, 2026-07-07 - Phase B of the Anlagen-IA)**: creating an Anlage is one sequenced flow in `src/components/AnlageFlow.tsx` - 1 · Anlage (Name + keyless Open-Meteo address search `LocationSearch` + Karte + Anlagentyp; Strompreis/anzulegender Wert/Netzladen collapsed behind "Feineinstellungen (optional)"; bidding zone derived from the address country via `zoneForCountry`, no WGS84/Gebotszone jargon), 2 · Gerät (Geräte-ID claim, skippable), 3 · Speicher (optional battery data saved WITHOUT a deviceId so the claimed inverter auto-links as the controlling device). BOTH entry points host this one component: the first-run wizard (`src/Onboarding.tsx`, any customer with zero devices; ends on the first-data poll "Ihre Anlage ist verbunden", 90 s check-your-device hint) and the `AnlageAnlegenDrawer` for existing customers (ends on an honest summary naming skipped steps; the host reload is deferred to drawer close so a mid-flow reload can't unmount it). Pure flow logic (step resume, battery form parsing, `normalizeDeviceIdInput`, `DEVICE_ID_FIELD`) lives in `src/anlageFlow.ts` (unit-tested). Skippable at every step; a customer with an Anlage but no device resumes at the Gerät step, and the zero-device dashboard keeps the "Einrichtung fortsetzen" banner. A SINGLE-Anlage customer (no Übersicht, no list) gets the "Sie haben eine weitere Anlage? Anlage anlegen" line at the bottom of the Anlagen-Seite - without it the 1->2 transition had no entry point. Customer-facing copy deliberately avoids internal vocabulary (no "beanspruchen"/"Mandant <uuid>"/pipeline/collector/PT15M wording anywhere in the portal); per captain decision 3 the customer surface says "Anlage" everywhere - "Standort" survives ONLY in the address sense (map, Technik "Standort & Einstellungen", MaStR register address).
