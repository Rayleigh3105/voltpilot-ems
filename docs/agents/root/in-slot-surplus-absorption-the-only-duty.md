# In-slot surplus absorption: the only duty that RAISES a charge (2026-08-02)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 82).


The third and last member of the in-slot duty family, and the one the other two structurally could not cover - the trim only ever LOWERS a charge, the follower only ever acts on a DISCHARGE, so **nothing could put an unforecast PV surplus INTO the battery**. Captain observation at Anlage Pilsting (02.08., ~10:41): PV 23,9 · Haus 4,3 · **Netz-EINSPEISUNG 16,6 kW** at a negative spot price, hour after hour, with the battery at **7 % SoC** - while the cockpit said "die PV wird gedrosselt". Report `firstmate/data/vp-pilsting-abregeln` §5b: the morning's real money is NOT the unexecuted curtailment (~0,1-0,7 €) but the **unstored surplus** (~2-10 €/day, every sunny negative-price day). Root cause: the solver charges only the FORECAST surplus (`charge ≤ pv_forecast − curtail`) and there is no nowcast, so every 15-min re-plan repeats the same too-small number. Same architectural law as its siblings: **THE CLOUD PRICES, THE EDGE ENFORCES** - the edge evaluates no price, ever.

- **The rule (`services/optimization/voltpilot_optimization/slot_trim.py`)**: storing one more kWh beats selling it iff **`η·λ_t − wear > export_value_t + margin`** (shared `SLOT_TRIM_MARGIN_CT_PER_KWH`), where λ is again the model's OWN LP dual (`stored_value_ct_kwh`). Note the marginal value here is **UNCLAMPED** (`marginal_storage_value_ct_kwh`), deliberately NOT the trim's `willingness_to_pay_ct_kwh`: that one floors at 0, which against a NEGATIVE export value would claim storing is worth it even where the wear spent exceeds the giveaway avoided. At a negative price the test is satisfied as soon as the water value covers the wear - the report's own reading.
- **Emission** (`solver._charge_surplus_to_battery`, stamped in `_with_explanation`; `PlanSlot.charge_surplus_to_battery`; own kill-switch `OPTIMIZER_SURPLUS_CHARGE_ENABLED`, passed through in BOTH composes): the economic test, PLUS the plan intends no deliberate SALE (`grid_kw >= -0.05 kW`, or the slot CURTAILS - which by definition prefers not to export), PLUS the plan's own SoC trajectory still has headroom (`slot END SoC < soc_max − 0.1 kWh`; an unfulfillable duty is never published). Deliberately NOT gated on the plan commanding a charge - the whole point is the slot planning 0,0 kW.
- **⚠ DELIBERATE DEVIATION from the report's literal formula 5b, argued in the rule's docstring:** 5b copied P1b's two-sided `|grid_kw| ≈ 0` exclusion, which would have killed the money case - under FK3 PV-bus semantics an ordinary EEG charging slot plans `grid_kw = +load` ("battery takes the PV, house buys its load"), measured at 4,3 kW on the very morning in question (~4,7 €/h at stake in ONE slot). A planned IMPORT is therefore NOT excluded, and it is structurally safe to allow: this duty is **UNIDIRECTIONAL** (it only RAISES, and only up to the measured surplus = predicted grid exactly 0), so it bites ONLY where reality is EXPORTING and can never touch a deliberate cheap-hour purchase, which charges MORE than the surplus by construction. That asymmetry to P1b - whose enforcement is BIDIRECTIONAL and therefore genuinely could undo a purchase - is the whole argument; do not "restore the symmetry".
- **Edge (`guards/surpluscharge.go` `SurplusCharger`, in `applySetpoint` after the trim AND the follower, before the peak guard)**: raise-only, and only on a NON-NEGATIVE command (never a direction flip - which is also what keeps it disjoint from the follower). **Because it RAISES, its target is re-run through the authoritative `guards.Clamp`** (rated band, SoC ceiling, EEG solar-only charge, §14a envelope) instead of a hand-rolled bound - the same technique the follower's deepen half uses with `PeakShave`, so it is impossible for it to write past a guard or widen one. **Safety by algebra:** bounded by the measured surplus, predicted grid = `load + min(kw, surplus) − pv ≤ 0`, so it can never create or raise an IMPORT (§14a import bound + the peak quarter-hour target untouched) and only ever moves an export TOWARD zero (§14a export bound + feed-in cap hold a fortiori). Unknown pv/load → INACTIVE. The self-consumption fallback already charges pv − load, so it is a no-op there. Hysteresis mirrors the trim (engage immediately, release after `AbsorbReleaseDwell`; the applied level follows a shrinking surplus at once, a growing one in `AbsorbStepKw` steps).
- **A raised setpoint is DELIBERATE, never a failed write:** the ABSORBED value is published, so the readback matches it. Surfaced as `state.AbsorbInfo` → `control.js VPControl.deriveAbsorb` → the same `#ctrlReason` line ("Lädt den gemessenen Solarüberschuss … – Ladung angehoben", NORMAL mode) and as the heartbeat `execution.mode: "absorb"` (checked FIRST in `executionSummary` because it runs LAST in the setpoint chain, so where it bit its value is the published one).
- **Cloud-side ingest of `mode: "absorb"` is deliberately NOT in this increment** (the api `ControlStatusListener`'s strict mode filter DROPS an unknown mode, so an un-updated portal degrades to its generic wording - the documented graceful path), and neither is persisting the flag into the `schedule` table like the Fahrplan-concept PR 4 did for the two older duties. Both are the natural follow-ups.
