# Einheitsmodell Stufe 0a: „Vorlagen werden Daten" (`component_template`)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 17).


Das Fundament des EINEN Anlege-Assistenten (Scout `data/vp-komponenten-einheit-h2` Teil 3.1 + Stufenplan Stufe 0a). **Reiner Unterbau: NICHTS konsumiert es** — die Flächen rendern weiter den Go-Katalog, und der Vorzustand läuft ohne diese Stufe byte-identisch weiter. Das ist ausdrücklich die Abnahme, kein Versäumnis.

- **Warum überhaupt:** der Geräte-Katalog (7 Marken, 44 Modelle) ist eine GO-FUNKTION auf der Box (`edge-app/core/internal/inverter` `DefaultCatalog()`) — nur die Box kennt ihn. Der Assistent im Portal braucht dieselbe Liste cloud-seitig, und eine „geprüfte Vorlage" (Stufe 6) soll ein DATENSATZ sein, kein Software-Release.
- **⚠ DER GO-KATALOG BLEIBT DIE WAHRHEIT.** Er entscheidet, was eine Box wirklich lesen kann (Decode-Profile, Node-RED-Adapter, Go-Executoren); die Tabelle ist seine cloud-seitige DARSTELLUNG. Die Brücke zwischen beiden ist die Spalte `family` (die Decode-Profil-Referenz).
- **Export statt Migrations-Seed, mit ZWEIGLIEDRIGEM Drift-Wächter** (die bewusste Wahl): `edge-app/core/cmd/vp-template-export` erzeugt aus `DefaultCatalog()` die eingecheckte Datei `services/api/src/main/resources/componenttemplates/builtin.json` (deterministisch, **ohne Zeitstempel** — sonst wäre kein Byte-Vergleich möglich), und `ComponentTemplateSeeder` spiegelt sie bei JEDEM Start idempotent in die Tabelle. Ein 44-Zeilen-Seed IN der Migration wäre ab dem nächsten Katalog-Edit falsch und jede Korrektur bräuchte eine weitere Migration (eine angewandte Migration ist unveränderlich). Die Gleichheit „Go-Katalog ⟷ Tabelle" wird deshalb in zwei Gliedern bewiesen, weil ein Java-Test kein Go ausführen kann: **Katalog ⟷ Datei** = `TestBuiltinTemplateExportMatchesTheCommittedFile` (BYTE-Vergleich — ein JSON-Round-Trip machte aus `502` die Zahl `502.0` und wäre blind für Formatierungs-Drift), **Datei ⟷ Tabelle** = `BuiltinComponentTemplatesTest` + `ComponentTemplateApiTest`. **Wer den Katalog ändert, führt `(cd edge-app/core && go run ./cmd/vp-template-export)` aus** — sonst ist der Go-Lauf rot (`--check` gibt es auch).
- **⚠ DIE EHRLICHKEITSREGEL, an der die Spalten hängen: `channels` und `writes` sind bei einer eingebauten Vorlage `NULL` = „hier nicht erklärt", NIE `[]` = „gibt es keine".** Die Kanäle eines Deye entstehen im Decode-Profil (`deye-decode.js` …), sein Schreibweg im Steuer-Adapter (freigegeben vom Register `inverter_control_certification`, nicht von dieser Tabelle) — ein leeres Array behauptete „liefert keine Messwerte" bzw. „kann nichts schreiben" und wäre glatt falsch. Deshalb sind beide Spalten nullbar **ohne Default**. Gleiche Regel für `rated_kw`: NULL = im Katalog unbekannt, nie 0. Der Selbstbau (Stufe 3) füllt `channels`, Stufe 6 die `writes`; die Formen stehen als Kommentar in der Migration und im `ComponentTemplateDto`.
- **Schema (Migration `V20260815000000`), global ohne `tenant_id`/RLS** wie `edge_release`/`provisioned_device`/`inverter_control_certification` — eine Vorlage ist eine Aussage über ein PRODUKT. Gefenced ist der Endpunkt. Grants nach dem `provisioned_device`-Muster: `GRANT SELECT` an die App-Rolle, `REVOKE INSERT/UPDATE/DELETE` (V2s `ALTER DEFAULT PRIVILEGES` gäbe ihr sonst Schreibrechte auf eine globale Tabelle); einziger Schreiber ist die BYPASSRLS-Rolle über den Seeder.
- **`kind` und `certification_status` beantworten VERSCHIEDENE Fragen** — kind = woher die Vorlage kommt (`builtin|certified|custom`), status = wofür die Plattform einsteht (`builtin|certified|in_certification|not_certified`). Eine eingebaute Vorlage ist bewusst `builtin`, **nicht** `certified`: das Wort gehört dem Prüfstand, und eine Baureihe, die nie auf einem Tisch stand, wäre damit überbehauptet.
- **`template_ref` ist OPAQUE** (`builtin:<marke>:<modell>`, Zeichenmenge per DB-CHECK gepinnt) — nie zerlegen, Marke/Modell stehen als eigene Spalten daneben. `version` ist die DEFINITIONS-Fassung; eingebaute bleiben auf **1**, weil ihre Fassung der Edge-Softwarestand IST (ein Katalog-Tippfehler soll keine Versionshistorie erzeugen) — der Seeder frischt deshalb AN ORT UND STELLE auf und schreibt bei unverändertem Katalog gar nichts. Die Lese-Route liefert je Schlüssel die höchste Fassung (`DISTINCT ON`).
- **⚠ `custom` ist RESERVIERT, nicht benutzbar.** Eine private Vorlage gehört EINER Anlage, diese Tabelle hat aber bewusst keine `tenant_id` — sie über eine mandantenlose Route auszuliefern wäre ein Leck. **Stufe 3 muss den Besitzer-Zaun ausdrücklich bauen** (nullbare site_id + Policy, oder eine eigene Tabelle). Bis dahin schreibt niemand `custom`, und `BuiltinComponentTemplates.PUBLIC_KINDS` (= builtin + certified) hält es aus jeder Antwort heraus; `ComponentTemplateApiTest` legt zum Beweis von Hand eine solche Zeile an.
- **Lese-Route `GET /api/v1/component-templates[/{ref}]`** (`ComponentTemplateController`, in `openapi.yaml`, tag `templates`): authentifiziert, NICHT admin-gegated (die Geräte-Auswahl ist keine Interna) und mandanten-agnostisch. Unbekannt und nicht-öffentlich antworten identisch mit 404 (die Enrollment-Disziplin „pending == unknown"). Eine leere Liste heißt „das Register ist leer", nicht „es gibt keine Geräte". Die Liste blendet abgelöste Schlüssel aus; der Einzelabruf hält ihren Bestands-Editor erreichbar. Beim Bearbeiten bleibt zusätzlich die gespeicherte `template_version` gebunden, und Verbindungstest-Belege sind auf `(template_ref, template_version)` statt nur den Schlüssel geprägt. **Schreiben/Verwalten gibt es in dieser Stufe gar nicht** (Stufe 6).
- **Zwei additive Spalten an `measurement_point`:** `source_kind` (`builtin|certified|custom|composed`) + `template_ref`/`template_version` (beide nullbar, CHECK „beides oder keines", **kein Fremdschlüssel** — die Fassung ist ein Schnappschuss wie `rollout_device.device_ref`: eine zurückgezogene Vorlage darf die Historie einer Komponente nicht löschen und ihr Löschen nicht blockieren). **Gestempelt wird NUR, wo die Auto-Komposition (#385) eine Zeile ANLEGT** (`EntityRegistryRepository.createBatteryHybridPoint`/`createComposedPoint` → `SOURCE_KIND_COMPOSED`); eine ältere komponierte Zeile bleibt ehrlich NULL („unbekannt") und wird bewusst nicht aus dem Auffrisch-Pfad nachgestempelt — der frischt auch ADOPTIERTE Erzeuger-Zeilen auf, die nicht komponiert sind, ein pauschaler Stempel würde sie falsch etikettieren. Ein Backfill ist eine bewusste Handlung der Stufe, die das Feld wirklich braucht.
- **Beweise:** Go `internal/inverter/templates_test.go` (6: Byte-Drift-Wächter, Vollständigkeit je Modell, Katalog-Fakten wörtlich, `null`-statt-`[]` **auch in den JSON-Bytes**, `rated_kw` null statt 0, Slug-Sicherheit, Determinismus) · api `BuiltinComponentTemplatesTest` (7, rein/ohne Docker) · Testcontainers `ComponentTemplateApiTest` (6: die Tabelle IST der Export, Ehrlichkeit in der Antwort, zweiter Abgleich schreibt NICHTS, geänderter Katalog frischt in place auf statt eine Fassung anzulegen, `custom` nie ausgeliefert + 401 anonym, App-Rolle liest aber schreibt nie, Bestandsneutralität + `composed`-Stempel nur auf frisch komponierten Zeilen).
