# Anlagen-Topologie-Read-Model (AE1): the ONE adaptive energy-flow read-model

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 56).


The foundation of the adaptive EMS-UI theme (spec `data/vp-ems-replatform/adaptive-ems-ui-v1-spec.md` §10; contract **`docs/contracts/v2/topology-read-model.md`**): a site is an entity graph; each entity capability is assignable to a **role** (`pv`/`storage`/`grid`/`consumer`, extensible); roles aggregate ACROSS entities into the role-grouped hub topology the adaptive energy-flow diagram renders (portal AE2 / edge AE6, both follow-ups). A hybrid inverter maps to SEVERAL roles at once (its `pv_power_kw` → pv, `battery_power_kw`/`soc_pct` → storage); several entities aggregate into one role (Σ PV); the **maßgebliche** (`primary`) grid measurement is markable. Additive, v1 byte-identical (a registry-less/v1 site yields an empty topology).

- **THE load-bearing piece = ONE shared derivation, THREE twins pinned to ONE vector file.** `topology.Derive`/`DefaultRole` turns {resolved capabilities + live values} into role nodes + directed flows: Go `edge-app/core/internal/topology` (canonical), TS `frontend/portal/src/topology.ts`, Java `services/api …/topology/TopologyDeriver`. All three assert against **`docs/contracts/v2/topology-vectors.json`** (the jcs-vectors precedent) — Go and TS are byte-identical (canonical key order + `json.Marshal`/`JSON.stringify`), Java structurally equal. **Change the rules in all three + the vectors together.** Flow signs (from `live.ts`/`dashboard.js`): pv → in, consumer → out, grid `power_kw` + = import → in / − = export → out, battery `battery_power_kw` + = charge → out / − = discharge → in; 0.05 kW deadband; kW rounded to 3dp; an absent value is NEVER coerced to 0. Default `capability → role` mapping keys on the measure channel + entity `category` (`storage|producer|meter|consumer`; the edge's `entities.Entity.Category()` "measure-only" aliases "meter") — `soc_pct` feeds the storage node's SoC, not a flow member. **⚠ Der TYP wird ZUERST geprüft, und zwar zweimal:** ein Ladepunkt (`IsChargingType`) bekommt seine Lade-Rolle bzw. gar keine, und ein SELBST GEBAUTES Gerät (`IsSelfBuiltType`: `modbus-generic`/`modbus-load`) bekommt **NIE eine Rolle** — auch nicht für einen Kanal, den der Kunde `power_kw` genannt hat. Ohne diesen Zweig entschied die KATEGORIE, und ein `modbus-generic` ist `meter`: der Zisternen-/Wärmepumpen-Sensor des Kunden wurde damit **als NETZANSCHLUSSPUNKT** gerendert (Scout `vp-portal-box-spiegel-s2`, L5, im Labor reproduziert). Der Netz-Knoten darf ausschließlich aus einem echten Netz-Zähler entstehen; die Zusage dahinter ist die Bilanz-Ehrlichkeit der Einheitsmodell-Stufe 3 („ein Selbstbau-Sensor … geht NICHT in die Energiebilanz ein"), die der Assistent dem Kunden beim Anlegen druckt. Die Messwerte gehen dabei nicht verloren (eigene Kanäle, eigener Verlauf) und die Box LISTET das Gerät seit dem 31.08.2026 in ihrer eigenen Gruppe „Eigene Geräte" — siehe `edge-app/AGENTS.md`.
- **Cloud:** `GET /api/v1/sites/{id}/topology` (RLS, foreign 404) = `{schemaVersion, entities[], topology}` — the entity graph (per-capability resolved role+`primary`+latest `telemetry_v2` value+health) + the server-derived hub topology (`TopologyService`/`TopologyRepository`). Role ASSIGNMENT overrides live in `entity_role_assignment` (migration **`V20260719040000`**, RLS; no row = the `DefaultRole` mapping + default first-of-role primary), set via `PUT .../topology-roles`. `openapi.yaml` tag `topology`.
- **The customer CLEANUP levers on a v2 component (vp-bereinigung-ui-k3; the Pilsting incident 2026-07-29).** On a plant where EVERY reported device is already pinned - to the WRONG components - there is no "unassigned source", so PR #271's re-pin could only ever answer 409 and its purge-delete existed on the platform-admin route alone: the customer had no way to clean up at all. Two additions to `SiteEntityAdoptController` (RLS-fenced customer routes, the `SiteFlowController` pattern) close it:
  - **`POST .../v2-entities/{entityId}/edge-source` takes `swap: true`** - a target held by ANOTHER component is then EXCHANGED instead of refused, both pins moving inside ONE transaction (`EntityRegistryService.repin(..., allowSwap, reportedSourceIds)`). A client-side "release, then set" was rejected on purpose: a failure between the two calls strands BOTH components unassigned. **The holder gets this entity's previous source only when that source is STILL REPORTED**, else its pin is cleared - handing over a vanished id would just move the orphan defect. Absent/`false` keeps the documented 409, so an older client can never steal an assignment.
  - **`DELETE .../v2-entities/{entityId}`** is the customer twin of the admin `purgePoint` delete: the measurement point goes, a producer's kWp is released from the aggregate `asset.pv`, the edge source is freed and reappears as "Neues Gerät gefunden". Guarded twice: the platform-composed base components (`battery-hybrid` / `house-load`) and any component WITHOUT a device pin (a grid meter / house load composed from the plant's own master data is its Grundausstattung) are 422.
  - **`repin` now pushes the registry** (`pushRegistryBestEffort`) - it did not before, and the pin rides IN the pushed descriptor (`edge_source_id`, PR #272), so the device kept serving its per-source values against the OLD assignment while the portal showed the new one. Adopt/create/update/delete already pushed; the assertion that the composed revision changes is part of the test.
  - `EntityController`'s `EntityDto` carries the additive **`capacityKwp`**, so the portal's delete dialog names exactly which kWp leave the plant total instead of warning vaguely. Proven by `PortalApiTest.customerSwapsCrossedAssignmentsAndDeletesTheGhostComponent` (the captain's exact constellation: 409 without consent, swap-with-release, true exchange, no row minted, both 422 guards, kWp released, freed device unassigned, RLS 404). Portal side: `frontend/portal/AGENTS.md` "Die BEREINIGUNG hängt an der Komponente".
- **U2 role-assignment is now customer-writable + the adoption bridge landed (design `data/vp-ems-ui-overhaul/report.md` §3, "Rollen & Zuordnung" + "Vom Gerät gemeldet").** The role-assignment loop moved into `TopologyService.applyAssignments` shared verbatim by BOTH the admin `PUT /api/v1/admin/sites/{id}/topology-roles` and the NEW customer twin `PUT /api/v1/sites/{id}/topology-roles` (`SiteTopologyController`, NO `@PreAuthorize`, RLS-fenced via `sites.existsForCurrentTenant` — foreign site 404; the `SiteFlowController` pattern). Safe by construction: a role is presentation-level and never widens control (guards/arbitration key on capabilities, not roles). **Adoption** (`POST /api/v1/admin/sites/{id}/v2-entities/adopt`, admin-only first increment): `EntityRegistryService.adopt(siteId, sourceId, entityType, …)` turns an edge-reported source into a v2 entity in one step — a consumer type via `createEntity`, a composed producer/grid-meter as a source `measurement_point` composed from the catalog (producer kWp sums into aggregate `asset.pv` via `AssetRepository`, the retired ErzeugerSourcesPanel job). Idempotent per `measurement_point.edge_source_id` (migration `V20260720010000` + a partial-unique index; **the rule is ONE point per (site, edge source), always**: deleting a COMPOSED entity only clears its config and LEAVES the point pinned to the source, so `adopt` probes with the unfiltered `pointByEdgeSource` (never an `entity_type IS NOT NULL` filter, which missed exactly that row and made the re-adopt INSERT die on the unique index → opaque HTTP 500 on a button the portal keeps offering) and RE-COMPOSES the existing row, applying the producer kWp as a DELTA since the aggregate still carries what it contributed; the same migration adds `entity_observed_state.edge_role`/`edge_brand` so the "Vom Gerät gemeldet" list can suggest the type). The entities surface (`EntityController`) now carries `edgeSourceId` per entity + `role`/`brand`/`adoptedEntityId` per `localSetup` item. **Strategy chips**: `GET /api/v1/sites/{id}/entity-strategies` (`FlowService.entityStrategies`, keyed by entity id) = which active flows' D-13 claims touch each entity, for the "Ihre Geräte" read-only chips. Proven by `PortalApiTest.customerAssignsTopologyRolesForItsOwnSiteAndStrategiesAreScoped` + `AdminApiTest.adminAdoptsEdgeReportedSourcesIntoV2EntitiesIdempotently`.
- **`entity_role_assignment` IST SEIT `V20260914100100` VERALLGEMEINERT — der maßgebliche Rollen-Wert eines Geräts ist ENTWEDER ein nativer Kanal (`capability`) ODER ein Gesamtwert / berechnete Messstelle (`quell_messstelle_id`), genau eines (CHECK), der Mandant reist im zusammengesetzten FK mit** (Konzept `vp-agg-konzept2-f3` §2.6.3 / `vp-agg-konzept3-r8`, Backend `vp-agg-be-h7`). Kein zweites Modell. **Kunden-Fläche „verwenden als"** (`SiteRollenController`, RLS wie jede `/sites/**`-Route, fremde Anlage 404): `GET/PUT /api/v1/sites/{id}/komponenten/{entityId}/rollen/{role}` setzt/liest den maßgeblichen Wert eines Geräts (ab Tag 1 nur `role=pv`; Struktur trägt `grid`/`storage`/`consumer` nach), `GET /api/v1/sites/{id}/rollen/{role}` liefert den kanonischen Anlagen-Wert (nur `pv` = Summe). **Ablösung (is_primary):** höchstens ein maßgeblicher je (Gerät, Rolle), service-geführt (`RollenZuordnungService.primaerLoesen` + upsert); ein zweiter Wert ersetzt den vorigen, die Antwort nennt den abgelösten. **Ehrlichkeit:** benannte Teil-Summe (jedes Gerät liefernd oder stumm mit Grund benannt), archivierte zugeordnete Messstelle wird aufgelöst statt stumm gezeigt. **Rückfall:** ohne PV-Zuordnung `zuordnung_vorhanden=false` → Cockpit bleibt bei `telemetry.pv_power_kw` (die Umlenkung ist ein Folgeschritt). **⚠ Das Topologie-Lesemodell bleibt byte-identisch:** `TopologyRepository.overrides()` filtert `capability IS NOT NULL`, Gesamtwert-Zuordnungen sind dort unsichtbar. Vertrag `topology-read-model.md` „Geräteseitiger Rollen-Wert"; Beweise `EntityRoleAssignmentQuellMigrationTest` (5) + `SiteRollenApiTest` (6).
- **⚠ DIE ROLLEN-ZUORDNUNG REIST SEIT BEFUND L4 IM REGISTRY-PUSH — und die zwei Auflösungs-Schleifen SIND ein Zwillingspaar** (Scout `data/vp-portal-box-spiegel-s2` §4 L4). Bis dahin schrieb `PUT …/topology-roles` NUR `entity_role_assignment`, und niemand las die Tabelle für den Push: `Agent.Topology()` löste immer über `DefaultRole` auf, ein im Portal umgewidmeter Messpunkt oder ein als maßgeblich markierter Zähler blieb auf `:8484` beim Default — zwei Energieflüsse über dieselbe Anlage, die sich widersprechen konnten.
  - **Draht:** additiver `role_assignment`-Block je Descriptor (`edge-entity.schema.json`, Fixture `edge-entity.valid.registry-push-roles.json`), JE KANAL ein Eintrag `{channel, role, primary?}` — dieselbe Grammatik wie das Portal, weil die Zuordnung dort per KANAL getroffen wird. Gefüllt aus `EntityRegistryRepository.roleAssignments` (nach Kanal sortiert = deterministische Bytes); **ohne eine einzige gespeicherte Zuordnung fehlt der Block überall und die Nutzlast ist byte-gleich zu vorher.** `primary` reist NUR wenn true (ABSENT = false).
  - **⚠ Die Vorgabe-Regel für „maßgeblich" ist WÖRTLICH die der Cloud** (`TopologyService.topology` ⟷ `topology.Resolve`): der Default-Primary wird nur für Rollen vergeben, für die NIEMAND ausdrücklich maßgeblich gesetzt wurde — deshalb sammelt `Resolve` die ausdrücklichen Wahlen in einem ERSTEN Durchlauf über die ganze Anlage. Ohne diese Zwei-Pass-Form schnappt sich die erste Kapazität die Marke im Vorbeigehen, die Anlage trägt zwei Primaries und Box und Portal behaupten verschiedene maßgebliche Zähler. **Beide Schleifen zusammen ändern** (`topology.Derive`/`DefaultRole` bleiben die vektor-gepinnten Drillinge; `Resolve` gibt es nur in Go, der TS-Zwilling konsumiert die server-aufgelösten Kapazitäten).
  - **⚠ Eine Rolle, die der Box-Build nicht kennt, fällt STILL auf den Default zurück** (`topology.IsKnownRole`, die EINE Stelle) — der Push wird deswegen nie abgelehnt: eine Rolle ist Anzeige, kein Steuerweg, und eine neuere Cloud darf den Energiefluss einer älteren Box nicht zerreißen. Das ist die bewusste Asymmetrie zum Schema, dessen `enum` die HEUTIGE Menge festhält.
  - **⚠ Sie ändert NICHTS an der Geräte-Ableitung.** `componentapply.Derive` liest den Block nie; `inverter.json`/`sources.json` leiten ihre Rolle weiterhin aus dem Entitätstyp ab (`roleFor` kennt das Topologie-Vokabular gar nicht — dieselbe Begründung, aus der `driverBlock` die Rolle bewusst NICHT emittiert). Ein Rollen-Push erzeugt daher `SameAs` = unverändert: kein Schreibvorgang, keine Neu-Veröffentlichung auf dem lokalen Bus. Gepinnt von `componentapply.TestARoleAssignmentNeverTouchesTheDerivedPlan`.
  - **Auslöser:** `TopologyService.applyAssignments` stößt bei nicht-leerem Stapel einen `pushRegistryBestEffort` an — **NACH dem Commit** (beide Controller sind `@Transactional`; das `EntityAutoComposer`-Muster samt Mitnahme des Mandanten) und **best effort** (eine Rolle ist Anzeige; ein verlorener Push heilt der nächste beliebige, wie beim Umbenennen). **Bewusst NICHT über die `component_activation_outbox`:** die ist auf `(entity_id, revision)` einer Komponenten-FASSUNG geschlüsselt, und eine Rollen-Zeile darin verfälschte den Soll/Ist-Satz, den das Portal aus derselben Tabelle liest (`ORDER BY revision DESC LIMIT 1`).
  - **Beweise:** rein `EntityRegistryRoleAssignmentTest` (5) + `TopologyRolePushTest` (5) · Go `topology_test.go` (Zuordnung schlägt Default, ausdrückliche maßgebliche Wahl auch als LETZTE, unbekannte Rolle, ohne Zuordnung byte-identisch) + `entities_test.go` (die Fixture PER PFAD) + `agent/entities_roles_test.go` (die ganze Strecke Push-Bytes → `Topology()`, inkl. „welcher Zähler zählt").
