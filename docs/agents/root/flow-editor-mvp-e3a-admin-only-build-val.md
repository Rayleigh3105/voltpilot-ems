# Flow-Editor MVP (E3a): admin-only build → validate → simulate → rollout

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 58).


The first RUNTIME slice of the flow platform (contracts: `docs/contracts/v2/flow-graph.md` + `flow-artifact.md`, decisions D-11/D-13): platform-admins build typed flows in the portal, validate them against the V-1..V-8 rules, dry-run them on the existing Ersparnis-Simulation infrastructure, and activate them - the E2 flowc compiler is now WIRED (the former "Compiler folgt" stub is gone; see the "flowc-serve bridge" bullet). Deliberately WITHOUT live monitoring/SSE and WITHOUT customer access.

- **Storage + lifecycle:** `flow_definition` (api migration `V20260719000000`, RLS like measurement_point; PK `(flow_id, flow_version)`, partial unique index = at most one ACTIVE version per flow). The AUTHORITATIVE lifecycle (draft → simulated → active → retired) lives in the shared **`flows/FlowService`** (since E3b - see that section; both `AdminFlowController` and `SiteFlowController` are thin delegates)/`FlowRepository`; the document's `lifecycle` field is the contract's informative snapshot. The server STAMPS all identity (flow_id/version/site_id/tenant_id) into every stored document; saving onto a simulated/active version creates a NEW draft version (the response carries it - callers must not assume the version they PUT to). Endpoints under `/api/v1/admin/sites/{siteId}/flows` (platform-admin + X-Tenant-Id switcher over the RLS path, in `openapi.yaml`).
- **ONE catalog truth:** `services/api/src/main/resources/flowcatalog/catalog.json` (the initial nodes; port names PINNED by the contract example fixtures), served at `GET /api/v1/admin/flow-catalog`; the portal's `src/flows/catalog.json` is a SYNCED COPY guarded by `catalog.sync.test.ts` - change both together. Adding a node type is additive (palette/inspector/validation are data-driven).
- **U3 catalog additions + device-automation activation (design `data/vp-ems-ui-overhaul/report.md` §4.3, epic UO #514).** Three catalog nodes were added in lockstep to all three catalogs: **`vp.logic.and`/`.or`** (boolean combinators, two `a`/`b` bool inputs → one bool `result`, so the guided builder can wire compound conditions — V-1 allows it since each input takes exactly one edge; **the runtime combine keys on a COMPILE-TIME per-edge discriminator, not `msg.topic`** — see "flowc combinators" below), and **`vp.price.current`** (the current spot price as a `number` in ct/kWh, `group:daten`, compiles to a `vp-feed` with `feed:'price_current'` — the palette runtime feed is edge follow-up; feeds `vp.logic.threshold` directly, no price→number widening needed). **flowc `vp.schedule.window` now accepts the editor's ENUM `days`** (`alle`/`werktage`/`wochenende` → day-number array in compile) — previously flowc demanded a `0..6` array, so EVERY schedule flow (incl. the E3b Heizstab-Zeitplan) was silently un-compilable; the `scheduleDays()` helper fixes it (no committed fixture used it, so no pinned hash broke). **`FlowSimulationMapper` maps a DEVICE AUTOMATION** (a `vp.entity.control` action, no battery strategy node) **to the `standardSpeicher` baseline dry-run**, so a Wenn/Dann rule reaches `simuliert` and activates (a notify-only flow counts as an automation action too — `FlowSimulationMapper.hasAutomationAction` includes `vp.notify.push` — so it is simulable and activatable; only a BARE read with no action at all stays honestly unsupported). Two new fixtures + pinned hashes prove compile: `flow-graph.valid.compound-wallbox.json` (AND + schedule) + `flow-graph.valid.price-wallbox.json` (price condition); `pinned-compound-hash.txt`/`pinned-price-hash.txt` (self-seeded on first `node --test compile.test.js` run). Proofs: `FlowPeakShavingApiTest.deviceAutomationsBuildValidateSimulateAndActivate` (build→validate→simulate→activate, flag ON, fake flowc), `FlowGraphValidatorTest` combinator/price vectors + fixture-clean, `FlowSimulationMapperTest.deviceAutomationMapsToStandardSpeicherBaseline`, flowc `compile.test.js`/`serve.test.js` (2 fixtures + hashes), portal `guidedBuilder.test.ts` (round-trip incl. both E3b templates) + `steuerung.test.ts`. Portal detail: `frontend/portal/AGENTS.md` "U3 Steuerung area".
- **THREE catalogs must agree on the node-type SET: api (`flowcatalog/catalog.json`) ⟷ portal (`src/flows/catalog.json`) ⟷ flowc compiler (`edge-app/nodered/flowc/catalog.js` `TYPES`).** api↔portal is byte-equal (`catalog.sync.test.ts`); api↔flowc is guarded on THREE axes in `edge-app/nodered/flowc/compile.test.js` (#518 + #519 MEDIUM-6): **type-id set** equality, **per-type PORT shape** (api input names minus flowc's synthetic `trigger`, output names, and `requires_any_input` ↔ `requiresAnyInput`; the helper is itself tested against the pre-fix `vp.entity.control` shape so the guard is proven to bite), and **compiled-implementation reachability** — every `vp-feed` feed flowc can emit must exist in the palette's `FEEDS` whitelist, the axis that would have caught the dead `price_current` node. A type the EDITOR offers but flowc can't compile makes activation die with `compiler_rejected` ("unbekannter Katalogtyp …") AFTER the flow validated + simulated - the #518 bug where `vp.logic.gate` (bool→event, feeds `vp.notify.push`) was api/portal-only and `vp.logic.if` (bool→number, sets a value) was flowc-only. Both now exist in all three; `vp.notify.push`'s input is `event` (fed by the gate's rising edge) in all three. NOTE the catalogs are set-equal, NOT byte-equal: flowc's per-type PORT SHAPES can differ from api/portal (e.g. `vp.entity.control` is a single `value: number|bool` in flowc vs `value`/`setpoint`/`plan` in api/portal - pre-existing, out-of-scope drift); the guard checks type-id existence, not port structure. The notification automation (Schwellwert → Wenn/Dann-gate → Benachrichtigung) is pinned end-to-end: `flow-graph.valid.notify-threshold.json` fixture + `pinned-notify-hash.txt` (flowc `compile.test.js`/`serve.test.js`), `FlowGraphValidatorTest`/portal `validate.test.ts` (validates clean). api activation Testcontainers tests (`FlowApiTest`/`FlowPeakShavingApiTest`) FAKE the flowc transport (no Node in the JVM) - the flowc `serve.test.js` fixture IS the real sidecar compile proof.
- **Validator twins (the EdgeRef precedent):** `flows/FlowGraphValidator` (Java) and `src/flows/validate.ts` (TS) implement the same V-1..V-8 rules with shared broken-flow vectors (`FlowGraphValidatorTest` ↔ `validate.test.ts`); the contract example fixtures are executable checks on BOTH sides. D-13 claim derivation exists twice too (`FlowClaims` ↔ `model.ts deriveClaims`) with ONE structural rule: an entity-control node plan-fed by a DELEGATED strategy on the same entity derives NO own claim (else the pilot chain would V-5-conflict with itself). The server re-derives and REFUSES documents whose stored claims disagree - claims are not hand-editable.
- **Dry-run:** `FlowSimulationMapper` compiles the flow to its deterministic scenario mapping (a market or peak-shaving strategy → the "voltpilot" scenario incl. its Speicherschonung param; anything else → honest German 422; Eigenverbrauch is no longer a strategy node, report vp-nacht-bezug-e7 §3.3) and submits a normal Ersparnis-Simulation job over the site's master data; the flow-scoped poll endpoint flips draft → simulated on completion and records the summary.
- **Activation:** `FlowActivationService` consumes the `FlowCompiler` seam via ObjectProvider; the bean is now ALWAYS present (`FlowCompilerConfig` registers `FlowCompilerClient`), so `compiler_missing`/"Compiler folgt" is only reachable via the null-provider test seam. The gate is still the flag `voltpilot.flows.activation.enabled` (VOLTPILOT_FLOWS_ACTIVATION_ENABLED, default OFF - simulator-rig only; no production site is flagged), checked BEFORE compile, so a flag-off env refuses with `activation_disabled` and never contacts the sidecar. With the flag on: compile the REAL artifact via the sidecar, `FlowDeployment.requireArtifactShape` validates the manifest+bundle, then the D-11 publisher rolls it out. A sidecar outage / compiler rejection is caught BEFORE any DB write and returns `activated:false` (`compiler_unavailable`/`compiler_rejected`, German copy) - the flow stays "simuliert", never half-activated. The D-11 publisher `FlowDeploymentPublisher` (retained QoS1 `ems/{t}/{s}/{d}/v2/flows`, rides `voltpilot.provisioning.*`) + `FlowDeployment` (complete-desired-state set builder, 256/512 KiB budgets) carry the artifact's flowc `content_hash`/`min_palette_version` verbatim; activation stores the compiled artifact per version, so rollback = re-activating a previous version.
- **flowc combinators + the `vp.entity.control` input set (#519, pre-activation-flip fixes).** Three laws the compiler now holds, all proven by committed fixtures + pinned hashes (`flow-graph.valid.{guided-setpoint,market-starter,two-window-and}.json`): (1) **`vp.entity.control` mirrors the api catalog's inputs exactly** — `value: bool` (Ein/Aus), `setpoint: timeseries` (the guided "Sollwert setzen" rule wires `vp.logic.if.value` here) and `plan: plan` (the delegated strategy `wunsch` of the pilot chain / the AE7 starter templates), with the any-of rule `requiresAnyInput` instead of a hard-required `value`; compilation collapses all three onto the ONE `vp-desired` anchor. Before this every setpoint rule and every auto-started starter flow validated, simulated and then died at activation with `compiler_rejected`. (2) **D-13 plan-fed claim suppression** now exists in flowc too (`compile.js deriveClaims`, the twin of the api's `FlowClaims` / the portal's `deriveClaims`): a control node whose `plan` input is fed by a delegated strategy on the same entity derives NO own claim — otherwise the documented strategy→control chain V-5-conflicts with itself. (3) **`vp.logic.and`/`.or` key on a COMPILE-TIME per-edge discriminator**: the compiler emits a generated tag node per incoming combinator edge setting `msg._vp_src` to the graph port name, and the combinator body keys its `seen` map on that (AND = every declared port seen true). The former `msg.topic || "_"` key made two topic-less branches (two `vp.schedule.window`s, or two reads of one entity+channel) collapse into ONE slot, so a two-window AND was not degraded but WRONG — it fired during EITHER window. Changing any of this changes the artifact `content_hash` and therefore the pins: regenerate them DELIBERATELY (the tests no longer self-seed a missing pin, LOW-6).
- **flowc-serve bridge (the E2↔E3a connector, PR fm/vp2-flowc-wire).** The JVM api has NO Node runtime and MUST NOT reimplement the RFC-8785 JCS content hash, so the E2 flowc compiler runs as a tiny CLOUD-side sidecar `flowc` (`edge-app/nodered/flowc/serve.js` + `Dockerfile`, stdlib Node, `POST /compile` + `GET /health`, internal-only) - the `simulate-serve` pattern. `FlowCompilerClient` (impl of `FlowCompiler`, wired by `FlowCompilerConfig`, `voltpilot.flows.compiler.base-url`=`http://flowc:8099`) POSTs `{document}`, gets the compiled artifact back WITH flowc's own hash (200), or throws `FlowCompilerException` (422 = `compiler_rejected` carrying the sidecar's German message; transport/unexpected = `compiler_unavailable`). The `FlowCompilerHttp`/`JdkFlowCompilerHttp` seam lets tests fake the transport offline (the SimulationHttp/MastrHttp pattern). Sidecar added to BOTH composes (dev under the `flows` profile, prod as a normal internal service + published image) and the deploy build matrices; api env `VOLTPILOT_FLOWS_COMPILER_BASE_URL` in both. The sidecar is dependency-free (built from `canonicalize.js`/`catalog.js`/`compile.js`/`serve.js`); its `content_hash` comes from `compile.js` (the Go/JS JCS lockstep is untouched).
- **Portal:** Plattform nav `flows` → `pages/admin/FlowsPage` (Mandant→Anlage picker, cards + Vorlagen row incl. the pilot template) and `FlowEditorPage` (palette | hand-rolled SVG canvas | inspector, dark guard bar, live client validation, sim strip reusing SimulationRunView/ResultView). The flow-graph schema carries NO node positions (`additionalProperties:false`), so the canvas always renders the deterministic layered auto-layout (`src/flows/layout.ts`) - no drag persistence; connecting is click-output-then-input with type-compatible ports highlighted.
