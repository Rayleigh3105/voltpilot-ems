# In-slot load following: the DISCHARGE mirror of the trim (2026-07-30, P1)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 81).


The same quarter-hour gap with the sign flipped, and the one that cost real money - the Pilsting NIGHT (scout report `firstmate/data/vp-netzbezug-nacht-s3`, §6 P1). The plan discharges exactly what it FORECASTS the house to draw, so the forecast error is settled at the grid **in whichever direction it points** - both halves measured live on 2026-07-30: 21:22 MESZ plan −4,332 kW into a **7,117 kW** house = **2,79 kW GEKAUFT at ~32,5 ct** while the battery sat at **77 % SoC** (and the plan, believing the night smaller than it was, carried ~15 kWh unused into the morning, **≈ 4,9 EUR in ONE night**); 23:12 the mirror image, plan −6,7 kW into a **5,1 kW** house = **1,4 kW EXPORTIERT at ~21 ct** while that kWh was worth ~32,5 ct as avoided import hours later. Same architectural law as the trim: **the cloud decides the economics of the slot, the edge only enforces against MEASURED values** (the edge evaluates no price, ever). Since P1b (2026-07-30, captain go) the enforcement is **BIDIRECTIONAL**: in a flagged slot the target is `Entladung = max(load − pv, 0)`, i.e. **grid ≈ 0**, reached by raising a short discharge AND by limiting an overshooting one.

- **The rule (same module `slot_trim.py`)**: covering one AC kWh of house load from the battery COSTS `λ_t/eta + wear` (delivering 1 AC kWh drains `1/eta` stored kWh) and SAVES `import_price_t`, so it is economic iff `import_price_t > λ_t/eta + wear + margin` (the shared `SLOT_TRIM_MARGIN_CT_PER_KWH`). This is STRICTLY tighter than the charge-side test, so **the two duties can never contradict each other** (`test_load_follow.py` pins that as a property sweep). Again the model's own optimality condition, not a threshold.
- **Emission** (`solver._cover_load_from_battery`, stamped in `_with_explanation`; `PlanSlot.cover_load_from_battery`): only where the plan actually COMMANDS a discharge **and** plans NO grid exchange worth the name - **`|grid_kw| <= PLANNED_GRID_EXCHANGE_DEADBAND_KW` (0,05 kW), the "Netz ≈ 0" kink of role `eigenverbrauch`**. **BOTH sides are excluded, each for its own reason** (P1b, 2026-07-30): a planned IMPORT is a deliberate cheap-hour purchase (role `warten`) the duty must never undo, and a planned EXPORT is a deliberate sale (role `verkaufen`) that the BIDIRECTIONAL edge enforcement would otherwise cut back to zero grid - the edge receives only the setpoint, never the plan's own forecast grid power, so **the trade/overshoot distinction has to be made HERE**, where both numbers exist. That one condition is what keeps the price arbitrage untouched in both directions. Own kill-switch `OPTIMIZER_LOAD_FOLLOW_ENABLED` (deliberately NOT shared with the trim - the two push the setpoint in opposite directions on a control path, so an operator must be able to stop one without losing the other); no explain layer → no flag.
- **Contract**: the OPTIONAL per-slot boolean **`cover_load_from_battery`** = the edge's duty to TRACK commanded DISCHARGE to the MEASURED deficit `max(load − pv, 0)` - raise a short one, limit an overshooting one, **hard floor at zero discharge** (never a charge, never a direction flip). FAIL-OPEN like its twin (an inferred duty would be the price-blind Eigenverbrauchslogik). NO payload change for P1b - only the description/`x-failsafe` were written forward, `schema_version` stays 1.0 and the cloud is untouched (the flag's "Netz ≈ 0, nicht handeln" semantics already carried both directions). Fixtures `mqtt-schedule.valid.cover-load.json` + `…invalid.cover-load-not-boolean.json`.
- **Edge (`guards/loadfollow.go` `LoadFollower`, in `applySetpoint` right after the trim, before the peak guard)**: the DEEPEN half **CALLS `PeakShave(kw, 0, …)`** rather than re-deriving the bounds, so rated band / SoC floor / never-raise come from ONE proven piece of arithmetic. **Safety by algebra (the ONE invariant, both directions):** the correction only ever moves the predicted grid power **TOWARD zero - never past it, never further away**, so the site is never pushed into export (§14a export bound + feed-in cap untouchable) and the import is never raised above what entered the guard (that bound was applied to it). Where it bites the BATTERY stops contributing: exactly 0 with a house deficit, the remaining PV surplus without one (absorbing that would take a CHARGE = a price decision this guard must not take). The LIMIT half needs no bound of its own (a shrinking discharge magnitude cannot escape the rated band or SoC floor, never touches the SoC ceiling or the EEG solar-only clamp) and can never undo the later peak guard (it lands at predicted import 0 ≤ every allowance ≥ 0). A commanded CHARGE is never flipped. The plan-carried **peak reserve raises the SoC floor of the DEEPEN half only** (ordinary load covering is exactly what the reserve must survive - the fallback's rule; peak DEFENSE may still go below it); limiting only ever PRESERVES stored energy. Unknown pv/load → INACTIVE. The self-consumption fallback already follows pv − load, so it is a no-op there. **Hysteresis is symmetric around the zero-grid target** (engage immediately when `|predicted| > FollowEngageMarginKw` either way, release only after `FollowReleaseDwell` of the plan's OWN value tracking within the margin; the engaged state carries across a direction change). **Deliberate deviation from the trim: no step-limited follower on the applied value** - both directions are load following, and holding a stale deeper discharge while the deficit SHRINKS is precisely the 23:12 symptom.
- **The trade/overshoot distinction lives in the CLOUD, never on the edge:** the edge receives only the setpoint, so it cannot tell a DELIBERATE export from a forecast overshoot - which is exactly why the emission rule above excludes both trade directions. An UNMARKED slot is byte-for-byte untouched on the edge, so a sell window (role `verkaufen`) and a cheap-hour purchase (role `warten`) are both safe from the correction. Safety does NOT rest on that, though: a device paired with an OLDER cloud can still see a marked slot planning a small export; limiting it then HOLDS that energy (worth ≥ the water value, re-dispatched by the next 15-min replan) - a bounded, self-correcting deferral, unlike the unpriced export the correction exists to stop.
- **A correction is DELIBERATE IN EITHER DIRECTION, never a failed write** (the same PR #280 lesson): the FOLLOWED value is published, so the readback matches it. Surfaced as `state.FollowInfo` (with `direction` = `deepen`|`reduce`) → `control.js VPControl.deriveFollow` → the same `#ctrlReason` line, naming the direction ("… – Entladung angehoben" / "Folgt dem gemessenen Hausverbrauch … – Entladung begrenzt", each with its OWN honest cause, NORMAL mode). An older device reporting no direction gets the neutral wording - never claim one it did not send.
