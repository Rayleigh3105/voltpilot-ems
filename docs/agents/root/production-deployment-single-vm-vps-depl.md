# Production deployment (single VM/VPS, "deploy like saalo")

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 41).


MVP-on-one-server: an external reverse proxy on another host terminates TLS (the company's **Nginx Proxy Manager** for the internal-VM deployment; Caddy stays documented as the alternative), the whole server-side stack runs from **`docker-compose.prod.yml`** (a self-contained, standalone file - NOT merged with the dev `docker-compose.yml`), and Forgejo does push-to-deploy once CI secrets are set. Full guide in [`docs/deploy.md`](docs/deploy.md); the recipe mirrors the saalo repo's proven pattern.

- **Two deploy paths, one compose.** (a) **Manual first deploy, no CI** (the leading `docs/deploy.md` section "Erstes Deployment (interne Ubuntu-VM)"): git clone to `/srv/docker/voltpilot` on the VM (the clone IS the deploy dir - the compose bind-mounts `infra/prod/`, `infra/mqtt/`, `deploy/keycloak/themes/` by relative path), fill `.env`, stage the MQTT certs (required - EMQX file-mounts them), then `docker compose -f docker-compose.prod.yml build && ... up -d`. Every app service carries a `build:` context next to its `image:` name, so `build` tags local images under the registry names and `up` uses them without pulling. **Seit dem Cutover VM -> k3s (03.08.2026) ist dieser Pfad HISTORISCH/Hand-Referenz** - die VM-Zwillinge sind gestoppt und der laufende Betrieb kommt aus dem Cluster. (b) **CI** (`.forgejo/workflows/deploy.yaml`): Images bauen/pushen + gitops-Tag-Bump; **der frühere SSH/SCP-Roll-out auf die VM ist ENTFERNT** (ein Lauf hätte die gestoppten Compose-Zwillinge wiederbelebt = zweiter Optimierer gegen dieselben Live-Anlagen; PR `fm/vp-deployfast-retire`).
- **Two public ports only.** `frontend` on `APP_PORT` (plain HTTP, firewalled so only the reverse-proxy host reaches it) and EMQX `8883` (mTLS, for devices - **TCP, not proxied by NPM's HTTP proxy hosts**; devices dial `<VM-IP>:8883` directly, or an NPM Stream). Everything else (api/keycloak/keycloak-db/timescaledb/redpanda/ingest/writer/collectors) is internal on the `voltpilot-prod` network; `1883`/`18083` are loopback-only. **The frontend's nginx is the single web entry point** (`frontend/portal/nginx.conf`): serves the SPA and reverse-proxies `/api/ -> api:8090` and `/auth/ -> keycloak:8080`, so the API and Keycloak stay internal. The proxy must forward `https://${DOMAIN} -> http://VM:${APP_PORT}` preserving `Host` and setting `X-Forwarded-Proto: https` - NPM's default proxy-host template does both (enable Block Common Exploits + Websockets Support); the `/auth` login flow breaks without that header.
- **Keycloak in prod mode.** `start --import-realm` against a **dedicated** `keycloak-db` (isolated from TimescaleDB, mirrors saalo). Served under the `/auth` relative path (`KC_HTTP_RELATIVE_PATH`, `KC_HOSTNAME=https://${DOMAIN}/auth`, `KC_PROXY_HEADERS=xforwarded`). Prod realm `infra/prod/keycloak/voltpilot-realm.json` parametrizes the browser origin, confidential secret and Portal-Admin password via `${VP_PUBLIC_ORIGIN}` / `${VP_API_CLIENT_SECRET:change-me}` / `${VP_PORTAL_ADMIN_PASSWORD:admin}` (Keycloak-26 realm-import placeholder replacement reads env vars as `${VAR}`/`${VAR:default}`; the Wildfly-era `${env.VAR}` prefix is NOT substituted and aborts the import - verified on 26.0.5; all vars set on the keycloak service). So the api's issuer is `https://${DOMAIN}/auth/realms/voltpilot` while JWKS is fetched internally at `http://keycloak:8080/auth/realms/voltpilot/...certs` (the same issuer-trap split as dev). The prod realm mirrors the dev realm's **admin increment** (platform-admin role, seeded `admin` Portal-Admin user, `realm-management` service-account grants, declarative user profile for `tenant_id`), and the prod api sets the matching env: `ADMIN_DB_PASSWORD` (the BYPASSRLS `voltpilot_admin` role would otherwise run on its hardcoded dev password) and `KEYCLOAK_ADMIN_BASE_URL=http://keycloak:8080/auth` (note the `/auth` path - the dev default without it 404s in prod). **Keycloak-26 prod-mode footgun:** `start --import-realm` strict-parses the realm JSON and ABORTS boot on unknown fields (e.g. a `_comment` key) - `start-dev` never caught this; docs for the prod realm live in `infra/prod/keycloak/README.md` instead.
- **VoltPilot Keycloak login theme** in `deploy/keycloak/themes/voltpilot/` (login only; saalo's structure: `parent=keycloak.v2` + one override stylesheet, so ALL flows incl. error/forgot-password pages inherit the styling). Colors/typography come from the portal design-system tokens (`frontend/portal/designsystem/tokens/*.css`), the wordmark is the real logo PNG copied from `designsystem/assets/`, DE/EN message overrides brand the titles, and both realm imports set `loginTheme: voltpilot` + enable `de` as the default locale. The theme dir is bind-mounted read-only into keycloak in BOTH composes; the deploy workflows scp it and `docker compose up -d --force-recreate keycloak` after `up -d`: in `start` mode themes are cached at boot AND pre-gzipped into `/opt/keycloak/data/tmp/kc-gzip-cache` on the container FS, which SURVIVES a plain `restart` - browsers (gzip) then still get the OLD css while curl (no gzip) sees the new one (haunted-cache footgun, verified on 26.0.5). Dev `start-dev` keeps the caches off, but an already-running dev keycloak needs ONE `up -d` recreate to pick up the new theme mount + realm setting.
- **Project Keycloak image (`deploy/keycloak/Dockerfile`) - the k8s-cutover prerequisite.** Compose bind-mounts the realm import + the login theme into the STOCK upstream image; Kubernetes cannot supply either the same way, so the GitOps Deployment pulls a project image that **bakes both in** and pre-runs `kc.sh build` (hence its `start --optimized`). Three facts that keep it correct: (1) the **build context is the REPO ROOT** (like `services/optimization`), because realm (`infra/prod/keycloak/`) and theme (`deploy/keycloak/themes/`) live in different directories - the CI matrix entry therefore carries an explicit `dockerfile:`; (2) exactly three Keycloak **BUILD** options are baked (`KC_DB`/`KC_HEALTH_ENABLED`/`KC_HTTP_RELATIVE_PATH`) and they MUST equal what the runtime supplies, or a `start --optimized` refuses to boot - everything host-/secret-specific stays runtime, so **no secret is in the image**; (3) the version pin lives in BOTH `ARG KEYCLOAK_VERSION` and the compose `image:` default and must move together (two Keycloak versions against one DB otherwise). All three, plus "does CI actually build it", are guarded by section 4 of `tools/deploy/verify-migration-deploy.sh` (proven to bite on each drift). Compose is switchable but UNCHANGED by default: `image: ${KEYCLOAK_IMAGE:-quay.io/keycloak/keycloak:26.0.5}` - with the var unset the resolved prod compose is byte-identical to before, and setting it to the project image leaves the mounts overlaying byte-identical files. `KEYCLOAK_IMAGE` is a full reference and is NOT pinned by `${IMAGE_TAG}`. Rationale + operator steps: [`deploy/keycloak/README.md`](deploy/keycloak/README.md); the `keycloak` service deliberately has **no compose `build:` block** (it would tag the local build under the upstream image name and shadow it).
- **Images for the CI path.** CI builds and pushes **nine** images to `git.tecmaxx.de/mamotec/voltpilot-ems/<component>:{latest,<sha>}` (`api`, `ingest`, `timescale-writer`, `frontend`, `market-data`, `forecast`, `optimization`, `flowc`, `keycloak`); the compose deploy pulls the first eight pinned to `${IMAGE_TAG}` = the commit SHA, while `keycloak` is built for the cluster and is opt-in on compose (see the bullet above). The build matrices of `deploy.yaml` and `deploy-fast.yaml` are kept in **lockstep** - add a component to both, or a gated deploy publishes a set the fast path does not. Each has a prod Dockerfile; the **frontend** Dockerfile grew an nginx.conf + `VITE_*` build args (`VITE_API_BASE` empty => same-origin `/api`; `VITE_KEYCLOAK_URL=https://${DOMAIN}/auth`) - the compose `build:` block passes the same args from `.env` for the manual path (changing `DOMAIN` means rebuilding the frontend).
- **Collectors** (all in the dev stack's `serve` mode, no hand-rolled loops): `market-data` (`serve --persist`, 6h refresh into `day_ahead_prices` over the superuser conn; source per `MARKET_DATA_SOURCE` - keyless energy-charts default, `entsoe` + `ENTSOE_SECURITY_TOKEN` switches to ENTSO-E, see `docs/deploy.md`), `weather-collector` (Open-Meteo `serve --persist`, 3h refresh into `weather_forecast`; reuses the forecast image with the `weather_collect` entrypoint) and `forecast` (the shadow-mode forecast collector `forecast_collect serve` - see "Shadow-mode forecasting"). The two non-RLS hypertables (`day_ahead_prices`/`forecast`) are created by the prod init script `infra/prod/timescale/00-collector-tables.sql` (mirrors the service migrations; runs on a fresh volume before the api's Flyway owns the core schema). Edge/Node-RED + the SunSpec sim are NOT in prod (they run on-device).
- **CI/CD** in `.forgejo/workflows/`: `deploy.yaml` (gated: test matrix over all services -> build+push all images -> `gitops-tag-bump`) and `deploy-fast.yaml` (dasselbe ohne Test-Gate). **Kein Job fasst die Prod-VM mehr an** (Cutover 03.08.2026): der `deploy`-Job samt scp/ssh-Action ist entfernt, `DEPLOY_HOST/USER/PASSWORD` werden nicht mehr gelesen; Argo CD deployt aus dem gitops-Repo. Benötigte Forgejo-Secrets: `FORGEJO_USERNAME/PASSWORD`, `DOMAIN`, optional `GITOPS_PUSH_TOKEN`. `edge-images.yaml` ist davon unberührt (Edge-Images sind kein VM-Deploy). No browser smoke suite yet, so that gate is deferred (the Testcontainers tests already cover ingest/RLS/OIDC).
- **CI-Zielpfad für den Cluster: der Deploy IST ein Commit (`gitops-tag-bump`, Captain-Go 2026-08-01).** Nach grünen Image-Builds schreibt derselbe Lauf den Bild-Stand ins **gitops**-Repo (`git.tecmaxx.de/mamotec/gitops`) fort: der Job setzt den `images:`-Block von `apps/voltpilot/overlays/prod/kustomization.yaml` auf `${GITHUB_SHA}` und committet als `ci(images): voltpilot-ems@<sha>`. Bewusst OHNE `:latest` und ohne Argo-CD-Image-Updater (Begründung im gitops-README „CI/CD-Zielpfad"); Rollback = `git revert`. Der Job hängt an `needs: build`, **nicht** am VM-Deploy - beide sind unabhängige Abnehmer derselben Images, der VM-Job bleibt bis zum Cutover unverändert. Argo steht auf manuellem Sync, der Bump landet also nur im Git. Vier Dinge, die man wissen muss: (1) **kein `kustomize edit set image`** - v5.8.1 (die von der gitops-CI gepinnte Version) formatiert die ganze Datei um, sortiert den Block und **löst die Kommentare von dem ab, was sie erklären**; gemessen 85 statt 9 Diff-Zeilen, was die Auditierbarkeit zerstört, auf der das ganze Deploy=Commit-Design ruht. Stattdessen `tools/deploy/gitops-image-bump.sh` (awk, nur `newTag:`-Zeilen im `images:`-Block) mit einem **Guard, der die eigene Ausgabe zurückliest und verweigert, sobald eine andere Zeile abwiche**. (2) Idempotent: gleicher sha = **kein Leer-Commit** (exit 2, Job grün). (3) **Ohne `GITOPS_PUSH_TOKEN` überspringt der Job sauber grün** (das `secrets`-Kontextobjekt ist in `if:` nicht verfügbar, die Prüfung steht deshalb im `run:`), damit der Zielpfad vor dem Secret mergebar ist. (4) Die Push-Schleife rebased NICHT - beide konkurrierenden Läufe fassen exakt dieselben Zeilen an; sie leitet bei jedem der drei Versuche vom frischen `origin/main` neu ab, was per Konstruktion konfliktfrei ist. Beweise (Docker-frei, im `deploy.yaml`-Test-Gate als Matrix-Leg `gitops-tag-bump`): `tools/deploy/test-gitops-image-bump.sh` (Edit gegen die committete Kopie des echten Overlays in `tools/deploy/testdata/`) und `tools/deploy/test-gitops-bump-workflow.sh` (führt den **echten `run:`-Text aus beiden Workflows** gegen ein lokales bare-Repo aus: Lockstep, Skip, Commit-Form, Idempotenz, verlorenes Push-Rennen, Form-Guard). Operator-Anleitung: [`docs/deploy.md`](docs/deploy.md) „gitops-Tag-Bump (CI-Zielpfad)".
- **Secrets** template: [`.env.prod.example`](.env.prod.example) (copied to `/srv/docker/voltpilot/.env`; `${VAR:?}` aborts the deploy if blank). Every required secret has an `openssl rand` hint. The device mTLS certs are staged on the VPS out of band (never in the repo/images); `SPRING_PROFILES_ACTIVE=local` seeds the demo tenants for a first look - blank it (and drop the demo realm users) for a real launch.
- **Host/domain are placeholders** throughout (captain fills `DOMAIN`, the VPS host, and the secrets later). Nothing here needs live infra to validate: `docker compose -f docker-compose.prod.yml config` and the workflow YAML both parse.

### Einen ROTEN CI-Lauf untersuchen (Forgejo 13.0.4)

Vier Dinge, die jede Untersuchung sonst in die falsche Richtung schicken:

- **Welches Leg rot war, sagt AUSSCHLIESSLICH `GET /api/v1/repos/mamotec/voltpilot-ems/actions/tasks`.** Auf dieser Forgejo-Version antworten `actions/runs/{id}/jobs`, `actions/jobs/{id}/logs` und `actions/runs/{id}/logs` **allesamt 404** - es gibt über die API KEINE Protokolle, nur den Ausgang je Task. `actions/tasks` liefert je Task `name` („Test (api)"), `status`, `head_sha`, `run_number` und `run_started_at`/`updated_at`; deren Differenz IST die Dauer. Beachten: `actions/runs/{run}` nimmt die **API-Run-Id** (z. B. 1538), die Weboberfläche zeigt die **`run_number`** (183) - die beiden sind verschieden, und mit der falschen bekommt man 404. Basic-Auth mit dem Git-Credential (`git credential fill`) genügt für die API; die WEB-Oberfläche lässt sich damit NICHT anmelden (ein PAT ist kein Web-Passwort), also führt auch der Browser nicht an die Protokolle.
- **`deploy-fast.yaml` hat KEIN Test-Gate, deshalb rottet die Gate-Fläche unbemerkt.** Fast alle Merges laufen über den schnellen Pfad; das geprüfte `deploy.yaml` wird nur von Hand angestossen und lag zwischen Lauf #95 (17.07.2026) und #183 (07.08.2026) drei Wochen still. Ein neu hinzugefügter Gate-Schritt ist damit bis zum nächsten Handstart **nie auf dem Runner gelaufen** - beim Lauf #183 traf das gleich zwei Legs: die beiden nginx-Rauchtests des Portals (`npm run test:csp` seit #160, `npm run test:cache` seit #283) und das ganze Leg `ota-release` (seit #327/#329). **Regel daraus: wer einen Schritt ins Gate hängt, stösst `deploy.yaml` EINMAL von Hand an** - sonst ist der erste Beleg ein roter Lauf Wochen später, dessen Ursache dann fälschlich beim jüngsten Merge gesucht wird.
- **Ob Docker auf dem Runner lebte, verrät der Dauer-Vergleich, nicht der Ausgang.** Die JVM-Legs überspringen ihre Testcontainers-Tests ohne Docker still (`disabledWithoutDocker`) und melden trotzdem **success** - ein grünes api-Leg beweist also nichts. Belastbar ist das Verhältnis CI-Dauer zu lokaler Dauer: liefen die Container wirklich, liegt es stabil bei ~2,6-2,7× (07.08.2026 gemessen: api 19m35s CI zu 7m28s lokal, ingest 3m01s zu 1m08s). Ein api-Leg, das in ein, zwei Minuten „durch" ist, hat in Wahrheit nur die Unit-Tests gefahren.
- **⚠ Ein `panic: test timed out` ist erst dann „zu langsam", wenn man es NACHGEMESSEN hat.** Der Tag-Lauf `edge-2026.08.20` starb im Edge-Gate an der 600-s-Vorgabe von `go test` im Paket `internal/agent` - und die naheliegende Lesart („`-race` auf einem geteilten Runner ist eben langsam") war falsch: es war ein echter Deadlock in `Bus.Close` (`edge-app/AGENTS.md`, mochi-mqtt). Der Unterschied ist LOKAL in Minuten zu klären, ohne CI: `go test -race -p 1 -timeout 40m -v ./internal/<paket>/` laufen lassen und beobachten, ob die Ausgabe STEHENBLEIBT (`ps` zeigt dann ~0 % CPU trotz laufender Uhr). Bleibt sie stehen, gibt `kill -QUIT <pid des .test-Binärs>` den vollen Goroutinen-Abzug - zwei Stapel, die auf derselben Sperre warten, sind der Beweis. **Ein Timeout hochzudrehen, ohne diese fünf Minuten investiert zu haben, verdeckt genau die Klasse Fehler, für die das Gate da ist.** Die Frist gehört trotzdem explizit in den Workflow (`-timeout` ist PRO PAKET, die Vorgabe sind 10 min) - als Wedge-Detektor, nicht als Budget.

**Ein Gate-Schritt, der nur auf einer Entwicklermaschine lief, ist ungeprüft - die drei Fallen des Laufs #183, alle reproduziert:**

- **Ein veröffentlichter Port landet auf dem DOCKER-HOST, nicht im Job.** Läuft der Job selbst in einem Container am gemounteten Socket (die Vorgabe eines Forgejo-/Gitea-Runners), ist sein eigenes `127.0.0.1` nicht das des Docker-Hosts: `docker run -p …` + `curl 127.0.0.1:$PORT` ist dort tot, während Testcontainers-Suiten überleben (sie lösen den Docker-Host selbst auf). Genau diese Asymmetrie liess die JVM-Legs grün und die zwei handgerollten Portal-Rauchtests sterben. Die Antwort ist ein **Sidecar-Container in DERSELBEN Netz-Namensraum** (`--network container:<cid>`, `frontend/portal/test/smoke-lib.sh`) - ein Weg, den beide Umgebungen gehen, statt eines Rückfalls, den nur die kaputte je ausführt. Nachgestellt mit `docker run -v /var/run/docker.sock:/var/run/docker.sock docker:cli`. **Der Bind-Mount eine Ebene tiefer ist die Schwester dieser Regel - siehe den eigenen Block am Ende dieses Abschnitts.**
- **`git tag -a` braucht einen TAGGER, und `-c user.*` vom vorherigen `git commit` gilt dafür NICHT.** Auf einem frischen Runner gibt es keine globale git-Identität → Status **128**. Jede Entwicklermaschine hat eine, also fällt es nur in CI auf. Identität nach `git init` ins Repo schreiben (`git config user.email/user.name`), dann erbt sie jedes Kommando des Blocks.
- **⚠ `stat -f` heisst auf BSD/macOS „Format", auf GNU/Linux „FILESYSTEM-Status" - und GELINGT dort.** `stat -f '%OLp' … || stat -c '%a' …` sieht portabel aus, ist es aber nicht: auf Linux wird der Rückfall NIE erreicht und der Vergleich bekommt einen Absatz Dateisystem-Daten statt `600`. Richtig ist die umgekehrte Reihenfolge (`ota_file_mode` in `tools/ota/selfcheck-env.sh`) - BSD kennt `-c` gar nicht und bricht sauber ab.

**⚠ DER RUNNER LÄUFT ALS ROOT, und root ignoriert das Schreib-Bit** (Lauf #278, Tag `edge-2026.08.21` - dieselbe Klasse, ein Lauf später). `agent.TestDeleteSourceRollsBackOnPersistFailure` machte das Datenverzeichnis per `os.Chmod(dir, 0o500)` unschreibbar und behauptete dann „der Persist muss scheitern". Für root ist das ein No-op (er umgeht die DAC-Prüfung): der Schreibvorgang GELINGT, `DeleteSource` gibt `nil` zurück, und die Zusicherung feuert - auf einem völlig gesunden Baum, während jede Entwicklermaschine grün bleibt. Nachgemessen im selben Image, derselbe Code: `uid=0` FAIL, `uid=65534` ok. **Regel: einen Fehlschlag NIE über Dateirechte erzwingen, sondern über eine TYP-Kollision** - ein Verzeichnis dort, wo eine Datei geschrieben wird (`EISDIR`, jetzt `sources.Store.TempPath`), oder eine Datei dort, wo ein Verzeichnis angelegt wird (`ENOTDIR`, der Präzedenzfall `enroll.TestLocalInitFailureSurfacesDeviceError`); über einen Typfehler kommt kein Privileg hinweg. Wächter gegen die ganze Klasse ist `sources.TestNoGoTestForcesAFailureWithFilePermissions` (läuft den Modulbaum ab und verweigert jedes `os.Chmod`/`os.Mkdir*` in einem `_test.go`, dessen Modus das Eigentümer-Schreibbit fallen lässt; mutationsgeprüft). Sichtbar wurde es erst jetzt, weil der Schritt `Go core (race)` erst mit #520 ins Tag-Gate kam und sein erster Lauf am localbus-Deadlock von #522 starb - **ein Gate-Schritt gilt als ungeprüft, bis er EINMAL grün durchgelaufen ist**, nicht schon, wenn er existiert.

**Und: ein Selbsttest, der sein stderr verwirft, kann seinen Ausfall nicht erklären.** Beide OTA-Selbsttests warfen die Fehlerausgabe ihres Stubs und ihres git-Blocks weg (`>/dev/null 2>&1`); übrig blieb ein nackter Abbruch. Sie melden jetzt zu Beginn ihre Umgebung (Werkzeuge, `GOPROXY`, Loopback, Netz, Container-Lage) und nennen bei einem Abbruch Zeile und Kommando - `tools/ota/selfcheck-env.sh`, von beiden Skripten eingebunden.

**⚠ DER RUNNER IST LINUX - EIN TEST, DER AUF DIE ZUSTELLREIHENFOLGE ZWEIER I/O-EREIGNISSE BAUT, IST EIN RENNEN** (Tag `edge-2026.08.22`, zwei Fehlschläge im Schritt „Node-RED runtime and drivers", 860/857/2). Beide hingen am Ein-Klient-Solarman-Stub in `edge-app/nodered/deye-control.e2e.test.js`: sein `state.live` zählt am `'close'` des SERVER-Sockets herunter, und das ist ein I/O-Ereignis - zugestellt erst in der nächsten Poll-Phase. Die ÜBERGABE der Bus-Warteschlange verbindet den nächsten Halter aber absichtlich unmittelbar (`bus-arbitration.js`: „wer freigibt, ÜBERGIBT"), also im selben Durchlauf. macOS stellte das `close` vor dem `accept` zu und gewann, Linux umgekehrt: der Stub verwarf die legitime Folgeverbindung, der Knoten wartete sein volles Socket-Budget ab (8 s Lese-Poll bzw. 12 s Einmal-Auftrag) und meldete `unreachable`/`Zeitüberschreitung`. **Beide Reihenfolgen sind erlaubt - der Test war auf JEDER Plattform ein Rennen, Linux verlor es nur zuverlässig.** Regel für jeden Stub, der EINE Ressource modelliert: über die ECHTE Überlappung urteilen, nie über die Ereignisreihenfolge - hält der Halter eine OFFENE Anfrage, ist eine zweite Verbindung sofort ein zweiter Klient; ist er still, kann sein Schliessen unterwegs sein, also parken und bedienen, sobald er wirklich zu ist. Festgenagelt von den zwei Tests „ein Halter MITTEN in einer Anfrage …" und „ein Nachfolger, dessen Vorgänger gerade SCHLIESST, …" (beide mutationsgeprüft). **Reproduzieren geht NUR im Container** - `docker run --rm -v "$PWD:/w" -w /w/edge-app node:22 …`; auf macOS ist der Lauf grün. Root ist hier NICHT die Variable (Node 22 und 25 fallen beide, als root wie als 1000).

**⚠ EIN TEST, DER EINE FRIST GEGEN GENAU DEN TIMER PRÜFT, DER AUF SIE GESETZT IST, IST EIN RENNEN - und `setTimeout` feuert bis zu 1 ms VOR `Date.now()`** (Befund 26.08.2026, `edge-app/nodered/curtail-lease.e2e.test.js` „HANG path"). Der Abregel-Executor kappt jede Operation auf das RESTBUDGET des Zyklus (`sunspec/curtail-lease.js` `opTimeoutMs`), gegen ein nie antwortendes Gateway läuft die Operation der ersten Einheit also GENAU auf der Frist ab - und ob die zweite Einheit danach `Date.now() > deadlineAt` sieht, entscheidet ein Bruchteil einer Millisekunde. **Nachgemessen: `setTimeout(fn, N)` ruft in ~2 % der Fälle zurück, während `Date.now() - start` noch `N-1` ist** (libuv rechnet mit seiner zwischengespeicherten Schleifenzeit); die zweite Einheit rutschte dann am Budget-Tor vorbei, machte eine zweite Operation auf dem `OP_TIMEOUT_MIN_MS`-Boden und die Ursache „Zeitbudget erschöpft" tauchte nie auf. Gemessene Fehlerrate des Tests: **2/40 ohne jede Last, 3/30 unter 24-facher CPU-Last** - ein Kandidat für einen roten Lauf ohne Codebezug, und ein größeres Budget verschiebt den Gleichstand nur. **Die Lösung ist, die verstrichene Zeit zu SAGEN statt sie zu erlaufen:** jeder Flow-Test in diesem Verzeichnis reicht dem vm-Kontext ohnehin sein eigenes `Date` (`Buffer, Date, Math, …`) - das ist die vorhandene Naht, also bekommt `runFunctionNode` ein `clock`-Argument (Vorgabe: das echte `Date`) und der Test schiebt die Uhr des KNOTENS in dem Moment vor, in dem die hängende Anfrage nachweislich auf dem Draht liegt (der `hang`-Stub liest seinen Socket jetzt und ruft `onRequest` - antworten tut er weiterhin nie). Echte Dauern bleiben unberührt, das Produktverhalten ändert sich um kein Byte. Danach 0/60 ohne und 0/45 unter Last. **Regel für jeden künftigen Test hier: nie eine Frist gegen ihren eigenen Timer behaupten - die Uhr injizieren.**

**⚠ EIN FELD, DAS DIE PRODUKTION NUR BEIM KONSTRUIEREN SCHREIBT, DARF EIN TEST NICHT NEBEN DER LAUFENDEN SCHLEIFE ZUWEISEN** (Tag `edge-2026.09.0`, Lauf 1889; fünf P6-Wallbox-Tests fielen mit „race detected"). `Agent.arb` wird in `agent.go New` genau EINMAL geschrieben, bevor die erste Goroutine existiert - deshalb liest der Executor es ohne Schloss, und das ist unter dem Go-Speichermodell korrekt. Der Test-Helfer wies dasselbe Feld aber NACH `startOcpp` zu, während die OCPP-Schleife es schon las: ein reiner TEST-Wettlauf über gesundem Produkt-Code. **Der Fix gehört deshalb in den Test, nie in eine neue Sperre am Produkt** - eine Mutex für eine Mutation, die es in Produktion gar nicht gibt, wäre test-getriebene Komplexität auf einem heissen Pfad. Die Form, die das Haus benutzt, ist die des echten Agenten: das Feld VOR dem Start installieren (leer) und danach ausschliesslich über die intern gesperrten Methoden des Objekts füllen (`Arbiter.SetEntities`/`SubmitInternal`/`Tick` - wörtlich der Registry-Pfad aus `entities.go`). **Regel für jeden künftigen Rig-Helfer: schreibt er ein `Agent`-Feld, gehört es entweder unter dessen bestehende Mutex (`entMu`, `ocpp.mu`, `wallbox.mu`) oder vor den Start** - `-race` findet den Rest, aber erst im Tag-Lauf.

**⚠ Ein fehlgeschlagener Test darf das Gate ROT machen, nie AUFHÄNGEN.** Lässt ein Test dieser Datei bei gerissener Zusicherung einen Klient-Socket offen, wartet `server.close()` im `finally` auf ihn, der Prozess wird nicht fertig - und der Lauf läuft statt in ein rotes Ergebnis in die 90-Minuten-Schranke des Jobs. Deshalb gehören die Sockets ins `finally`, nicht ans Ende des `try` (beim Bau am eigenen Mutationstest aufgefallen: die Mutation hing, statt zu melden).

**⚠ `node --test` an der nodered-Wurzel ist NICHT die Gate-Form** - Node sammelt jedes `test/`-Verzeichnis mit ein und zieht damit die Mocha-Specs von `vp-palette` herein (`describe is not defined`). Die reproduzierbare Form ist **`npm test` in `edge-app/nodered`**: dieselbe Auswahl wie der Gate-Schritt, vp-palette ausgeschlossen (es hat seinen eigenen Schritt). Der Workflow schliesst vp-palette seit dem Fix ausdrücklich aus - heute trennt sie nur die Namenskonvention (`*_spec.js` gegen `*.test.js`), eine einzige künftige `*.test.js` dort hätte den Schritt sonst still gerissen.

**⚠ EIN LOCKFILE, DAS AUF DEN FIRMEN-SPIEGEL ZEIGT, MACHT SEINEN GATE-SCHRITT AUSSERHALB DES FIRMENNETZES UNAUSFÜHRBAR.** `edge-app/nodered/vp-palette/package-lock.json` löste JEDES seiner 600 Tarballs über `http://artifactory.dach041.dachser.com:80/...` auf (Klartext-HTTP) - `npm ci` scheiterte damit überall sonst mit `ENOTFOUND` je Paket und dem irreführenden `Exit handler never called!`, mocha wurde nie installiert. Seit dieser Runde zeigt es wie `frontend/portal/package-lock.json` auf `registry.npmjs.org` (reiner Präfix-Tausch; **`npm ci` prüft jeden Tarball gegen den gespeicherten `integrity`-sha512, ein grüner Lauf IST deshalb der Beweis, dass die öffentliche Registry bytegleiche Tarballs liefert** - Paket, Version und Hash bleiben unverändert). Gemessen: `npm ci` exit 0, `npm test` 119 passing. **`edge/sim/package-lock.json` hängt weiterhin am Artifactory** und wurde bewusst nicht angefasst: es liest kein `npm ci`, sein Dockerfile nutzt `npm install` gegen die Vorgabe-Registry. Wer ein neues Lockfile einbringt, prüft die `resolved`-Hosts - der Gate-Schritt `vp-palette` war bis hierher NIE grün gelaufen, weil frühere Läufe vorher starben.

**⚠ EIN BIND-MOUNT AUS DEM WORKSPACE FUNKTIONIERT AUF DIESEM RUNNER NIE** (Tag `edge-2026.08.23`, Lauf 281 - der vierte Fehlversuch in Folge, jeweils an der nächsten Stufe). Es ist dieselbe Ursache wie beim veröffentlichten Port oben, nur die andere Seite: **was der DAEMON auflöst - Pfade wie Ports - gehört dem HOST, nicht dem Job.** Der Job fährt selbst in einem Container und spricht den Daemon des Hosts an; den Workspace-Pfad des Jobs gibt es dort nicht. Linux-Docker **legt eine fehlende Bind-Quelle als leeres VERZEICHNIS an** und scheitert dann daran, ein Verzeichnis auf eine DATEI zu mounten - die Meldung `Are you trying to mount a directory onto a file` beschreibt also nicht das Compose, sondern den Runner. Drei Konsequenzen, alle in `edge-app/test/e2e-compose.sh` + `Dockerfile.broker` umgesetzt:

- **Eine Datei kommt über einen BUILD-KONTEXT in einen Container, nie über einen Bind** - den Kontext streamt der CLI-Client aus SEINEM Dateisystem zum Daemon, er ist also von dieser ganzen Klasse nicht betroffen (deshalb bauten die Images auch im roten Lauf fehlerfrei). Ein winziges Image mit eingebackener Konfiguration ist der Weg; compose `configs:` mit `content:` wäre der andere, setzt aber Compose ≥ 2.23 voraus - eine Version, die ein Rig vom Runner nicht annehmen darf.
- **Ein Dienst, der einen Bind braucht und für den Beweis nicht gebraucht wird, wird über ein nicht angefordertes `profiles:` weggelassen.** Ein Overlay kann einen Dienst der Basisdatei nicht löschen, und `volumes: !reset` braucht Compose ≥ 2.24. (So fällt der OTA-Sidecar mit seinem `.:/deploy` aus dem E2E-Rig; dass er im GERÄTE-Compose ohne jedes Profil mitläuft, beweist weiterhin `test/install-selfcheck.sh`.)
- **Jede Anfrage des Rigs läuft INNERHALB des Compose-Netzes** (Seitenwagen, Dienste bei ihrem Namen: `core:8484`, `core:1502`) statt gegen einen veröffentlichten Port. Das ist die Port-Regel oben, angewandt auf die Rigs - und derselbe Weg auf dem Laptop wie auf dem Runner, nie ein Rückfall, den nur die kaputte Umgebung fährt.

Wächter gegen die ganze Klasse: `e2e-compose.sh` liest VOR dem `up` das aufgelöste Compose (`docker compose config --format json`) und bricht bei JEDEM Bind-Mount ab - mit dem Dienst, der Quelle, dem Ziel und der REGEL im Text, damit der nächste rote Lauf sich selbst erklärt statt zwei Untersuchungsrunden zu kosten (mutationsgeprüft in beide Richtungen). **`edge-app/test/e2e-ocpp.sh` ist von der ganzen Klasse nicht betroffen und soll es bleiben: es ist bewusst docker-frei** (alles läuft als Prozess). Wer ein drittes Rig ins Gate hängt, prüft beide Regeln, BEVOR er es aufnimmt - und stösst `edge-images.yaml` einmal von Hand an (die Regel „ein Gate-Schritt gilt als ungeprüft, bis er EINMAL grün durchgelaufen ist").

**⚠ `cmd | python3 - <<'PY'` KANN NICHT FUNKTIONIEREN** (beim Bau genau dieses Wächters passiert): das Here-Dokument ist die LETZTE stdin-Umleitung und ersetzt die Pipe - python bekommt das Skript, die Daten nie, und `json.load(sys.stdin)` scheitert an leerer Eingabe. Der Fehlschlag sieht dabei aus wie ein Treffer des Wächters, ist aber keiner. Richtig ist: Ausgabe in eine Datei, Pfad als `argv[1]` (`python3 - "$F" <<'PY'`), oder die Daten über die Umgebung. Dasselbe gilt für `docker exec -i … python3 - <<'PY'` - dort reist der Zustand deshalb als `-e`-Variable.

**⚠ Ein Rig lokal nachstellen heisst: Linux, ROOT, UND ein Workspace, den der Daemon NICHT sieht.** Ein Bind-Mount des Arbeitsbaums in den Job-Container versteckt genau den Befund, um den es hier geht - der Pfad existiert dann auf dem Host und alles läuft grün. Die faithful Form ist ein NAMED VOLUME als Workspace (das ist auch, was ein act_runner mit Docker-Backend vorgibt): `docker run -v /var/run/docker.sock:/var/run/docker.sock -v <ws-volume>:/workspace …`. **Und beim Befüllen von macOS aus `COPYFILE_DISABLE=1 tar --exclude='._*'`** - sonst landen AppleDouble-Dateien im Baum, `find … -name '*.test.js'` sammelt sie ein und `node --test` fällt mit `SyntaxError: Invalid or unexpected token` über einen Befund, den es in CI nie gab.
