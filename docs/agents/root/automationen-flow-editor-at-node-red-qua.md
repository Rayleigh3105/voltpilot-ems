The customer-facing automation editor + the production GO-LIVE of flow activation (spec `docs/portal-v3/M5-automationen.md`; locked decisions D1 code-node-edge-only+watchdog, D2 own-editor-via-flowc). All contracts additive; a device/site before M5 behaves byte-identically.

- **Contract decision D-16 (`docs/contracts/v2/README.md` + `flow-graph.md` §6):** a sandboxed code node (`vp.logic.function`) is a CATALOG addition (no graph-schema change) - runtime `edge` ONLY (the cloud never runs customer code), compiled by flowc into a Node-RED `function` node wrapped in a CPU/time WATCHDOG (`timeout_ms` ≤ 500 → the NR `timeout` in seconds + an in-body deadline; error → `node.status` red + `node.error`), with `net`/`http`/`https`/`require`/`global`/… SHADOWED as `new Function` params so they are `undefined` in the customer scope; every device effect still leaves through `vp-desired` → arbitration → the guard chain (a code node can only ever WISH). Added to all THREE catalogs in lockstep (api `flowcatalog/catalog.json` ⟷ portal `src/flows/catalog.json` byte-equal ⟷ flowc `catalog.js` `TYPES`; the `compile.test.js` type-set/port/feed guards bite). New param `kind: "code"` (validators: api `FlowGraphValidator` + portal `validate.ts`, length-cap only - safety is flowc's wrapper). Fixture `flow-graph.valid.function-node.json` + `pinned-function-hash.txt`.
- **Canvas positions live OUTSIDE the hashed document (load-bearing).** flowc assigns the artifact bundle x/y inside `content_hash` and the flow-graph schema is `additionalProperties:false`, so a dragged position must never reach `flow_definition.document` (it would re-deploy the device on every drag). Own table `flow_layout` (migration `V20260723010000`, keyed on `flow_id` so a forked draft inherits it; RLS like `flow_definition`) via `FlowLayoutRepository`; `GET/PUT /sites/{siteId}/flows/{flowId}/layout` (+ admin mirror) drop unknown node ids server-side. Portal: pure `src/flows/positions.ts` (merge saved with the `layout.ts` auto-layout fallback + drag maths), `FlowLayoutApiTest` proves layout never enters the stored document.
- **Device-reported live flow state (Part B + C):** the FOURTH `ems/+/+/+/status` sibling `FlowNodeStatusListener` (flag `VOLTPILOT_FLOWS_MQTT_LISTENER_ENABLED`, on in both composes; same broker-ACL/mTLS-CN + topic==payload identity posture as the control/entity/source listeners) replaces the device's set wholesale into `flow_device_ack` + `flow_node_status` (migration `V20260723020000`, RLS). `GET /sites/{siteId}/flow-node-status` feeds the editor's "Läuft auf dem Gerät · v{N}" badge (from the deployment acks - the EXISTING heartbeat `flows` block) and the per-node states. The per-node block is ADDITIVE + FEATURE-FLAGGED on the edge (`VP_FLOW_NODE_STATUS_ENABLED`, default OFF; `cloud.FlowNodeStatusSummary`, bounded, published via the `vp-node-status` palette node flowc wires from the compiled nodes). **Fallback is the point:** without the block the editor shows channel values only and NO node state - never a guessed one (pure `src/flows/liveValues.ts`; channel values come from the shipped `GET /sites/{id}/topology` capability values, no edge change).
- **Guided "Ausrollen" (pure `src/flows/rollout.ts`):** ONE button orchestrates the EXISTING validate → simulate+poll → activate calls; every backend refusal maps to CUSTOMER-grade German (`compiler_unavailable`/`compiler_rejected`/`gated_node_not_enabled`/`peakshaving_not_configured`/`activation_disabled`) - since the go-live these are customer copy, so `rollout.test.ts` pins that no internal component is named. Phone (`≤720px`) renders the read-only step list (`src/flows/stepList.ts` + `FlowStepList.tsx`), never a mini canvas.
- **🔴 GO-LIVE: `VOLTPILOT_FLOWS_ACTIVATION_ENABLED` defaults `true` in `docker-compose.prod.yml` + `.env.prod.example`** - customer automations really control devices from the v3 release. The safety net is STRUCTURAL (flow → desire → arbitration → guard chain, all DO-NOT-TOUCH). **Two rollback levers, both rehearsed in the dress rehearsal, documented in `docs/deploy.md` "Automationen (Flow-Aktivierung)":** (1) set the flag `false` + redeploy the api → NEW activations refuse `activation_disabled` (does NOT un-deploy retained artifacts); (2) `POST /sites/{siteId}/flows/{flowId}/deactivate` stops ONE live rule (never flag-gated). The api tests that pin `activation_disabled` (`FlowApiTest`/`CustomerFlowApiTest`) now set the flag OFF explicitly (they PROVE the flag still works). `tools/deploy/verify-migration-deploy.sh` asserts the prod compose resolves the flag ON.
