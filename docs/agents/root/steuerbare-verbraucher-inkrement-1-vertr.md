# Steuerbare Verbraucher - Inkrement 1 (Vertrag + Stammdaten + CRUD + Assistent)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 54).


The FIRST increment of controllable-consumer support (full concept: [`docs/verbrauchssteuerung.md`](docs/verbrauchssteuerung.md), §19 Inkrement 1; contract decision **D-18**). A consumer STAYS a v2 entity (a `measurement_point` with a consumer `entity_type`); this increment adds the declarative operating requirements + master data + the Anlagen-Modell assistant. **Increment 1 authors + stores a policy DRAFT ONLY - there is no compiler, optimizer or edge command, so every surface honestly reads "Steuerung noch nicht aktiviert".** Increments 2-6 (optimizer shadow, edge, reactive rules, productivisation, local deadline fallback) are NOT built.

- **Contract `docs/contracts/v2/consumer-policy.schema.json`** (schema_version 1.0): the policy document (entity_id, timezone, `requirements[]` of the four kinds `reactive`/`fixed_window`/`flexible_task`/`opportunistic`) + a `$defs/control_profile` snapshot carrying the D4 non-convex **`power_ranges_kw`**. The SEMANTIC rules JSON Schema can't express live in **`docs/contracts/v2/consumer-policy-vectors.json`** (the shared cross-language vectors) and are enforced by the **`ConsumerPolicyValidator` twins** - Java (`services/api .../consumers/ConsumerPolicyValidator`) ⟷ TS (`frontend/portal/src/consumers/validate.ts`); BOTH test suites load that ONE file and must produce the same verdict per case (the FlowGraphValidator / topology-vectors / EdgeRef precedent - **change both sides + the vectors together**). Rule codes: kind/enforcement coherence, `must_run`⇒grid allow (`must_run_grid_conflict`), condition-tree depth/size, cloud-vs-local signal hysteresis (`cloud_signal_hysteresis`, D1 - price signals compile to windows and carry no `reset_value`/`max_age_s`), catalog signal names (`unknown_signal`, from `ConsumerSignalCatalog` / `signals.ts`), target value coherence, 24:00 recurrence, the levels/D4 power-range rules. `examples/consumer-policy.*.json` (3 valid + 1 JSON-schema-invalid) are pinned by both validators + Python jsonschema. `content_hash` is derived server-side from canonical JSON (`ConsumerService.contentHash`), NOT in the document.
- **Migration `V20260810000000__consumer_profile_and_policy.sql`** (date-versioned ABOVE the highest shipped stand): `consumer_profile` (one row per entity - `entity_id` FK to `measurement_point`, control_kind/rated/levels/min/resolution/**`power_ranges_kw` JSONB**/storage_relation/grid policy/failsafe/enabled/version; a composite FK `(entity_id, tenant_id, site_id) → measurement_point(id, tenant_id, site_id)` pins tenant/site consistency - the unique key on measurement_point is added FIRST) + `consumer_policy` (versioned draft/active/retired, `UNIQUE(entity_id, version)`, ≤1 active). ENABLE+FORCE RLS + default-deny + app-role grants exactly like `flow_definition`/`measurement_point`. **`consumer_requirement_state` is DELIBERATELY NOT created** (no writer until the fulfilment path lands). The D4 disjointness + levels rules are enforced in the app validator (the FlowGraphValidator precedent), not a DB CHECK.
- **Entity catalog:** `entitytypes/catalog.json` gained **`pump`** (category consumer, controllable, non-composed, like wallbox/heating-rod/generic-load); the portal has no separate copy to sync. §16 capability rule: a consumer's requested `controlKind` is mapped onto the INTERSECTION of the device type's `default_actuate` (`continuous`/`stepped` need `setpoint_kw`; `on_off` needs `on_off`) - so `generic-load` (no setpoint) is on_off-only and a `continuous` request is **422**, never silently widened.
- **API `SiteConsumerController`** (`/api/v1/sites/{siteId}/...`, tenant-scoped like every site route - NO `@PreAuthorize`, RLS is the fence, foreign site 404, body tenant never trusted): `GET consumer-options` (capability-/context-filtered types + the signal catalog + intents + `hasStorage` + reported edge sources + defaults), `GET/POST consumers`, `GET/PATCH/DELETE consumers/{id}` (PATCH optimistic via `expectedVersion` → 409; DELETE = fachlich stilllegen, **409 while still connected** = edge_source/device bound), `GET/PUT consumers/{id}/policy` (a new DRAFT version; the document's `entity_id` is stamped from the path). `ConsumerService` creates the consumer via `EntityRegistryService.createEntity` (a proper v2 entity + registry push) then inserts the profile; a connected consumer binds `measurement_point.edge_source_id`. Routes in `openapi.yaml` (tag `consumer`). Proofs: `ConsumerPolicyValidatorTest` (shared vectors + fixtures, always runs) + `ConsumerApiTest` (Testcontainers: options filtering, draft/connected create, the §16 422, optimistic 409, DELETE-while-connected 409, policy draft versioning + German 400 on invalid, RLS 404).
- **Portal:** pure `src/consumers/` (`validate.ts` twin + `signals.ts` + `questions.ts` `consumerQuestions(ctx, draft)` the §14.4 Fragenbaum + `policy.ts` `buildPolicyDocument`/`policySentence`/`reviewFacts`; unit-tested `validate.test.ts`/`questions.test.ts`/`policy.test.ts`). The rule builder's permanent German preview + the review both derive from the SAME document, so they can never disagree. A flexible task carries the honest §14.7 note "Bei Verbindungsausfall kann diese Aufgabe entfallen." (no local deadline fallback yet).
