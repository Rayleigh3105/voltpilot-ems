# Self-maintaining battery-asset <-> device link + manual battery editor

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 93).


Captain design 2026-07-07: the battery is controlled by the inverter, the inverter is the edge device, so `asset.device_id` (what `services/optimization` `publisher.py` publishes the plan against) must maintain ITSELF.
Before this, MaStR-created (and dev-seed) battery assets left `device_id` NULL, so the optimizer PERSISTED a plan but NEVER published it - the edge showed "noch kein Fahrplan empfangen" while the portal showed a plan (a real customer plant hit exactly this).

- **The rule (one place):** `AssetRepository.autoLinkBatteryDevice(siteId)` links a site's UNLINKED battery asset to its device WHEN the site has EXACTLY ONE device (`(array_agg(id))[1]` - Postgres has no `max(uuid)`; `HAVING count(*)=1` makes the pick unambiguous). A multi-device site is left alone on purpose - never guess which inverter controls the battery; already-linked batteries are never re-pointed. RLS-scoped (only the caller's tenant).
- **Three layers, same rule:** (1) BACKFILL migration `V20260707010000` (runs as the Flyway superuser, heals all tenants on deploy incl. the captain's live plant); (2) ON CLAIM - `DeviceController.claim` calls it after a fresh claim (a claim can make a site single-device); (3) ON WRITE - `MastrController.apply` (after `applyBattery`) and the manual battery editor call it.
- **Manual battery editor (also closes the long-standing "non-MaStR plants can't maintain battery data" gap):** `PUT /api/v1/sites/{siteId}/battery` (`SiteBatteryController`, `SaveBatteryRequest`) upserts capacity/charge/discharge/`roundtrip_efficiency_pct` (leaves registry provenance untouched, so a manual battery keeps a NULL registry) and maintains the link: an explicit `deviceId` (validated to belong to the site, else 404) picks the controlling device on a multi-device site; omitting it runs the auto-link. Tenant-scoped like every site route (foreign site 404; admins via the `X-Tenant-Id` switcher).
- **Speicherschonung customer preset (FK4, captain decision from the vp-solver-xlsx-f2 audit):** the same battery PUT takes an optional `speicherschonung` enum (`aggressiv|ausgewogen|schonend`) mapped server-side by the ONE constant `web/Speicherschonung.java` onto `asset.wear_cost_ct_per_kwh` (1/4/8 ct; values sit safely inside the report's dispatch-invariance band - tipping point ~12 ct) and touching ONLY that column, never the admin SoC-band/backup-reserve overrides; null/absent keeps the stored value, and the optimizer needs NO change (inputs.py reads the column per 15-min cycle). Read side: `SiteAssetDto.speicherschonung` is the derived EFFECTIVE preset (NULL wear→`ausgewogen` since it equals the 4-ct platform default; off-ladder admin value→`individuell`, shown as "Individuell (durch VoltPilot konfiguriert)" and overwritten when the customer picks a preset - the raw ct value stays admin-only in optimizer-config). Portal: three-option radio "Umgang mit dem Speicher" in the `BatteryEditForm` + a read-first row, copy WITHOUT ct/kWh numbers, pure helpers in `src/speicherschonung.ts` (the edit form sends the field only when the choice actually changed, so an untouched save never pins/overwrites). Proven by `PortalApiTest.speicherschonungPresetsWriteExactlyTheWearColumnAndDeriveHonestly` + portal `speicherschonung.test.ts`/`AnlageTechnik.test.tsx`.
- **Visible warning, not silent failure:** `OverviewSiteDto.batteryWithoutDevice` (a battery asset with `device_id` NULL - `OverviewRepository.sitesWithUnlinkedBattery()`) drives the plain-German warning (`fleet.ts` `BATTERY_NO_DEVICE_WARNING`/`_SHORT`): an amber "Speicher ohne Gerät" badge on the fleet site card, the same alert in the single-site Übersicht status card, and the full "Speicher & Steuerung" section in the `StandortePage` detail drawer (params table + controlling device + editor + warning, sourced from ALL assets not just registry-linked). `SiteAssetDto` gained `deviceId` + `roundtripEfficiencyPct`.
- **Optimizer is UNCHANGED** - it already keys publish off `asset.device_id`; the api's auto-link is what heals a site (`test_engine.py::test_autolink_makes_a_previously_unpublished_site_publish`).
- **Tests:** `PortalApiTest` (`batteryAssetAutoLinksToTheSitesSingleDeviceAndNeverGuessesOnMultiDeviceSites` - on-claim + on-write + multi-device no-guess + explicit picker + overview flag; `batteryEditorIsTenantScopedAndValidatesTheChosenDevice`; `backfillLinksSingleDeviceSitesButLeavesMultiDeviceSitesUnlinked` - the migration SQL in isolation via superuser); portal `StandortePage.test.tsx` (`BatteryControlSection` warning/linked/add/save) + `fleet.test.ts` (warning copy).
