# Portal-Admin optimizer surface (diagnostics + config + what-if, `services/api` `optimizer/` package)

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 86).


Backend for the admin "understand + tune the optimizer" GUI (design: firstmate `vp-admin-optimizer-ui-design`). FOUR `platform-admin`-gated routes under `/api/v1/admin/sites/{siteId}/...` (`AdminOptimizerController`), all reading/writing THROUGH the RLS-scoped app datasource via the `X-Tenant-Id` switcher (no BYPASSRLS; no tenant selected / wrong tenant = 404). Two of them look alike and must not be confused: a config PUT changes what the optimizer's NEXT 15-min cycle reads and triggers no solve, while `optimizer-what-if` (§4.3, see its own section below) solves IMMEDIATELY and commits NOTHING.

- **`GET .../optimizer-diagnostics?generatedAt=&date=`** (default = latest run; unknown timestamp 404; `availableRuns` lists ONE Europe/Berlin day's runs - `date=YYYY-MM-DD` picks the day and without `generatedAt` shows that day's newest run, a day without runs = empty well-formed body, never 404; `firstRunDate`/`lastRunDate` bound the UI date picker - the hypertable keeps every run, the former newest-30 list only reached ~7.5 h back): the run's `schedule` slots plus the per-slot €-decomposition in ct/kWh - `solverPriceCtKwh` (bare spot), `importPriceCtKwh`/`exportValueCtKwh` (the REAL P1 pricing), `wearCostEur`/`wearCostCtKwh` (from the PERSISTED `schedule.wear_cost_eur`, real P2 - not an estimate), `valueOfStoredEnergyCtKwh` (forward best-use price × one-way η minus half-wear - an APPROXIMATION, flagged run-level as `storedEnergyValueIsApproximation`; the exact number would be the MILP's SoC shadow price, not persisted), `decisionLabel` (`solarladen|netzladen|entladen|ruhe`, the server twin of `schedule.ts chargeKind`, same 0.05 kW deadband) and a composed German `whyText`. Null wherever honestly not computable (no persisted spot, pre-P2 rows, battery-less site) - never a fake 0. The §14a limit a run used is NOT persisted, so it is not returned (known gap); forecast-model lifecycle comes from `forecast-quality`.
- **Pricing consistency is the load-bearing invariant:** `optimizer/SlotEconomics.java` mirrors `services/optimization/voltpilot_optimization/pricing.py` rule-for-rule (tarif_art branching; DV Marktprämie `max(aw − Monatsmarktwert, 0)` suspended at negative spot + missing-month = no premium; merchant mode = bare spot despite configured EEG remuneration; eigenverbrauch feste Vergütung incl. §51a and 20-year expiry), and `optimizer/EegRates.java` is the Java twin of `config.py`'s `DEFAULT_EEG_RATE_SCHEDULE` + tranche blending - `EegRatesTest` pins the SAME vectors as `test_pricing.py`, so a schedule change must land on both sides. The api reads the same `OPTIMIZER_EEG_RATES_JSON` env.
- **`GET`/`PUT .../optimizer-config`**: platform defaults vs. per-site/per-asset overrides vs. effective values. Overrides (NULL = platform default, additive nullable columns): `asset.wear_cost_ct_per_kwh` (V20260710000000), `asset.soc_min_pct`/`soc_max_pct` (**V20260710020000**, the formerly hard-coded 5-95% band from `domain.py` - now per-battery-asset, read by `inputs.load_battery_sites` with an inconsistent-band fall-back-and-warn), `site.backup_reserve_soc_pct` (V20260710010000). The PUT is FULL-REPRESENTATION (null clears; battery fields without a battery asset = 409; effective min ≥ max = 400). The pre-existing site levers (netzladen/plant_kind/tariff/anzulegender Wert) are echoed read-only - they stay on `PUT /api/v1/sites/{id}`. Terminal-value config is read-only (env-level).
- **The api mirrors the optimizer's env** via `voltpilot.optimizer.*` (`OptimizerProperties`): BOTH composes pass `OPTIMIZER_WEAR_COST_CT_PER_KWH` / `OPTIMIZER_TERMINAL_VALUE_*` / `OPTIMIZER_EEG_RATES_JSON` to the api service too - keep api + optimization env in sync (the `VOLTPILOT_ACTIVE_*_MODEL` discipline) or the panel displays defaults the solver is not using.
- **The controller carries a `ResponseStatusException` `@ExceptionHandler`** (the MastrController/AdminSimulation pattern), so every refusal on this surface - including the pre-existing config 400/409 - arrives as a German `{message}` body the panel can render instead of a bare status.
- **Tests:** `EegRatesTest` + `SlotEconomicsTest` (pure unit, always run - pricing vectors, wear derivation, stored-value math, decision label, whyText, null discipline); `AdminApiTest.optimizerDiagnosticsDecomposeSlotsWithRealTariffAndRemuneration` (hand-computed DV dynamic-tariff + Marktprämie/§51 and EV fest-tariff + feste-Vergütung slots, run selection, auth/tenancy incl. wrong-tenant 404) + `optimizerConfigMergesDefaultsWithOverridesAndWritesThem` (defaults/override/effective merge, writes land on the exact columns `inputs.py` reads, clear-to-default, band validation, battery-less 409, auth); optimization `test_freshness.py` SoC-band section (NULL = defaults, configured band, inconsistent-band fallback).
