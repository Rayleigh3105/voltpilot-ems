# Netz-null-Reduzieren: die Reduzieren-Erlaubnis ohne Wirtschafts-Test (2026-09-08, P1)

Der Fix für das **Nacht-Leck der Box** (Scout-Bericht `firstmate/data/vp-nachtreserve-konzept-k2`, P1). Er ist die Fortsetzung des Abschnitts „In-slot load following" darüber und ändert an dessen Semantik NICHTS - er teilt nur seine beiden Hälften auf zwei Erlaubnisse auf.

**Der Befund.** `cover_load_from_battery` koppelt BEIDE Richtungen der Nachführung an EINEN Wirtschaftlichkeits-Test (`import_price > λ/eta + wear + margin`). Bei einer **Festpreis-Anlage** (Pilsting/Herzogau, Bezug 25 ct fest) kippt dieser Test genau dann auf false, wenn der Speicher knapp wird: λ steigt über den Bezugspreis, weil die gespeicherte kWh später mehr wert ist als der Bezug, den sie jetzt ersetzt (gemessen 23:15: 25,0 ct < 23,5/0,959 + 0,5 + 0,5 = 25,5 ct). Die Box fiel damit auf `deepenOnly` zurück - und der Sollwert des laufenden Slots liegt durch die Nowcast-Reserve **0,1 bis 1,8 kW ÜBER der Viertelstunden-Last**, also gingen **3,8 kWh je Nacht** zu 6-12 ct ins Netz und fehlten Stunden später zu 25 ct (13 Nächte: 49,2 kWh gemessen).

**Die Einsicht (Bericht §2 F).** **Begrenzen ist NIE unwirtschaftlich.** Es hält nur Energie, die der Plan in einem Netz≈0-Slot selbst höher bewertet als den Export - sonst hätte er dort verkauft, und dann markiert die Cloud den Slot gar nicht. Das steigende λ, das den wirtschaftlichen Zwilling ausschaltet, macht das Begrenzen sogar WERTVOLLER. Also braucht die Reduzieren-Hälfte keinen Preis; nur die Vertiefen-Hälfte (die gespeicherte Energie AUSGIBT) bleibt an ein Urteil gebunden.

- **Vertrag**: neues OPTIONALES `slots[].limit_discharge_to_load` (boolean, `schema_version` bleibt 1.0, fail-open wie die drei Geschwister). true = die Cloud plant hier eine Entladung UND Netzaustausch ≈ 0; die Box DARF die kommandierte Entladung auf `max(load − pv, 0)` BEGRENZEN, nie erhöhen, Untergrenze 0 kW, nie ein Laden. Fixtures `mqtt-schedule.valid.limit-discharge.json` (Slot 1 nur das Recht, Slot 2 das Recht UND die Wirtschafts-Pflicht) + `…invalid.limit-discharge-not-boolean.json`.
- **Emission** (`slot_trim.limit_discharge_to_load`, gestempelt in `solver._limit_discharge_to_load` / `_with_explanation`; `PlanSlot.limit_discharge_to_load`): `battery_kw < -0,05 kW` UND `|grid_kw| <= 0,05 kW` - dieselben zwei Totbänder wie beim Zwilling, **OHNE dessen Wirtschafts-Test und ohne λ**. Damit ist das Feld auf einem entladenden Netz≈0-Slot eine **OBERMENGE** von `cover_load_from_battery`; beide dürfen auf demselben Slot stehen (`test_load_follow.py` pinnt das als Plan-Eigenschaft). Die beidseitige Ausnahme (geplanter Verkauf / geplanter Billig-Einkauf) wird VERERBT und aus demselben Grund: die Box kann eine gewollte Einspeisung nicht von einem Prognose-Überschuss unterscheiden. Eigener Kill-Switch `OPTIMIZER_LIMIT_DISCHARGE_ENABLED` (Vorgabe AN, im gitops-Repo nachziehen), weil dieses Feld die Box-Befugnis OHNE Wirtschafts-Test weitet. Keine Persistenz in `schedule` (wie die Geschwister).
- **Edge** (`guards/loadfollow.go`): die beiden Hälften werden GETRENNT autorisiert - `deepenAllowed = coverLoad || unplannedLoad || deficitCover`, `reduceAllowed = coverLoad || unplannedLoad || limitToLoad`. Der Waechter meldet den Pfad der Autoritaet, die TATSÄCHLICH gehandelt hat (`follow` | `idle_follow` | `deficit_cover` | **`limit`**), nicht bloß eine, die der Slot auch trägt: ein Vertiefen über `deficitCover` heißt weiter `deficit_cover`, auch wenn derselbe Slot das Reduzieren-Recht trägt. Frischeprüfung, Boden-Stapel (`effective_floor_soc_pct`), Hysterese (0,2 kW / 90 s) und `FollowInfo.direction` bleiben unverändert; das Recht wird an denselben Fakten-Satz gehalten wie jede andere additive Erlaubnis. `plan.Slot.LimitDischargeToLoad` + `Plan.ActiveLimitDischargeToLoad` spiegeln `ActiveCoverLoadFromBattery` exakt (überlebt Staleness NICHT).
- **Cloud-Rückweg**: neuer Ausführungs-Modus **`limit`** (Richtung immer `reduce`) im Herzschlag → `ControlStatusListener.EXECUTION_MODES` **und** `DIRECTED_MODES` (die Richtung wurde bis dahin nur für `follow` gespeichert) → `command_log` Stream `batterie` → Portal `EXECUTION_MODE_LABEL.limit` / `befehle.MODUS.limit`. Eigenes Wort auf Zweck: `follow` behauptete, die Cloud habe für diesen Slot den Preis abgewogen - genau das hat sie hier NICHT getan.
- **Admin-Diagnose**: `OptimizerDiagnosticsSlotDto.limitDischargeToLoad` (additiv, nullable). ⚠ **ABGELEITET** aus den beiden persistierten Zahlen der Zeile (`battery_kw`/`grid_kw`), weil das Flag nicht persistiert wird - und das GEHT nur, weil diese Regel keinen Preis und kein λ liest. Die Fläche sagt deshalb „dieser Slot erfüllt die Regel", NIE „die Box hat das Recht bekommen".
- **Geteilte Vektoren**: `docs/contracts/v2/load-follow-vectors.json` - Block `ausfuehrung` (7 Fälle) fährt der Go-Zwilling durch den echten Waechter, Block `emission` (6 Fälle) der Python-Zwilling durch die echten Regeln. Wer eine Seite ändert, ändert beide Seiten UND die Datei.
- **Tests**: `tests/test_load_follow.py` (Emissions-Vektoren, Obermengen-Eigenschaft im gelösten Plan, Schalter, byte-identische Sollwerte), `tests/test_contract.py` (Fixture ↔ Publisher, omit-unless-true), Go `guards/loadfollow_test.go` (Ausführungs-Vektoren + Reduzieren-Grenzen), `agent/load_follow_test.go` (die Fixture bis zum veröffentlichten Sollwert und bis zum Herzschlag-Modus), `plan/plan_test.go`, `ControlStatusListenerTest`, `AdminApiTest`, Portal `control.test.ts` / `befehle.test.ts`. **Braucht ein Edge-Release** - eine laufende Box behält ihr Image.
