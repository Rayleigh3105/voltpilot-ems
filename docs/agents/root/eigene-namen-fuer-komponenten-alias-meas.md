# Eigene Namen für Komponenten (Alias): `measurement_point.label` trägt NUR noch Menschen-Namen

Ausgelagert aus `AGENTS.md` am 05.09.2026 (Abschnitt Nr. 15).


Der Kunde benennt seine Komponenten selbst („Dach Süd" statt „Fronius Anlage WR1"; Konzept `data/vp-entity-alias-k1`, Captain-Entscheide 09.08.2026: Datenmodell **Pfad B**, PV-Zeilen-Stift sofort, Inkrement-2-Politur mit im selben Wurf). Das Feature war zu ~70 % gebaut — Feld, Stift, Dialog und die Verteilung bis zur Edge existierten; **es fehlten die Kunden-Schreibroute, der Vorrang des Kundennamens und die Trennung „vom Menschen vergeben" vs. „automatisch komponiert"**.

- **⚠ DIE INVARIANTE, an der alles hängt: `label != NULL` ⇒ VON EINEM MENSCHEN VERGEBEN** (Migration `V20260812000000`, reine Daten-Migration). Das Feld hatte zwei Schreiberklassen — Menschen (Umbenennen-Stift, Übernehmen-Dialog, Verbraucher-Assistent) UND die Komposition, die drei feste Herkunfts-Sätze schrieb („Batteriespeicher (Hybrid-Wechselrichter)", „Netzanschluss/Hausverbrauch (Messung über Wechselrichter)"). Genau diese Doppeldeutigkeit war der EINE strukturelle Grund, warum ein Kundenname nicht gewinnen konnte: hebt man das Label auf Rang 1, ohne die Konstanten zu räumen, heißt die Deye-PV-Zeile plötzlich „Batteriespeicher (…)". Die Migration nullt die drei Konstanten, `EntityRegistryService` schreibt **gar kein Label mehr** (`COMPOSED_LABEL = null`, Bootstrap *und* Preview im Lockstep) — **nie wieder ein komponiertes Vorgabe-Label einführen**, ein von der Plattform erfundener Name ist von einem gewählten nicht unterscheidbar. Haus-Präzedenzfall: dieselbe Bereinigung lief für die Edge-Quellen (`V20260729020000`, „label carries ONLY the operator-given"). Sichtbare, bewusst in Kauf genommene Folge: eine UNBENANNTE komponierte Zeile liest sich als Rollenwort („Speicher") statt als Klammer-Satz — die Herkunft sagt seit M6 die Provenienz-Zeile besser („gemessen über Deye SUN-30K"). Abgelehnt: ein Flag `label_custom` (Doppeldeutigkeit bliebe für immer im Schema + Flag-Pflege in DTOs und allen DREI Topologie-Ableitungen) und ein zweites `alias`-Feld (zwei Wahrheiten über denselben Namen).
- **Kundenroute `PUT /api/v1/sites/{siteId}/v2-entities/{entityId}/label`** (`SiteEntityAdoptController`, wo adopt/repin/delete wohnen): RLS-gefenced ohne `@PreAuthorize`, fremde Anlage 404, Admins über den `X-Tenant-Id`-Umschalter. Delegiert an das bestehende `updateEntity(siteId, id, label, null, null, null)`; Semantik = die des Admin-PUT (absent/null behält, LEER löscht ⇒ NULL ⇒ Ableitung), damit es EINE Label-Schreibregel gibt. Trim + Steuerzeichen/Zeilenumbrüche zu Leerzeichen, `@Size(max=200)` (Parität), Duplikate ausdrücklich erlaubt. In `openapi.yaml` (tag `topology`).
  - **⚠ R1 ist KONSTRUKTIV, nicht versprochen: die Route nimmt AUSSCHLIESSLICH `label` entgegen.** Es gibt kein Typ-, Rollen-, Pin- oder Guard-Feld im Request, also lässt sich durch die Umbenennen-Tür nichts schmuggeln; Zuordnung und Steuerung behalten ihre eigenen, längst gegateten Routen. Genau deshalb ist es eine EIGENE Route und kein label-only `update` (der ist admin-gegated und führt Guard-/Capability-Felder mit).
  - **⚠ Das `PLATTFORM_MANAGED`-Gate von repin/delete gilt hier BEWUSST NICHT** (Captain 09.08.2026): **jede** Komponente ist benennbar — Batteriespeicher, Netzanschluss, Hausverbrauch, Verbraucher, Erzeuger. repin/delete verweigern die komponierten Zeilen, weil sie ÄNDERN, was eine Komponente ist bzw. ob sie existiert; ein Name ändert beides nicht. Nur TYP und ROLLE bleiben unser.
- **Der Alias reist ohne neuen Verteilweg:** `EntityDto.label` → Topologie-Member (Cloud `TopologyDeriver` wie Edge `internal/topology`) → Registry-Descriptor (`EntityRegistryService.descriptor`). Ein Label-Edit stößt `pushRegistryBestEffort` an, also lernt auch die Box den Kundennamen (`:8484`-Topologie) — erwünscht, und die Revision springt (Soll/Ist kurz „ausstehend"). Die Edge ist gegen das FEHLENDE Label abgesichert (`dashboard.js` fällt auf „PV-Anlage"/„Speicher" zurück, der Knoten trägt ohnehin das Rollenwort); Beweis `entities_test.go TestRegistryPushCarriesTheCustomerNameAndDegradesWithoutOne`.
- **OCPP-Ladesäulen benutzen seit `V20260856000000` denselben Alias — ohne ein zweites Namenssystem.** Sobald `device_charge_point.entity_id` gebunden ist, liefert `/sites/{id}/chargers` als `label` ausschließlich `measurement_point.label`; das vom Edge gemeldete Label ist dann nur noch der Bootstrap-Beleg und darf einen späteren Kundennamen nie überschreiben. Ohne Alias bleibt `label` NULL und alle Säulen-Flächen fallen auf die eindeutige ChargePointId zurück. `ChargerComponentComposer` speichert deshalb eine nackte ChargePointId NIE mehr als Label — auch nicht, wenn die Box ihr leeres Label bereits selbst auf die Id normalisiert hat; die Hygiene-Migration nullt genau diese Altzeilen (`measurement_point.label = charge_point_id`). Auf der OCPP-Geräteseite öffnet „Anzeigename ändern" den bestehenden schmalen `UmbenennenDialog`/die bestehende Kundenroute — kein erfundener `component_definition`-/Treiber-Editor für eine Säule, die sich selbst per OCPP verbindet. Beweise: `ChargerComponentComposerTest`, `ChargerApiTest.theChargePointsReachTheCloudAndBecomeComponentsWithoutASingleClick`, Portal `GeraetSeiteSection.test.tsx`.
- **⚠ `Stream.map(EntityRow::label).findFirst()` wirft NPE**, sobald ein Punkt unbenannt ist — seit der Hygiene der NORMALFALL einer komponierten Zeile (im `preview`-Test als 500 statt Antwort aufgefallen). Richtig ist `findFirst().map(EntityRow::label)`.
- **Beweise:** `PortalApiTest.customerNamesEveryComponentAndClearingRestoresTheDerivation` (echte DB + Keycloak: eine PLATTFORM-KOMPONIERTE Zeile wird benannt, Typ/Guards/`control` danach unverändert = R1, Registry-Revision springt, Trim+Kollaps, Leer ⇒ NULL ⇒ Ableitung, absentes Feld ist ein No-op, Duplikate erlaubt, 200-Zeichen-Grenze, RLS 404, unbekannte Entität 404).
