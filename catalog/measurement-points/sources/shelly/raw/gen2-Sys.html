System

The system component provides information about general device status, resource usage, availability of firmware updates, etc.

The system component can be used to configure aspects of the device behavior:

  • log streaming over websocket, UDP or serial port. Logs can provide valuable insight about firmware behavior and enable debugging;
  • UDP RPC channel availability, useful in some integration scenarios;
  • Local timezone and geolocation, used for scheduling and sunrise/sunset event time calculation;
  • Experimental ECO Mode, which, when enabled throttles CPU speed and enables low-power mode for the WiFi radio when possible. This can signifficantly decrease power consumption, but may increase latency.

It also facilitates backing up and restoring device settings as well as changing the factory defaults.

The system component uses Sys as RPC namespace. It handles the system services of a device and provides the methods:

  • Sys.GetConfig to obtain the component's configuration
  • Sys.SetConfig to update the component's configuration
  • Sys.GetStatus to obtain the component's status
  • Sys.SetTime to set system time settime

It uses the key sys when enumerated in objects including multiple component payloads, like Shelly.GetStatus.

Secure provisioning​

(since 1.7.5)

Access Point & BLE RPC protection​

  1. Open AP & BLE RPC auto-shutdown: Open AP & BLE RPC are only available for 15 minutes after boot on devices that have never yet acquired IP over Wi-Fi or Ethernet. Once an IP is acquired, AP (unless protected with a password) & BLE RPC are automatically disabled. In case no IP was acquired during the initial setup window, AP (unless protected with a password) & BLE RPC are temporarily shut down - until the device is power-cycled or a factory/network reset occurs.

  2. AP password persistence: Once an AP password has been set, it cannot be changed back to empty (open AP).

Provisioning state​

The device reports its provisioning state in Shelly.GetDeviceInfo via the provision field:

  • pending: initial device provisioning available over a 15 minutes setup window (3 minutes on battery-powered devices)
  • confirmed: device provisioned, unprotected interfaces remain available over a 5 minutes grace window (on battery-powered devices, the original 3-minute setup timer continues instead)
  • complete: grace window expired, AP (unless protected with a password) & BLE RPC are automatically disabled
  • locked: initial setup window expired without going online, AP (unless protected with a password) & BLE RPC are temporarily shut down until device is power-cycled, a factory/network reset occurs, or user button is pressed (latter only applicable to battery-powered devices). While in this state, the device emits a BLE advertisement with the locked flag (bit 5) set in the 0x01 Shelly-Specific Flags block of the Shelly manufacturer-specific data, so it remains discoverable even though BLE RPC is disabled. The device is still connectable while locked, but the only accessible service is GAP.

When provision field changes, the device emits a corresponding notification event: provision_pending, provision_confirmed, provision_complete, provision_locked, for example:

Notify that device provisioning is completed.
{
   "src": "shellypro4pm-f008d1d8b8b8",
   "dst": "user_1",
   "method": "NotifyEvent",
   "params": {
      "ts": 1631266683.84,
      "events": [
         {
            "component": "sys",
            "event": "provision_complete",
            "ts": 1631266683.84
         }
      ]
   }
}

Provisioning object in Sys.GetStatus​

While the device is in the pending or confirmed provisioning state, Sys.GetStatus includes a provisioning object with:

  • stage — the current provisioning stage
  • started_at — when the device entered the stage (Unix timestamp)
  • started_ut — when the device entered the stage (Uptime in seconds)
  • duration — how long the stage lasts, in seconds

A NotifyStatus event is emitted when the object appears or its contents change.

NotifyStatus event with the provisioning object.
{
   "src": "shellyhtg3-dcda0cb79604",
   "dst": "user_1",
   "method": "NotifyStatus",
   "params": {
      "ts": 1778246311.0,
      "sys": {
         "provisioning": {
            "stage": "confirmed",
            "started_at": 1778246311,
            "started_ut": 3,
            "duration": 180
         }
      }
   }
}

Battery Device Provisioning​

(since 2.0.0)

Battery-powered devices have modified provisioning behavior:

  • Setup window: The provisioning window is 3 minutes (tied to setup mode), not 15 minutes
  • No grace window: The 5-minute confirmed grace timer does not apply; the original setup timer continues until completion
  • Button wake recovery: Pressing the device button while in locked state restarts setup mode and returns to pending
  • Periodic wake: When the device wakes from deep sleep via periodic timer (not button press), it remains in locked state with AP and BLE RPC disabled
  • Upgrade path: Devices that already have Wi-Fi configured (station mode enabled, AP disabled) before updating to firmware 2.0.0 boot directly into complete — the provisioning state machine is skipped entirely

(Since firmware 2.0.0)

info

The nsteps property in available_updates is meant to aid in designing user interaction for a special case of updates that may require a two step pass, which although rarely may be necessary as for example updates of certain devices after release 2.0.0 which will perform server assisted repartitioning. For regular updates the property will not be present. For a two step update, based on information sent by the server when the update is determined to require two steps the nsteps property will be shown in Sys.Status with a value of 1 and also will be included in a status change. Due to the specifics of OTA implementation in firmware for this kind of updates the same update may not require a second pass in which case nsteps won't be shown. When the second pass starts, which will happen automatically after the delay for committing update, the server will send nsteps with a value of 0, denoting last step. After completion available updates will change and will not include the entry for the version firmware just updated to, thus not showing nsteps.

MQTT control​

Since version 0.14.0

The system component MQTT functionality provides commands for OTA updates.

  • Shelly will subscribe to the following topics, accepting commands:

    • <topic_prefix>/command/sys

  • Shelly publishes on:

    • <topic_prefix>/status/sys - topic where the result of the status_update and ota_update_check commands is published. The status_update command can be sent either on the common device topic or the component specific topic. This topic is already used for existing status notifications, if enabled.
    • <topic_prefix>/error/sys - error message is published if update is requested and the corresponding stage is not found.
    • <topic_prefix>/events/rpc - regular event notifications of OTA progress are published on this topic when update is started with the ota_update_to commands.

  • Accepted commands are:

    • status_update - causes status of the sys component to be published on the <topic_prefix>/status/sys topic, which includes available updates information.
    • ota_update_check - causes the device to request information of available updates and then publishes component status which includes available updates information on the <topic_prefix>/status/sys topic. Also event notification with information for updates is published on the <topic_prefix>/events/rpc topic.
    • ota_update_to_stable, ota_update_to_beta, ota_update_to_test - starts an update for the specified stage.
note

<topic_prefix> is a custom prefix if set or defaults to <device_id>
